# Executive Result

Q2.10F.3 is ready for one small human field proof. Dad mode now stays quiet when a dispatchable Player has only historical Unknown, failed, interrupted, completed, or report-linked evidence. Current Starting, Working, Queued, Waiting, and genuinely actionable Needs You states remain attached to the exact Player. Returned work remains in Incoming.

The machine evidence was not deleted, acknowledged, or weakened. This repair inserts a presentation policy between canonical `ExecutionView` truth and the ordinary TEAM/Player UI.

Friendly Player labels now come from one generic, current-roster, exact-instance projection. One instance is unnumbered; siblings are numbered contiguously and recompact without changing any `playerInstanceId`.

Dispatch success now has one inline acknowledgement. The redundant `Dispatch accepted by Stadium provider.` toast was removed, and the View Player action is available immediately.

# North Star Conformance

The repository North Star was treated as the governing contract. Internal lifecycle importance no longer creates permanent customer-facing alarm state. The UI answers the current human questions—availability, current work, and current intervention—while retaining richer evidence for routing, reconciliation, diagnostics, and history.

Names remain presentation. Exact opaque identity remains routing authority.

# Human Field Failure Reproduced

The deterministic regression starts with an On Field Controlled AntiGravity instance that is dispatchable but has an old canonical Unknown outcome. Dad mode renders only its normal identity and capability, and TEAM has no historical Needs You count. The same exact instance then receives a new Play and renders its Working strip, truthful elapsed clock, and summary. Completion removes the strip while the old and new terminal evidence remains stored.

Parallel cases cover historical failure and a Terminal instance with historical Unknown evidence.

# Root Cause

The browser directly mapped terminal `ExecutionView` states to present-tense customer alarms:

- `unknown` and `couldnt-finish` were counted as Needs You;
- completed/report-linked history created persistent Player and TEAM Report Ready presentation;
- the presentation layer did not distinguish current actionable work from historical terminal evidence;
- some response and Stadium labels retained stable seat numbers while roster cards independently compacted them;
- successful dispatch produced both the correct inline Outgoing acknowledgement and a plumbing-oriented global toast.

# Observation vs Dad-Mode Policy

The Control Plane and Instance Work Ledger remain the canonical observation layer. Their states, revisions, timestamps, acknowledgement records, and report links are unchanged.

Dad-mode policy now presents temporary strips only for live/actionable states. Terminal history projects to no ordinary Player strip. This is a rendering decision, not a lifecycle mutation: no automatic acknowledgement, deletion, or history rewrite is used.

# Idle Player Presentation

An idle, available Player now renders its name, field state, capability, and lifecycle controls only. Old Unknown, failed, interrupted, completed, and report-ready records do not add warnings, buttons, or scars to the card.

# Live Play Presentation

Starting remains visible without a timer. Working remains visible beneath the exact Player with the one canonical elapsed clock. Queued and waiting states remain temporary and do not receive a clock. When current execution reaches a terminal outcome, the temporary strip retires and the Player returns to its ordinary presentation.

# Needs You Semantics

Dad-mode Needs You now means current work is blocked on an actual human action. The current producers are an exact current Play whose controlled session reports a human-required state, or a current queue item that explicitly needs a decision. Historical terminal outcomes never qualify.

Canonical `unknown` and `couldnt-finish` remain available internally and remain test-covered as machine truth.

# TEAM Semantics

TEAM summarizes only current live/actionable work:

- ACTIVE counts Starting and Working Players;
- NEEDS YOU counts only current actionable blockers;
- historical terminal outcomes do not contribute;
- Report Ready is not duplicated in TEAM.

With no live/actionable state, the heading is simply `TEAM`.

# Incoming / Report Ownership

Incoming is the durable Dad-mode home for returned reports. Report links and acknowledgements remain canonical in the Ledger. Selecting, opening, or copying a report continues to use the exact acknowledgement path, but report readiness no longer leaves persistent Player-card or TEAM residue.

# Historical Truth Preservation

The repair does not clear the Ledger, rewrite terminal states, auto-acknowledge records, or discard reports. Tests assert that hidden historical Unknown/failure states are still present in the browser execution store and that server acknowledgement remains exact, Game-scoped, revisioned, and idempotent.

# Friendly Label Architecture

`src/player-display-labels.ts` is the shared presentation resolver. It groups the current roster generically by Player type, orders stable exact instances, and projects:

- one instance as `Claude`, `Codex`, `AntiGravity`, or the future type name;
- multiple siblings as contiguous `Name 1`, `Name 2`, and `Name 3`;
- immediate recompaction after removal or addition.

The resolver never mutates roster records and never changes instance IDs. The daemon projects `displayName`; router messages, Stadium-managed presentation, TEAM/roster rows, selectors, Outgoing, View Player, queue copy, and execution strips resolve names from exact identity.

# Exact Instance Audit

`dispatchAttempt.playerInstanceId`, canonical execution-store keys, roster-row `data-instance-id`, and View Player targeting remain exact and authoritative. Daemon-returned `playerName` is a fallback only; the browser resolves the current label from the exact ID before showing it.

Tests cover stale response labels, relabelling, concurrent siblings, selector/roster agreement, Outgoing/strip agreement, Game isolation, and exact dispatch stability across compaction.

# Terminal Label Audit

Coach-created and freshly restored managed terminal presentations use the current shared label projection. Restore now adopts all exact instances before creating terminal presentations so sibling labels are coherent.

The installed VS Code public API exposes `Terminal.name` as read-only. An already-live terminal therefore cannot be safely renamed after a sibling is removed. Sideline does not kill or recreate the Player for cosmetics, and the tab name is never used as identity. The Dad-mode UI recompacts immediately; future-created or naturally restored terminal presentations use the current canonical label.

# Action Acknowledgement Amendment

Successful AUTO and MANUAL dispatches retain the inline Outgoing result, exact recipient, accessible status announcement, and immediate View Player action. They no longer emit the redundant provider-success toast. Normal dispatch success contains no Stadium/provider plumbing language.

Failure and Unknown delivery remain local, actionable, and truthful. Unknown still protects against accidental duplicate execution and requires explicit Recover Play Text. Passive toasts retain `pointer-events: none`, so any remaining informational toast cannot intercept touch or pointer input.

# WAS / IS / WILL BE

## WAS

Historical Unknown/failure records impersonated current Player health, TEAM counted them as Needs You, report readiness was duplicated across TEAM/Player/Incoming, stable seat labels leaked into Dad mode, and dispatch success covered its own View action with a plumbing toast.

## IS

The Ledger retains rich machine truth. Dad mode shows only current execution and current actionable intervention. Incoming owns returned work. One shared exact-ID label projection provides simple contiguous current names. Dispatch produces one inline, non-blocking human acknowledgement.

## WILL BE

Advanced diagnostics may expose historical execution evidence without promoting it into ordinary roster UI. A future supported VS Code terminal-rename capability could synchronize already-live tab cosmetics. Neither changes the rule that names are presentation and exact IDs are identity.
