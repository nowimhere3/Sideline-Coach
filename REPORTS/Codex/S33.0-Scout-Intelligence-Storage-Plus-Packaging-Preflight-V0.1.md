## Question A — multi-host global storage

### Direct live evidence

At observation time, all three hosts configured by `tools/dev/dev-games.json` were concurrently running. Their live `Code.exe` command lines and extension-host inspector ports showed:

| Game | Inspector | Active `--user-data-dir` | Resolved extension global-storage leaf |
|---|---:|---|---|
| Ai Usage - Real Time / GS3 | 9229 | `C:\Users\dmcal\.sideline\dev-hosts\gs3\user-data` | `C:\Users\dmcal\.sideline\dev-hosts\gs3\user-data\User\globalStorage\local.sideline-coach` |
| Trend and Tap Assist | 9230 | `C:\Users\dmcal\.sideline\dev-hosts\trend\user-data` | `C:\Users\dmcal\.sideline\dev-hosts\trend\user-data\User\globalStorage\local.sideline-coach` |
| SidelineCoach-GameTest | 9231 | `C:\Users\dmcal\.sideline\dev-hosts\gametest\user-data` | `C:\Users\dmcal\.sideline\dev-hosts\gametest\user-data\User\globalStorage\local.sideline-coach` |

This was not inferred from launch-plan construction alone:

- the three live top-level processes carried those distinct command-line roots;
- ports 9229, 9230, and 9231 each answered as an active Node extension host;
- each user-data root had its own live `User/globalStorage/state.vscdb`, with independent current write times;
- the three global-storage parent directories existed at three different physical paths.

The extension id is `local.sideline-coach`, derived from the active manifest's `publisher: local` and `name: sideline-coach`. The extension-specific leaf does not yet exist in any of the three profiles because current Scout code does not use `globalStorageUri`. That absence is expected: the installed VS Code API declaration explicitly says the extension directory may not exist until the extension creates it, while its parent is guaranteed to exist.

### Answer

The supported development hosts do **not** share one logical `globalStorageUri`. Each isolated `--user-data-dir` yields a separate Sideline extension storage location. Relocating the depth chart directly to each host's unadapted `context.globalStorageUri / Scout Intelligence` would turn today's one shared Scout department into three independent departments in the currently configured harness (and likewise one per isolated host for any additional harness entries).

### Development versus installed product

- **Development topology:** deliberately isolated VS Code user-data profiles; therefore isolated extension global storage. This is proven above.
- **Installed-product topology:** windows/Games running the extension in the same installed VS Code user profile use that profile's one extension-global storage namespace. That matches the intended per-user, update-surviving Sideline ownership. Separate VS Code profiles or separate user-data roots remain separate by design; they should not be silently treated as one product identity.

No runtime instrumentation was added, and no secret values were read or logged.

## Question B — actual package behavior

### Supported command result

The repository's supported command was run exactly as declared:

```text
npm run package
  -> vsce package
  -> npm run vscode:prepublish
  -> npm run compile
```

Compilation completed, but VSCE 3.9.2 aborted packaging with:

```text
ERROR Both a .vscodeignore file and a "files" property in package.json were found.
VSCE does not support combining both strategies.
```

No `.vsix` existed before the command and none was produced. Therefore there is no truthful current VSIX payload to install or inspect.

### Which rule wins

For `vsce package`, **neither rule wins**: the conflict is fatal. The current package is unbuildable.

`npx vsce ls` does still expose VSCE's candidate inclusion set. That projection demonstrably follows the broad `.vscodeignore` shape rather than the narrow `package.json files[]` allowlist: it listed tests, reports, tools, Scout runtime trees, SOPs, and other paths which are not in `files[]`.

This distinction is load-bearing:

- literal current shipped VSIX: **none**, because packaging fails;
- current VSCE candidate set if the conflict were resolved in favor of the existing ignore strategy: developer evidence and runtime debris would be included;
- intended narrow `files[]` set: not currently enforceable by VSCE while `.vscodeignore` is present.

### Scout evidence exposure in the candidate set

## Question C — recommendation boundary

### PROCEED WITH DEV-HARNESS ADAPTATION

The evidence does not contradict S31's installed-product ownership decision, so a new storage architecture review is not required. It does contradict proceeding *exactly* with an unqualified per-host `context.globalStorageUri / Scout Intelligence` root in the development harness.

Slice 1 implications are:

1. Keep `context.globalStorageUri / Scout Intelligence` as the installed-product default and preserve the strictly additive, never-delete, destination-non-empty no-op migration contract.
2. Add or approve the smallest explicit **development-only shared-root seam** for the supported isolated-host harness so GS3, Trend, GameTest, and future harness Games continue to observe one canonical depth chart. The seam must remain Sideline-owned and must not point at a Game.
3. Prove at least two isolated Game hosts resolve through that seam to the same Scout Intelligence root before Slice 1 is considered complete.
4. Resolve the VSCE strategy conflict as packaging work associated with the relocation: select one supported inclusion strategy and prove the resulting VSIX omits `REPORTS/Scout Only/**`, `Scouts/**`, developer reports, test/runtime evidence, local diagnostics, and local settings while retaining the extension's required runtime files.
5. Do not migrate or duplicate evidence independently into each current development host's `globalStorageUri`; that would change one Scout department into one per Game without architectural approval.

This recommendation does not prescribe the detailed mechanism for the development seam. That decision belongs to Slice 1 implementation/architecture review within the stated boundary.
