==================================================
EXACT CONSERVATIVE DECISION POLICY
==================================================

AUTO chooses Scout only when all of the following are true:

1. no explicit human route constraint is present;
2. the Play expresses primary reconnaissance intent;
3. at least one supporting condition is present: a material evidence gap,
   action explicitly blocked pending evidence, or a bounded comparison across
   multiple current seams;
4. if implementation language is present, the Play explicitly defers that
   action until the evidence is gathered;
5. the prompt is not recognizably Scout-produced evidence;
6. current context is not already owned by Scout;
7. the exact canonical capability is present as instance `scout`, Player type
   `scout`, controlled execution type `scout-formation`, state `ready`, with
   freshness other than `unavailable`.

This is a conjunctive, explainable classification. There is no numeric score
or confidence theatre. A single word such as `find`, prompt length, difficulty,
architecture language, or parallelism alone cannot select Scout.

==================================================
POSITIVE SIGNALS
==================================================

The bounded signal families recognize intent such as:

- scouting, reconnaissance, investigation, audit, or evidence gathering as
  the requested job;
- determining which current implementation/subsystem owns behavior;
- finding contradictions or the authoritative seam;
- inspecting current repository/implementation truth before modifying it;
- comparing multiple current systems, implementations, paths, reports, or
  architecture seams where independent inspection has real value.

The returned `RoutingDecision.scoutNeed` records the contributing booleans and
plain-language reason so the choice can be explained without exposing
subordinate providers or claiming a receiver before Formation selects one.

==================================================
NEGATIVE / ANTI-OVERROUTING GUARDS
==================================================

Ordinary implementation, a known bug/fix, approved architecture work, a lone
`find`, generic difficulty, and negated reconnaissance intent remain on the
existing Claude/Codex/AntiGravity route.

Scout remains `autoEligible: false` in generic provider ranking. The specialized
policy can choose it only through the explicit conservative seam; it cannot
accidentally enter the ordinary fallback pool.

Loop prevention has two layers:

- canonical Scout report markers disqualify the prompt classifier;
- Scout-owned context is a handoff evidence source, never an AUTO reason to
  launch another Scout Formation.

No decision-layer source imports or calls Formation, Combine, Coach Refresh, or
the Combine-to-Formation bridge.

==================================================
AVAILABILITY AND FALLBACK
==================================================

AUTO requires current canonical Scout readiness. Disabled/absent Scout, busy
Scout, unavailable state/freshness, or no eligible receiver means Scout cannot
win. The policy then falls through to the pre-existing eligible non-Scout AUTO
route without starting maintenance or claiming that Scout ran.

Explicit `PLAYER: Claude`, `PLAYER: Codex`, or `PLAYER: AntiGravity` continues
to outrank detection. Explicit `PLAYER: Scout` continues through the existing
canonical manual route and fails truthfully when that capability is unavailable.

When an AUTO Scout decision is attached to an Incoming report, its report path
and compact handoff preamble now travel with the decision. This closes a risk
found by the real field reconnaissance without pasting report contents into the
routing layer.

==================================================
ROUTING RATIONALE AND EXECUTION CONTRACT
==================================================

A Scout-winning decision reports:

- Player/instance: canonical `scout`;
- provider identity: logical `scout`, not a subordinate provider/model;
- display: `Scout Formation`;
- action: ordinary dispatch, or handoff when existing report context travels;
- reason: the actual qualifying evidence signals plus current availability;
- receiver selection: explicitly delegated to Formation using current
  verification and Combine evidence.

AUTO and MANUAL both emit the normal `dispatch.request` frame with target
`scout`. Stadium resolves that target to the existing `ScoutPlayerAdapter`, and
the adapter invokes the existing Formation engine. Formation outcome truth
(`COMPLETE`, `PARTIAL`, `BLOCKED`, `FAILED`, or `UNKNOWN`) remains the routed
Scout Play's outcome truth.
