# Browser Execution Store

`src/public/index.html`:

```js
const executionStore = { gameId: '', epoch: '', serverOffsetMs: 0, views: new Map() }; // key: exact instanceId within store.gameId
```

- Scoped to the presented Game: `resetExecutionStore(gameId)` on Game switch, and whenever a rendered status names a different Game.
- Filled only from `status.execution` and `execution` SSE.
- No key or value derives from the selected Player, friendly names, provider type, route preview, or AUTO decision.
- A frozen, read-only diagnostic accessor `globalThis.__sidelineCoach` returns copies of the store and attempt. Tests use it and devtools can; nothing writes through it.

# Epoch / Revision Merge Rule

One function, `applyExecution(payload, kind)`, handles both `kind: 'snapshot'` and `kind: 'event'`:

1. **Game isolation.** Rejected unless `payload.gameId === currentGameId` **and** the store belongs to that Game. The second check closes the Game-switch window where `currentGameId` has not yet changed.
2. **Epoch.**
   - A different epoch from a **full snapshot** replaces the store wholesale, even at lower revisions.
   - A different epoch from an **event** is ignored and triggers a single coalesced full refresh (`requestExecutionResync`).
3. **Revision.**
   - Events apply per instance only when `incoming.revision > stored.revision`.
   - Snapshots apply per instance when `>=`, and reconcile presence: an instance absent from the snapshot leaves the store, **unless** its stored revision is higher than every revision in that snapshot. That snapshot is older than the stored view, so the view is kept rather than deleted.
4. **No time-based ordering.** Arrival time, `Date.now()` and roster timing never decide conflicts.

Both required regressions are impossible and tested:
- working rev 12, then a delayed idle rev 10 snapshot: ignored;
- finished rev 20, then working rev 19 (event or snapshot): ignored.

# serverNow / Offset Handling

- Each accepted payload sets `serverOffsetMs = serverNow − Date.now()`, taking the latest observation, with no NTP.
- `serverNow()` gives display time.
- Elapsed text is computed as `serverNow() − executionStartedAt`.
- The browser never writes or originates `executionStartedAt`. When it is absent, Working shows no clock.

# Dispatcher Attempt State

```js
dispatchAttempt = { id, phase: 'submitting'|'sent'|'queued'|'failed', mode: 'auto'|'manual',
                    playerInstanceId?, playerName?, clientRef?, delivery?: 'received'|'sent-to-terminal'|'unknown'|'queued'|'failed',
                    failure?: { message, capacityLimited }, prompt }
```

- **Single slot**, set before the request is awaited.
- `delivery` distinguishes a confirmed handoff from an Unknown one without adding an `unknown` phase to the frozen list.
- `prompt` keeps the submitted text for a later deliberate action (Slice E). It is never re-inserted automatically.
- `fullUntil` is left for Slice D.

**`renderDispatchButton()` is the only writer of the button:**
- **submitting:** `Sending Play…` (MANUAL) or `Finding the best Player…` (AUTO); disabled; `aria-busy="true"`.
- **otherwise:** `Dispatch Play`, or `Queue for {Name}` when AUTO staged a queue.
- **disabled only for:**
  - an in-flight attempt;
  - lost connection;
  - an offline Game;
  - an AUTO route error;
  - in MANUAL, when the **exact chosen** Player's canonical view is `starting`/`working` (the pre-existing form guard, now read from the store; the Queue offer remains).
- It **never** shows Received, Working, Completed, Failed, Interrupted, Unknown or Sent to terminal.

# Dispatch Reply Normalization

`normalizeDispatchReply(body, httpFailed)`:

| Reply | Result |
|---|---|
| `status: 'received'` | `sent` / `received` |
| `status: 'queued'` | `queued` |
| `status: 'unknown'` (incl. HTTP 504/502 bodies), legacy `outcome: 'unknown'` | `sent` / `unknown` |
| `status: 'failed'`, legacy `outcome: 'refused'`, or any HTTP failure without an Unknown body | `failed` |
| legacy `outcome: 'accepted'` | `sent` / `received` |
| legacy `outcome: 'sent-to-terminal'` | `sent` / `sent-to-terminal` |
| unrecognised 2xx shape | `sent` / `unknown` (cannot be confirmed; never success, never failure) |

Effects by result:
- **Sent:** prompt cleared if unchanged; toast `Play sent to {Name}.` (daemon message when present).
- **Queued:** prompt cleared if unchanged; the existing `refresh()` runs.
- **Failed:** prompt preserved; the attempt carries the failure message; Dispatch free for Try Again.
- **Unknown:** prompt **cleared** from the box if unchanged (the Play may already be running, so no resend-ready copy is left) but **kept on the attempt**. Toast: "Coach can't confirm {Name} received this Play. Check the Game before sending it again." It is never auto-resent. A later canonical `unknown` view never restores the prompt.

# Game Switch / Reconnect Behavior

**Game switch:**
- `switchGame` resets the store to the target Game immediately.
- Events for the old Game are rejected during and after the switch (the store's Game no longer matches).
- The new Game's full snapshot establishes its epoch and views (B-6).
- Server truth is untouched.
- A status that names a different Game (e.g. selection changed elsewhere) also resets before merging.

**Reconnect / reload:**
- `hello` runs the existing full refresh, and the snapshot rebuilds the store.
- `executionStartedAt` is the original server value; the offset is recomputed; a lower-revision event afterwards is ignored (B-18).

**Stale daemon** (no `status.execution`):
- the store stays empty and nothing is fabricated from roster `turnState`, capability `busy`, Ledger `work`, or raw `turn` events;
- the transitional status stays hidden (B-19).

# Compatibility Notes

- **Legacy in-extension server replies** (`outcome`) still normalize; its status has no `execution`, so no execution truth is shown there. That is the stale-daemon rule, and intentional.
- **Button behaviour change:**
  - Dispatch now re-enables as soon as the reply arrives. The old 1.5 s Received/Completed/Failed labels are gone.
  - In MANUAL, a working exact Player still disables Dispatch and offers "Queue for …".
  - In AUTO, another Player's work never locks it.
- **Prompt behaviour change on Unknown:** previously the prompt was restored when a raw `turn: unknown` arrived. Now the box is cleared (the Play may be running) and the text is held on the attempt.
- **Existing AUTO behaviour, unchanged:** with an empty prompt, `status.routing.autoError` can disable AUTO Dispatch while every Player is busy. This comes from the status route for an empty Play; typing a Play re-previews. Observed in the trace, not introduced here.
- The `execution` SSE sent on connect can arrive before the first snapshot; the merge rule turns that into one coalesced refresh, never a partial store.

# Remaining Limitations

- **No visible multi-Player execution yet.** Only the transitional below-Dispatch status for the last attempt; the store holds every Player's truth for Slice C.
- **Recovering an Unknown attempt's text is Slice E.** It is not reachable in the UI until then; the toast tells the human to check the Game.
- **Projection changes that don't bump a revision only arrive via full snapshot.** Examples: `awaitingReport` expiring after the report grace window, or a control-state change to needs-sign-in. Same-revision events are ignored by design. Status SSE refreshes already bring these snapshots often.
- **Page-wide Game selection is still global.** A refresh started before a Game switch can still flip the whole page back to the Control Plane's selected Game. The store follows the presented Game, so no cross-Game truth appears.
- The raw `turn` SSE still travels to browsers unused.
