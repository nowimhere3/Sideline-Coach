# Actual secret-storage architecture

`src/scout-openrouter-credential.ts` is the single credential owner. It adapts VS Code's canonical `ExtensionContext.secrets` facility through `ScoutOpenRouterCredentialStore` under the extension-scoped key `sidelineCoach.scout.openrouterApiKey`.

The active extension constructs that store once during `activate(context)`. Save calls SecretStorage `store`; Replace calls the same secure replacement operation; Disconnect calls SecretStorage `delete`. Storage failures become generic credential-safe errors rather than returning underlying exception text.

The local browser never reads SecretStorage directly. Its authenticated HTTP request crosses the existing local Control Plane and exact-Game Stadium RPC bridge to the activated extension. The Control Plane does not cache or persist the credential. The response is reshaped to safe state only:

```text
configured: true/false
available: true/false
```

The raw stored value is never returned across the response path.

# Dad Mode UI behavior

The existing Settings screen now contains a `Scout Intelligence` / `OpenRouter` card.

- Not configured: password input plus Save.
- Save: sends one transient request, clears the plaintext input immediately, and shows `API key saved securely` only after the secure store confirms success.
- Configured: shows configured wording without claiming provider health.
- Replace Key: opens an empty input and explicitly says the old key is never shown.
- Disconnect: deletes the SecretStorage entry and returns to the not-configured state.
- The browser retains only configured/available booleans; it does not put the key in localStorage, IndexedDB, status state, diagnostics, or ordinary application state.
- The card follows the existing Scout capability/dev seam. Secret storage does not decide future commercial entitlement.

# Execution credential flow

The trusted execution path is:

```text
Settings input
-> authenticated local Control Plane request
-> exact activated Stadium RPC
-> ExtensionContext.secrets
-> just-in-time ScoutPlayerAdapter resolver
-> Formation request
-> shared Scout execution environment
-> existing createCombineExecutor()
-> ephemeral child-process OPENROUTER_API_KEY
-> OpenCode/OpenRouter
```

`createScoutExecutionEnvironment()` is the one credential precedence and environment-construction seam used by both Combine and Formation.

Formation resolves the stored secret only when its candidate set contains an OpenRouter receiver. The resulting in-memory environment reaches the Combine-derived candidate's existing `createCombineExecutor()` path. Isolated OpenCode config/data homes, read-only authority, bounded concurrency, telemetry, readiness feedback, and current redaction behavior remain intact.

Combine accepts the same trusted runtime resolver and sends its result through the same environment helper and same executor. No second credential implementation or Scout runner was created.

# CLI fallback and precedence

Credential precedence is explicit:

1. trusted runtime credential supplied by the activated Sideline extension path;
2. otherwise the existing process-local `OPENROUTER_API_KEY` for standalone CLI/developer execution;
3. otherwise missing credential and truthful pre-spawn BLOCKED.

Disconnect removes the secure Sideline credential. A deliberately configured standalone CLI environment remains independent, as requested.

# Security guarantees

- No key in VS Code settings, repository files, localStorage, IndexedDB, Sideline JSON state, reports, diagnostics, Scout artifacts, or provenance.
- No stored key is returned to the browser or used to repopulate the input.
- No key is printed by the feature to stdout/stderr.
- Credential operation errors are generic and do not forward underlying exception text.
- Combine and Formation include the resolved runtime value in the existing redaction list before writing stdout, stderr, reports, telemetry, results, or provider boundaries.
- The Control Plane is a transient authenticated bridge, not a credential store.
- Diagnostics were not changed. A standalone RM-1 process cannot safely read VS Code SecretStorage and therefore does not mirror configured state into plaintext diagnostics.
