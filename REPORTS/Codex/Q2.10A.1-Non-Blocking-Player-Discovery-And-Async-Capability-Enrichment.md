# Q2.10A.1 — Non-Blocking Player Discovery and Async Capability Enrichment

## Verdict

**Q2.10A.1 READY FOR HUMAN PROOF — PLAYER DISCOVERY NO LONGER BLOCKED BY PROVIDER ENRICHMENT**

Automated proof is complete. This report does not claim field proof.

## Root cause

Q2.10A put optional Claude control inspection in `PlayerDiscoveryService.discover()`. The Stadium therefore held the `player.discover` response while it ran three Claude CLI operations:

- `claude -p '/model' --no-session-persistence`
- `claude -p '/effort' --no-session-persistence`
- `claude --version`

AntiGravity measured the combined provider probe at about 6,011 ms. The detached Control Plane expires every Stadium RPC after 5,000 ms. It deleted the pending request before the Stadium answered, so the late response was orphaned and Check Players deterministically failed. Fresh Control Plane and Stadium processes were already proven; stale runtime was not the cause of this failure.

## Old synchronous timing path

The old path was:

```text
Check Players
  → Control Plane player.discover RPC (5,000 ms budget)
  → Stadium process/command discovery
  → await Claude /model + /effort + --version (~6,011 ms)
  → response arrives after pending RPC was deleted
  → browser receives timeout instead of any Players
```

Increasing the generic bridge timeout was rejected as the fix. It remains 5,000 ms.

## New fast discovery path

`PlayerDiscoveryService.discover()` now performs only core scouting:

- supported Player catalog construction;
- command availability checks;
- Game-scoped process observation;
- running-in-this-Game candidates;
- running-elsewhere disclosure.

The process scan and independent command checks run concurrently. No control enricher is called from `discover()`. Claude may initially have no `controls` property, but it is still truthfully returned as Ready or Running. Codex, Claude, AntiGravity and Terminal therefore do not depend on provider model/reasoning/version introspection.

## Async enrichment architecture

Provider capability work is represented by data-driven `PlayerDiscoveryEnricher` records. Each record identifies a Player type, a cancellable probe, an explicit Unknown projection and a timeout budget. This is an extension seam for future Codex, AntiGravity and third-party enrichers rather than a Claude branch in core discovery.

After `discoverPlayers()` stores and publishes the core snapshot, it returns that snapshot and schedules enrichment with `setImmediate`. Concurrent enrichment requests for the same `(stadiumId, gameId)` share one in-flight provider pass, preventing repeated Check Players clicks from spawning duplicate probe sets. A later completed cycle may probe again; there is no automatic retry loop.

`PlayerRoster` gives each discovery cycle a generation. Results from an older cycle or a disposed roster are discarded. When enrichment completes, Coach merges only `catalog[].controls` into the current discovery. This is important: adoption or duplicate reconciliation may have removed a running candidate while Claude was being inspected, and enrichment must never restore that stale candidate.

## Claude stdin-delay repair

Claude probes continue to use PowerShell, a neutral temporary working directory and quoted slash commands. This preserves the Q2.10A protection against Git Bash rewriting leading `/model` or `/effort` into filesystem paths and avoids running Game-local hooks before the human's trust decision.

The implementation now uses the callback form of `execFile` and immediately calls `child.stdin?.end()`. Claude therefore observes EOF instead of waiting roughly three seconds for stdin. The three local inspections still run concurrently.

## Provider probe timeout policy

- Generic optional-enrichment default: 8,000 ms.
- Claude child-process timeout: 7,500 ms.
- Claude enricher budget: 8,000 ms.
- The generic enricher supplies an `AbortSignal`; timeout aborts the provider process tree exposed through `execFile`.
- Failure, malformed output, unavailable PowerShell/CLI or timeout becomes a Claude control profile whose model and effort states are `unknown`.
- No provider failure changes the successful core discovery result.
- No aggressive retry or recurring process loop was added.

The child deadline is intentionally slightly inside the enrichment deadline so normal child-process cleanup can finish before the outer budget wins.

## Canonical state update path

```text
core player.discover response
  → PlayerRoster.lastDiscovery
  → background PlayerDiscoveryEnricher
  → generation-safe controls-only merge
  → PlayerRoster.changed.fire()
  → StadiumClient player.discovery.changed
  → Control Plane discoveryByGame cache
  → broadcastStatus()
  → existing SSE status event
  → browser refreshes canonical /api/status
```

The new notification is typed as `PlayerDiscoverySnapshotParams`. The Control Plane accepts it only when its `instanceId` and `gameId` match the authenticated Stadium session, preserving Game isolation. Stadium reconnect also republishes the last discovery snapshot, so an already-enriched host can converge a fresh daemon.

## UI convergence

The browser gained no competing state store. Its existing SSE `status` listener refreshes `/api/status`; Q2.10A's existing control projection then reads the richer `playerDiscovery.catalog[].controls`. No page refresh and no second Check Players action is required. If enrichment cannot establish controls, Claude remains recruitable and the canonical control state is Unknown.

## Preserved Q2.10A behavior

The Play Analyzer, single-Player AUTO route, Claude control profile and strict parsing, running-in-this-Game detection, running-elsewhere disclosure, fresh duplicate guard, adoption ownership, Roster/Dispatcher instance identity and provider-managed routing remain unchanged. ## Known constraints

- Claude control enrichment currently uses the Windows/PowerShell local probe proven in Q2.10A. Other platforms receive Unknown until they gain their own provider enricher.
- Strict parsing intentionally turns changed or malformed provider output into Unknown.
- The core Windows process scan still has its existing 8-second defensive timeout. Normal measured discovery was below 350 ms before Q2.10A; this Play removes the deterministic 6-second provider wait but does not pretend OS process enumeration can never fluctuate.
- Initial core status and enriched status are two canonical projections of the same discovery cycle. A brief absence of controls is truthful, not an error or a loading block.
- No detached runtime was restarted automatically, so active development sessions were not disrupted.

## Control Plane Freshness Guard breadcrumb

The existing Q2.9C breadcrumb remains the correct separate V1 stabilization item:

```text
extension/startup
  → health check
  → compare running daemon build fingerprint with current compiled daemon closure
  → current: reuse
  → stale + ExtensionMode.Development: replace safely
  → Stadiums reconnect
```

The guard must use build identity rather than wall-clock age and must be development-mode gated so a customer daemon is never killed merely because another window has a different bundle. Q2.10A.1 does not confuse that known fossilization risk with the proven synchronous timeout regression.

## WAS / IS / WILL BE

### WAS

Check Players synchronously waited for Claude model, effort and version inspection. The probe took about 6 seconds, the Stadium bridge allowed 5 seconds, and one slow provider prevented every Player type from being discovered.

### IS

Check Players returns core scouting independently of provider controls. Provider enrichers are optional, bounded, cancellable and in-flight deduplicated. Their results merge into canonical per-Game discovery and reach the browser over the existing live-state path. Slow, broken, unavailable or changed providers become Unknown without blocking recruitment.

### WILL BE

Q2.10B can prove a controlled Claude adapter on top of this separation. Later Plays can add multi-Player smart routing, Architect + Workers, AUTO/CONSERVE/MANUAL, Usage Sentinel, controlled AntiGravity, the Control Plane Freshness Guard, Mobile Sideline, remote Stadiums and V1 stabilization without putting provider introspection back into scouting.
