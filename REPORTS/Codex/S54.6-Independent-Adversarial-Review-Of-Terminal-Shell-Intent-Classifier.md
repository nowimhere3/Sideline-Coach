## Subset-invariant proof

The invariant holds:

`classifyShellIntent(input).kind === "shell"` implies `checkTerminalCommand(classified.command).ok === true`.

Structural proof:

1. A shell verdict can be returned only after `text` is normalized by ASCII-edge trimming.
2. The final gate calls `checkTerminalCommand(text)`.
3. It returns reasoning unless both `guard.ok` is true and `guard.command === text`.
4. The returned shell verdict sets `command: text`.
5. Therefore every reachable shell verdict's command is accepted unchanged by the explicit Terminal boundary.

Dynamic corroboration:

- The focused TI-8 property passed over its curated corpus, exhaustive grammar combinations, and 60,000 seeded fuzz inputs.
- The independent 150,000-input probe produced 109 positives, with 0 subset failures and 0 boundary-command fidelity failures.
- Strictness (not mere equality) is demonstrated by explicit-Terminal-accepted inputs the AUTO classifier rejects, including `check git status`, `git branch feature`, `rm -rf x`, `npm install`, `git status && ls`, `cd ..`, and `cat .env`.

## Pager / hang assessment

**Classification: BLOCKER for wiring the current Git grammar unchanged; bounded by the small narrowing above.**

Git's current documentation states that pagination applies when output is written to a TTY, that command-specific `pager.<cmd>` configuration can turn pagination on, and that `git -P` / `git --no-pager` is the command-line override. Git's branch documentation specifically states that branch listing uses a pager by default. See [Git command documentation](https://git-scm.com/docs/git) and [git-branch documentation](https://git-scm.com/docs/git-branch).

`runTerminalCommand` executes through VS Code shell integration in the Coach-managed integrated terminal. That is a TTY-like interactive surface, unlike this review's non-TTY shell runner (where `git var GIT_PAGER` returned `cat`). Local non-TTY behavior therefore does not prove the Coach path safe. Repository/global/user Git configuration can also change pager behavior.

Current accepted risk by family:

- `git diff`: unbounded output; can page and wait for pager input.
- `git log`: even `-n 100` can exceed a terminal screen; bare `git log` is unbounded.
- `git show`: a single commit can contain an arbitrarily large patch; can page.
- `git branch`, `-a`, `-r`, and verbose listing: Git documents pager use for listings; branch count is unbounded.
- `git branch --show-current`: one branch name or no output; retain as the bounded non-listing form.
- `git status` and version probes: no pager risk identified in the accepted forms.

The Coach path prevents a second command while one is active and has no approved interrupt facility. A waiting pager is therefore operationally material, not cosmetic.

## Project-defined npm/pnpm/yarn script assessment

### Intent classification safety

Accepting exact inputs such as `npm test` and `npm run build` does not create an intent false positive. These are unmistakable commands, and the classifier returns the exact command the human typed. Keeping the script-name set closed remains appropriate; it must not be described as proving the script itself safe.

### Command execution risk

The names are labels controlled by the Game's manifest. npm documents `npm run` as running arbitrary package scripts and also documents matching pre/post lifecycle scripts; Yarn likewise runs the workspace-defined script or, depending on version/state, a matching local tool. See [npm run-script documentation](https://docs.npmjs.com/cli/v9/commands/npm-run-script/), [npm scripts documentation](https://docs.npmjs.com/cli/v9/using-npm/scripts/), and [Yarn run documentation](https://yarnpkg.com/cli/run).

Accordingly, `test`, `build`, `lint`, `check`, `compile`, and `typecheck` are not intrinsically read-only, non-networking, non-destructive, bounded, or non-interactive. This is execution risk, not classification ambiguity.

Under the present architecture, their AUTO eligibility is conditionally acceptable because the human supplied the exact package-manager command, the Terminal must be Coach-managed, on-field, idle, and pinned to the selected Game root, and the command remains visible/observable. Play 5 must preserve those controls and must not infer “safe script” from the allowlisted name. Script-content inspection would not reliably prove safety and is not required by this classifier gate. A timeout/interrupt design would improve liveness for long-running or watch-mode scripts, but that is a separate Terminal execution-policy concern.

## Bare-command assessment

`ls`, `dir`, `pwd`, `whoami`, `hostname`, `Get-Location`, and `Get-ChildItem` are sufficiently unmistakable when they are the entire normalized input. The grammar accepts no arguments or flags for these commands, and any prose, punctuation, casing variation, prompt prefix, path, comment, or second token is rejected. They may remain eligible.

## Command-fidelity assessment

The classifier never synthesizes or rewrites command content. It removes only leading/trailing ASCII space, tab, CR, and LF. Internal tabs/newlines and every non-ASCII/control character are rejected. The final guard requires `checkTerminalCommand(text).command === text`, then returns that same `text` as `verdict.command`.

The independent trim probes confirmed:

- `" git status "` -> `git status`
- leading tab plus trailing CRLF -> `git status`
- leading CRLF plus trailing tab -> `npm test`
- leading/trailing LF -> `git log -5`

These are safe only if Play 5 executes `verdict.command`. Sending the raw prompt would reintroduce a trailing Enter/newline or other surrounding whitespace and violate the reviewed fidelity contract. Play 5 must pass `verdict.command` unchanged into the existing explicit Terminal boundary. It must not trim again, append options, or reconstruct from tokens.

No unexpected ASCII-trim edge was found. A string containing only ASCII edge whitespace becomes empty; exotic edge whitespace is not trimmed and is rejected by the printable-ASCII gate.
