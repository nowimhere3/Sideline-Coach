## Exact old failure mechanism

`renderScoutPlay()` listed section names as bullets but never required Markdown hashes. `evaluateScoutReport()` nevertheless required every section to match a strict `#{1,3}` Markdown-heading regex. `deriveCombineStatus()` then mapped any COMPLETE attempt with `reportStructurallyUsable === false` directly to LIMITED.

Qwen used plain uppercase section lines. Inkling used colon-delimited section lines and an inline `Executive answer: ...`. Both had COMPLETE execution, read-only authority, the required reconnaissance statement, useful evidence, and real Game artifacts. Punctuation alone stranded them for the seven-day retry window.

## Prompt repair

The canonical semantic Scout prompt now says:

`Use these Markdown headings on their own lines:`

and renders the eight preferred headings explicitly:

```text
# Executive answer
# FACTS
# INFERENCES
# UNKNOWNS
# CONTRADICTIONS
# Relevant files / symbols
# Recommended next step
# Provenance
```

The required statement remains unchanged:

`This report is reconnaissance, not final architectural authority.`

## Evaluator repair

Section recognition remains anchored at line starts and case-insensitive. It accepts:

- one to three Markdown heading hashes;
- plain section labels on structural lines;
- trailing colons;
- `**bold**` and `**bold:**` headings;
- inline `Executive answer: <text>`.

Arbitrary prose that merely mentions the section names does not pass. All eight recognizable sections and the exact required reconnaissance statement remain mandatory.

READY is no longer based on section labels alone. A COMPLETE tryout now requires all of the following:

- a report was actually created;
- the read-only contract was confirmed held;
- the complete structural/result contract passed;
- a cited path mechanically matched a real Game artifact;
- no obvious unsupported claim was recorded.

Missing structure, missing statement, missing repository evidence, missing report creation, or failed read-only authority remains LIMITED. `obviousUnsupportedClaim` remains a conservative existing telemetry field; automatic unsupported-claim detection was not invented in this bounded Play.

## Evaluation-contract revision design

Evaluation semantics are versioned separately from S25 execution semantics:

- legacy evaluator: `strict-markdown-headings-v1`;
- current evaluator: `structural-lines-and-evidence-v2`;
- execution qualification remains `authenticated-isolated-opencode-v1`.

New attempt telemetry records `evaluationContractRevision`. Scorecards record separate `evaluationEvidence` with the current revision, observation time, source report path, and—when re-evaluated—the prior evaluator revision and prior status.

`reevaluateCombineEvidence()` is the bounded correction seam. It only accepts a LIMITED scorecard whose preserved report is inside canonical Scout evidence and is backed by matching COMPLETE telemetry with `reportCreated === true` and `readOnlyContractHeld === true`. It reads the report, evaluates it under the current contract, and changes only canonical interpretation metadata/status plus an audit note.

It does not:

- execute a provider;
- alter reports or Combine completion artifacts;
- increment counters or route attempts;
- change `lastTryoutAt`;
- reuse or overwrite S25 execution qualification metadata.

The original run’s `COMBINE-COMPLETE.json` still records both LIMITED observations, while each scorecard now explains why the canonical interpretation changed.
