## Contract Implemented

`ProviderResourcePolicy` exposes:

- `provider`: `claude` or `codex`
- `isConserveActive`: derived scarcity-active boolean
- `conserveLevel`: `none`, `low`, or `critical`
- `evidenceState`: `known` or `unknown`
- `rationale`: compact deterministic explanation
- `activeResetsAt`: canonical Unix-second reset horizon or `null`

`ResourcePolicyService` is constructed with the existing read-only AlarmEngine-compatible `getState()` seam and provides:

- `get(provider)` for one provider
- `getAll()` for Claude and Codex from one snapshot

`projectProviderResourcePolicy(snapshot, provider)` is also exported as the pure deterministic projection used by the service and tests.

The service stores no mutable resource state. Each query reads canonical state and derives a new value.

## Canonical Resource-State Source

The only scarcity input is `AlarmStateSnapshot.rules`, exposed defensively by the existing `AlarmEngine.getState()` method. The policy module consumes each window's already-evaluated `NORMAL`, `LOW`, `CRITICAL`, or `UNKNOWN` state plus its canonical `horizonResetsAt`.

The module does not import AlarmPreferences, HealthAuthority, percentages, utilization, or threshold values. A deterministic integration test evaluates identical 15% remaining telemetry under two different Dad-configured LOW thresholds. AlarmEngine produces LOW at 20 and NORMAL at 10; Resource Policy projects those states without seeing or recalculating the percentage.

This preserves the ownership chain:

`HealthAuthority → AlarmEngine → ProviderResourcePolicy → future routing consumer`

## Provider Aggregation

Each provider is evaluated independently across 5-Hour and Weekly windows.

Severity precedence is:

1. any canonical CRITICAL window → provider `critical`
2. otherwise any canonical LOW window → provider `low`
3. otherwise all known NORMAL windows → provider `none`

LOW and CRITICAL set `isConserveActive: true`. NORMAL and fully unproven states set it false. Stage 2A interprets scarcity only; it performs no routing action.

## UNKNOWN Handling

Missing rules and canonical `UNKNOWN` rules are treated as unknown evidence, never NORMAL.

- both windows UNKNOWN/missing → `conserveLevel: none`, `evidenceState: unknown`, rationale states that provider usage evidence is UNKNOWN
- one NORMAL and one UNKNOWN → no proven scarcity, but `evidenceState: unknown` and rationale identifies incomplete evidence
- one LOW/CRITICAL and one UNKNOWN → proven scarcity remains authoritative while `evidenceState: unknown` and the rationale identifies the unproven window

This deliberately leaves future UNKNOWN routing behavior to Stage 2B.

## Reset-Horizon Selection

Only windows at the provider's strongest proven scarcity state may drive `activeResetsAt`.

- one strongest window → its canonical `horizonResetsAt`
- multiple windows tied at the strongest state → earliest defined canonical horizon
- equal horizons are stable in fixed 5-Hour-then-Weekly window order
- no defined horizon among strongest windows → `null`
- no active LOW/CRITICAL scarcity → `null`

The module never synthesizes a reset time and owns no timer.

## Rationale

Rationales are deterministic and bounded. They identify:

- provider
- driving window or tied windows
- canonical LOW/CRITICAL state
- that Dad's configured threshold is the source of that state
- selected reset timestamp when known, rendered as ISO time
- any incomplete UNKNOWN window evidence

This is routing-explanation data, not a notification-message engine.
