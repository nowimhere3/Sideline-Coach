## Live human evidence that motivated the repair

Post-S27 field evidence proved Scout was visible and routable in TEAM and MANUAL, and that the card changed from Ready to Scouting during a real run. It also proved the live card had no timer, Play summary, or selected Scout count, then returned directly to Ready without Report ready, View Report, or durable Formation handoff.

Field truth overruled the prior fixture-only confidence.

## Root causes

Two production seams were disconnected:

1. `ControlPlaneDaemon.buildExecution()` projected only `PlayerRoster` instances. Scout is intentionally synthetic and absent from that roster, so its real work-ledger turn never reached the synthetic card even though Formation lifecycle events existed.
2. ordinary report discovery scans the active Game. The canonical Scout `FORMATION-RESULT.md` lives under Sideline Scout infrastructure, so it never entered the active Game's report registry, never linked to the logical Scout Play, and never reached Incoming/View/acknowledgement.

A smaller data-shape issue also existed: the selected receiver count was carried in the generic turn `summary`, competing with the actual Play summary. The two truths now have separate fields.

## Existing plumbing preserved

- `ScoutPlayerAdapter` and `runScoutFormation`;
- Formation `onSelected(...)` as the authoritative selected-count event;
- the Control Plane work ledger and its genuine execution-start timestamp;

- the existing report registry and Incoming preview/copy surface;
- exact-path `viewReport(...)` selection;
- `/api/work/acknowledge` after successful intentional report opening;

Ordinary Claude/Codex lifecycle and report handoff remain on their existing paths.

## Lifecycle / event flow

```text
Play accepted
  -> Scout adapter selects the actual Formation
  -> onSelected emits promptSummary + "N Scouts running"
  -> work ledger stamps the genuine started event
  -> logical Scout execution projection reaches the synthetic card
  -> card shows Scouting + count + concise task + elapsed time
  -> Formation writes its exact FORMATION-RESULT.md
  -> Stadium registers that exact parent with explicit Play provenance
  -> terminal Formation event records truthful COMPLETE/PARTIAL/etc. summary
  -> report registry links the parent to that exact Scout Play
  -> card remains Report ready
  -> View Scout Report selects that exact Incoming artifact
  -> successful opening calls the existing acknowledgement endpoint
  -> acknowledged card returns to normal Ready presentation
```

No timeout, status poll, Incoming refresh, or rerender acknowledges the report.

## Working card telemetry

The ledger and execution view now carry `activitySummary` independently from `promptSummary`.

For a real selected Formation the card can render:

```text
Scout
Scouting · 3 Scouts running · Investigate Scout report lifecycle... · 02:14
```

The count is the actual `onSelected` count, not requested size. The task is a bounded summary of the logical Play. The elapsed origin is stamped when the selected Formation emits its real started event; the prior unconditional early fallback start was removed.

## Formation report identity and handoff

On completion, Stadium reads and registers the exact `result.formation.resultPath` produced by that turn. It does not scan for “latest,” compare file modification recency, or choose a receiver report.

The registered item is:

- `FORMATION-RESULT.md` from the exact Formation ID/path;
- associated with the active Game for Incoming isolation;
- owned by logical Player `scout`;
- linked to the exact Play/client reference through explicit provenance;
- placed ahead of ordinary scanned reports so bounded status projection cannot omit it.

Receiver reports remain subordinate evidence and may still appear in the Formation tree/report content, but they are not the Dad-facing parent artifact.

COMPLETE displays `Formation complete · N Scouts`. PARTIAL displays `Formation partial · X of N Scouts completed`. A blocked/failed Formation with a parent artifact still exposes its truthful report instead of hiding the intelligence gathered. A report-registration failure does not rewrite a real Formation outcome into false negative Player game film.

## Acknowledgement semantics

The existing exact-path View Report behavior already had the correct human-intent seam. This Play connects Scout to it:

1. unacknowledged Formation parent remains Report ready indefinitely;
2. View Scout Report opens/selects the exact registered parent through Incoming;
3. only a successful intentional open acknowledges the exact report/Play;
4. acknowledgement is idempotent;
5. ordinary rerenders, polls, refreshes, and arbitrary time do not acknowledge it.

## Dev Mode explicit receiver seam

Settings now contains a small Dev Mode operator under Scout Intelligence:

- lists only receivers currently eligible under canonical Scout depth-chart evidence;

- accepts one bounded read-only objective;

The adapter still resolves the API key ephemerally inside the extension runtime. CLI environment fallback remains unchanged.

This is a diagnostic/operator seam, not a second routing mode, runner, credential store, or production Dad feature.
