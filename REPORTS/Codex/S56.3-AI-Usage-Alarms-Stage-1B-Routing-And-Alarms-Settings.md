## Canonical AlarmPreferences Reuse

The Settings page does not maintain a browser-only preference model and does not introduce another store or endpoint. Initial values come from the canonical preferences returned in daemon status. Saves use the existing preference API and backend normalization/validation path. A failed save rolls the form back to canonical status rather than leaving optimistic browser state authoritative.

Stage 1A represented CRITICAL as one shared percentage. Stage 1B requires Dad to configure CRITICAL independently for all four resource windows, so the existing canonical threshold object was minimally graduated in place:

- each provider now owns 5-Hour LOW, 5-Hour CRITICAL, Weekly LOW, and Weekly CRITICAL;
- all CRITICAL defaults remain 5%;
- the AlarmEngine reads the matching canonical per-window CRITICAL value;
- legacy Stage 1A `criticalPercent` data is accepted and fanned out during normalization, preserving existing installations.

This is a compatible preference-contract extension, not a second alarm configuration system. AlarmEngine transition, hysteresis, reset-horizon, deduplication, persistence, and delivery architecture did not change.
