RESULT

PASS. Sideline can now express one canonical logical routing target:

`Player: Scout`

An explicit MANUAL Scout route travels through the normal Control Plane

==================================================
CANONICAL SCOUT ROUTING REPRESENTATION
==================================================

The machine identity is defined once in `src/scout-player-contract.ts`:

- instance id: `scout`;
- player type: `scout`;
- field label: `Scout`;
- transport: the existing controlled dispatch channel;
- execution type: `scout-formation`;
- provider/model display: `Scout Formation`, without claiming that Scout is
  itself a provider model.

The lightweight identity contract is deliberately separate from the
Stadium-side adapter so the Control Plane runtime closure does not pull Scout
execution/provider code into the daemon build.

==================================================
MANUAL ROUTE BEHAVIOR
==================================================

The existing routing-capability projection supplies Scout to the current
MANUAL selector. Selecting it sends the ordinary `/api/dispatch` request with
`routingMode: manual` and `playerInstanceId: scout`.

`ControlPlaneRouter.dispatch()` validates that the exact advertised capability
is ready and has `executionType: scout-formation`. It then creates a canonical
manual `RoutingDecision`, clears model/effort overrides, and sends the normal
`dispatch.request` frame. Human selection therefore outranks AUTO exactly as
it does for other Players.

The browser describes Scout's subordinate model/effort as `Formation managed`
and states that Combine remains the scorecard authority. The logical Scout
capability appears in the selector but not in the process roster, so this Play
does not accidentally create the protected future Scout Player card.

If Scout is disabled, already working, or has no eligible receiver, it is not
manually dispatchable. A forged direct request fails truthfully instead of
falling through to a provider terminal or another Player.

==================================================
AUTO SEAM
==================================================

Scout sets `autoEligible: false`. Unconstrained AUTO therefore retains the
existing Claude/Codex/AntiGravity behavior, including when Scout is available.
No keyword classifier or pretend Scout-need intelligence was added.

The existing explicit-constraint recognizer does know the logical name
`Scout`, even when the capability is absent. `PLAYER: Scout` can therefore
produce the same canonical target when Scout is ready, or a truthful
unavailable result without silently substituting another Player. Future AUTO
Scout Need Detection only needs to choose this same target; it does not need a
new dispatch or execution path.

Busy Scout does not accept or queue another Formation in V0.1. Its capability
advertises `supportsQueue: false`, and both MANUAL and constrained routing
honor that boundary.

==================================================
SCOUT EXECUTION ADAPTER AND FORMATION REUSE
==================================================

`ScoutPlayerAdapter` in `src/scout-player.ts` owns only translation between a
routed Play and Formation:

1. it inspects the same candidate universe and the same `eligible()` predicates
   Formation uses;
2. it publishes the logical capability only when at least one receiver is
   currently eligible;
3. it guards one active Formation at a time;
4. it passes the routed prompt to the existing `runScoutFormation()` callable;
5. it returns the unmodified Formation outcome and completion evidence.

`inspectScoutFormationAvailability()` was added beside Formation selection in
`src/scout-formation.ts`. Both availability and execution read built-in
verification plus `combineDerivedFormationCandidates()` fresh. There is no
cached depth chart and no hardcoded receiver/model in the adapter.

Combine remains the only authority that writes Scout scorecards. Coach Refresh
remains the bounded due-candidate maintenance seam. Formation remains the
authority for receiver selection, 1–3 concurrency, canonical ScoutPlay
normalization, execution, failure isolation, synthesis, and durable reports.
Routing does not invoke Coach Refresh or start recruitment when no receiver is
eligible.

==================================================
RESULT AND LIFECYCLE TRUTH
==================================================

The Stadium acknowledges Scout through the normal `dispatch.accepted` contract,
then emits accepted/started turn evidence. On completion it carries:

- the exact Formation outcome;
- Formation id;
- result path; and
- a summary naming the outcome and evidence.

Control Plane ledger truth now preserves `partial` and `blocked` in addition to
the existing completed/failed/interrupted/unknown outcomes. COMPLETE maps to a
completed Player turn; PARTIAL remains a distinct terminal result; BLOCKED is
not presented as success; FAILED and UNKNOWN remain truthful. Formation
provider failure isolation is unchanged underneath the adapter.

==================================================
SCOUT AVAILABILITY / ENABLE BOUNDARY
==================================================

`coach.scout.enabled` is a boolean configuration seam, defaulting on. Turning
it off removes Scout from the capability snapshot. Turning it on does not force
availability: current Formation evidence must still yield at least one eligible
receiver.

This is an enable/disable architecture seam, not licensing or packaging.
Unavailable Scout is not an AUTO candidate, does not appear as a MANUAL target,
and rejects a forged manual dispatch at both Control Plane and Stadium
boundaries.
