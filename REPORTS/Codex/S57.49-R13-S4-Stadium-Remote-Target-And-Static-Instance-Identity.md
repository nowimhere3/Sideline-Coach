## Instance identity and header behavior

Each successful StaticPreviewServer start mints `randomBytes(16).toString('base64url')`: 128 bits of cryptographic randomness represented as a 22-character base64url value. It is not derived from the port, Game, Stadium, path, or time. Startup failure clears the provisional identity. Disposal and Game switching close the listener and clear its identity; a later start mints a different value.

The exact header is `X-Sideline-Preview-Instance`. Once a request reaches an active listener, the server sets that response header before method, URL, containment, or filesystem processing. A supplied value different from the listener identity returns 409 `Preview Instance Changed`; no Game asset bytes are returned. The response echoes the actual identity on successful GET/HEAD and on 400/403/404/405/409-style server rejections. During listener shutdown the identity remains available until connections are closed, then is cleared.

Requests without the expected-instance header follow the existing code path unchanged. Focused proof confirms an ordinary desktop request returns the same 200 body as a request carrying the correct identity. Existing loopback-only binding, ephemeral port assignment, containment, dotfile protection, MIME types, methods, and multi-page behavior remain intact.

## Stadium RPC contract

`game.preview.remoteTarget` uses the existing `withExactGame` guard and is observation-only. It does not call `resolveGamePreview`, `prepare`, or `urlFor` and cannot start or replace a listener.

For a co-located Stadium with an already-running server bound to the exact Game, it returns:

`{ success: true, gameId, available: true, port, instanceId }`

With no current exact-Game listener it returns `{ success: true, gameId, available: false, reason: 'not-running' }`. After disposal or `prepare(otherGame)`, the old port and identity are unavailable. A mismatched Game is rejected by the existing exact-Game contract and exposes no port.

When `remoteName !== undefined`, the RPC returns `{ success: true, gameId, available: false, reason: 'not-colocated' }`, even if a local static listener exists, so it never leaks an unusable loopback target. The `game.preview.remote.v1` hello feature is appended only when `remoteName === undefined`; SSH/WSL/Codespaces-style remote names do not advertise it. Existing features remain unchanged.

## Lifecycle and stale-port protection

Proof starts one listener with identity A, disposes it, starts a replacement with identity B, and verifies A differs from B. A request sent to the replacement target while presenting A receives 409 and the response identifies B. This simulates the stale caller following a port coordinate now owned by a new listener and proves that port reuse alone cannot validate the target. Switching Games clears the prior identity before the target can be reported for the new Game.
