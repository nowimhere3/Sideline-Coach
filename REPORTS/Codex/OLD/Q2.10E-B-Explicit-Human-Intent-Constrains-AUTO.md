# Constraint Representation

`RouteConstraints` is a typed, hidden routing contract containing independently optional dimensions:

- Player type;
- exact `playerInstanceId`;
- model id and display name;
- reasoning effort;
- excluded model ids;
- the set of dimensions conservatively recognized;
- source = `play`.

The dimensions are never collapsed. A Player is not a model; an exact instance is not a Player type; and effort is not inferred from either. Higher-priority fields narrow the live Game-scoped candidates, while existing AUTO policy fills only fields the human did not specify.

When a busy controlled target is queued, the resolved exact instance, model, effort, constraints, selected-report reference, owner identity, and provider-neutral handoff preamble are persisted with that queue item. Restart deserialization intentionally omits meaningless JavaScript `undefined` properties while preserving every routing fact.

# Natural-Language Recognition Boundary

`src/control-plane/route-constraints.ts` implements deterministic, conservative recognition—not general NLP.

Recognition is limited to:

- unmistakable imperatives near the first eight non-empty Play lines, including `Use`, `Give this to`, `Route this to`, and `Send this to`;
- an optional bounded `For ..., use ...` prefix matching the field defect;
- explicit routing fields such as `Player:`, `Worker:`, `Implementation Agent:`, `Route:`, or `Routing:`;
- known Player types and friendly numbered instances from the current Game;
- model ids/display names and efforts present in the selected Player's live capability catalog;
- unmistakable `don't use`, `do not use`, or `never use` exclusions for known models.

Technical prose that merely mentions a provider or model remains ordinary AUTO. Unknown Players and models are never created. A recognized known Player followed by an unknown model constrains only the known Player; the unknown token does not become a capability. This conservative boundary is visible in staged rationale because Coach says exactly which known dimensions it honored and which omitted dimensions it chose.

`Same Player, cheaper model` is deliberately not interpreted yet: the current routing data has no truthful cost ordering. Implementing that phrase now would manufacture a meaning for “cheaper.”

# Routing Precedence Implementation

The implemented flow is:

`Game → explicit Play constraints → context ownership / handoff evidence → exact instance → work state / queue → provider → model → effort → transport`

This realizes the approved precedence as candidate narrowing:

1. MANUAL and existing explicit UI selection remain authoritative and are not reparsed.
2. Recognized Player/exact-instance constraints narrow eligible instances.
3. Recognized model and effort constraints narrow the selected Player's live catalog.
4. Model exclusions remove only catalog-proven models.
5. Context ownership chooses continuity inside the valid set or supplies a handoff to a different requested executor.
6. Existing task classification, work-state policy, provider policy, and defaults fill the remaining fields.

Without any explicit constraint, Q2.10D behavior is unchanged: a proven context owner remains preferred, busy-owner queue/handoff policy remains intact, and Unknown remains valid.

# Context Handoff Behavior

When the report owner differs from the constrained executor, routing now produces a Q2.10D handoff decision rather than discarding the report or choosing its owner. The decision retains:

- exact context-owner instance;
- explicit report provenance and report path/name;
- prior Play summary when available;
- a compact provider-neutral instruction to read the report before proceeding.

For the field case, the result is Codex execution with the Claude architecture report supplied as context. The dispatch prompt is still stamped with Q2.10E-A provenance for the actual Codex instance/model/effort; context provenance and new execution provenance remain separate facts.

# Staged-Route UX

The existing Dad Mode staged-route card requires no new routing cockpit. It receives the canonical decision and shows:

- the requested Player / exact instance;
- the resolved model and effort;
- an “as you asked” rationale for recognized dimensions;
- which dimensions Coach filled;
- the selected report sent as context when the action is a handoff.

Examples include:

- `Codex · GPT-5.6 Sol · Medium` with “Codex and GPT-5.6 Sol selected as you asked. Coach chose the reasoning.”
- `Codex · GPT-5.6 Sol · High` with all three dimensions acknowledged as requested.

Preview and actual AUTO dispatch use the same canonical computation. The dispatch result now also carries the exact `RoutingDecision`, enabling direct automated comparison with the staged decision.

# Unavailable-Route Behavior

A constrained route that has no valid current candidate returns a truthful error and never falls through to an unrelated Player. Explicit Terminal in AUTO is refused with its existing MANUAL-only explanation. A busy but otherwise valid controlled Player receives the Play on its exact durable queue, with constraints and report handoff preserved.

Dedicated `Wait for Codex` / `Let Coach choose another Player` controls and Usage-Sentinel capacity-aware waiting remain future work. Q2.10E-B does not silently implement either policy.

# WAS / IS / WILL BE

## WAS

AUTO could correctly identify Claude as the owner of selected-report context and then incorrectly treat that knowledge as execution authority, overruling an unmistakable request for Codex and Sol.

## IS

AUTO recognizes a narrow set of known, explicit human route instructions and carries typed Player, exact-instance, model, effort, and model-exclusion constraints through preview, dispatch, and durable queue state. Those constraints narrow the route first. Context ownership remains authoritative evidence and becomes a handoff when the requested executor differs. Unspecified dimensions remain Coach decisions. Unavailable constraints never silently fall through.

## WILL BE

Future Plays may add structured Play metadata, dedicated AUTO Customize controls, Wait / Relax actions, Usage-Sentinel capacity, CONSERVE/YOLO policies, and a truthful `Same Player, cheaper model` preference. All must reuse the constraint contract and preserve the invariant that lower-priority inference cannot override explicit human intent.
