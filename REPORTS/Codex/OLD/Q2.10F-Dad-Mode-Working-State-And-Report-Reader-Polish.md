# Executive Result

Q2.10F is ready for human field proof.

The shared Sideline UI now projects active work as a compact, accessible status with an elapsed Play Clock; hides Sideline provenance plumbing from normal report reading and copying without modifying the source report; improves report typography responsively; acknowledges successful and failed clipboard operations directly on the Copy control; and gives Refresh Incoming consistent, truthful local feedback.

This was a presentation-only pass over existing canonical runtime, Work Ledger, Incoming, report-provenance, and routing contracts. It did not introduce a second activity owner or alter routing, queueing, ownership, report transport, Player control, staged routes, or dispatch mechanics.

# Existing Canonical Timing Seam

The required authoritative timing already reached the browser through two existing projections:

- The Control Plane capability status includes `work.currentPlay.startedAt`, sourced from the Instance Work Ledger.
- Stadium Player state includes canonical `turnState.state` and `turnState.at` through the existing status and live-event flow.

The UI prefers the Ledger Play start time when both are available and falls back to the canonical turn timestamp. A local one-second display tick computes elapsed text from that backend timestamp. It cannot create, extend, or terminate Working state. Refresh and reconnect therefore reconstruct elapsed time from canonical truth instead of restarting at zero.

If Working arrives without a usable canonical timestamp, the UI truthfully shows `◉ Working` without inventing elapsed time.

# Play Clock Implementation

Working elapsed time is rendered in compact forms such as:

- `◉ Working · 0:38`
- `◉ Working · 4m 18s`
- `◉ Working · 1h 03m`

The clock is visible only while canonical state is Working. Moving to Completed, Failed, Interrupted, Unknown, or another non-Working state clears the local timestamp and removes the running clock.

Status reconstruction combines the authoritative projections conservatively:

1. use `work.currentPlay.startedAt` when the Ledger exposes an active Play;
2. otherwise use the canonical Stadium turn timestamp;
3. never synthesize a start time from the browser clock.

# Working-State UX

The former large brown/gold, disabled-looking `Working...` control is now a compact green status pill with explicit text and ARIA state. Color is supplementary rather than the only indicator.

The existing duplicate-send guard remains intact. The existing Q2.10D behavior allowing AUTO to stage independent work despite a previously busy target was not changed.

# Provenance Hiding

Normal Preview Report rendering omits the standard one-line invisible marker:

`<!-- sideline-provenance: {...} -->`

The filtering exists only in the human presentation helper. The raw report object and report file remain unchanged, so explicit provenance continues to support exact-instance ownership, Ledger attribution, context routing, provider/model/effort evidence, and diagnostics.

Dad-mode Copy Report also copies the human-readable projection rather than JSON plumbing. No stored report content is rewritten or stripped.

# Desktop / Mobile Typography

The shared report reader now uses responsive typography rather than separate desktop and mobile implementations:

- Desktop preview body: `14.5px` with `1.6` line height.
- Narrow/mobile preview body: `16.5px` with `1.65` line height, increased padding, and a mobile-appropriate viewport-height cap.
- Long prose and technical content can wrap without horizontal page overflow.
- Existing preformatted/code presentation remains available inside the same reader.

The deferred expanded/fullscreen mobile reader was intentionally not implemented. Human field testing should first determine whether this inexpensive typography correction is sufficient.

# Copy Acknowledgement

Copy Report now follows the actual clipboard promise:

- while pending: `Copying…`;
- after confirmed success: `✓ Report Copied` with a positive local treatment;
- after failure: `Copy Failed · Try Again` with truthful failure styling and help text.

Success is never shown before the clipboard operation resolves. Selecting another report, or receiving a revised version of the selected report, resets the action to `Copy Report to Clipboard`. A delayed result from an earlier report cannot leak onto the newly selected report.

# Refresh Incoming Parity Finding

Inspection found one shared `Refresh Incoming` element, one shared handler, and no responsive CSS rule that intentionally hid it on desktop. The observed desktop/mobile discrepancy was therefore not evidence of a separate recovery control or a deeper Incoming transport defect. Stale loaded UI or placement/scroll state is the most likely explanation.

The existing recovery path remains unchanged. Its presentation is now explicit at all widths and its local action states are truthful:

- `Checking Incoming…` while the existing rescan and fetch run;
- `✓ Incoming Refreshed` after success;
- `Couldn’t Refresh · Try Again` after failure.

Automatic report publication remains the normal path; Refresh Incoming remains a recovery action.

# WAS / IS / WILL BE

## WAS

- Working appeared as a large brown/gold disabled-looking `Working...` block.
- Active Play duration was not visible.
- Normal report preview exposed raw provenance JSON and opaque identifiers.
- Report body text was difficult to read, especially on mobile.
- Copy Report gave little or no direct acknowledgement.
- Refresh Incoming presentation appeared inconsistent during dogfooding.

## IS

- Working is a compact, textual, accessible status with elapsed time calculated from canonical backend start evidence.
- Refresh/reconnect reconstructs elapsed time without creating a browser-owned lifecycle.
- Normal Preview and Dad-mode Copy show human report content while raw provenance remains intact internally.
- One responsive report reader provides noticeably larger desktop text and a stronger mobile increase.
- Copy and Refresh actions acknowledge pending, success, and failure directly at the initiating control.
- Refresh Incoming remains one shared recovery action across desktop and mobile.

Automation proves these contracts. Human desktop/mobile field proof remains required.

## WILL BE

- If field testing shows typography alone is insufficient, a later bounded Play may add an expanded/fullscreen-ish mobile report reader with its own scrolling document and Copy action.
- A future Advanced/Diagnostics experience may expose raw report metadata intentionally.
- Broader action-feedback consistency can continue incrementally without introducing a global notification framework.
