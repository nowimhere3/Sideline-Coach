# Work Ledger Extensions

`LedgerPlay` now carries optional `executionStartedAt`. `LedgerRecentPlay` carries preserved `executionStartedAt`, `turnRef`, and optional `acknowledgedAt`. `LedgerReportLink` carries optional `acknowledgedAt`. Each `InstanceLedgerEntry` carries its most recent global mutation `revision`.

The Ledger exposes narrowly scoped APIs for:

- testing whether an exact instance still has a pending dispatch;
- recording a durable queue mutation without making PlayQueue a second execution authority;
- acknowledging a linked report or terminal failed/Unknown Play by Game, instance, Play reference, and report path as applicable.

Existing bounded history and report serialization remains the persistence owner. No completion or acknowledgement database was added.

# executionStartedAt Semantics

`startedAt` was not redefined. It remains the timestamp at which Coach dispatched/attributed the Play.

`executionStartedAt` is set:

- only on the first matching semantic `started` event;
- using the Control Plane's `now()`;
- never by `accepted`;
- never from browser time;
- never moved by repeated `started`, delivery acknowledgement, status refresh, or reconciliation;
- preserved into terminal history for duration calculation.

If a capability proves a Player is busy after a Control Plane replacement but the start cannot yet be recovered, the projection truthfully reports Working without a clock origin. Slice A does not fabricate a timestamp.

# Revision / Epoch Semantics

Each Ledger lifetime generates one random `epoch`. A global monotonic counter assigns the revision stored on each exact instance entry whenever canonical projected truth changes. Revisions therefore never decrease inside an epoch, while a new Control Plane lifetime receives a new epoch and a fresh revision space.

The mutation path advances revisions for dispatch, delivery, semantic turn transitions, disconnect/reconciliation, report linking, acknowledgement, and queue state changes. Repeated evidence that changes no canonical truth does not manufacture a new revision.

Revisions are intentionally not compared across epochs and are not browser-owned.

# Terminal Monotonicity

The first terminal outcome recorded for an exact `turnRef` is final. Late `accepted`, `started`, or another terminal event for that same provider turn is ignored. This includes the fast-path case where terminal evidence arrives before accepted evidence: the terminal record now retains the incoming `turnRef`, allowing stale later evidence to be rejected deterministically.

No arbitrary time window is involved. Identity, not timing, establishes finality.

# ExecutionView Projection

The new pure module projects:

- `idle`
- `starting`
- `working`
- `queued`
- `waiting-capacity` (reserved, no V0 producer)
- `needs-you`
- `finished`
- `couldnt-finish`
- `unknown`

The implemented precedence is:

`needs-you > working > starting > waiting-capacity > queued > unknown > couldnt-finish > finished > idle`

Working includes `executionStartedAt` only when genuine evidence exists. Starting covers pending delivery and accepted-before-started. Unknown remains uncertainty rather than failure and retains exact current Play identity when delivery truth is uncertain. Terminal durations use `executionStartedAt`, never dispatch `startedAt`.

The module has no browser logic, timers, persistence, routing decisions, or provider-specific behavior.

# Queue Projection

Existing durable PlayQueue remains unchanged and authoritative for waiting work. The daemon translates its current exact-instance items into projection metadata with:

- queue count;
- head reason kind (`own-current-play`, `waiting-for-player`, or `unspecified`);
- friendly waiting-on name where available.

Working or Starting remains the primary state when queued work coexists; queue count rides alongside it. A queued Play never receives an execution clock.

Every queue add, cancel, retry, dispatching transition, requeue, completion, or needs-attention transition advances the affected exact instance's canonical projection revision and schedules publication.

# Report / Acknowledgement Semantics

Finished projection uses only existing legitimate Ledger report links. Explicit Q2.10E provenance and existing conservative single-active-Play attribution remain the supported evidence. Reports are matched to the terminal Play by `clientRef`; unattributed reports do not appear under arbitrary Players.

A completed Play projects:

- Finished + awaiting report during the existing report grace window;
- Finished + linked unacknowledged report when one arrives;
- Idle after that report is acknowledged.

Failed, interrupted, not-sent, and terminal Unknown Plays can be acknowledged exactly and idempotently. A delivery-timeout Unknown that is still represented as the current uncertain Play can also be acknowledged; it is closed into acknowledged Unknown history rather than written to another store. A later genuinely new identified turn can still provide new canonical evidence.

Acknowledgement timestamps survive existing Ledger serialization and restore.

# status.execution Contract

`GET /api/status` now additively includes:

```text
execution: {
  gameId,
  epoch,
  serverNow,
  byInstance
}
```

`byInstance` contains one `ExecutionView` for every exact instance in the selected Game's canonical roster, including benched instances. On-field-only `capabilities[].work` remains unchanged for routing compatibility. `serverNow` and the status timestamp are taken from the same Control Plane clock observation.

The projection remains strictly Game isolated and uses opaque instance IDs as keys. Friendly numbering is presentation only.

# execution SSE Contract

SSE connections now receive an initial:

```text
event: execution
data: { gameId, epoch, serverNow, views }
```

Canonical Ledger and queue mutations schedule an execution publication after the mutation. Bursts in one event-loop turn are coalesced, so consumers receive the newest projection caused by that burst. The server does not emit elapsed-time ticks; future browsers calculate display elapsed time from the canonical start plus `serverNow` skew correction.

Raw `turn` SSE remains present for compatibility and diagnostics.

# DispatchResult Identity

Successful AUTO and MANUAL results now include the exact `playerInstanceId` and `playerName`. Queued results include the same fields. Timeout, rejected, disconnected, and immediate send-error outcomes also preserve a known exact target.

No routing choice changed. The response simply stops future browser work from guessing the target from selected UI state.

# Acknowledgement API

`POST /api/work/acknowledge` accepts a Game plus an exact report or terminal work identity:

```text
{
  gameId,
  reportPath?,
  instanceId?,
  playRef?
}
```

The operation is authenticated through the existing Control Plane API path, strictly Game scoped, deterministic, and idempotent. It returns 404 when the requested canonical record does not exist in that Game. A successful first acknowledgement advances the canonical revision and schedules persistence/publication; repeating it reports `changed: false`.
