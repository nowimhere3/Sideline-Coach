# Result

PASS with one external proof boundary.

The common OpenRouter failures were execution-layer failures, not evidence that roughly ten unrelated models were incompetent. The actual failed processes had no OpenRouter credential available inside their intentionally isolated OpenCode data homes. OpenCode consequently omitted the `openrouter` provider, internally raised `ProviderModelNotFoundError`, and exposed only an opaque `UnknownError` reference on its normal CLI stream. Sideline then reduced that multiline error to `Error: {`.

The OpenRouter model route shape was valid. With a deliberately invalid, non-secret placeholder present only for local model-catalog inspection, OpenCode listed the exact previously failed routes, including `openrouter/nex-agi/nex-n2.5-mini:free`. No provider generation was attempted with that placeholder.

Big Pickle was a different failure. Its successful Combine tryout and later Formation used the same OpenCode 1.18.31 binary, `opencode/big-pickle` route, generated read-only agent definition, CLI execution adapter, and isolated execution layout. The provider accepted that contract on September 17 and rejected the same field contract on September 18 with:

`OpenCode's free tier can only be used from within OpenCode`

That is a hosted-provider/headless eligibility change or restriction, not a Combine-versus-Formation adapter fork and not negative Big Pickle game film. OpenCode's live catalog still advertises Big Pickle, so catalog presence alone is not proof of headless fieldability.

The repaired system now:

- fails closed before spawning OpenCode when an OpenRouter prospect has no environment credential;
- captures OpenCode ERROR logs and preserves structured provider/harness evidence instead of `Error: {`;
- classifies missing credentials, quotas, unavailable models, and hosted-tier restrictions separately;
- keeps Combine and Formation on the same `createCombineExecutor()` field contract;
- lets a definitive real Formation infrastructure block suspend stale READY truth through Combine's canonical scorecard writer;
- leaves prior Player-quality counters untouched when infrastructure blocks execution;
- makes a catalog-disappeared prospect due when it returns, while a recent field-blocked prospect respects the existing retry window;
- redacts the OpenRouter credential from Combine and Formation logs, provider errors, and failure boundaries.

# Root cause and raw failure evidence

## OpenRouter candidates

The examined failures in both requested runs had the same persisted stderr structure:

```text
Error: {
  "name": "UnknownError",
  "data": {
    "message": "Unexpected server error. Check server logs for details.",
    "ref": "err_..."
  }
}
```

Examples included references `err_a591fa36`, `err_1907d48d`, `err_098210f1`, and `err_194dd022` across DeepSeek, inclusionAI, Nex AGI, and NVIDIA candidates.

Re-running one prior invocation with OpenCode ERROR/DEBUG log visibility recovered the hidden cause:

```text
ProviderModelNotFoundError: Model not found: openrouter/nex-agi/nex-n2.5-mini:free.
Did you mean: nex-agi/nex-n2.5-mini:free?
```

This message was initially ambiguous between route shape and provider registration. The credential and catalog checks resolved that ambiguity:

- process environment `OPENROUTER_API_KEY`: absent;
- user environment `OPENROUTER_API_KEY`: absent;
- machine environment `OPENROUTER_API_KEY`: absent;
- isolated attempt `opencode auth list`: zero credentials;
- adding a placeholder credential made OpenCode register `openrouter` and list the exact route.

Therefore the owning failure layer was credential/environment propagation into OpenCode's provider registry. The model IDs were not malformed.

The key was not printed, read, copied, or persisted. Only boolean presence was inspected. The result was `false` in all three Windows environment scopes available to this work.

## Big Pickle

The September 17 successful Combine attempt completed in 28.446 seconds and produced a structurally usable Scout report. Its generated read-only agent file has the same SHA-256 hash as the September 18 Formation agent file, and both logs identify OpenCode 1.18.31 with provider `opencode` and model `big-pickle`.

The September 18 Formation reached the provider but was rejected in approximately five seconds with the hosted-tier restriction above. This failure belongs to OpenCode Zen/provider eligibility for headless execution. It is not an auth failure, a model reasoning failure, or a different Formation adapter.

# Combine versus Formation execution

## A. How Combine executes a prospect

Combine discovers a provider/model prospect, creates one `ScoutPlayExecutor` through `createCombineExecutor()`, writes the shared `sideline-combine-scout` read-only agent into an attempt-local config directory, sets attempt-local `OPENCODE_CONFIG_DIR` and `XDG_DATA_HOME`, inherits process credentials, and invokes OpenCode against the Game root.

The repaired safe command shape is:

```text
opencode --print-logs --log-level ERROR run
  --agent sideline-combine-scout
  --model <provider/model>
  --format default
  --dir <Game root>
  <canonical semantic Scout prompt>
```

Before this repair the command was the same except for the two diagnostic-log flags.

## B. How Formation executes the same prospect

`combineDerivedFormationCandidates()` rebuilds the prospect from the current canonical scorecard and calls the same `createCombineExecutor()` with the label `Formation dispatch`. Formation does not have a second OpenCode runner.

## C. Are the contracts equivalent?

Yes at the code and process-contract level: same executor, agent, model route, read-only permissions, environment construction, timeout, stdout/stderr capture, and report evaluation. Attempt directories differ by design so concurrent receivers remain isolated.

The historical Big Pickle mismatch was temporal provider truth: an older tryout passed, then the external hosted provider stopped accepting the same headless contract.

## D. Could Combine mark READY when Formation could not field the receiver?

Yes before this repair. A truthful older READY scorecard remained eligible after a later real Formation observed a definitive infrastructure block. The live catalog could also continue advertising the route.

Now a real Formation `BLOCKED` infrastructure observation is submitted to `recordFormationInfrastructureBlock()` in the Combine module. Combine remains the canonical scorecard writer. READY is suspended to the derived infrastructure status, but starts/completions/failures and prior tryout evidence are not rewritten.

## E. How OpenRouter enters through OpenCode

OpenCode is the execution harness. The model route is `openrouter/<OpenRouter model id>`. The attempt-local OpenCode data home intentionally contains no user's stored OpenCode credentials, so `OPENROUTER_API_KEY` in the inherited process environment is the credential seam. Sideline does not write the key into config or evidence.

## F. Why Big Pickle passed then failed

It passed because OpenCode Zen accepted the same headless CLI contract on September 17. It failed because the provider rejected that contract on September 18. The unchanged CLI version, model, agent hash, and adapter rule out a Combine/Formation invocation fork. The current OpenCode catalog continuing to list Big Pickle proves catalog advertising and fieldability are separate observations.

# OpenCode architecture decision

## A — Repair OpenCode and keep it

- Reliability: improved materially by credential preflight and full error evidence; OpenCode Zen's hosted free-tier headless eligibility remains externally unstable.
- Complexity: low; repairs stay in the existing adapter.
- Portability: strong across OpenCode-supported providers/models.
- Read-only enforcement: already proven through the generated primary-agent contract.
- Observability: now adequate for provider/harness errors.
- Concurrency: already supported by isolated attempt homes and bounded Formation workers.
- Credentials: environment-only for OpenRouter; never persisted by Sideline.
- Maintenance: dependent on OpenCode CLI/provider behavior.

## B — Keep OpenCode and normalize Combine + Formation on one contract

This is the recommended present architecture, and the source already has one executor. This Play repaired the missing readiness feedback and error/credential seams rather than creating a replacement engine. Reliability is acceptable for continued bounded proof, with the important caveat that OpenCode-hosted catalog presence is not fieldability proof.

Complexity and maintenance remain lowest; provider portability, read-only enforcement, and concurrent execution stay intact. Credential handling remains explicit. Real Formation blocks now correct canonical eligibility without becoming Player-quality film.

## C — Replace OpenCode with another lightweight harness

- Reliability: UNKNOWN until a replacement proves repository tools, process isolation, and concurrent headless execution.
- Complexity: medium/high migration and parity work.
- Portability: depends on the replacement's provider adapters.
- Read-only enforcement: must be reproven.
- Observability: could improve but is not guaranteed.
- Credentials and maintenance: a new external dependency surface.

Current evidence does not earn this replacement.

## D — Minimal Sideline-owned direct provider/OpenRouter harness

- Reliability and error observability: potentially strongest for direct API boundaries.
- Complexity: highest; Sideline would own streaming, tool calls, bounded repository reading, read-only enforcement, model differences, concurrency, cancellation, and credential plumbing.
- Portability: requires one maintained adapter per provider protocol.
- Credentials: can be explicit and controlled but creates greater product security responsibility.
- Maintenance: substantial ongoing provider/API work.

This becomes justified only if an actually authenticated OpenRouter environment still fails through repaired OpenCode or OpenCode changes repeatedly break field execution.

# Recommendation

KEEP + REPAIR OpenCode under Option B for now.

Do not treat OpenCode Zen's hosted free catalog as guaranteed headless capacity. Continue using one OpenCode executor for Combine and Formation, require explicit environment credentials for OpenRouter, and let canonical scorecard readiness consume definitive real-field infrastructure blocks without negative Player film.

Do not replace OpenCode yet. The dominant OpenRouter failure was a missing credential, not a demonstrated OpenCode inability to run authenticated OpenRouter models. Replacement is not evidence-earned until the repaired authenticated route receives one real bounded proof.
