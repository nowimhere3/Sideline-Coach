## IMPLEMENTATION

### Synchronous read attachment

`runTerminalCommand` (observed path):

```ts
const execution = shell.executeCommand(check.command.trim());
// Same tick as executeCommand(): read() only yields data written after it is first called.
const watching = this.watchCommandOutput(execution, instanceId);
this.runningCommands.set(execution, { instanceId, turnRef });
...
```

`watchCommandOutput` feature-detects (`typeof execution.read === 'function'`), calls `execution.read()` and obtains its async iterator **in the same synchronous path**, then starts `void pumpTerminalOutput(...)`. Because an `async` function runs synchronously up to its first `await`, even the first `iterator.next()` is issued in that same tick. Nothing is scheduled, deferred, or awaited before `read()`.

### No general recording

There is no terminal-wide listener anywhere (`onDidWriteTerminalData`, `onDidStartTerminalShellExecution` are absent). The single `read()` call site is on the execution that `executeCommand()` returned for a command Coach dispatched. `runningCommands` remains the completion authority and was not restructured.

### Line assembler (`TerminalLineAssembler`)

- `push(chunk)` joins the held tail with the chunk, splits on `\n`, holds the incomplete tail, returns whole lines.
- `flush()` returns the unterminated tail at stream end.
- CRLF keeps its trailing `\r` for projection to drop; a `\r` and `\n` split across chunks assemble correctly.
- **Bounded:** a tail longer than 8,000 chars first collapses `\r` repaints to the last visible one (so a repaint-only progress bar cannot grow without limit), then is force-split if still oversized.

### Projection (`projectTerminalLine`)

Splits a line on `\r` and takes the last segment that still has visible text **after** the shared `sanitizeActivityText(…, 'output')` (ANSI/OSC/control strip, secret redaction, 240-char cap, indentation preserved, trailing trimmed). Blank results are dropped. This means a trailing escape-only repaint (`real text\r\u001b[0m`) does not erase the visible line. Redaction/ANSI logic is *called*, not re-implemented.

### Terminal session key

`terminalSessionRef({shellPid, shellStartedAt}) = "${shellPid}:${shellStartedAt}"`, then the existing `sessionKeyFor` digest (SHA-256, first 8 hex). The roster looks the facts up in the **existing** `this.provenance` (already written by `recordProvenance`) **per notice** — no new persistence schema, no new process probing, no `providerSessionRef` fiction. Only the digest enters the activity transport; tests assert neither the pid nor the start time appears anywhere in the emitted notices.

Consequence worth knowing: `recordProvenance` is asynchronous (it awaits a PID lookup and a `Get-Process` probe). A command dispatched in the first moments after adding a Terminal may publish its first few lines with **no** `sessionKey`; later notices pick it up once provenance lands. The browser and daemon already accept a key appearing on an existing bucket without rotating, so this is safe, and it is stable from then on. A restarted shell yields a new key, which the daemon's existing session-rotation rule turns into a fresh transcript.

### Throttle and ceiling (`TerminalOutputBudget`)

Simple counter, injectable clock, no timers: **500 lines per one-second window** and **2,000 lines per command** (exported constants). Overflow is counted, never silently forgotten. When the stream ends, **one** `channel` notice states the truth: `Output trimmed — N lines not shown` (singular handled). The daemon's 300-line store is unchanged.

### Failure isolation

`pumpTerminalOutput` never rejects. Reading, projecting, and publishing are each guarded; a throwing sink does not stop reading; `iterator.return()` is called in `finally`; if the stream dies mid-way, what was read (including the partial tail) is kept and one notice says `Live output stopped early`. `publishTerminalActivity` wraps sanitize + fire in try/catch, mirroring `publishActivity`. Nothing in the pump can reach the command, its exit code, ownership, or the Play.

### Degradation (Dad-facing wording, no plumbing vocabulary)

| Situation | Behaviour | Notice (`channel`) |
|---|---|---|
| No shell integration | unchanged `sendText`, `observed: false`, no turn events | `Command sent · live output unavailable` |
| Multi-line command | unchanged `sendText` path | `Command sent · live output unavailable` |
| `read` missing or throws in the same tick | command still runs and is still observed for completion | `Command running · live output unavailable` |
| Stream fails mid-run | lines so far kept | `Live output stopped early` |
| Exit code not reported | unchanged: `describeTerminalExit` → `unknown` | (existing lifecycle) |

A test asserts none of these strings contains PTY / stdout / stderr / shell integration / transport / AsyncIterable / PlayerActivityNotice.

## SECURITY / OWNERSHIP

**Only Coach-dispatched executions are captured.**
- Structural: exactly one `read()` call site exists in `player-roster.ts` (asserted by a source-scan test that ignores comments), and no terminal-wide data/start listener exists (also asserted).
- Behavioural: a "human" execution delivered through the shared end-event emitter is never read (`readCalls === 0`) and produces zero activity.

**Layers.** Host: line projection (ANSI/control strip → redaction → cap) → `publishTerminalActivity` re-sanitizes once more before firing → daemon `PlayerActivityStore.record` re-sanitizes again → both gates (Dev Mode AND View Player Terminal) → browser. T1's store accepts and retains the notices unchanged (proved in `T2-5`).

**Ownership unchanged.** Coach-managed terminals are still disposable by Coach; adopted terminals still detach and stay open. `T2-11` runs the tap against an adopted terminal and confirms `Remove` leaves it open (`disposed === false`).

**Honest limits (not claimed solved):**
1. Anything the terminal *displays while a Coach-dispatched command runs* is in that command's stream — including text the human might type into a running interactive program and have echoed. The scope guarantee is "only during a Coach-dispatched command", not "nothing the human types is ever visible".
2. Redaction is best-effort pattern matching, exactly as documented in `player-activity.ts`; `cat .env` with unconventionally-named values is not protected by it.
3. The host reads, projects, and publishes output even when the two daemon gates are off (the daemon then discards it). This is local-only and matches how controlled Players already behave, but it is not free.

## ARCHITECTURE FEEDBACK

**No architecture contradiction found.** The decision held: the tap needed no change to any protected file, and the substrate/contract/session model behaved as S48.0 predicted.

Three observations for the architect — none redesigns anything, none is acted on here:

1. **S48.0 factual correction (event table).** S48.0 listed the `working` ("Running: …") and `result` ("Completed · exit code 0") bookends as "(exists)" on the activity rail. Source shows they do **not**: `emitTurn` fires only `turnChanged` (→ ledger → strip); `publishActivity` is fed only by `handleControlEvent`. So the Live Player Terminal for a Terminal Player will show `OUTPUT` lines (and the notices above) but **no `WORKING`/`RESULT` bookend lines**; completion is visible in the strip, as before. T2 followed the Play ("completion continues through the existing lifecycle; do not duplicate it in the pump") and did not add bookends. If the architect wants them, it is a small, separate follow-up — ordering against the output drain would need care because `onDidEndTerminalShellExecution` may fire before the last chunks are read.
2. **Flood policy keeps the head, not the tail.** With 500/s and 2,000/command, a large burst loses its *last* lines — often the most useful (a failing test's summary). The daemon keeps only the last 300 of whatever is forwarded anyway. A tail-preserving policy is a real product choice worth making after field data, not a bug.
3. **Terminal closed mid-command is still unhandled.** `retireTerminal` does not clear `runningCommands` or emit a terminal `unknown` turn for an in-flight command (S48.0's lifecycle table implies it should). This is pre-existing behaviour, outside the T2 Play, and unchanged. The pump itself does stop when the Player is retired or the roster disposed.
