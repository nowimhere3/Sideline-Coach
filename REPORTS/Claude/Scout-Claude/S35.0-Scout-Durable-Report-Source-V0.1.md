==================================================
PROVENANCE CONTRACT
==================================================

The existing `sideline-provenance` marker (`formatReportProvenance`) is written as the **first
line** of `FORMATION-RESULT.md`, inside the parser's 4,096-byte head window. No second format.

```text
<!-- sideline-provenance: {"gameId":"…","clientRef":"…","playerInstanceId":"scout",
     "playerType":"scout","provider":"scout-formation","at":"<Formation endedAt, ISO>"} -->
```

* **Only true facts are stamped.** No `model`, no `effort`: one parent spans N receivers, so
  claiming either would be fabrication. The test asserts both are absent.
* **Attribution is optional and never invented.** `FormationRequest.reportAttribution` is
  supplied only by the Stadium's Scout dispatch, which genuinely knows the Game and Play. A
  CLI/standalone Formation, or a half-known attribution (empty `gameId` or `clientRef`), writes
  **no marker** at all.
* `clientRef` is the router's Play ref, or the turn ref for the Dev Mode operator path. The same
  value is used for the marker and the fast-path registration, computed once before execution.
* The workspace copy of `FORMATION-RESULT.md` is byte-identical to the durable parent.

==================================================
VALIDATOR WIDENING, AND WHY IT REMAINS SAFE
==================================================

**Before:** `INSTANCE_ID = /^[a-z]+-[0-9a-f]{8}$/`. A declared `playerInstanceId: "scout"` was not
rejected loudly; the parser silently dropped it to `undefined`, and the Ledger then skipped the
report (`typeof declared.playerInstanceId !== 'string'`). Scout could never name its own reports.

**After:** `isTrustedPlayerInstanceId(v)` = minted seat regex **OR** exact membership in
`LOGICAL_PLAYER_INSTANCE_IDS`, a `Set` containing only `SCOUT_PLAYER_INSTANCE_ID`, imported from
the Player's own contract.

Why this is the narrowest workable change:

* It is an **exact string match**, not a pattern, prefix or case-fold. The regex was not loosened.
* The allowlist is derived from the existing contract constant, so it cannot drift from the id
  routing already uses.
* `report-provenance.ts` stays free of `vscode` imports, and the new import (`scout-player-
  contract.ts`) is a leaf module, so no import cycle was introduced.
* A future Virtual Player earns admission by adding its own constant plus a test. The breadcrumb
  says so at the seam.

The tests prove both directions. Accepted: `scout` and the four minted seat types. Rejected
(dropped to Unknown, other marker facts preserved): `Scout`, `SCOUT`, ` scout`, `scout `,
`scout\n`, `scouts`, `scout-`, `scout-1`, `scout-zzzzzzzz`, `../scout`, `scout/../x`, `__proto__`,
`constructor`, `toString`, `hasOwnProperty`, uppercase-hex and 7-hex seats, empty, `null`,
numbers and objects.

Two other regexes (`player-control/bindings.ts:26`, `player-instances.ts:37`) look similar but
guard terminal/controlled **process seat** persistence, not report provenance. They were
deliberately left untouched, as S31 said.

**One residual exposure is recorded honestly under UNKNOWNs.**

==================================================
SOURCE DISCOVERY BEHAVIOR
==================================================

`ScoutIntelligenceReportSource({ scoutIntelligenceRoot })`, pure `fs`, no `vscode`.

`ReportSource` contract as built (small deviations from the sketch are noted):

```ts
interface ReportSource {
  readonly id: string;                 // 'scout-intelligence'
  readonly agentLabel: string;         // 'Scout'
  roots(): readonly string[];          // [<root>/Formations]
  readonly parentGlob: string;         // '**/FORMATION-RESULT.md'   (added: the watch contract)
  list(gameId, context?: { project?, limit? }): Promise<CoachReportItem[]>;   // context added
}
```

`parentGlob` exists so the extension does not hardcode a Scout filename. `context.project` exists
because `CoachReportItem.project` is Incoming's Game label and the source cannot know it.

`list(gameId)`:

1. Reads only `<root>/Formations`, only **directories** whose names satisfy Formation's own id
   pattern, and only a regular `FORMATION-RESULT.md` in each. `Dirent.isDirectory()` is false for
   a link and `lstat` rejects a linked file, so nothing can redirect the scan outside the root.
   Verified with a real directory junction.
2. Never enumerates `*-SCOUT-REPORT.md` or anything else under the tree.
3. Parses the file's own marker through the existing `parseReportProvenance`.
4. Keeps a parent only if `isTrustedScoutParentFor` holds: **this** `gameId`, `playerInstanceId
   === 'scout'`, `playerType === 'scout'`, `provider === 'scout-formation'`, and a non-empty
   `clientRef`. Anything less is skipped, never guessed. No timing inference, no folder-name
   inference.
5. Projects the existing `CoachReportItem` (unchanged type).
6. Orders newest-first by mtime with a path tie-break, so the order never depends on directory
   enumeration. Bounded at 10 per Game (the same bound the in-memory path used), at most 200
   files inspected, and files over 2 MiB skipped rather than truncated.
7. A missing or unreadable root returns `[]`.

`ReportSource` is one interface with one implementation. There is no registry, priority system,
database or child registry.

==================================================
IMMEDIATE PATH VERSUS DURABLE PATH
==================================================

| | Fast path (S30) | Durable path (S35) |
|---|---|---|
| Mechanism | `registerScoutFormationReport` into `scoutFormationReports` Map | `ScoutIntelligenceReportSource.list` from disk |
| Survives restart | No (memory, capped at 10) | Yes |
| Role now | **Latency optimization only** | **Owner of durability** |

Both feed the one merge point that already existed, `sendReportSnapshot`, via
`mergeSidelineOwnedParents(durable, registered)`:

* The same exact path is **one report**. The key is `path.resolve` plus lowercasing on Windows.
* **Disk wins** for a shared path. A registration only contributes a path the disk listing did
  not return, so the two can never become competing truths.
* The merged Scout parents still sit **ahead** of ordinary Game-scanned reports, and any ordinary
  entry with a colliding path is dropped, as in S30.
* A throwing source is caught: ordinary Game reports still publish (tested).

Because the post-Formation `publishReportsChanged()` now also reads disk, a parent appears
immediately even without a watcher tick. The Map remains to guarantee registration in exactly
the cases S30 proved, such as a source that is absent.

`CoachReportItem`, Incoming, the browser, the Ledger and Assistant Coach code were not changed.

==================================================

* Game ownership is **not inferred** from folder location, timestamps, or the `gameRoot` field
  that `FORMATION-COMPLETE.json` happens to contain. Mapping a filesystem root to a `gameId` is a
  guess, and the Play forbade guessing.

  holds **9** legacy parents, and the source discovered **0** for each of the four Games
  connected in the last diagnostics snapshot.
* Consequence: after a restart, Scout parents produced **before** this build do not reappear in
  Incoming. Every parent produced **after** it does.

If historical parents are ever wanted back, that needs a deliberate, human-approved attribution
Play. It must not be a silent heuristic.

REMAINING UNKNOWNs
==================================================

1. **`scout` is a well-known constant, so it is easier to spoof than a minted seat.** Any file a
   Game's own report scan picks up could declare `playerInstanceId: "scout"` for that Game, and
   the Ledger would link it to the Scout entry. Blast radius is limited: same Game only, and it
   attaches a report link to the Scout card without granting authority. The Ledger was
   deliberately not redesigned here. If it matters, the fix belongs in the Ledger or
   Stadium-scan attribution, not in loosening this validator.
2. **The watcher is not proven live.** Whether VS Code's file watcher fires for a
   recursive `RelativePattern` on an out-of-workspace folder inside a real Extension Development
   Host is untested; only the wiring and glob are asserted. This does not threaten durability,
   because every snapshot (connect, reload, rescan, post-Formation publish) lists from disk. It
   would affect only convergence when another process writes a parent for the same Game.
3. **Acknowledgement persistence lives in the Control Plane Ledger, as before.** It is tested
   against the in-memory `InstanceWorkLedger` only. Its cross-process persistence
   (`work-ledger.json`) and its bounds (10 report links, 10 recent plays per instance) were not
   exercised here, and no second store was added. If that file is lost, an acknowledged parent
   could again read as unacknowledged in Incoming.
4. **First restart after upgrade lists up to 10 historic self-describing parents** for a Game in
   Incoming, where before a restart left none. This is intended ("Scout intelligence should simply
   arrive"), but Dad may see older Formations return. There is no retention or pruning policy.
5. **Legacy parents remain unattributed** (see boundary above), as designed.
6. **Continuation readability across roots** (S31 §L.1) is still open and untouched: whether a
   Controlled Player can read an absolute Scout path outside its Game root.
7. **The VSIX was not re-audited** after this change.
