THE CONSENT STATE CONTRACT (EXACT)
==================================================

| Element | Contract |
|---|---|
| States | `not-decided`, `authorized`, `declined`. Absence of a stored value means `not-decided`. |
| Owner | `ScoutBootstrapConsentStore` in `src/scout-bootstrap.ts`, over the extension's own `context.globalState`. |
| Stored value | `{ state: 'authorized' \| 'declined', decidedAt: <ISO> }` under key `sidelineCoach.scout.bootstrapConsent`. Nothing else, and nothing secret. |
| Not stored in | a Game, a scorecard, the Scout Intelligence tree, browser storage, or SecretStorage. It is a preference, not secret material. |
| Malformed values | A wrong state string, a missing timestamp, a string, a number or `null` all read as `not-decided`, never as consent (tested). |
| Written by | only `authorizeAndStart` (Start tryouts) and `decline` (Not now). |
| Server-enforced | `refresh` throws `authorization-required` unless consent is `authorized`, whatever the browser sends. |

Behavior by state:

| State | Settings shows | Runs anything? |
|---|---|---|
| `not-decided` | **Find Scouts** button, which only opens the confirmation | No |
| `authorized` | **Refresh Scouts** button, no second ceremony | Only on a click |
| `declined` | "Scout tryouts are off" with a manual **Find Scouts** button | No, and it does not nag |

`declined` is remembered so Dad is not asked again on every render or startup. The manual action stays
available, and choosing it again simply re-opens the confirmation. Human choice wins.

**Where it persists.** `globalState` survives a restart and is shared by every window of the same VS Code
profile. Restart is tested by rebuilding a fresh store and service from the *serialized* bytes only.

THE EXACT TRIGGER PATH
==================================================

```text
Settings card (browser)
  click "Find Scouts"  -> only reveals the confirmation; calls nothing
  click "Start tryouts"-> POST /api/scout/bootstrap  { gameId, action: 'authorize' }
        |
Control Plane daemon    -> proxyExactGameRpc(feature 'scout.bootstrap.v1', 'scout.bootstrap.authorize', { gameId })
        |
Stadium (extension host)-> withExactGame -> ScoutBootstrapService.authorizeAndStart(<this Game's root>)
        |                     1. entitlement (coach.scout.enabled), 2. credential configured, 3. no session running
        |                     4. record consent,  5. claim the machine-wide guard,  6. return immediately
        v
   runCoachRefresh({ gameRoot, durableReportRoot: <Scout Intelligence root>,
                     resolveOpenRouterApiKey: <SecretStorage resolver> })     <- the EXISTING Coach Refresh, unchanged
        |
   Combine 'refresh-due' -> canonical scorecards + <Scout Intelligence>/Work (S36) + hygiene (S37)
        |
   onFinished -> stadiumClient.sendCapabilitySnapshot()   -> Scout appears without a reload
```

* Other actions: `decline`, `refresh` (requires consent), and `status` (a read).
* **Nothing else starts a session.** A source scan (Bootstrap-16) confirms the only callers of the starting
  methods are the Stadium's RPC handlers, and that neither the service nor the extension wiring contains
  `setInterval`, `setTimeout`, `cron`, `schedule`, `onStartup`, or an activation-time call.
* The Settings script polls **status only** (a GET, every 4 s, only while Settings is open and a session is
  running). A source test asserts the poll and the loader never POST.
* No Scout runner was added and Combine was not forked. The service imports `runCoachRefresh` and nothing else
  that runs tryouts (asserted).

CREDENTIAL BOUNDARY (S24 PRESERVED)
==================================================

The credential never enters this flow's data. It travels only:

```text
SecretStorage -> ScoutOpenRouterCredentialStore.resolveForExecution()
   -> the resolver handed to runCoachRefresh -> Combine's ephemeral execution environment -> OpenCode -> OpenRouter
```

* **Browser -> Control Plane:** the POST body is `{ gameId, action }`. A test posts a body that also carries
  `apiKey` and `gameRoot`; the RPC still carries **only** `{ gameId }`, and the browser's key never appears in any
  frame.
* **Control Plane -> browser:** the response is rebuilt field by field from an **allowlist** with type and bounds
  checks. A hostile Stadium answer carrying `apiKey`, `rootFsPath`, `workspacePath`, `providerError`, and
  `rawStderr` is stripped; none of those strings reach the browser or any Control Plane file.
* **Status, consent, scorecards, run evidence, Work, logs:** none contains the key (Bootstrap-12 searches every
  file under the Scout root and the Game).
* **Error path:** when a run throws with the key in its message, the log line is redacted to `[REDACTED]`, the
  status carries only a generic "stopped before finishing" note, and raw error text is not exposed.
* **The page** never touches `apiKey`, and never uses `localStorage`, `sessionStorage`, or `indexedDB` in this
  block (asserted).
* **Shipped files:** no key-shaped string (`sk-or-…`) appears in `out/`, `index.html`, or `ws`.

RATE LIMIT AND INFRASTRUCTURE BEHAVIOR
==================================================

Bootstrap-6, for both `RATE LIMITED` and `AUTH ISSUE`:

* Scorecards classify as `RATE LIMITED` / `AUTH ISSUE`. `totals.failures` and `totals.completions` stay `0`; the

* No raw provider text (`rate-limited`, `unauthorized`, `OPENROUTER_API_KEY`, `upstream`) appears anywhere in
  the status Settings receives.

**This test caught a real bug in my own first draft.** I had counted `CALL BACK LATER` as an infrastructure
status. But Combine derives it from a plain `FAILED` attempt and counts that in `totals.failures`, so a model
that merely produced nothing would have been shown to Dad as "Provider limited". The infrastructure set is now
exactly the statuses Combine derives from `BLOCKED` attempts (`RATE LIMITED`, `AUTH ISSUE`,
`PROVIDER UNSTABLE`) plus `UNAVAILABLE` (a model gone from the catalog). `LIMITED`, `UNKNOWN`, and
`CALL BACK LATER` are not infrastructure, and the source records why.

==================================================
ORPHAN SWEEP DECISION: NOT IMPLEMENTED
==================================================

The Play allowed a sweep only if safety was obvious and deterministic. It is not, so I left it out.

* **The main orphan is unprovable.** A crash leaves a `Work/<id>` folder with **no** completion artifact. From
  disk alone that is indistinguishable from an active run or an unknown one, and the Play forbids deleting
  active or UNKNOWN work or anything decided by an age guess.
* **The provable case is nearly empty.** A run with a completion artifact has already been cleaned by S37's
  per-receiver hygiene. The only residue would be a cleanup that failed (for example a locked file), and that
  failure is already recorded in the run's `workspaceHygiene`. A retry-sweep would address only that rare case.
* The crash residue is bounded to one run and is preserved. Aging out old `Work/` folders remains a future
  extension of the S37 rule, not a second mechanism.

FINDINGS BEYOND THE BRIEF
==================================================

### 1. A tryout sends content from the user's real Game to an outside provider

Combine's tryout objectives tell a hosted model to find **the Game's own top-level manifest** and, for another
route, its **README**, and to cite what it finds. The read-only agent can read any file in the Game except
`*.env` and `*.env.*`, and the models are typically free OpenRouter tiers. So a tryout is not "contact a
service to check it works". It is "let a third-party model read files from your project". The Play's required
disclosures did not cover this, so **I added it to the confirmation**: "read a few project files from your open
Game … so that content is sent to that provider."

I did not change Combine. Whether tryouts should instead run against a small Sideline-owned fixture repository,
so no user code leaves the machine, is a real product decision for Coach. I recommend deciding it before this
ships to anyone outside this machine. It is also the strongest argument that the confirmation should stay honest.

### 2. Two windows could have started two sessions (fixed)

The first design's "one session at a time" lived in one window's memory. Several windows share one Scout root,
and the second would have offered "Refresh Scouts" mid-session. Starting it would double provider spend and put
two writers on the same scorecards, because both sessions select the same due receivers (a scorecard changes only
when a receiver finishes). I added a **tiny machine-wide guard**, `Work/.coach-refresh.lock`, created with an
exclusive flag so exactly one process wins. It is stale if its process is gone or it is older than 30 minutes,
so a crash can never wedge Scout. Other windows now report **Holding Scout tryouts…** truthfully, and a refused
start records no consent and spends nothing (Bootstrap-18 to 20, including a live holder process, a dead one, an
ancient one, and garbage files). This is small and was not in the brief; it exists because consent and quota are
the load-bearing concern of this Play.

### 3. Which receivers this bootstrap can and cannot create

Only **Combine-derived** receivers (OpenRouter, and OpenCode-hosted) come from tryouts. The two built-in receivers
still depend on developer tooling:

* AntiGravity needs `Player Verification/antigravity.json`, which only the developer CLI `npm run scout:verify` writes.
* Gemini Flash Direct needs a Google key in the process environment.

Neither is bootstrapped by this Play. Also, by the brief, the flow is gated on an **OpenRouter credential**, even
though some discovered receivers (OpenCode-hosted free) need no credential. A user with no OpenRouter key cannot
bootstrap at all.

### 4. This machine cannot demonstrate a fresh install

The real Scout root already holds **27 scorecards**, several READY. Settings here will show "✓ N Scouts ready"
with a **Find Scouts** button, and the first click would be a `refresh-due` session over whichever receivers are
new or a week old. It would not reproduce a true fresh install. That case is proven only by the automated
fresh-root test, not in the field.

REMAINING UNKNOWNs
==================================================

1. **Nothing here has run in a real extension host, a real browser, or against real OpenCode/OpenRouter.** The
   UI is verified by a source contract and a JavaScript parse check, not by driving a DOM. The end-to-end
   behavior of a real session (timing, real OpenCode install, real rate limits) is unobserved.
2. **A session cannot be cancelled and reports no progress**, because Combine has neither. If the extension host
   reloads mid-run, the session's children die with it; the guard goes stale (dead process) and the Work folder is
   left as an orphan (see the sweep decision).
3. **Other windows' Scout capability refreshes late.** Only the initiating Stadium republishes its capability
   snapshot when a session ends. Other windows recompute it at their next snapshot, so Scout may appear on their
   Team only after a roster or capability event. Unmeasured.
4. **Consent is per VS Code profile.** In the multi-host development harness each host has its own profile and
   therefore its own consent, while the depth chart is shared. Fine in the product (one profile); in development
   it means a fresh host asks once.
5. **Privacy design** (Finding 1): tryouts read the user's real Game. Unresolved by design.
6. **Prerequisites are undeclared.** A fresh machine needs the OpenCode CLI. Settings says the tooling "could not
   be used on this computer" but gives no way to fix that. Behavior of OpenCode resolution on a truly clean
   machine is unobserved.
7. **Installed-product long paths** remain UNKNOWN and are unchanged. Record for the fresh-install Windows test.
8. **The per-attempt npm reinstall** (S37) is still an inference. The consent copy therefore says "may download or
   set up provider tooling" and claims no size.
9. **Intermittent tests:** five load-sensitive tests are now on record and none has a captured cause.
10. **No OpenRouter credential means no bootstrap** (Finding 3), and the two built-in receivers are still
    developer-seeded.
