==================================================
THE VIRTUAL PLAYER CONTRACT
==================================================

`src/virtual-player.ts` (new, no `vscode` import; the memento is injected).

```ts
interface VirtualPlayer {
  instanceId: string;                 // 'scout'
  playerType: 'scout';                // VirtualPlayerType, NOT part of PlayerId
  displayName: string;                // 'Scout'
  executionType: 'scout-formation';
  entitled(): boolean;                          // is it offered at all
  readiness(gameRoot): { state: 'ready'|'busy'|'unavailable', label: string };
  capability(gameRoot): PlayerRoutingCapability | undefined;   // only when it can run now
  execute(objective, gameRoot, options?): Promise<VirtualTurnResult>;
}
```

`ScoutPlayerAdapter` implements it. `execute(...)` is unchanged and still runs the existing Formation machinery.
Receivers (Qwen / Laguna / Inkling / Gemini) are internal to Scout and never roster Players.

==================================================
ENTITLEMENT vs MEMBERSHIP vs READINESS
==================================================

| Concept | Question | Owner | Stored? |
|---|---|---|---|
| ENTITLEMENT | Is Scout offered at all? | `coach.scout.enabled` via `entitled()` | Setting |
| MEMBERSHIP | Did Dad recruit it to THIS Game? On Field or Bench? | `VirtualMembershipStore` | **Yes**, per Game |
| READINESS | Can it run a Play right now? | `readiness(gameRoot)` from the shared depth chart | **Never** |

Readiness labels: `Ready`, `Scouting` (a Formation is in flight), `No Scouts ready yet`, `Provider limited`
(infrastructure evidence: RATE LIMITED / AUTH ISSUE / PROVIDER UNSTABLE / UNAVAILABLE), `Scout is turned off`.
A QUALITY status (LIMITED) is deliberately **not** "Provider limited".

==================================================
PERSISTENCE MECHANISM
==================================================

The workspace's own `workspaceState` (the memento `PlayerRoster` already receives, so it is per Game), key
`sidelineCoach.virtualMembership.v1`:

```json
{ "version": 1, "compatibilityChecked": true,
  "members": { "scout": { "playerType": "scout", "onField": true, "recruitedAt": "…" } } }
```

Nothing else: no READY, no provider health, no receiver names, no depth chart (a test greps the stored bytes
for those and asserts absence). It survives browser refresh (the browser holds nothing), Extension Dev Host
reload, VS Code restart and Control Plane restart, because all four re-read `workspaceState`. Malformed
persisted values are dropped rather than trusted (`Virtual-12b`). Virtual membership lives **outside**
`PlayerInstanceBook`, so process-seat guarantees are untouched.

==================================================
RECRUIT / ON FIELD / BENCH / REMOVE
==================================================

| Human action | Effect |
|---|---|
| Recruit | Recruit catalog shows `Scout / Ready` or `Scout / No Scouts ready yet` when entitled. Add recruits it On Field. Not entitled: not offered and refused with "Scout is not available." Recruiting a not-yet-ready Scout is allowed; it joins as unavailable. |
| Bench | `onField:false`, persisted. A benched Scout has no routing capability. Readiness returning does **not** unbench it. |
| Put back On Field | `onField:true`. |
| Remove | Deletes the membership record and nothing else. Scout Intelligence, scorecards, run evidence, Formation history and reports, credentials and bootstrap consent are byte-identical afterward. Scout can be recruited again. |

Scout is a singleton: the browser offers no "Add another Scout", and its removal copy says the tryouts, results
and reports are kept.

If the entitlement is turned off after recruiting, the member stays on the Team as `Scout is turned off`
(unavailable); it is not silently removed.

==================================================
UNAVAILABLE SCOUT BEHAVIOR
==================================================

A recruited Scout with zero READY receivers, or with infrastructure-limited evidence, **stays on the Team**
(On Field, unchanged), never deleted, never silently benched, never faked ready. Its routing capability is
present but `unavailable` in every dimension routing checks (`state`, `freshness`, `autoEligible:false`,
`supportsQueue:false`, no models, `transportLabel` = the reason). `Virtual-19` also pins S31 finding F6: a
Formation in flight stays `busy` even if its own run suspends the last READY receiver, rather than vanishing
mid-run.

==================================================
ROUTING BEHAVIOR
==================================================

- **AUTO** never chooses an unavailable Scout. The proof has a control: with Scout READY the same reconnaissance
  Play routes to Scout; with Scout unavailable it routes to another Player, and with nobody else there is no
  route (never a route into a dead Scout). An explicit `PLAYER: Scout` is refused with "Scout is currently
  unavailable. Coach did not choose another Player."
- **MANUAL** shows Scout truthfully as `Scout · No Scouts ready yet`, and the real router refuses a MANUAL
  dispatch to it, sending nothing to the Stadium.
- The Stadium refuses a routed dispatch to a Scout that is not On Field in this Game. The Dev Mode operator
  (a diagnostic) is unchanged and skips that check.
- No routing-policy change was needed; it was already state-aware.

==================================================
REPORT-READY PRESERVATION
==================================================

There is no second report state. The Ledger entry and its exact-path Formation parent report are keyed by the
Player instance and Play, not by readiness. Through the real Control Plane (`Virtual-13`) an unacknowledged
finished Scout report stays `finished` with `acknowledged:false` after the depth chart empties; the card still
says why Scout cannot run. In the browser (`S31.5-B4`) the same `Report ready · View Scout Report` handoff
survives on an unavailable member.

Dad-facing output is still exactly one parent report; receiver reports stay supporting evidence (`Virtual-15`).

==================================================
COMPATIBILITY ADOPTION (DECISION, DOCUMENTED)
==================================================

Before this slice a READY Scout was drawn on every Team automatically. Dropping a Scout Dad can see today
would be a regression, so there is ONE explicit compatibility rule, in `PlayerRoster.adoptExistingVirtualPlayer`:

- The first time a Game's roster meets a Scout that is entitled **and currently READY**, it is recruited On
  Field, once, and `compatibilityChecked:true` is recorded.
- A fresh install (nothing READY at first registration) is recorded as checked and **never** auto-recruited,
  including when tryouts finish later (no implicit recruit on OpenRouter configuration or tryout completion).
- A Scout Dad removes stays removed, including across restart with READY receivers.
- Not entitled at first registration: nothing is recorded; the check waits for a later activation.

`Virtual-12` covers all four cases. This is a one-time migration, not an ongoing auto-recruit.

==================================================
FINDINGS BEYOND THE BRIEF
==================================================

1. **Compatibility adoption is the one judgment call.** Without it, every existing READY Scout would vanish
   from Dad's Team on upgrade. It is one-time and documented above; Dad can veto it by removing Scout.
2. **Recruiting a not-ready Scout is allowed.** It joins as unavailable and says why. The alternative
   (refusing) would make "Scout / No Scouts ready yet" in the catalog a dead end.
3. **Other-window convergence lags truthfully.** No new event bus was added. Readiness is recomputed on each
   roster and capability snapshot, and a Formation finishing triggers a refresh in the window that ran it. Another
   window that never runs a Formation shows the change at its next snapshot. Membership is per workspace, so
   there is nothing to converge.
4. **Membership is per workspace state.** Dev-harness profiles that use separate workspaces get separate
   membership, which matches "Game-specific" but means a profile switch is a separate Team.
5. `Scouts/` at the repo root is untracked and predates this slice; I did not touch it.
