==================================================
ARCHITECTURE
==================================================

    Human objective (string)
            |
    runScoutFormation()
            |
    createScoutPlayEnvelope()  -- one canonical ScoutPlay (src/scout-play.ts, unchanged)
            |
    FormationCandidate registry -- eligible(context) / createExecutor(context)
            |
    selectFormation()  -- explicit players outrank auto; bounded 1-3; default min(2, eligible)
            |
    bounded concurrent worker pool (cursor pattern, same shape as scout-play-runner.ts)
       /                \
    Scout A (Player)   Scout B (Player)
    independent evidence  independent evidence
       \                /
    FormationCompletion + FORMATION-RESULT.md (mechanical synthesis, not invented)

`src/scout-formation.ts` is new. It does not duplicate `scout-play-runner.ts`
or `scout-interchangeability-runner.ts` — it reuses their provider-neutral
seam directly:

- `ScoutPlay` (src/scout-play.ts) supplies the one canonical envelope; unchanged.
- `ScoutPlayExecutor` / `ScoutAttemptTelemetry` / `evaluateScoutReport` /
  `REQUIRED_SCOUT_STATEMENT` (src/scout-interchangeability-runner.ts) are reused
  as-is for per-Scout execution and evidence evaluation. `RESULT_SECTIONS` was
  changed from a private constant to `export const` (one-line change) so the
  Formation dispatcher's default report contract stays byte-identical to the
  interchangeability runner's, instead of forking a second copy.
- `createAntiGravityExecutor` / `createDirectGeminiExecutor` /
  `validateDirectGeminiAgent` (same file) are reused unmodified as the two
  built-in Formation candidates.

What is genuinely new in `scout-formation.ts`:
- `FormationCandidate` registry (`DEFAULT_FORMATION_CANDIDATES`): a small,
  explicit eligibility + executor-factory seam, not a scoring engine.
- `selectFormation()`: bounded (1-3), explicit-human-outranks-auto selection.
- A concurrent worker pool (adapted from `scout-play-runner.ts`'s cursor
  pattern) driving `ScoutPlayExecutor`s in parallel instead of the
  interchangeability runner's fixed sequential (`maxConcurrency: 1`) loop.
- `buildSynthesis()`: a mechanical Formation index (consensus count, each
  Scout's own "Executive answer" / "CONTRADICTIONS" section extracted by
  structure, missing-evidence and failed-Scout lists) — no invented
  cross-Scout judgment, per the Play's explicit instruction.
- `resultMarkdown()` / `FORMATION-RESULT.md`: the one human-facing handoff.

==================================================
FORMATION SELECTION SEMANTICS (V0.2)
==================================================

Two built-in candidates, chosen from current repo truth, not old report
archaeology:

1. **AntiGravity** — eligible if and only if a persisted Player Verification
   record exists at `<durableReportRoot>/Player Verification/antigravity.json`
   with `state: "READY"`. This is real field evidence (from
   `npm run scout:verify`), not an invented health score. Live launchability
   is still decided by the real attempt (AntiGravity's own capability query),
   so a stale-but-READY record cannot silently corrupt a Formation — it can
   only produce an isolated BLOCKED/FAILED attempt for that one Scout.
2. **Gemini Flash Direct** — eligible only if `validateDirectGeminiAgent`
   passes AND a Google Gemini credential (`GOOGLE_GENERATIVE_AI_API_KEY` or
   `GEMINI_API_KEY`) is present in the process environment. Neither was
   present during this Play's field run, so it was correctly skipped — not
   dispatched, not counted as a failure. No authentication debugging was
   performed, per instruction.

OpenCode/OpenRouter free-model Scouts (`scout-play-runner.ts`'s
`SCOUT_ROSTER`) were deliberately **not** wired into the Formation registry
in V0.2. They remain fully usable via `npm run scout:play` for Games that
expose `.opencode/agents/*` (e.g. Trend and Tap Assist does; the SidelineCoach
repo itself does not). Adding an `opencode-roster` `FormationCandidate` is a
clean, isolated future addition — the registry shape (`eligible` +
`createExecutor`) is the seam; nothing about it needed building now.

Explicit `players: [...]` always outranks automatic eligibility (human
authority outranks inference), bounded to the V0.2 maximum of 3; an unknown
id is a hard input error, not a silent skip.

==================================================
FAILURE SEMANTICS
==================================================

Reused directly from the interchangeability runner's `InterchangeabilityState`
(`COMPLETE | FAILED | BLOCKED | INTERRUPTED | UNKNOWN`) per Scout attempt.
Formation-level `outcome` is derived mechanically:

- `COMPLETE` — every selected Scout completed.
- `PARTIAL` — at least one completed, not all.
- `BLOCKED` — none completed, at least one provider/auth/capacity BLOCKED.
- `FAILED` — none completed or blocked, at least one hard FAILED.
- `UNKNOWN` — none of the above (interrupted/unknown only).

Measured telemetry (`completionState`, exit code, signal) stays separate from
qualitative evaluation (`evaluation.reportStructurallyUsable`,
`existingGameArtifactObserved`) exactly as the interchangeability runner
already separates them — this distinction is what caught the AntiGravity
permission defect below (lifecycle said COMPLETE; evaluation correctly said
"not structurally usable, no cited evidence").

FIELD PROOF
==================================================

Real objective (not synthetic), gameRoot = this repo, read-only:

> Investigate why Reports appear correctly for some Games such as Trend and
> Tap Assist but have historically been absent or inconsistent for other
> mature Games. Trace the current report-discovery pipeline... (full text

**Run 1** — `Scout-Formation__2026-09-17_075139_921_MDT`
- 1 Scout selected automatically (AntiGravity; Gemini Flash Direct correctly
  skipped — no credential in this process).
- Lifecycle: COMPLETE, exit 0, 10.2s.
- **But** `reportCreated: false`, `evaluation.reportStructurallyUsable: false`.
  `providerError`: `"jetski: no output produced — a tool required the
  \"read_file\" permission that headless mode cannot prompt for, so it was
  auto-denied."`
- Root cause: the Formation's AntiGravity candidate launched with AntiGravity's
  default main agent directly at `gameRoot`, unlike the proven
  `scout-player-verification.ts` path, which runs a custom minimal-tool agent
  (`view_file`/`grep_search`/`code_search`, never `read_file`) rooted at an
  isolated `playerPath` with `gameRoot` added via `--add-dir`. AntiGravity's
  headless mode auto-denies any tool permission it can't prompt for, and the
  default agent reaches for `read_file`.

**Seam fix** (`src/scout-formation.ts`, `ANTIGRAVITY_CANDIDATE.createExecutor`):
reused the exact proven pattern from `scout-player-verification.ts` —
`executionRoot: playerPath`, `additionalDirectories: [gameRoot]`, and a
per-attempt custom agent file
(`sideline-formation-scout`, same restricted tool list) written into
`playerPath/.agents/agents/` before each execution. One targeted fix at the
seam that actually caused the failure; no broader debugging campaign.

**Run 2** — `Scout-Formation__2026-09-17_075321_685_MDT` (after the fix)
- 1 Scout selected automatically (same reasoning as Run 1).
- Lifecycle: COMPLETE, exit 0, **240.7s** (a real, non-trivial reconnaissance).
- `reportCreated: true`, `evaluation.reportStructurallyUsable: true`,
  `existingGameArtifactObserved: "src\\game-filesystem-contract.ts"`.
- Real findings, with exact file/line citations: four distinct bottlenecks in

  canonical root list vs. `server.ts#L831`'s narrower fallback check) and a
  4-step recommended repair sequence.
- Full report:
  `REPORTS\Scout Only\Scout-Formation__2026-09-17_075321_685_MDT\antigravity-SCOUT-REPORT.md`
- Formation result:
  `REPORTS\Scout Only\Scout-Formation__2026-09-17_075321_685_MDT\FORMATION-RESULT.md`

TESTS
==================================================

`test/scout-formation.test.mjs` (9 tests, all passing), using injected fake
`FormationCandidate`s — no real provider calls in the unit suite:

1. Formation identity is generated automatically and filesystem-safe.
2. The same canonical Play (identical `playHash`/`semanticPromptHash`) reaches
   every selected Scout, and a 2-Scout Formation's executions genuinely
   overlap in time (concurrency proof, not just a completion-order check).
3. Formation size is bounded 1-3, defaults to `min(2, eligible)`, and never
   fails merely because the eligible roster is smaller than requested.
4. Explicit human Player selection outranks automatic eligibility.
5. One Scout's FAILED outcome does not corrupt another Scout's independent
   evidence; Formation outcome correctly reports PARTIAL.
6. A provider BLOCKED outcome is distinguished from a hard FAILED outcome at
   the Formation level.
7. A Scout's self-reported CONTRADICTIONS section is surfaced verbatim in the
   Formation synthesis rather than averaged away.
8. Formation results persist to durable evidence with no-overwrite protection
   and one obvious `resultPath`.
9. Read-only authority evidence (`readOnlyContractHeld`) is preserved per
   Scout in the Formation telemetry.

Full existing regression suite: `npm test` → **970/970 passing**, including
all prior Scout Runner, Scout Interchangeability, and Scout Player
Verification tests unchanged. `npm run check` (tsc --noEmit) is clean.

Note: one test-authoring bug was caught and fixed during this work — the
first draft of the concurrency-overlap test indexed `observed[observed.length
- 1]` to stamp an end time, which is invalid under real concurrent execution
(both Scouts' entries exist by the time either resolves, so the wrong entry
was stamped). Fixed by capturing a direct object reference at push time. This
is a test-fixture correction, not a dispatcher bug — verified separately with
a standalone Node script showing genuinely overlapping start/end timestamps.
