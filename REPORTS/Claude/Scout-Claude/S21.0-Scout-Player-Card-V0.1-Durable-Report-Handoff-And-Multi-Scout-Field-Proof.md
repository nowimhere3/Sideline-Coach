==================================================
WHAT SCOUT LACKED (confirmed by reading current source, not assumed)
==================================================

Two independent arrays feed the browser: `status.players` (the real
`PlayerRoster`/roster instances) and `status.routing.capabilities` (dispatch
targets). Scout only ever populated the second — `StadiumClient.
sendCapabilitySnapshot()`'s `scoutPlayer?.capability(...)` merge — so it
could be routed to but never had a Team card, because `renderPlayerStrips()`
only ever iterated roster rows.

Separately, `entry.currentPlay.promptSummary` (read by the browser as
`view.summary`) is normally set ONLY by the router's `play-dispatched` event
+ `DispatchRecord`. Scout's dispatch is client-initiated and bypasses the
router entirely, so a working Scout card would have had no truthful
"N Scouts running" text available even if it existed.

==================================================
FIX — Scout Player Card
==================================================

- `src/scout-formation.ts` — `FormationRequest.onSelected?(info: {count,
  candidateIds})`, called exactly once, synchronously, right after
  `selectFormation()` and before any receiver executes. The real selected
  count, never a guess, never a live per-receiver feed (none exists).
- `src/scout-player.ts` — `ScoutPlayerAdapter.execute()` takes an
  `{onSelected}` option and forwards it unchanged into `runFormation()`.
- `src/stadium-client.ts` — `deliverScout()` now sends a `started` turn event
  carrying `summary: "N Scout(s) running"` the moment `onSelected` fires,
  ahead of the pre-existing unconditional `started` fallback (kept for
  safety if a `runFormation` implementation never calls `onSelected`).
- `src/control-plane/work-ledger.ts` — `recordTurn()`: a `started` event's
  `turn.summary` now fills `currentPlay.promptSummary` **only when it is
  still empty** — reusing the already-transmitted-but-previously-ignored
  `TurnRecord.summary` field, adding no new wire surface. A real dispatched
  Play's own promptSummary (set at dispatch time via `recordDispatch`) is
  never overwritten.
- `src/public/index.html` — a Scout card is synthesized directly from
  `status.routing.capabilities.find(c => c.executionType ===
  'scout-formation')` (never folded into `rawInstances`, so it can never
  double up in the dispatch dropdown or gain roster-only actions like
  bench/remove). Idle → "Ready"; busy → "Scouting", then the normal
  `renderPlayStrip()`/`stripCopy()` machinery takes over using the SAME
  `execution.byInstance` view Scout's `SCOUT_PLAYER_INSTANCE_ID` entry
  already carries — one canonical elapsed-clock architecture, never a
  second timer.

SCOPE TRIM (explicit, documented per instruction): no distinct "Drafting
report..." UI state was built. There is no cheap existing signal
distinguishing "all receivers done, now synthesizing" from "still awaiting
receivers" without a second callback surface, and Formation's synthesis step
is near-instant relative to receiver runtime (tens of seconds to minutes,
confirmed again by this Play's own field run below). The card goes straight
from "Scouting" to the finished/report-ready state.

==================================================
FIX — Durable Report-Ready Handoff (applies to Scout AND every ordinary Player)
==================================================

Root cause: `stripCopy()`'s `case 'finished':` unconditionally returned
`null` once `isRichFinished(view)` (the 30s `RICH_FINISHED_MS` window)
expired, regardless of whether the report was acknowledged. `viewReport()`
itself was already fully correct — exact report open via
`openReportByPath`/`fetchReports` retry, `scrollToIncoming()`, then
`acknowledgeWork()` only on a successful open — so no changes were needed
there.

Fix, one seam, `src/public/index.html`'s `stripCopy()`:
```
case 'finished': {
  const reportReady = isReportReady(view);
  const rich = isRichFinished(view);
  if (!rich && !reportReady) return null;
  ...
  return { glyph: '✓', word: rich ? 'Finished' : 'Report ready',
    summary: filename || ..., action: reportReady ? 'view-report' : undefined };
}
```
Past the 30s window, an unacknowledged canonical report now keeps the strip
alive as "Report ready" / "View Report" — durable until an explicit click
opens/reveals it and `acknowledgeWork()` succeeds. Acknowledged (or
never-reported) Finished still quiets exactly as before at the same 30s
boundary. No auto-scroll was added or existed — the viewport only ever moves
on the explicit click, unchanged.

1. Scout Feature/Commercial Gate — `src/scout-player.ts`, directly above
   `ScoutPlayerAdapter.capability()`. WAS: Scout began as internal Formation
   plumbing with no routing identity. IS: the returned capability is pure
   capability truth (enabled + ≥1 eligible receiver), mirrored as-is into

   reuse. None of that is built.

2. Scout Depth Chart/Real Game Film — `src/scout-formation.ts`, directly
   above `selectFormation()`. WAS: only a small number of receivers have
   meaningful real-game proof. IS: Combine, Coach Refresh, and this
   selection step already discover/evaluate receivers; `eligible()` is a
   bare READY gate, not a ranking. WHY: a large discovered roster is not a
   proven depth chart. WILL BE: the receiving corps should grow via
   truthful tryouts and real-game film, receivers moving up/down by
   task-specific evidence, reliability, observable cost/capacity, and
