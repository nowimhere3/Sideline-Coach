==================================================
THE SMALLEST SEAM
==================================================

`durableReportRoot` is already a required Formation parameter, and it is the Scout Intelligence
root. So the default is derived from it in one place:

```ts
// src/scout-formation.ts
const workspacePath = path.join(
  path.resolve(request.workspaceRoot ?? resolveScoutWorkRoot(request.durableReportRoot)), formationId);
```

`resolveScoutWorkRoot(scoutIntelligenceRoot)` takes **only** the Scout root. It has no Game
parameter, so it cannot depend on a Game, and an omitted `workspaceRoot` can never again fall back
into a repository. The explicit `workspaceRoot` override is retained.

Passing `workspaceRoot` from `extension.ts` (S31's original suggestion) was rejected because it
would put the same fact in two places. A caller that forgot it would silently regress to the
Game, which is exactly the failure being removed.

==================================================
COLLISION AND SAFETY
==================================================

Formation ids embed a millisecond timestamp and zone, and are the only isolation. Evidence:

* Work-5: two Games at different times get distinct workspaces under **one** shared Work root,
  each recording its own Game as target.
* Work-5b: two Games forced to produce the **same** id (identical clock). The second **fails
  closed** with "Formation workspace already exists"; the first Game's working state and durable
  evidence are byte-identical afterward, and the second Game is not used as a fallback.

**Residual, reported rather than fixed.** The existing guard is `existsSync` followed by
`mkdirSync({ recursive: true })`. The sequential case is proven safe. Two *concurrent* processes
(for example two Stadiums for different Games) hitting the same millisecond could both pass the
check and share a folder. This is not new: `Formations/<id>` has been shared across Games since
S27. Moving Work made it exist for the working folder too. A non-recursive leaf `mkdir` would make
it atomic, but I did not widen the slice for a probability this small.

FINDINGS THE MOVE EXPOSED
==================================================

### 1. Working state is now invisible, unbounded, and ~91% regenerable scaffolding

Measured from the two real Formation working folders in Trend and Tap Assist (a small sample):

```text
7,378 files, 113 MB total  →  ~3,700 files and ~57 MB per Formation
```

Breakdown of one Formation (58.9 MB, 3,692 files):

| Folder | Size | Files | Share |
|---|---|---|---|
| `<receiver>/.opencode-combine` | 53.8 MB | 3,671 | **91.4%** |
| `<receiver>/.opencode-combine-data` | 5.0 MB | 7 | 8.6% |
| logs, telemetry, `SCOUT-REPORT.md` | 29 KB | 8 | ~0.05% |
| Formation top-level (canonical Play, prompts, candidates) | 26 KB | 5 | ~0.04% |

`.opencode-combine` is OpenCode's isolated config dir. I confirmed it holds a `node_modules` tree
(1,587 `.ts`, 877 `.js`, 874 `.map`) that OpenCode installs for `@opencode-ai/plugin`, generated
around **one 594-byte Sideline-authored agent file**. It is harness scaffolding recreated per
receiver per Formation, not evidence.

Why this matters now: before, that bulk sat inside the Game, where it was visible and deletable.
Now it accumulates in `~/.sideline` (or, installed, VS Code global storage), which Dad is never
meant to see, with no pruning, which is exactly what this Play instructed. At about 57 MB per
Scout Play, 100 Plays is roughly 5.7 GB. Slice 4 makes it worse by adding automatic tryouts. A
future retention Play has an obvious safe target: the regenerable scaffolding, keeping the
roughly 55 KB of real evidence. That is a recommendation for Coach to schedule, **not** something
implemented here.

A side observation, uninvestigated: reinstalling ~50 MB of npm packages per receiver per Play is
also a latency and network-failure source.

### 2. Installed-product path lengths are unproven

The longest existing relative path under a Formation is 227 characters (inside the OpenCode
`node_modules`). Projected full length, against the classic 260-character Windows limit:

| Root | Full length |
|---|---|
| dev Work root (`C:\Users\dmcal\.sideline\…\Work`) | 276 |
| **old** Game-local, Trend and Tap Assist | 287 |
| installed, typical user (`AppData\Roaming\Code\User\globalStorage\…`) | 329 |
| installed, long username + Insiders + profile | 377 |

All exceed 260, **including the old location, which worked in the field** (a real successful
Laguna Formation produced that 227-character path). So long paths evidently work on this machine,
and the dev move is a small improvement (276 vs 287), not a regression. But the installed
product's global-storage prefix is roughly 40 to 90 characters longer than the Game-local one, and
whether OpenCode's child processes tolerate that on another user's Windows is **unknown**.

1. **Real harnesses may still write into the Game.** Only files *Sideline generates* were moved,

   files in the Game while it is their cwd or `--dir` is unproven. It needs the field check above.

5. **Adapter's own fallback.** `ScoutPlayerAdapter` with *no* `durableReportRoot` falls back to
   `<Game>/REPORTS/Scout Only`, so a caller omitting both roots would derive Work inside the Game.
   The product always passes `durableReportRoot`, and only tests construct it bare, but the
   guarantee lives in `extension.ts`, not the adapter.
6. **Same-millisecond concurrent collision** is a theoretical race, as described above.
7. **The package audit is shell-dependent** (`tools/dev/audit-vsix.mjs` shells out to whichever
   `tar` is first on `PATH`). A future fix could use an explicit `--force-local` or the Windows
   system `tar.exe`. It was not changed here.
