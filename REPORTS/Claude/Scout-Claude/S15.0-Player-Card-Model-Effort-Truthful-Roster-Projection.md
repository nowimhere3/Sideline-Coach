==================================================
ARCHITECTURE / OWNERSHIP
==================================================

    Provider truth (Codex thread/start, Claude/AntiGravity init frame)
            |
    control.model / control.effort   <- the ONE active-state truth, mutated
    in place by CodexAppServerControl / StructuredPrintControl before each
    `settings` ControlEvent fires (unchanged; already existed)
            |
    PlayerRoster.status()  -- NEW: resolves `control` + the Player's
    capabilityService snapshot, calls controlledControlProfile() (already
    existed, used elsewhere for the SAME purpose) to get a human display
    name for the SAME active id, and projects modelDisplayName/effortDisplayName
            |
    roster.snapshot -> Control Plane daemon -> projectFriendlyRoster()
    (already additive-only; untouched) -> /api/status.players[].instances[]
            |
    src/public/index.html: makePlayerText() renders a compact identity line
    between the Player name and the existing "On Field · Controlled" state —
    only when at least one of modelDisplayName/effortDisplayName is present

No second truth system was created. `record.routing`/`PlayerRoutingLabel`
(the dead seam the S14.0 report found — declared in `player-instances.ts`,
never written anywhere) was deliberately NOT resurrected: its `fieldLabel()`
concatenates routing into the SAME string as the "· Controlled"/state
suffixes already appended in `player-roster.ts`'s `controlledProjection()`,
which is the wrong shape for a separate secondary line and would have
required disentangling unrelated suffix logic. The live `control.model`/
`control.effort` + `controlledControlProfile()` path was already exactly
right and already reaches `PlayerRoutingCapability.activeModel/activeEffort`
(the Dispatcher's own routing surface) — this Play threads the SAME truth
into the roster-card surface instead of inventing a parallel one.

**Capability vs. active state, kept separate, per instruction**: the
capability catalog (`capabilityService.get(playerType)`) is consulted ONLY
to resolve a human-readable label for the id `control.model`/`control.effort`
already truthfully reports — never to pick or infer which model is active.
Verified directly: a two-model catalog with the SECOND (non-default) entry
active correctly shows that second entry, never the catalog default
(Q2.12-4); an active id present nowhere in the catalog is never matched onto
an unrelated catalog entry, only humanized from its own text (Q2.12-7/8, and
the real field proof).

IMPORTANT FILES
==================================================

- `src/provider-control.ts` — `controlledControlProfile()`'s active-model
  lookup widened from exact-id-only to exact -> family-prefix (covers
  AntiGravity's `family` vs. `family-effort` id shapes) -> humanized raw id
  (last resort, never a guess at a different catalog entry). New private
  helpers `matchActiveModel()`/`humanizeModelId()`. No signature change; no
  existing caller's behavior changes when an exact match already succeeded
  (Codex, unaffected).
- `src/player-roster.ts` — `status()`: controlled-instance branch now
  resolves the live `PlayerControl` and capability snapshot, calls
  `controlledControlProfile()`, and adds `modelDisplayName`/`effortDisplayName`
  to the returned instance object (falls back to the raw truthfully-known
  value, via `effortLabel()`, when capability hasn't been queried yet —
  never blank when something real is already known). `handleControlEvent()`:
  a `settings` event now fires `this.changed.fire()` (previously silently
  discarded — the exact CONTRADICTION #2 the S14.0 AntiGravity reconnaissance
  found) — this is the ONLY new "wake up" plumbing; the control's own
  model/effort fields are already updated in place by the adapter before
  that event fires, so `status()` always reads current truth.
- `src/public/index.html` — `makePlayerText()` accepts an optional 4th
  `identityText` param, rendered as a new `.player-identity` line between
  name and state (falsy -> nothing rendered, no `MODEL:`/`EFFORT:` label
  prefix). New `playerModelEffortLine(instance)` builds `"Model · Effort"`,
  `"Model"` alone, or `''` from the two canonical fields — the browser does
  no provider-truth reconstruction of its own. New `.player-identity` CSS
  rule, sized/colored consistently with the existing compact card style.
- `src/scout-formation.ts` — the required breadcrumb only (see BREADCRUMB
  below); no logic changed. Confirmed by the full Scout Formation/Combine/
  Bridge suites passing unchanged.

TRUTHFULNESS BEHAVIOR (verified, not just designed)
==================================================

- Known model + known effort -> both shown (Q2.12-1).
- Known model + unknown effort -> model alone; effort never defaulted to a
  guessed value like "Medium" (Q2.12-2).
- Neither known (no Play sent yet on a freshly opened session) -> both
  genuinely absent, not a fabricated placeholder (Q2.12-3).
- Multi-model catalog -> the ACTIVE model wins, never the catalog default
  (Q2.12-4).
- `settings` ControlEvent -> existing `roster.onDidChange` broadcast fires;
  a subsequent `status()` read reflects the new value with no caching lag
  (Q2.12-5).
- Legacy/external (non-Controlled) instances receive no
  `modelDisplayName`/`effortDisplayName` key at all — not even `undefined`
  spuriously added — since this Play's reconnaissance and this
  implementation both scope to the Controlled transport, where a trustworthy
  per-instance active-state bridge already exists (Q2.12-6). Legacy/terminal
  Players remain a truthful UNKNOWN for this feature; not addressed here.
- AntiGravity-shaped variant id (`gemini-3.8-flash-medium` active against a
  family-keyed catalog `gemini-3.8-flash`) -> family-prefix match, clean
  `"Gemini 3.8 Flash"`, no duplicated `"(Medium)"` (Q2.12-7).
- An active id matching NO catalog entry, even loosely, is never coerced
  onto an unrelated one (Q2.12-7's second assertion).
- Claude-shaped mismatch (catalog alias `sonnet`, active full slug
  `claude-sonnet-5`) -> humanized last-resort `"Claude Sonnet 5"`, not the
  catalog's `"Sonnet"` label and not the raw unformatted slug (Q2.12-8).

FIELD PROOF
==================================================

`test/control-plane-roster-projection.test.mjs`, new test **Q2.12-9**: boots
the REAL `PlayerControlHost` + `CodexAppServerFactory` against the REAL
`fake-codex-app-server.mjs` fixture (a faithful stand-in for the actual
Codex app-server JSON-RPC protocol) inside a REAL `ControlPlaneDaemon`,

from `src/public/index.html` via `vm` — the same technique
`control-plane-roster-projection.test.mjs` already used for prior field
proofs, extended here to inspect the rendered card's DOM node tree.

The fixture's `thread/start` reports active model `gpt-5.6-terra` /
`reasoningEffort: medium` — a model id that is **not present at all** in
that same fixture's own `model/list` catalog (`gpt-5.6-sol`, `gpt-6-astra`,
`gpt-5-luna`). This is exactly the "capability catalog doesn't answer the
question" edge case the mission warned about, and it happened by fixture
coincidence rather than by test design. Result: `modelDisplayName` =
`"Gpt 5.6 Terra"` (the honest humanized fallback of the real id — casing on
"GPT" is imperfect, the underlying identification is not), `effortDisplayName`
= `"Medium"`, and the rendered card's `.player-identity` node's
`textContent` is exactly `"Gpt 5.6 Terra · Medium"`. No wrong catalog entry
was ever matched.

A literal running VS Code window + browser was not exercised (this
environment has no interactive VS Code host); this real-process, real-HTTP,
real-unmodified-script proof is the closest available field check and is
the same standard prior Plays in this repo have used for UI field proof.
