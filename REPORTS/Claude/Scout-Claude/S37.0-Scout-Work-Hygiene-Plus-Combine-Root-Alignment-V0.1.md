==================================================
THE RETENTION RULE (EXACT)
==================================================

Implemented in one new module, `src/scout-work-hygiene.ts`. For each receiver, **only after** its
outcome, telemetry, durable report and (for Combine) scorecard are final:

| Removed | When |
|---|---|
| `.opencode-combine/node_modules` | **Always**, whatever the outcome |
| `.opencode-combine-data` | **Only** if the attempt is `COMPLETE` **and** its durable report was written |

Nothing else is ever removed. The set is a two-item constant allowlist, not a pattern, and a
defense-in-depth check refuses any path that does not resolve strictly inside the receiver's own
folder.

Why these two:

* `node_modules` is OpenCode's plugin install, **regenerable** from the `package.json` and
  `package-lock.json` that stay beside it. It was 91% of a Formation's storage.
* `.opencode-combine-data` is OpenCode's own session store (SQLite DB, WAL, snapshot, log). Once an
  attempt completed, its meaning is already in the durable report and telemetry. After any other
  outcome it is **kept**, because it is the nearest thing to a transcript of what went wrong.

A `COMPLETE` attempt that produced **no** report (empty output) is deliberately treated as *not*
safely secured, so its session store is kept (tested).

The cleanup is **asynchronous** (`fs.promises.rm`). I first wrote it synchronously and caught the
problem during review: Formation runs in the shared VS Code extension host, and a synchronous
delete blocks that thread for ~0.5 s per receiver. The async version is also faster on real data
(~230 ms vs ~500 ms).

==================================================
PRESERVED VERSUS DISPOSABLE
==================================================

**Disposable (regenerable scaffolding only):**
`<receiver>/.opencode-combine/node_modules/`, and, for completed receivers,
`<receiver>/.opencode-combine-data/`.

**Never touched, in any outcome:**

| Retained | Why it matters |
|---|---|
| `stdout.log`, `stderr.log`, `telemetry.json`, `SCOUT-REPORT.md` | the attempt's evidence |
| `.opencode-combine/agents/*.md`, `package.json`, `package-lock.json`, `.gitignore` | records exactly which agent contract and plugin version ran |
| Formation/Combine-level files (`canonical-play.json`, `semantic-prompt.txt`, `candidates-considered.json`, `discovery.json`, `*-COMPLETE.json`, `*-RESULT.md`) | run-level evidence |
| **Everything durable:** `Formations/**` (`FORMATION-RESULT.md`, children, provenance), `Combine/Scorecards/**`, `Combine/Runs/**`, `Player Verification/**` | never inside the cleanup's reach |
| Historical `<Game>/Scouts/**` | not touched, migrated, or deleted |

==================================================
FAILURE SAFETY
==================================================

* **Ordering.** Cleanup is the *last* statement in each receiver's slot. Status, telemetry and
  scorecards are derived and written **before** it runs, so it cannot influence them.
* **Never throws.** `releaseReceiverScaffolding` returns errors as data, including asynchronous
  rejections. One failing target does not stop the next.
* **Reported separately.** The result is a new `workspaceHygiene` field on `FormationCompletion` and
  `CombineCompletion` (`receiversCleaned`, `pathsRemoved`, `failures[{receiver,path,message}]`),
  written to the durable `*-COMPLETE.json`. It is not in any attempt, scorecard, evaluation,
  synthesis, or Dad-facing parent report.
* **Proven by direct comparison** (Hygiene-8, 11, 12). Each treatment run is compared with a
  **control run whose remover is a no-op**:
  * Formation with an always-failing remover: `outcome` stays `COMPLETE`, 2 completed / 0 failed / 0
    blocked, attempts identical (`completionState`, `reportCreated`, `failureBoundary`,
    `providerError`, `rateLimitOrQuotaEvent`), children identical, and the error text `EBUSY` appears
    in **no** attempt, synthesis, or parent report.
  * Combine with an always-failing remover: scorecards (`currentStatus`, `totals`, `routeAttempts`,
    `notes`, `availabilityEvidence`) are byte-equivalent to the control.
  * BLOCKED / FAILED / thrown-executor attempts: identical outcomes and failure boundaries to the
    control, with `stderr.log`, `telemetry.json`, the agent record and the session store retained.
* **Cleanup can never modify a Game** (Hygiene-13): even Game folders that *look like* scaffolding
  (a `.opencode-combine/node_modules` and a `node_modules/left-pad` placed inside the Game) stay
  byte-identical.

**A limit on "reported truthfully."** Failures are recorded on disk, but nothing currently reads or
surfaces `workspaceHygiene`. There is no log line, no UI, and no alert. That is intentional for
scope (no Dad-facing cleanup settings), but it means a persistent cleanup failure would be
invisible until someone opens a `*-COMPLETE.json`.

PACKAGE AUDIT
==================================================

### My first "tiny fix" was wrong

The Play authorized a tiny deterministic fix if one existed. My first attempt passed `tar` a relative
archive name with an explicit `cwd`, which removes the `C:`-as-remote-host confusion. I ran the
package gate under **both** shells to check it, and **Git Bash then failed with a different error**:
`tar: This does not look like a tar archive`.

**Root cause, which I had not seen before:** a `.vsix` is a ZIP. GNU tar (Git Bash, and most Linux)
cannot read ZIP at all; only bsdtar (Windows `tar.exe`, macOS) can. The drive-letter error was
masking that. So the audit was never shell-independent, and it would also have failed on Linux. A
relative path could not have fixed it.

### The fix that is actually portable

`tools/dev/zip-entries.mjs`, a pure-Node reader of the ZIP **central directory** (names only, never
contents). About 45 lines, no dependency, no child process. `audit-vsix.mjs` no longer imports
`child_process` at all. ZIP64 and corrupt archives fail loudly rather than returning a wrong list.

### Tested three ways

* **Synthetic ZIPs** written by the test itself: entry names with spaces, brackets, directories and
  unicode; an archive comment after the end record; not-a-ZIP, truncated, ZIP64-sentinel and
  smashed-directory inputs all rejected.
* **A real-package cross-check** (Zip-5, ran, not skipped): the in-process listing of the real VSIX
  equals **bsdtar's own listing of the same archive**.
* **The real gate, under both shells, on the final code:**

| Shell | `tar` on PATH | Result |
|---|---|---|
| Git Bash | GNU tar 1.35 (the shell that failed twice before) | **`VSIX content audit PASS: 89 archive entries`**, exit 0 |
| PowerShell | Windows bsdtar 3.8.8 | **`VSIX content audit PASS: 89 archive entries`**, exit 0 |

I also listed the archive independently rather than trust the script's verdict. **89 entries** (S36:
88; +1 is `out/scout-work-hygiene.js`). Present: `scout-work-hygiene.js`,
`scout-intelligence-report-source.js`, `scout-intelligence-root.js`, `scout-formation.js`,
`scout-combine.js`, `scout-coach-refresh.js`, `extension.js`. **Absent (each counts 0):** `Work/`,
`Scouts/`, `REPORTS/`, `Scout Intelligence`, `Formations/`, `Combine/`, `.opencode-combine*`,
`node_modules` other than `ws`, tests, `tools/` (so `zip-entries.mjs` is not shipped), `Diagnostics/`,
`.claude/`, source maps, nested `.vsix`.

The package was built and inspected only, **not installed**.

FINDINGS BEYOND THE BRIEF
==================================================

### 1. The previous package gate was shell-dependent in two ways, not one

Covered above. S34's audit (and S36's PowerShell-only "PASS") worked only where `tar` was Windows
bsdtar. That is now fixed and tested, and the gate passes in both shells.

### 2. My own test suite made the repository less reliable, and I had to fix it

While running the full suite repeatedly I saw failures in tests unrelated to Scout, in different
tests each time, all of which pass in isolation. I ran a controlled comparison rather than assume it
was pre-existing:

| Full-suite configuration | Runs with at least one failure |
|---|---|
| **Without** my hygiene test file | 0 of 5 |
| With my hygiene tests, **heavy** fixtures (~300 files per receiver) | **2 of 5** |
| With my hygiene tests, **lightened** fixtures (12 files) | 2 of 8, both the same continuation test |
| Final code, lightened + async | 3 of 3 clean, after 4 clean runs just before |

Cause, in my judgment: `node --test` runs files in parallel, and my fixtures created thousands of
small files across a dozen runs. File creation is the costly operation on Windows, so I was starving
daemon and loopback-HTTP tests of I/O. The fix: light fixtures by default and the heavy 6 MB scale
only in the one test that measures reduction. The suite dropped from ~9.5 s to ~1.3 s.

**What I cannot claim.** The samples are small and I cannot separate a small residual effect from
those tests' own base rate. One of them, `real Control Plane chain returns COMPLETE Scout evidence…`,
also failed in S34 and S36, before this Play existed. I looped the suite 14 more times specifically
to capture its error text and did not observe it, so **its cause is still unknown**. Failures I did
capture: `Coach Routines B9` failed with `fetch failed` / `ECONNRESET`, a loopback network reset in a
test that starts a real daemon. `WI-6` and `S10-21` each failed once, uncaptured. I confirmed
`continuation` and `WI-6` pass in isolation; I did not isolate `B9` or `S10-21`. My conclusion is that
these are load-sensitive daemon/filesystem tests with a low base rate that I aggravated and then
reduced, not that they are fixed.

### 3. Every receiver re-installs about 50 MB of npm packages, every run

That `node_modules` exists in each receiver's *own* isolated config folder, so each attempt appears to
reinstall `@opencode-ai/plugin`. This is an **inference** from the design (a per-attempt isolated
config directory) and the folders observed; I did not observe the network traffic. It matters for
Slice 4: a Coach Refresh of 5 tryouts would install this 5 times, which is a latency, offline-failure
and data-usage cost that a consent prompt may need to be honest about. Cleanup does not change it. If
anything it means the scaffolding is genuinely regenerable, which is why deleting it is safe.

### 4. Cleanup only runs on the normal path

If the process dies mid-run, or a receiver's slot throws before its last statement, that receiver's
scaffolding is left behind, and nothing ever sweeps it. Bounded to that run, but permanent.
