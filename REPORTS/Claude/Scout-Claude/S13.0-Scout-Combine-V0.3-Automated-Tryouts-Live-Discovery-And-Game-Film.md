==================================================
LIVE PROSPECT DISCOVERY (no hardcoded roster)
==================================================

Two independent sources, either one failing never blocks the other:

1. **OpenRouter's public model catalog** (`GET https://openrouter.ai/api/v1/models`,
   unauthenticated). A prospect qualifies only if its id ends in `:free`,
   pricing is exactly zero for prompt and completion, `supported_parameters`
   includes `tools`, and output modality includes `text`.
2. **The installed OpenCode CLI's own hosted free models**
   (`opencode models --verbose`), run against a fresh, isolated
   `XDG_DATA_HOME` scratch directory rather than the human's real OpenCode
   home. A prospect qualifies if `cost.input`/`cost.output` are both zero and
   `capabilities.toolcall`/`capabilities.output.text` are both true.

This environment's real OpenCode installation has a corrupted local database
(`~/.local/share/opencode/opencode.db`: "Database is not empty and has no
session table" — a pre-existing OpenCode defect, unrelated to Sideline, that
this Play does **not** attempt to repair). Isolating `XDG_DATA_HOME` per
invocation was the correct bounded fix at Sideline's own seam: it means every
Combine discovery/tryout is fully independent of that installation's health,
never touches or risks the human's real session history, and needed no
"repair" of third-party state — confirmed live: `opencode models` fails
against the real home and succeeds cleanly against an isolated one.

Live discovery on 2026-09-17 found **26 current prospects** — 18 from
OpenRouter, 8 from OpenCode's own hosted catalog — confirming the mission's
premise directly: `poolside/laguna-*`, `nvidia/nemotron-3-*` are still live
and free; `cohere/north-mini-code` is still live; several prospects
(`nex-agi/*`, `inclusionai/ling-3.0-*`, `liquid/lfm-2.5-*`,
`thinkingmachines/inkling*`, `z-ai/glm-5.2`, `google/gemma-4-*`, OpenCode's
own `big-pickle`/`union-alpha`/`muse-spark-*`/`mimo-v2.5`) did not exist in
the old hardcoded `SCOUT_ROSTER` (`scout-play-runner.ts`) at all. That
roster was left unmodified — it remains the proven fixed-route path for
Games that expose `.opencode/agents/*`; Combine discovery is additive, not a
replacement.

==================================================
TRYOUT FUNNEL
==================================================

Three route classes are defined (`TRYOUT_ROUTES` in `scout-combine.ts`) —
Repository Archaeology (A), Contradiction Hunt (B), Bounded Evidence Answer
(C) — matching the Play's required classes. V0.3's funnel dispatches **Route
C only**, one inexpensive, gameRoot-generic snap per selected prospect
("identify this Game's own top-level project manifest and cite one real
entry it defines"): cheap, fast to fail closed, and answerable in any
reasonably-normal repository. Routes A/B exist as a real, structurally ready
seam for a future earned second snap — never exercised in V0.3, per
instruction not to run a tournament.

Budget: default 5 tryouts, concurrency 2 (`CombineBudget`, overridable via
`--max-tryouts`/`--max-concurrency`). Selection priority, in order: newly
discovered (no scorecard) > stale evidence (scorecard older than 7 days) >
previous callback status (AUTH ISSUE / RATE LIMITED / PROVIDER UNSTABLE /
CALL BACK LATER / UNKNOWN / LIMITED) > recently-proven (lowest priority,
never re-tested without reason).

==================================================
FAILURE CLASSIFICATION AND SCORECARD STATUS
==================================================

Measured telemetry (`ScoutAttemptTelemetry.completionState`: COMPLETE /
FAILED / BLOCKED / INTERRUPTED / UNKNOWN) stays separate from the scorecard's
coaching status (`deriveCombineStatus`):

- COMPLETE + structurally usable report -> READY
- COMPLETE but NOT structurally usable -> LIMITED (ran fine; report didn't
  satisfy the contract — worth another look, not proof of quality)
- BLOCKED, text matches sign-in/credential/"provider not found" -> AUTH ISSUE
- BLOCKED, text matches rate-limit/quota/429 -> RATE LIMITED
- BLOCKED, other -> PROVIDER UNSTABLE
- FAILED (a genuine hard failure) -> CALL BACK LATER, never a cut
- INTERRUPTED / UNKNOWN -> UNKNOWN

`createCombineExecutor` itself promotes a non-zero OpenCode exit to BLOCKED
(instead of FAILED) when its own output matches the same provider/auth/quota
signatures — otherwise a real auth failure would misclassify as a hard
FAILED. **Known limitation, not fixed in V0.3**: one real field FAILED
(`openrouter/cohere/north-mini-code:free`, this environment has no
`OPENROUTER_API_KEY`) surfaced OpenCode's error as `{"name":"UnknownError",
"data":{"message":"Unexpected server error..."}}` — generic JSON, not a
recognizable auth/quota phrase — so it landed in CALL BACK LATER rather than
the more precise AUTH ISSUE. Both are reversible, non-punitive buckets, so
the mission's hard requirement (never CUT FROM TEAM) holds; only the
*specificity* of the classification is imperfect for this one error shape.
Flagged in REMAINING UNKNOWNS rather than chased further.

No status here ever retires a Player. Removal remains outside this module
entirely — nothing in Scout Combine deletes a scorecard, a candidate, or a
Formation/roster entry.

==================================================
SCOUT SCORECARDS
==================================================

`REPORTS/Scout Only/Combine/Scorecards/<candidateId>.json` — one file per
discovered prospect, created on first tryout, merged (never replaced) on
every subsequent one: `firstSeen` never regresses, `totals.*` counters
accumulate, `latestEvidencePaths`/`notes` are bounded, prepended lists (10
and 20 entries respectively) that keep the newest evidence without deleting
history outright. Verified directly (`Combine-7`): running the same
candidate twice keeps the first run's completion count and its `firstSeen`
timestamp intact after a second, failing run.

FIELD COMBINE (run against this real repository)
==================================================

**Run 1** — `Combine__2026-09-17_084604_806_MDT` (aborted, defect found)

The default budget CLI path built `budget: { maxTryouts: undefined,
maxConcurrency: undefined }` (flags simply not passed). `{ ...DEFAULT_BUDGET,
...request.budget }` let those explicit `undefined`s silently overwrite the
defaults; `Array.prototype.slice(0, undefined)` returns the *entire* array,
so instead of 5 bounded tryouts the run began sweeping **all 26 discovered
prospects sequentially** — a real, live-observed retry-storm-shaped defect,
caught only because this Play required running the actual Combine rather
than trusting the unit suite (which only ever passed explicit numeric
budgets). I stopped the run manually after 6 real tryouts had already
completed (3 READY/LIMITED, 1 UNKNOWN via a genuine 5-minute timeout, and 2
more in flight) rather than let it continue.

**Fix** (`src/scout-combine.ts`): the budget merge now resolves each field
individually (`request.budget?.maxTryouts ?? DEFAULT_BUDGET.maxTryouts`),
immune to an explicit-`undefined` key from any caller; the CLI
(`run-scout-combine.mjs`) was also hardened to omit unset flags from the
budget object entirely (defense in depth). New regression test
`Combine-3b` reproduces the exact field shape (`{ maxTryouts: undefined,
maxConcurrency: undefined }`) and asserts the default (5) still holds against
8 discovered prospects.

==================================================
ARCHITECT OPINION — FUTURE OPTIONAL-MODULE / USER-OWNED-PROVIDER BOUNDARY
==================================================

Clean. Discovery is fully unauthenticated (OpenRouter's public catalog;
OpenCode's own zero-credential hosted models) — Sideline never stores, reads,
or requires a credential. Executing an OpenRouter-routed prospect uses
whichever credential OpenCode itself already has configured in the process
environment; there is no Sideline-owned key anywhere in this code. The whole
capability is a standalone CLI (`npm run scout:combine`), never wired into
extension activation, the VS Code UI, or any always-on path — gating it
behind a future Dev Mode toggle or edition check is a single call-site
change, not a redesign. I found no decision in this Play that would close
that door.
