### F1 — BLOCKED "Report ready" is one unreachable predicate (bounded Worker repair)

`src/public/index.html:2048`

```js
const isReportReady = (view) => view?.state === 'finished' && Boolean(view.report) && view.report.acknowledged !== true;
```

`src/public/index.html:2246-2259` handles `case 'couldnt-finish': case 'unknown':` and contains
the correct, deliberate Scout branch:

```js
if (scout && isReportReady(view)) return { glyph: '✓', word: 'Report ready', ... };
return null;
```

`isReportReady` hard-requires `state === 'finished'`. Inside a `couldnt-finish` / `unknown`
case it can never be true. **The branch is dead code**, so the strip returns `null`, the strip
is removed, and the card falls back to its base line — `Scout · Ready`. That is exactly the
symptom the human observed.

The server side is already correct and needs no change:
`src/control-plane/execution-projection.ts:121-123` routes `blocked | failed | interrupted |
not-sent` through `terminalView(..., reportFor(entry?.reports, latest), ...)`, so the
`ExecutionView` for the BLOCKED Qwen Formation **did** carry `report: { path, filename,
acknowledged:false }`. The data arrived. The browser discarded it.

Test coverage confirms the gap rather than contradicting it:
`test/q2-10f-2-completion-report-ready-acknowledgement.test.mjs:578,586` cover Scout
`finished` and `PARTIAL` (which projects to `finished`). No test drives a Scout turn to
`blocked`. `test/q2-10f-3-dad-mode-projection-friendly-labels.test.mjs:70` still asserts the
older `couldnt-finish → return null` shape, which is why the new branch passed review while
being unreachable.

**This is not architectural.** It is a worker-sized repair with a one-line fix shape and a
real regression test.

### F2 — Scout intelligence physically lives inside the extension INSTALL directory

`src/extension.ts:79`

```ts
const scoutDurableReportRoot = context.asAbsolutePath(path.join('REPORTS', 'Scout Only'));
```

`context.asAbsolutePath` resolves against the **extension's own installation folder**. In the
Extension Development Host that folder happens to be this repository, which is why everything
works today and why the evidence tree is sitting in the working copy. For an installed VSIX it
resolves to something like `~/.vscode/extensions/<publisher>.<name>-<version>/REPORTS/Scout Only`,
which VS Code **replaces wholesale on every extension update** and which is not a user-data
location.

Consequences:

* Every Combine scorecard, Player Verification record and durable Formation is destroyed by a
  routine extension upgrade.
* Packaging is ambiguous and wrong either way: `package.json:22` `files[]` lists only
  `out/**`, `src/public/index.html`, `README.md`, `LICENSE` (so npm would omit the tree), while
  `.vscodeignore` does not exclude `REPORTS/**` (so `vsce` would ship *this developer's*
  scorecards to every user as if they were that user's field evidence).
* The correct VS Code home for Sideline-owned, per-user, update-surviving state is
  `context.globalStorageUri`. It is not used anywhere for Scout.

### F3 — Scout capability has no product bootstrap path at all

Eligibility comes from exactly two evidence readers:

* `src/scout-combine-formation-bridge.ts:92` — one candidate per
  `<root>/Combine/Scorecards/*.json`.
* `src/scout-formation.ts:56` — the built-in AntiGravity candidate reads
  `<root>/Player Verification/antigravity.json`.

Both files are produced **only** by developer CLI tools. A repository-wide search finds no
caller of `runScoutCombine` or `runCoachRefresh` inside `src/` — the only callers are
`tools/scouts/run-scout-combine.mjs` and `tools/scouts/run-coach-refresh.mjs`, and both hardcode

Therefore, on a fresh install with zero scorecards:

Scout is today a developer-seeded capability. It is not yet a shippable one. Related: the
Qwen scorecard was suspended to `RATE LIMITED` by the field test (see F4 evidence below), and
nothing in the product can ever restore it, because only the CLI runs Combine.

Scout also requires the OpenCode CLI on the host (`src/scout-combine-discovery.ts` /
`resolveOpenCodeExecutable`). That is a second undeclared install prerequisite.

C. RECOMMENDED SCOUT INTELLIGENCE OWNERSHIP MODEL
==================================================

**Decision: two roots, one identity rule.**

```text
GAME-OWNED ARTIFACTS                    SIDELINE-OWNED SCOUT INTELLIGENCE
what a Player produced for this Game    what Sideline knows about its own Scout capability
lives under the Game's Reports root     lives under the Sideline Scout Intelligence Root
discovered by the Game's report globs   discovered by ONE Sideline-scoped source (§E)
belongs to the Game                     belongs to the installation, shared across Games
```

`REPORTS/Scout Only/` keeps its shape — `Combine/{Runs,Scorecards}/`, `Formations/<id>/`,
`Player Verification/` — and gains `Work/` (§ F4 repair). What changes is only *where that root
is anchored*:

```
context.globalStorageUri / "Scout Intelligence" / …
```

not `context.asAbsolutePath(...)`. `globalStorageUri` is per-user, Sideline-owned, writable,
survives extension updates, and is never confused with a Game or a repository.

**Do not duplicate the tree into every Game.** RM-1 shows six Stadiums each currently exposing
one shared Scout capability from one shared root; duplication would multiply tryout cost by
Game count, fracture the depth chart, and make a receiver READY in one Game and not another for
no truthful reason.

**Game identity survives separation because it travels in the artifact, not the path.**
That is already half-built: `registerScoutFormationReport` stamps `gameId`, `clientRef`,
`playerInstanceId: 'scout'`, `playerType: 'scout'`, `provider: 'scout-formation'`, `at`
(`stadium-client.ts:1203-1218`). The change §E recommends is to move those same facts **into the
file** so the artifact is self-describing and no in-memory object has to survive anything.

One consequence to accept deliberately: a Formation folder under the Sideline root may be
attributed to a Game that no longer exists on this machine. That is correct. Scout evidence
outlives a Game the same way game film outlives a season. Incoming filters by `gameId`
(`stadium-client.ts:358`) and simply will not show it; nothing breaks.

D. PARENT / CHILD ARTIFACT CONTRACT
==================================================

**One Dad-facing parent. N supporting receiver artifacts. Only the parent is ever publishable.**

That is already the behaviour; make it a stated invariant so no future scanner enumerates
children into Incoming.

### Minimal identity/provenance fields required

Almost everything already exists. The parent needs exactly these, and nothing else:

| Field | Meaning | Status |
|---|---|---|
| `formationId` | **the logical report ID** | exists (`FormationCompletion.formationId`) |
| `gameId` | reconnaissance target | exists in registration — must move into the file |
| `clientRef` | the exact Play this answers | exists in registration — must move into the file |
| `playerInstanceId` / `playerType` | `scout` / `scout` | exists |
| `provider` | `scout-formation` | exists |
| `at` | Formation end time | exists |
| `children` | receiver artifact paths, **relative to the Formation folder** | derivable from `attempts[].durableReportPath`; add to the already-written `FORMATION-COMPLETE.json` |

**Do not invent a second report ID.** `formationId` is already unique, filename-safe,
timestamped and zone-stamped (`freshFormationId`). **Do not invent a child registry.** Children
are addressed by path relative to their parent's own folder — the folder *is* the container.

### The mechanism, in one sentence

Write the existing `sideline-provenance` HTML comment into `FORMATION-RESULT.md`.

`src/report-provenance.ts:75` `formatReportProvenance` already renders that exact line, and
`work-ledger.ts` `recordReports` already treats explicit provenance as authoritative over
timing attribution, even for reports that predate the Ledger. One small gate must be widened:

`src/report-provenance.ts:46`

```ts
const INSTANCE_ID = /^[a-z]+-[0-9a-f]{8}$/;   // drops the logical id 'scout'
```

That regex was written when every Player instance was a minted seat. A logical/virtual Player's
stable id must be admissible. This is the one line that makes a self-describing Scout parent
possible.

**Why self-describing beats a durable registry:** it removes a whole class of disagreement
between an in-memory index and the disk it describes, it survives extension restarts, machine
moves and backups for free, and it is the same mechanism ordinary Controlled Players already
use. A persisted `scoutFormationReports` map would be a second copy of the truth.

==================================================
E. REPORT DISCOVERY / SOURCE CONTRACT
==================================================

**Decision: yes — introduce a report SOURCE, but not a report-source framework.**

### Why explicit registration is no longer sufficient

S30's explicit registration answered "how does a non-Game artifact reach Incoming?" correctly,
and the field proved it. It does not answer "how does it *stay* reachable?" Three independent
forces now converge:

1. The registry is memory-only and capped at 10 (`stadium-client.ts:170,1220`).
2. The artifact is physically outside every Game scan root, so no watcher, no rescan
   (`/api/reports/rescan`) and no `ReportPublisher` pattern can ever re-find it. Registration is
   not an accelerator over discovery — it is the *only* path.
3. F2 will move that root. A root that moves needs a named owner, not five call sites.

Two of those three are new information since S30. That is what earns the abstraction.

### The smallest viable contract

```ts
/** One place Sideline-owned (non-Game) report artifacts come from. */
interface ReportSource {
  readonly id: string;                 // 'scout-intelligence'
  readonly agentLabel: string;         // 'Scout' — the Incoming badge
  /** Absolute roots this source owns. Never a Game root. */
  roots(): readonly string[];
  /** Parent artifacts only. Never children, never every file under the root. */
  list(gameId: string): Promise<CoachReportItem[]>;
}
```

Implementation shape, deliberately boring:

* One implementation: `ScoutIntelligenceReportSource`, globbing
  `<scoutRoot>/Formations/*/FORMATION-RESULT.md`, parsing each file's own provenance marker,
  filtering by `gameId`, newest first, bounded.
* Merged at **the merge point that already exists** — `sendReportSnapshot`
  (`stadium-client.ts:355-361`) — replacing the `scoutFormationReports` Map with the source's
  result, keeping the exact same "Sideline-owned reports first, then scanned reports, dedupe by
  path" ordering that S30 proved.
* Watched by **the watcher that already exists** — `ReportPublisher`
  (`src/report-publisher.ts`) — by contributing the source's roots as additional patterns.
  Nothing new debounces, nothing new serializes.
* Keep S30's synchronous post-Formation registration as a **latency optimization only**: it
  makes the parent appear instantly instead of one watcher tick later. It stops being the
  durability mechanism, so it stops being a single point of failure.

Nothing else changes. `CoachReportItem` is unchanged. Incoming is unchanged. The Ledger is
unchanged. The browser is unchanged. Assistant Coach is unchanged. That is the test for
whether an abstraction is small enough.

### Alternatives considered

| Alternative | Why rejected |
|---|---|
| Copy `FORMATION-RESULT.md` into the Game's Reports root | Makes Scout evidence Game-owned, contradicting S27; duplicates bytes; breaks one-logical-report identity when one Formation informs two Games; requires write access to a Game Scout must only read. |
| Persist the `scoutFormationReports` Map to disk | Second copy of truth that can disagree with the filesystem; helps only Scout; does not survive a machine move; the artifact still cannot explain itself. |
| Add the Scout root to `coach.reportGlobs` | Exactly the "Dad configures `REPORTS/Scout Only`" failure the Play forbids; also enumerates receiver children into Incoming; also re-triggers the multi-Game glob regression `src/report-glob-policy.ts` was written to fix. |
| A general pluggable source registry with priorities and capabilities | No second source exists. Build it when there is one. |

F. ASSISTANT COACH INTEGRATION
==================================================

### How it works today, exactly

1. Coach Routines evaluates due routines per Game and, in Dev Mode, projects one bounded
   envelope: `RoutinesProjection.handoff = { text, deliveries, names }`
   (`src/control-plane/coach-routines.ts:481-499`), rendered by `buildStrategyBoardEnvelope`
   (`:613`) — "reread these canonical sources, say plainly what you could not open."
2. The browser shows only `✓ AI Assistant Coach brief included` plus a `View brief` disclosure
   (`index.html:961-963`, `syncIncomingCoachHandoff` at `:5011`).
3. **Copy Report** emits `handoff.text + reportText` (`index.html:5818-5819`) and, on success,
   marks the routine delivered.
4. Separately, in-product continuation prepends `buildScoutContinuationPreamble` to the next
   Player's Play, naming the exact Scout report path.

There is exactly one Assistant Coach pipeline and Scout already rides it.

### Recommended contract — three small things, no second system

1. **The Formation parent IS the Assistant Coach payload.** Once §E makes it durable and
   selectable, Copy Report already produces `brief + FORMATION-RESULT.md`. Nothing to build.
2. **Children are reachable, never included.** `resultMarkdown` already ends with
   `Evidence: <durablePath>` (`scout-formation.ts`), which is precisely the "drill in only when
   needed" affordance. Keep that line and keep it valid across the §C root move. Adding
   `children` to `FORMATION-COMPLETE.json` (§D) makes it machine-followable without putting one
   byte more in front of Dad.
3. **Never add Scout folders as Coach Routine `sources`.** That would put internal Scout paths
   into a Dad-facing configuration surface — the exact prohibition in this Play.

### One risk to resolve with field evidence, not design

`buildScoutContinuationPreamble` hands the continuing Player an **absolute path outside the
Game root** (true today for every Game except SidelineCoach itself; true for all Games after
the §C move). A Controlled Claude/Codex launched with the Game as its working directory may not
be permitted to read it. If field evidence shows that, the fix is to carry a bounded excerpt of
the parent in the preamble rather than only a path — not to move Scout evidence back into the
Game. Flagged as an UNKNOWN (§L), deliberately not decided here.

H. VIRTUAL / ORCHESTRATED PLAYER CONTRACT
==================================================

### What actually blocks roster-native Scout (smaller than it looks)

`PlayerInstanceBook` (`src/player-instances.ts:65`) is already process-agnostic: seats,
identity, `onField`, retire. It assumes nothing about a PID. The genuine blockers are three:

1. `PlayerId` is a closed union of four literals (`player-adapters.ts:11`) and
   `PlayerInstanceBook.project()` calls `getPlayerAdapter(record.playerType)!`
   (`player-instances.ts:132`) — a non-adapter type would crash on the `!`.
2. `getRoutingCapabilities` (`player-roster.ts:1246-1311`) branches exhaustively over
   terminal / controlled / legacy transports and has no branch for "ask a descriptor."
3. `isPlayerProvenance` hardcodes the same four types (`player-instances.ts:37`) — but that
   governs **terminal shell-PID provenance persistence only**, which a virtual Player never
   uses. Not actually a blocker; must simply be left alone.

Everything else already works. Notably `removePlayer` (`player-roster.ts:441`) falls straight
through to `book.retire()` when there is no controlled binding and no terminal — Remove works
for a virtual Player with **zero** changes.

### The contract

**Separate the three things that are one boolean today.**

```text
ENTITLEMENT   may this user use Scout at all?        enabled() / future licensing
MEMBERSHIP    is Scout on this Game's Team?          PlayerInstanceBook record, persisted
READINESS     can it run a Play right now?           depth-chart evidence, NEVER persisted
```

Today all three collapse into `capability() === undefined`, which is why F6 exists and why
Bench/Remove are impossible to express.

```ts
/** A Player with no process, no terminal, no PID. It knows how to say whether it can
 *  work right now, and how to do one logical turn. Nothing else. */
interface VirtualPlayer {
  readonly instanceId: string;      // stable logical id, e.g. 'scout' — not a minted seat
  readonly playerType: string;      // open vocabulary; not PlayerId
  readonly displayName: string;
  /** Readiness truth, recomputed on every snapshot. Never cached, never persisted. */
  capability(gameRoot: string): PlayerRoutingCapability | undefined;
  /** One logical turn; may fan out to N workers internally. */
  execute(objective: string, gameRoot: string, options?): Promise<VirtualTurnResult>;
}

interface VirtualTurnResult {
  readonly outcome: 'COMPLETE' | 'PARTIAL' | 'BLOCKED' | 'FAILED' | 'UNKNOWN';
  readonly reportPath?: string;      // the ONE parent artifact (§D)
  readonly activitySummary?: string; // "3 Scouts fielded"
}
```

`ScoutPlayerAdapter` already implements this shape almost exactly (`capability()`, `execute()`,
`availability()`). The interface is a description of what was built, not a redesign.

| **Team membership** | `adoptVirtual(instanceId, playerType, preferredSeat)` beside the existing `adoptControlled` (`player-instances.ts:90`), which already admits an externally-supplied Sideline-owned id. Scout keeps the literal `'scout'`, so `scout-player-contract.ts`, provenance, router and UI are all untouched. | ~15 lines |

latent crash. `isPlayerProvenance` keeps its four-type regex, correctly, because virtual Players
never persist shell provenance.

==================================================
I. FUTURE DEPTH-CHART COMPATIBILITY
==================================================

Nothing below is built here. These are the three properties that must not be destroyed.

**1. Observation stays separate from inference and policy.** Scorecards record what happened
(`totals`, `routeAttempts`, `notes`, `evaluationEvidence`). `eligible()` is a bare
READY / not-READY gate (`scout-formation.ts:311-318`) — no scoring anywhere. Keep ranking out of
the scorecard. When a ranker arrives it belongs at `selectFormation` as a **function**, which is
already the seam the file's own breadcrumb reserves.

**2. Infrastructure evidence must never become quality film.** This is already enforced at the
write: `recordFormationInfrastructureBlock` (`scout-combine.ts:317-335`) suspends
`currentStatus`, writes `availabilityEvidence.state = 'FIELD_BLOCKED'`, and explicitly leaves
`totals` alone. The Qwen scorecard on disk proves it. A future Team-specific depth chart must
therefore read **two** inputs, never one:

```text
quality film      totals, routeAttempts, evaluationEvidence   → "how good is this Player for this work?"
situational truth currentStatus, availabilityEvidence         → "can it play right now?"
```

The AI Usage Scorecard (5-hour capacity, weekly capacity, reset times, local time) maps cleanly
onto the **situational** side and must never touch the quality side. That is the whole
integration seam; build nothing now.

**3. Film needs a home that is neither the ledger nor the scorecards.** `InstanceWorkLedger`
already holds exactly the right lineage — Play → Player → model/effort → turn → truthful
outcome (`work-ledger.ts:141-180`) — but it is in-memory, bounded to 10 recent plays, and
serialized only for crash recovery. Do **not** widen it into an archive; that would make a
Control Plane restart a data-loss event and give orchestration memory an unbounded cost.

Record the decision now so a future Play does not have to re-derive it: **game film belongs in
a new durable, append-only lane under the Sideline Intelligence root**, written from the same
terminal-turn evidence the Ledger already receives. Scorecards are *per-candidate current
state*; film is *per-outcome history*. Conflating them is the trap, because a rate limit would
then overwrite a quality record.

The §H membership split is what makes any of this possible: a Player that is on the Team but
`unavailable` can still own film. A Player that vanishes when it is busy cannot.

6. **Formation size bound of 3.** `selectFormation` throws above 3 and the default is

   exists on this machine. Recommended behaviour is to keep it (Incoming filters it out
   naturally). No retention or pruning policy is proposed; none is needed yet.
8. **Sample size.** Every READY receiver on disk has `starts: 1, completions: 1`. One sample is
