==================================================
SECURITY / REDACTION POLICY
==================================================

**Primary control is structural (allow-list), not regex.** Only two things are ever read from a ControlEvent: the
`kind`-derived category and the event's own short `summary` string. Env objects, headers, raw provider frames, tool-
argument objects and protocol metadata are never read (the LPT-3 / LPT-7 tests feed events carrying `env`/`headers`/`raw`
and assert none of it appears).

**Redaction is defense in depth for the free text that remains** (assistant messages, command lines, tool/file targets,
failure details). It is applied twice: at the source (so secrets never cross the WS) and again in the daemon store (so
the browser boundary never trusts the sender). Idempotent, tested.

Redacted (pattern classes): PEM private key blocks; `Authorization`/`Proxy-Authorization` values; `Bearer …`;
`sk-`/`pk-`/`rk-` keys (incl. `sk-ant-`, `sk-or-v1-`, `sk-proj-`); GitHub `ghp_/gho_/ghu_/ghs_/ghr_/github_pat_`; AWS
`AKIA/ASIA`; Google `AIza`; Slack `xox*`; `npm_`; JWTs; `scheme://user:pass@`; secret-named query parameters; CLI flags
`--api-key/--token/--password/--secret/--auth…`; `NAME=value` / `NAME: value` / JSON `"name": "value"` where the name
contains api-key/token/secret/password/credential/private-key/access-key/auth/cookie/bearer; and long opaque
letter+digit runs (≥40 chars, no path separators).

**Bounds:** command/tool/other lines ≤ 240 chars, single line; messages ≤ 1200 chars; ANSI and control characters
stripped; regex input capped at 8,000 chars before matching.

**Session identity:** the provider session ref is never sent. `sessionKey` = first 8 hex of SHA-256 of it — enough to
distinguish sessions, useless for resuming one.

**Gating (least exposure):** the daemon stores and broadcasts NOTHING unless Dev Mode AND View Player Terminal are both
on. Turning either off discards retained activity. Enabling mid-Play shows only later activity.

**Residual risk — stated plainly:** pattern redaction cannot prove absence of secrets in free text. A novel token format,
or a secret an assistant writes in prose with no recognizable shape, can pass. It is mitigated by opt-in (two settings),
localhost + token auth, length caps and the structural allow-list — not eliminated. A secret split across two streaming
fragments is caught once the daemon joins them, but a partial prefix may already have been broadcast in the earlier
fragment (a few characters).

==================================================
DATA ALLOWED TO THE BROWSER
==================================================

Per line: `seq` (daemon-assigned, monotonic per Player), `at` (timestamp), `category`
(`working|message|command|tool|declined|result|channel`), sanitized `text`. Envelope: `gameId`, exact `instanceId`,
daemon `epoch`, opaque `sessionKey`.

Mapping: turn accepted/started → `working`; turn completed/failed/interrupted/unknown → `result`; progress message /
command / tool → same; request declined → `declined`; channel lost/exited → `channel`. `settings` and channel-`ready` are
not activity.

==================================================
DATA PROHIBITED FROM THE BROWSER
==================================================

Raw provider payloads or frames; environment objects or values; HTTP headers / authorization values; tool-argument
objects (only the compact command line or `name path` summary the adapter already builds); provider metadata; the raw
provider session ref; anything not in the allow-list above; anything from a Game other than the selected one.

==================================================
RETENTION
==================================================

- **Daemon:** in memory only; 300 lines per Player; 64 Players tracked (oldest evicted). Lost on daemon restart.
- **Browser:** in memory only; 300 lines per Player (mirrors the daemon). Dropped when either gate closes or the Game
  changes. No disk logging.
- **Ordering / dedup:** entries are idempotent by `seq`. Replays, re-renders, reconnect backfill overlap and streaming
  growth update the same line and never duplicate (LPT-11). A `hello` (reconnect) re-merges the daemon's buffer for
  expanded terminals. A daemon restart changes the `epoch`; the browser then starts a fresh transcript instead of
  merging colliding `seq`s (LPT-20).

==================================================
COPY ALL / COPY NEW
==================================================

- **Copy All:** every retained line for this exact Player + provider session, as human-readable text:
  `[HH:MM:SS] COMMAND  git status`. Never JSON. Enabled only when lines exist.
- **Copy New:** lines added since the last **successful** Copy All or Copy New for this Player + session. Streaming
  growth after a copy contributes only the appended text. Disabled with the tooltip "No new activity since your last
  copy" when nothing is new.
- **Cursor scoping:** per (`instanceId`, `sessionKey`) bucket — not global. Claude 1's copy never moves Claude 2's cursor.
  A new provider session (or new daemon epoch) starts a fresh transcript and a fresh cursor.
- **Failure safety:** the payload and cursor target are captured before the clipboard call; the cursor advances only
  after the write resolves, never backwards, and only within the same transcript. A failed write shows "Copy failed" and
  leaves the same lines eligible (LPT-13; I mutation-tested this by moving the cursor advance before the write — the test
  failed, then I restored the code).
- Feedback: the button briefly reads "✓ Copied" / "Copy failed" (same idiom as Copy Report).
- **Persistence:** browser-session only. A page reload resets cursors. Not persisted across browsers.

==================================================
SESSION / COMPLETION BEHAVIOR
==================================================

- **Session:** a different provider session for the same Player starts a fresh view/cursor; canonical work and report
  history are untouched.
- **Completion:** the terminal is now offered on `working`, `starting` **and `finished`** cards, so an expanded terminal
  survives a Play finishing for as long as the existing strip does (the ~30 s rich-Finished window, or longer while a
  report is unacknowledged) and remains readable/copyable. No fake "still running" state.
- **Limit:** once the strip disappears (quiet phase), the terminal disappears with it; the retained lines remain in
  memory and reappear when the Player next has an active strip. Keeping a terminal on an idle card would mean widening
  the strip lifecycle — not attempted.

UNKNOWNS / LIMITS
==================================================

- **Live provider behavior is unobserved.** Everything is proven against fakes shaped like the real events.
- **Codex delta rate/shape** unverified; token-level deltas mean many SSE events per message (each is small, local).
- **Redaction is best-effort** (see policy). Over-redaction is possible on purpose (e.g. `tokens: 12`, a 40+ char
  opaque identifier).
- **Legacy `CoachServer` (`src/server.ts`)** also serves `index.html` but has no `/api/preferences` and is not fed by
  this rail, so the terminal is a daemon-served-page feature. I did not investigate that server's current role.
- **SSE broadcast reaches every connected client** (existing behavior; Scout noted no per-subscription scoping). The
  browser filters by Game and the daemon only broadcasts when the feature is on.
- **Enabling mid-Play** shows only later activity; earlier lines were not retained.
- **Multiple browser tabs** each keep their own copy cursors.
- **Quiet-phase terminal** disappears with the strip (above).
