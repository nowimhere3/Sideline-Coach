==================================================
RESULT
==================================================

PASS. A Scout continuation whose second dispatch is queued for a busy
instance now retains that lineage: when the Play Queue later releases it to
its real turn, the SAME `ScoutContinuationRecord` binds that exact turn
identity, and when the turn finishes, the existing terminal-turn handler
closes the SAME record truthfully — instead of it remaining stuck reading
`queued` forever, as S19.0's own REMAINING UNKNOWNS section named. No second
queue, no polling loop, and no changes to the queue or continuation state
machine's existing shapes beyond one new optional identity field.

==================================================
ROOT CAUSE (confirmed by reading current source, not assumed from the report)
==================================================

`ScoutContinuationLedger.recordContinuationOutcome(gameId, turnRef, state,
summary)` already correctly matched records in EITHER `received` or `queued`
state by `continuationTurnRef` — that part was already right. The actual gap:
when a continuation's second dispatch is queued
(`router.dispatch()` returns `{status:'queued', queueItemId, turnRef:
undefined}`, because nothing has run yet), `recordContinuationDispatch()`
stored the state as `queued` but had **no field at all** linking the record
to the Play Queue item it was waiting on. `PlayQueue`'s `QueuedPlay` type
likewise carries no continuation identity. So when `daemon.ts`'s
`drainQueue()` later actually released that exact queue item — a real
`router.dispatch({..., queueItemId: head.id})` call that DOES return a real
`turnRef` on success — there was no way to find which continuation record (if
any) that release belonged to, and `continuationTurnRef` stayed `undefined`
forever. The existing terminal-turn matcher could never find a match, so the
record silently stayed `queued` even after the Play it represented finished.

==================================================
FIX
==================================================

One new optional field, one new ledger method, two call sites:

- `src/control-plane/scout-continuation.ts`
  - `ScoutContinuationRecord.continuationQueueItemId?: string` — set only
    when the continuation's dispatch result was `queued`.
  - `recordContinuationDispatch()` now accepts and stores `queueItemId`
    (cleared to `undefined` for any non-`queued` status, so an immediately-
    received continuation never carries a stale queue reference).
  - New `bindQueueRelease(queueItemId, turnRef)`: finds the record whose
    `continuationQueueItemId` matches AND whose state is still `queued`,
    sets `continuationTurnRef` to the real released turn, and transitions
    `state` to `received` (the same state an immediate dispatch reaches) —
    so the existing `recordContinuationOutcome()` matcher needs no changes
    at all. A non-matching `queueItemId`, or a record that already left
    `queued` (already bound, or the whole record already finished), is a
    no-op — idempotent by construction, not by an added guard flag.
- `src/control-plane/daemon.ts`
  - `continueAfterScout()`: passes `queueItemId: result.queueItemId` into
    `recordContinuationDispatch()` (the value `router.dispatch()` already
    returned; nothing new computed).
  - `drainQueue()`: after a successful release (`result.success` with a real
    `result.turnRef`), calls `this.scoutContinuations.bindQueueRelease(head.id,
    result.turnRef)` — one line, in the exact branch that already marks the
    Play Queue item `complete()`.

No changes to `PlayQueue`/`play-queue.ts` at all — the queue itself remains
completely unaware that some of its items happen to belong to a Scout
continuation, exactly as instructed ("do not redesign the queue or
continuation architecture"). The `/api/status` continuation projection
(`daemon.ts`'s hand-picked `scoutContinuations` field list) already excludes
internal plumbing like this by design; `continuationQueueItemId` was not
added to it and is not customer-visible.

==================================================
TRUTHFULNESS
==================================================

- `queued -> received -> completed/partial/blocked/failed/unknown`, never a
  shortcut to `completed`.
- `interrupted` still maps to `failed` (existing behavior, unchanged,
  reconfirmed for the queue-release path specifically).
- A record that never gets released (queue item still waiting) is untouched
  by this change — it correctly stays `queued`, truthfully reflecting reality.
- Duplicate/replayed release or terminal-turn events cannot double-bind or
  reopen an already-finished record: `bindQueueRelease` only acts on a
  `queued` record, and `recordContinuationOutcome` only acts on `received`/
  `queued` records — a `completed` record matches neither.
