## 2. Exact root cause: why no Android notification arrived

Three independent causes. Any one of them was enough to block delivery.

1. **The phone never received alarm events.** `deliverAlarmEvent` called `broadcast('ai-alarm', event, /*localOnly*/ true)`. A relay-paired phone is a `remote-device` principal, so it was skipped even with the page open in the foreground.
2. **Android Chrome can't show page-constructed notifications.** Android Chrome does not support `new Notification()`; it throws `TypeError` and requires `ServiceWorkerRegistration.showNotification()`. The existing `try/catch` logged that error to the console, so the failure was silent.
3. **Nothing could deliver in the background.** There was no service worker and no Push API. Once Chrome backgrounded or closed the page, the SSE stream stopped and nothing could reach the tray.

"Permission granted + preference ON" therefore produced **zero** Android notifications in every page state:

| State | Before | After |
|---|---|---|
| Page foregrounded | none (causes 1 + 2) | push → service worker → tray |
| Page backgrounded | none | push → service worker → tray |
| Chrome backgrounded | none | push → service worker → tray (Chrome wakes the worker) |
| Page closed | none | push → service worker → tray |

## 3. Deployment and security findings

- Web Push needs a secure context and a same-origin service worker. **Both are satisfied by the relay origin.** No change to the relay, Tailscale, pairing, or the security boundary was needed.
- The service worker script request (`GET /sw.js`) passes through the relay's in-process adapter like any other path. That adapter still requires the paired-device cookie (`sl_dev`) for everything except the pair page, and a same-origin service worker fetch sends that cookie. The route is classified `public` only so it doesn't consume Remote Minutes and so it matches `/index.html`.
- Web Push delivery goes through the browser vendor's push service (FCM for Chrome/Android). **This is built into every Chrome installation. It needs no account, has no cost, and adds no third-party SaaS.** Payloads are end-to-end encrypted (RFC 8291), so Google sees only ciphertext and metadata. No COACH REVIEW trigger was hit.
- No new npm dependency. VAPID and aes128gcm use only `node:crypto`.

## 6. Service worker behavior (`/sw.js`)

- `install` → `skipWaiting`; `activate` → `clients.claim`. It caches nothing and has **no `fetch` handler**, so it can't affect app traffic.
- `push`: parses JSON, bounds the title to 60 characters and the body to 180, strips control characters, validates the tag against `[A-Za-z0-9_:-]{1,80}`, and always calls `showNotification`. Chrome requires a notification for every push, so an unreadable payload gets a generic one.
- `renotify: false` and the same tag as the page fallback mean a duplicate replaces the existing notification silently.
- `notificationclick`: closes the notification, focuses an open Sideline window on the same origin, or otherwise opens `/`. **The tap target never comes from the payload.**
- Served with `Content-Type: text/javascript`, `Cache-Control: no-cache` (so a Developer Refresh can't leave a stale worker installed), and `nosniff`.

## 7. PushSubscription lifecycle

- **Enable (toggle ON):** permission (existing flow) → `GET /api/push/config` (public key) → register `/sw.js` → `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })` → `POST /api/push/subscriptions` → the daemon validates and persists → the page shows "registered" **only after the daemon confirms**.
- **Page load with the channel already ON:** registers quietly, once per page load, which is idempotent. This covers enabling on another device, recovering after the daemon dropped a dead subscription, and a rotated VAPID key: a subscription whose `applicationServerKey` differs from the daemon's is unsubscribed and replaced.
- **Disable (toggle OFF):** `POST /api/push/unsubscribe` plus browser `unsubscribe()`, then the global channel is saved OFF.
- **Device revoked on desktop (`DELETE /api/devices/:id` or revoke-all):** that device's subscriptions are deleted along with its credential.
- **Push service rejects (404/410 gone, 403 wrong VAPID key, or an undecodable browser key):** the subscription is removed permanently. **429/5xx or network errors:** kept, with `lastFailure` recorded.
- `pushsubscriptionchange` is not handled. The page-load re-registration covers it.

## 8. Server-side delivery, persistence, and VAPID

- **Owner model:** each subscription records `owner` as `local` (desktop admin session) or `device:<pairedDeviceId>`, plus a label such as "Android · Chrome". Subscriptions are never keyed to a Game or Player. Delivery is install-wide.
- **Persistence:** `~/.sideline/push/subscriptions.json`. It follows the same pattern as `remote/devices.json`: 0700 directory, 0600 temp file, atomic rename. It is capped at 20 entries (oldest evicted) and validated on load. Nothing is written to Routing Film, HealthAuthority, alarm state, resource policy, or Game files.
- **VAPID:** a P-256 key pair is generated on first use at `~/.sideline/push/vapid.json` (0600). An unusable file is quarantined to `.bak` and regenerated; devices then re-register automatically. The private key is used only in `vapidAuthorization()` inside the daemon. **Browsers receive only the public key**, and `GET /api/push/config` returns exactly `{ success, publicKey }`. The JWT sets `aud` to the push origin, `exp` to 12 hours (the RFC cap is 24), and `sub` to `https://mysidelinecoach.com`.
- **Headers:** `TTL: 21600` (6 hours), `Urgency: high` (so Android Doze delivers promptly), `Topic` derived from the event id (the push service collapses queued duplicates), and `Content-Encoding: aes128gcm`.
- **SSRF guard:** a paired phone supplies the endpoint URL, so the daemon accepts only HTTPS on the default port with no credentials, and only for FCM, `android.googleapis.com`, Mozilla autopush, WNS (`*.notify.windows.com`), and Apple (`*.push.apple.com`). `localhost`, IP addresses, look-alike hosts, and other ports are rejected.

## 9. Alarm-event integration and dedupe

- **One call site:** `deliverAlarmEvent` → `webPush.deliverAlarm(event, prefs.alarms)`. It is fire-and-forget; errors are caught and logged, so VS Code and SSE delivery are unaffected.
- **Gates** mirror the existing page-side `browserAlarmPolicyAllows`: `enabled && channels.browser && (reset ? notifyOnReset : notifyOnThreshold)`. **No thresholds, telemetry, or health state are read.** A test asserts that `web-push.ts` references none of them.
- **AlarmEngine, HealthAuthority, ResourcePolicy, hysteresis, and reset detection are untouched.**
- **Dedupe:**
  1. AlarmEngine already emits each transition once, with a stable id and persisted state.
  2. The notifier keeps a bounded set of event ids it has pushed (200), so a replayed id is never pushed twice.
  3. It sends exactly one push per registered subscription.
  4. `Topic` collapses duplicates queued at the push service.
  5. The page skips its own notification when this device is push-registered (one path per device).
  6. The same tag plus `renotify: false` means any remaining collision replaces silently.
- **Payload** is exactly `{ v, kind, title, body, tag, url:'/' }`. The body is the AlarmEngine's own bounded message, for example "Claude 5H quota low · 19% remaining · resets in 2h", truncated at 180 characters. It never contains prompts, reports, terminal output, credentials, or paths.
- **Parity note:** the browser channel has always delivered every AlarmEngine event type that passes its gates, so `recovered` and `stale` events also push. This is unchanged product behavior, now reaching the phone.

## 13. Known limits (not blockers)

- Alarms originate on the desktop daemon. If the computer is asleep or off, no alarm fires. This is the same as every alarm channel today.
- A phone that registers from **two origins** (relay and Tailscale `ts.net`) gets two subscriptions, because service workers and tags are per origin, so it could see two copies. Tailscale is stopped today, and the relay is the product path.
- `ai-alarm` SSE remains local-only. On the phone, push replaces the in-page toast rather than adding to it.
