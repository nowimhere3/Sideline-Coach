## Controlled Claude architecture

- **One Coach-owned Claude session per Player instance, driven one Play at a time through structured print mode:**
  ```
  Play → claude -p --input-format stream-json --output-format stream-json --verbose
         --permission-mode acceptEdits --permission-prompts none
         (--session-id <uuid> | --resume <uuid>) [--model <alias>] [--effort <level>]
       → stdin: {"type":"user","message":{"role":"user","content":"<Play>"}}
       → stdout: system/init → assistant(text | tool_use) → system/permission_denied → result
  ```
- **One process per Play, not one long-lived process:** a process fixes its model at launch, so per-Play model/effort (MANUAL and AUTO) needs a launch per Play. This is also exactly the Q2.10B-proven, settings-safe path.
- **Shared runtime:** `StructuredPrintControl` / `StructuredPrintFactory` implement the existing provider-neutral `PlayerControl` / `PlayerControlFactory` contract and plug into `PlayerControlHost.register('claude', …)`. There is no Claude-shaped fork: bindings, the delivery guard, pending-Play durability and restore concurrency are the Codex host's.
- **Provider syntax** is isolated in `claudeDialect()`: args, frame parser, session check, capability probe.

## Controlled Claude implementation

**Open:**
- Verify the contract (`--help` terms, `--version`).
- Mint the session id (`randomUUID`). No process runs, because Claude persists nothing until a Play runs.
- Record the binding (`adapter: claude-print-stream`).

**Deliver:**
- Spawn in the Game root and write the prompt frame.
- **Accepted** on `system/init` for the exact session. If init is slow, Coach accepts after 8 s, because the Play has already crossed on stdin.
- Then emit `started`, progress events (message / command / tool), and `request: declined` for each permission denial.
- `result success` → **completed**, with a summary such as "Completed · 1 action needed approval and was skipped". An error result → **failed**. Exit without a `result` → **unknown**, never completed.

**Session handling:**
- "Session ID … already in use" at start (a Play ran but its record was lost) → continue with `--resume` once.
- "No conversation found" → the channel is lost and restore decides truthfully.

**Capabilities:**
- Claude's own local answers, `claude -p /model` and `/effort` (no model call), run from the OS temp folder: models `opus / sonnet / haiku / fable` (Claude's default is marked) and efforts `low / medium / high / xhigh / max` (`auto` excluded).
- Recorded as the `claude` capability, so `projectInstanceControls` yields **available**, not requires-proof.

**Interrupt:** `interrupt()` kills the process tree and the turn becomes **interrupted**. It is contract only; no UI yet.

**Environment:** `CLAUDECODE` is removed from the child environment, so a Stadium started from a Claude session never makes the Player think it is nested.

## Controlled AntiGravity architecture

Same shared runtime, `antigravityDialect()`:

```
Play → agy --input-format stream-json --output-format stream-json --mode accept-edits
       --conversation <id> --print-timeout 24h [--model <variant-id> | --effort <level>] -p=
     → stdout: init (conversation_id) — Coach verifies the id — then stdin:
       {"event":"user","message":{"role":"user","content":"<Play>"}}
     → step_update (agent_response text_delta | tool) → result (SUCCESS | ERROR, denied_actions)
```

**Q2.10C discoveries that shaped the design:**
1. **Input shape:**
   - `-p` takes a value, so print mode uses `-p=` with stream-json stdin.
   - The stream message needs `event:"user"` plus a `message` object (not a string).
   - Found from the CLI's own decode errors and binary strings; verified live.
2. **`--print-timeout` defaults to 5 minutes.** Real Plays run longer, so Coach passes `24h` and owns liveness itself.
3. **Stale-conversation hazard:** an unknown `--conversation` id prints only `warning: conversation "<id>" not found` and **silently starts a new conversation**. Observed live: the Play ran and answered in a new conversation.
4. **Order:** `init` (carrying `conversation_id`) is emitted about 2 s after start **before stdin is read** (verified with stdin held open). So Coach writes the Play only after confirming `init.conversation_id` equals the instance's conversation. On a mismatch it kills the process, refuses with "Can't reach this Player's conversation. Nothing was sent.", and marks the channel lost so restore decides.

## Instance Work Ledger design

**Question it answers:** "what is this exact instance doing, and what did it just do?" It is kept beside eligibility (On Field) and never merged with it.

```
InstanceLedgerEntry {
  gameId, playerInstanceId, playerType?
  workState: idle | working | waiting | queued | completed | unknown | disconnected
  currentPlay?: { clientRef, playLabel, promptSummary (≤80 chars, first line), model, effort, transport, startedAt, turnRef }
  recentPlays: [{ clientRef, playLabel, model, effort, outcome: completed|failed|interrupted|unknown|not-sent, summary, startedAt, finishedAt }]  // ≤ 10
  reports: [{ path, filename, mtime, attribution: 'single-active-play', clientRef }]                                                         // ≤ 10
  updatedAt
}
```

**Only what Coach knows moves state:**

| Signal | Effect |
|---|---|
| Router `play-dispatched` | pending only; nothing is claimed |
| Stadium turn `accepted`/`started` | **working** (currentPlay from the pending dispatch) |
| Router `received` | Controlled → working; **Terminal → unknown** (no completion signal) |
| Router `failed` | recent `not-sent`; no current Play |
| Turn `completed` | **completed**; the Play joins history |
| Turn `failed`/`interrupted` | idle; the outcome is recorded |
| Turn `unknown` / delivery timeout | **unknown** |
| Stadium session removed / game disconnected | **disconnected**; current Play kept, never completed |
| Capability snapshot after reconnect | Controlled `ready` → idle; a lost Play → recent `unknown`; `busy` → working; removed instance leaves |

Nothing is inferred from elapsed time.

## Instance Work Ledger implementation

**Code:**
- `src/control-plane/work-ledger.ts`: `InstanceWorkLedger`, in memory and bounded.
- **Daemon wiring:** router `play-dispatched` / `status-update` → dispatch and delivery; WS `turn.changed` → `recordTurn` (Game from the authenticated session); registry `session-removed` / `game-disconnected` → disconnected; `capabilities-updated` → `observeRoster`; `reports-updated` → `recordReports`.
- **Status contract:** each `capabilities[]` entry carries `work: { workState, currentPlay, lastPlay }` (`unknown` when unrecorded, never idle), plus `workLedger` for the selected Game.
- **Roster card:** On Field · Controlled · **Working** / **Idle** / **Disconnected**. Unknown is left unsaid rather than guessed.

**Ordering handled explicitly:** the Stadium emits turn events before `dispatch.accepted`, and a very fast Play can complete before `received`. It is never resurrected as working (test L2).

**Live:** the fresh daemon's GameTest status shows `codex-0a6eab81 controlled ready work=idle`, and the two old terminal Players show `work=unknown`.

## Report provenance status

**Implemented (conservative):**
- When the Stadium publishes reports, each **new** path is linked to an instance only if exactly one instance in that Game had a Play running, or finished within 2 minutes, at the report's mtime.
- Attribution is recorded as `single-active-play` with the Play's `clientRef`.
- Reports that existed before the Ledger was watching, and reports written while two Plays overlapped, stay **unattributed**. Unknown is valid.

**The Ledger can now answer:**
- What is Claude 1 working on? (`currentPlay`)
- What did Claude 1 just complete? (`recentPlays[0]`)
- What did Claude 2 work on? (history)
- Which Player produced this report? (when unambiguous)

**Follow-up (breadcrumbed):** an explicit provenance header written by the Player (Game, clientRef, instance, model, effort) would make attribution exact.

## AUTO idle/working instance behavior

- Stadium `busy` (turn accepted or started, or the control is active) still removes a sibling from the ready pool: a working sibling is never chosen.
- Among ready siblings, a Ledger-known `idle`/`completed` instance beats one with `unknown` activity. Rationale: "claude-22222222 chosen: idle".
- With a busy sibling present, the summary reads "Claude 2 is free and can run this Play now."
- Context affinity (preferring a busy owner of the right context) is deliberately **not** built.

## Known constraints

- **Stadium reload pending:** Controlled Claude and AntiGravity are live-proven at the adapter level, but not yet in the human's Game hosts.
- **One process per Play:** startup overhead of about 1.2 s (Claude) and 1.5 s (AntiGravity) before Received. Opening an AntiGravity Player takes about 2 s per conversation.
- **AntiGravity empty conversations:** opening a Player, and checking a missing conversation, create an empty AntiGravity conversation.
- **Entitlement:** Claude and AntiGravity plan entitlement is not discoverable. Models are offered as each provider lists them; a Play on an unavailable model fails truthfully.
- **Per-model effort support:** Claude reports one effort list for all models, applied to every alias; a model that rejects a level fails that Play truthfully.
- **Authority UI:** no Permissions Settings UI or durable key yet. The default is fixed at accept-edits and cannot widen.
- **Ledger persistence:** in memory only; a daemon restart rebuilds activity as Unknown/Idle from snapshots.
- **Report provenance** is timing-based and conservative.
- **Interrupt** exists in the contract only (no Dispatcher button).
- **Version drift:** the adapter trusts the installed CLI's advertised flags rather than an exact version pin. A CLI that keeps the flags but changes their meaning would not be caught; frame parsing is strict and unknown frames are ignored.
- **Stale-daemon hazard** persists until the Freshness Guard exists.
