## RESULT

**Primary recommendation: SMALL ADAPTIVE COMPATIBILITY SLICE.**

Codex 0.155.1 is rejected **only** because its version string is not in a one-entry allowlist (`['0.154.0']`). No required behavior fails. I verified this two independent ways against the real installed Codex, without sending a turn or changing any source:

- **Static:** all **96 of 96** methods, fields and enum values the adapter reads or writes are present in the schema Codex 0.155.1 generates.
- **Behavioral, zero-turn:** the real compiled adapter, with the version allowlist widened through its own existing test seam, **opened Ready** against real 0.155.1. It passed every authority, cwd and sandbox check, discovered live capabilities, and handled both missing-conversation restore paths correctly.

The gate is also broader than it looks. It runs before `account/read`, so it blocks Codex's read-only capability discovery too, and it makes **Try Again unable to ever succeed**.

This is not a Terminal AUTO regression (see First Question). Dad stays blocked until the next Play lands. Session-only workarounds (downgrading Codex) were not used.

## FIRST QUESTION — where is the gate, exactly

**The user-facing string exists at two source locations, both in `src/player-control/codex-app-server.ts`:**

```ts
// line 10
const CERTIFIED_VERSION = '0.154.0';

// open()    lines 250-256   →  ControlOpenError('needs-verification', "Installed provider version '…' is not certified for controlled dispatch.")
// restore() lines 339-345   →  { kind: 'needs-verification', message: "… is not certified for controlled resume." }
const userAgent = stringValue(initialized.userAgent);
const runtimeVersion = parseRuntimeVersion(userAgent);
const certified = options.certifiedVersions ?? [CERTIFIED_VERSION];
if (!runtimeVersion || !certified.includes(runtimeVersion)) { … }

// line 702
function parseRuntimeVersion(userAgent) { return userAgent.match(/\/(\d+\.\d+\.\d+)(?:\s|$)/)?.[1]; }
```

1. **Where:** identically in `open()` and `restore()`, immediately after `initialize`. Nothing else in `src/` spawns `codex app-server` (`extension.ts:57` registers `new CodexAppServerFactory()` with no options, so the default applies).
2. **What it allows:** exactly the string `0.154.0`. It is not a range, not a family and not a minimum. An unparsable `userAgent` (for example a pre-release suffix such as `0.156.0-alpha.1`) also fails.
3. **Why it was introduced:** Stage 1.17 (2026-09-11, commit `317c3bf`): "The exact **proof-stage** version gate certifies `0.154.0`. Any other reported version becomes NeedsVerification; there is no silent legacy fallback." Stage 1.18 §16 adds "Recovery. Certify the new version (code update, conformance run, schema diff)" and a second rationale: "a provider upgrade may also change the stored history format". Stage 1.16 had originally asked for something stronger: a certified version **range**, plus "detect drift in CI: regenerate the schema for each new Codex release and diff only the methods and fields the adapter uses", plus a supported fallback (`codex exec resume`). The proof-stage exact string was shipped and the range/drift work was never done.
4. **What it was meant to protect:** that `initialize`, `thread/start|resume|read`, `turn/start`, the notification stream and the approval requests all keep the shape and meaning the adapter was proven against, and that authority (`approvalPolicy: never`, `danger-full-access`), Game cwd and session identity cannot be silently changed by a provider update.
5. **Does 0.155.1 fail any of those?** No (below).
6. **Rejected solely by version number?** **Yes.** Proven by running the shipped code (item 1 below) and the same code with only the allowlist widened (item 3).

**Not a Terminal regression.** The Terminal Player path never spawns Codex. The only uncommitted change to this file before this Play is one line (`streaming: true` on the agent-message delta, from the S43 activity transport) and is unrelated to the gate. The gate constant has been `0.154.0` since 2026-09-11.

## HOW CLAUDE AND ANTIGRAVITY DO IT (the stronger pattern that already exists)

`src/player-control/structured-print.ts` `verifyContract()` runs the installed CLI's own `--help` and requires every term in `dialect.requiredHelpTerms(authority)` (the flags the adapter relies on, authority flags included). A missing term gives `needs-verification` with the exact missing terms in the message. `--version` is read afterwards and returned only as a display string (`runtimeVersion`). **There is no version gate at all.** The file header states the principle: "an update that removes a required flag fails closed (Needs verification) instead of silently changing authority."

**Reusable principle:** *prove the required terms of the provider's own self-description before dispatch; version is a label.* For Codex the equivalent self-description is its generated protocol schema. Codex is the only controlled provider still gated by version.

## ANSWERS TO THE ELEVEN QUESTIONS

1. **Why exactly is 0.155.1 rejected?** `['0.154.0'].includes('0.155.1')` is false, in `open()` and `restore()`.
2. **Version-string-only or behavioral?** Version-string-only (proven above).
3. **What must be proven before dispatch?** The ten-row contract table above.
4. **Already dynamically verifiable?** Rows 1–4 and 6, already enforced per open/restore, plus row 5's runtime handling.
5. **Not verifiable?** Execution of `turn/start` and its notifications without a model turn.
6. **Does 0.155.1 look compatible?** Yes on everything provable without a turn (96/96 static; zero-turn adapter run Ready). **Not observed:** a real turn.
7. **Smallest durable way to support routine upgrades?** Replace the version allowlist with a declarative required-contract probe (below).
8. **Role of version?** Informational (always shown and recorded), plus a **cache key for "already proven"** (exact version only), plus a hard block only for an explicit known-bad list. **Not** a family hint and **not** a general hard gate.
9. **How do unknown future versions fail safely without disabling a compatible Player?** Probe runs; pass → Ready; required item missing/contradicted → `needs-verification` naming the missing items; probe cannot run → `needs-verification` "compatibility unproven". A compatible new version therefore never breaks, and an incompatible one never dispatches.
10. **Files and tests:** below.
11. **Solvable without touching identity, routing, session authority or Player Control architecture?** Yes. The change is confined to the Codex adapter. Outcome kinds (`needs-verification`), the bindings store, the host, roster identity, the router and all authority checks are unchanged.

## RECOMMENDED FUTURE-VERSION POLICY

| Situation | Outcome |
|---|---|
| Exact version already proven (cache seeded with `0.154.0` and now `0.155.1`) | Skip the schema probe; still run every per-open authority/cwd/sandbox check |
| Unknown version, schema probe passes all required items | **Ready** ("verified by contract"); cache the result for that exact version and binary |
| Unknown version, any required method/field/enum missing or changed | `needs-verification` naming the missing items (Dev diagnostic); zero thread calls; binding kept |
| Version unparsable (pre-release, odd `userAgent`) | Not a failure by itself; the probe decides |
| Probe cannot run (tool absent, times out, output unparsable) | `needs-verification` "compatibility unproven" (fail closed; *cannot be proven*) |
| Version on the explicit known-bad list | `needs-verification` regardless of probe (starts empty) |
| First real turn on a newly proven version | **Tripwires:** no `turn.id` in the acknowledgement (already handled as `lost`/unknown), no `turn/completed`, or an unrecognized status → latch that version as failed and fail closed |

Static schema conformance catches shape drift but **cannot** catch behavior-only drift (the 0.154.0 `thread/read` change was behavioral). That is why the policy layers three things: the static probe, the existing zero-turn authority checks, and first-turn tripwires.

## RISKS / UNKNOWNS

- **A real `turn/start` on 0.155.1 has not been observed** (it would consume model usage). Rows 7–8 execution and `clientUserMessageId` handling remain unproven. The first Play after implementation is the field proof.
- **`generate-json-schema` is labeled experimental** by Codex. If it changes or disappears, the probe fails closed as "unproven" (by policy), which is safe but would re-bench Players for versions not already cached. A second self-description source or a persisted cache would reduce that exposure.
- **Static conformance is shape, not behavior.** Mitigated by the layered policy, not eliminated.
- **The table can drift from the adapter** as the adapter changes. Mitigated by the coverage test tied to `REQUEST_ALLOWLIST`, but any newly read field must be added to the table.
- **No 0.154.0 install to diff against.** I could not compare schemas across versions; I verified against what the adapter reads instead. A stored contract fingerprint would enable future diffs.
- **Observation, not investigated:** the thread started with `gpt-5.6-sol` / `low`, while `model/list` reports `gpt-6-astra` as default. That looks like Dad's Codex configuration (a thread default versus the model catalog default), unrelated to compatibility.
- **The zero-turn run launched Dad's Codex CLI in a scratch folder** (thread/start with no turn creates nothing durable). The CLI itself was not modified, downgraded or reinstalled, and Dad was not asked to retry anything.
