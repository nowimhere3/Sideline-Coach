## Architecture

**Existing implementation discovered:**
- **Launcher:** `launcher.ts` reused *any* daemon that answered `/api/health` with `status: ok`. There was no identity, and a lock-staleness rule based on mtime.
- **Daemon manifest:** `{ pid, port, startedAt }`, nothing about the build.
- **Stadium reconnect:** `StadiumClient` re-dialled the same port every 2 s, driven only by socket `close` events. It never re-ran discovery, so a replaced daemon on another port, or a daemon that needed starting, was never found.
- **Selected Game:** in-memory only. After any restart the first Stadium to reconnect became the selection.
- **Terminal:** `PlayerRoster.addTerminalPlayer()` already created a Coach-managed, Game-rooted terminal with ownership-aware removal, and Recruit already offered Terminal (always available).
- **Terminal gaps:**
  - `getRoutingCapabilities()` explicitly **skipped** Terminal, so it could never be chosen in the Dispatcher.
  - Terminal-backed provider Plays were delivered by **visible terminal name** (`sendTerminalText(name)`), which same-named siblings can share.
  - There was no deliberate path to adopt a plain human shell.
  - Roster names used historical seats ("Codex 3").

**Root causes:**
1. **Stale runtime:** reuse was decided by liveness ("does something answer health?") instead of compatibility ("is it the build I expect?"), and nothing in the Stadium could re-resolve the Control Plane.
2. **Terminal unusable:** an earlier safety decision — never type a Play into a shell — was implemented as "never a target" instead of "a target with explicit command semantics".

## Build identity design

- **Definition:** `computeControlPlaneBuild(daemonScriptPath)` in `src/control-plane/freshness.ts` hashes the daemon's compiled **runtime closure**:
  - start at `out/control-plane/daemon.js`;
  - follow every relative `require("./…" | "../…")` in the compiled JS, transitively;
  - SHA-256 over sorted `relativePath \0 sha256(content)` → `cp-<24 hex>`. A missing transitive module is part of the identity, not ignored.
- **Real closure includes:** daemon, router, stadium-registry, work-ledger, protocol, freshness, routing-policy, play-analyzer, provider-control, running-players, game-lifecycle, and so on.
- **Real closure excludes:** `player-roster`, `extension`, `stadium-client`, the adapters and `public/index.html`. UI and Stadium-only edits do not churn the daemon (test P0.1-1/2).
- **Expected build:** the Stadium computes it **once at activation**, from its own installation. A later compile on disk therefore can never masquerade as what that window is running.
- **Truthful self-description:** the daemon computes its identity at construction and publishes it in:
  - the manifest, written atomically: `service`, `instanceId` nonce, `buildId`, `daemonScriptPath`, `supersedes`;
  - `/api/health`;
  - `/api/diagnostics` (plus `replacementReason`).

**Decision matrix** (`assessFreshness`, no time anywhere):

| Situation | Verdict |
|---|---|
| running build = expected | **current**: reuse |
| running daemon has no build identity (legacy) | **Unknown → stale**: replace (after ownership proof) |
| same installation, window's loaded build ≠ disk build | **stadium-outdated**: defer (the window was not reloaded) |
| same installation, window loaded = disk, running differs | **stale**: replace (a revert to an older source also wins) |
| different installation, expected ∈ running.supersedes | **stadium-outdated**: an old installed version never replaces its successor |
| different installation, otherwise | **stale**: replace |

**Packaged V1:** a VSIX upgrade changes both the installation path and the closure hash. The new version replaces an old daemon, and a still-open window of the old version defers (lineage), so versions cannot flap.

## Replacement / election protocol

`ensureControlPlaneRunning()` in `launcher.ts` works in five steps:

1. **Read the manifest.** Missing or corrupt → start a daemon (under the lock).
2. **Prove ownership** (`provesOwnership`): the listener on the manifest port must report the manifest PID through the health API, plus the nonce when the manifest has one. If it is silent but the PID is alive, look 3 more times.
   - **Not provable** (a PID reused by another process, or a foreign or hung listener): **never terminated**. A new daemon starts and takes the next free port; the manifest follows it.
3. **Verdict:** current or outdated → reuse; stale → replacement.
4. **Election lock:** atomic `control-plane.lock` (`wx`), content `{ pid, nonce }`.
   - It is broken only when the holder PID is dead (liveness, not age).
   - Losers wait and re-evaluate from step 1, so they converge on the winner's daemon.
   - Release checks the nonce, so a Stadium never removes another's lock.
5. **Winner step-down**, done under the lock:
   - Re-read the manifest; if someone already replaced it, stop and re-evaluate.
   - Send an authenticated, instance-addressed `POST /api/control-plane/shutdown { instanceId }`. A mismatched instance is refused with 409.
   - Wait for the old process to go, re-prove ownership, and only then use `process.kill` as a fallback (legacy daemons have no route). No PowerShell.
   - Spawn the new daemon with `SIDELINE_DAEMON_INSTANCE` (a nonce the winner chose), `SIDELINE_SUPERSEDES` (lineage) and `SIDELINE_REPLACEMENT_REASON`.
   - Accept only the manifest and health that carry that exact nonce.

**Reconnect:**
- `StadiumClient.reconnect()` calls `resolveControlPlane` (the guard) before every attempt and follows port and token changes. It retries when a connect attempt fails, not only on `close`.
- The extension sets the status bar to **"Coach: Updating…"** while resolving, and passes the expected build and verdict in `stadium.hello`.
- Diagnostics show each session's expected build and `controlPlaneCompatibility`.

**State across a restart:**
- **Selected Game:** persisted in `~/.sideline/control-plane-state.json` on every `selected-game-changed`, and restored when that Game's Stadium reconnects, even if another Game reconnected first.
- **Reports:** republished by each Stadium on connect (P0 publisher).
- **Ledger:** restarts empty and rebuilds as Unknown or Idle from snapshots, never fabricated.
- **Controlled Player sessions:** live in the Stadiums and are untouched by a Control Plane restart.

## Field defects found by the live proof (fixed)

1. **A superseded daemon did not exit.**
   - What happened: the graceful `stop()` awaited `httpServer.close()`, which stays pending while keep-alive or SSE sockets (the phone's event stream) linger. The old process stopped listening but stayed alive; the launcher correctly refused to kill it once ownership was no longer provable.
   - Fix: `server.closeAllConnections()` before close, plus a hard `process.exit` 3 s after an owner-verified shutdown of a detached daemon.
   - Test: P0.1-16 (open SSE stream → port released and stream closed in under 3 s).
2. **The Stadium reconnect chain died on a hung connect.**
   - What happened: a connect attempt that hit the half-closed daemon timed out; `ws` raised "closed before the connection was established"; `StadiumClient` re-emitted it as an **unobserved `'error'` event, which throws**, and the retry chain stopped. Live, all three Game windows stayed disconnected after the graceful A→B handover.
   - Fix: re-emit only when someone listens, and retry whenever `connect()` returns false.
   - Test: P0.1-17 (a TCP listener that never answers the upgrade, then the real daemon → the client recovers).

## Terminal semantics

- **Contract** (`src/terminal-player.ts`): `executionType: direct-shell`; model, reasoning and provider are not applicable.
- **Command fidelity:** the text the human approved is the command, byte for byte (NUL bytes only removed). Coach does no transformation, no model call and no command guessing.
- **Natural-language guard** (`checkTerminalCommand`): refuses empty text, and text that plainly reads as a request — it opens like a request ("please…", "why…", "can you…") or ends in a question mark, has 3 or more words, and contains no shell syntax. The message: "Terminal runs exact commands, and that reads like a request. Send it to Claude, Codex or AntiGravity — or type the command itself."
  - It is a guard, not a parser: `echo "why does this fail?"`, `npm run compile && npm test`, multi-line scripts and PowerShell cmdlets all pass.
- **Execution** (`PlayerRoster.runTerminalCommand`, exact instance only):
  - refuses a removed, closed or **benched** Terminal ("Nothing was run");
  - refuses while its own command is still running; never uses a sibling;
  - **with VS Code shell integration** (`terminal.shellIntegration.executeCommand` + `window.onDidEndTerminalShellExecution`): turn *accepted/started* → **Working**, then **Completed · exit code 0** or **Failed · exit code N**; a missing exit code is **Unknown**. Commands the human types into the same terminal are ignored, never recorded as Plays;
  - **without shell integration**, or for multi-line input: `sendText` exactly, with **no turn events**. The Ledger shows **Unknown**, never Completed.
- **Routing:**
  - `getRoutingCapabilities()` now lists on-field Terminals with `executionType: 'direct-shell'` (busy while a command runs).
  - `computeAutoRoute` filters Terminal out. If only a Terminal is on field: "Terminal runs exact commands, so AUTO does not send it Plays. Choose Terminal in Manual…"
  - The router strips model and effort for a Terminal target.
- **Stadium dispatch:** Terminal → `runTerminalCommand(exactId, prompt)`. Terminal-backed provider Players → `sendToProviderTerminal(exactId, …)`, **no longer by visible terminal name**.

## Terminal ownership model

| Terminal | How it joins | Bench | Remove |
|---|---|---|---|
| Coach-managed | Recruit → Terminal → **Add**, or "+ Add another Terminal" (rooted in the Game, the Game's default shell) | stays alive, not a target | closes **that exact** terminal |
| Adopted (human) | Recruit → **Adopt as Terminal** on one listed open terminal (`/api/players/adopt-terminal { shellPid }`) | stays alive | **detaches**; the terminal stays open |

**Never automatic:**
- Open shells appear in `discovery.adoptableTerminals` only as offers.
- Coach's own terminals, rostered terminals and shells already running a recognised agent are excluded.

## Dispatcher / Roster UX

**Roster:**
- Terminals appear like any Player: *Terminal 1 · On Field · Terminal · Working/Idle*.
- **Human numbering is contiguous by position** in stable seat order (Terminal 1, Terminal 2 — never "Terminal 3" after a removal); opaque instance ids stay the identity. This applies to every Player type.

**MANUAL with Terminal selected:**
- Model: **Not applicable**. Reasoning: **Not applicable** (both disabled).
- Notice: "Terminal runs exactly the command you type, in this Game. No model, no reasoning, no quota."
- The payload label changes from **Prompt payload** to **Command**, with placeholder "Exact command, e.g. git status --short". Switching back restores it.

**Recruit:** the Terminal card lists open terminals with **Adopt as Terminal**.

**Dad Mode vs Advanced:** Dad Mode never shows PIDs, build hashes or lineage. VS Code shows "Coach: Updating…"; the phone shows the existing "Reconnecting…" (see constraints).

## Constraints

- **One reload per open Game window, this time only.** Your current Extension Development Hosts run pre-guard Stadium code with the old reconnect bug, so after the graceful handover they will not rejoin on their own. After one reload each, future Control Plane replacements heal automatically.
- **Wording on the phone:** it shows "Reconnecting…" during a replacement; the page cannot tell an update from a network drop (follow-up: daemon announces `updating`).
- **In-memory Control Plane state:** the Ledger and routing mode restart truthfully (Unknown/Idle), and in-flight dispatch acknowledgements at the exact moment of replacement resolve as Unknown — never resent. The selected Game and reports survive.
- **Unprovable daemons:** a daemon whose ownership cannot be proven (hung, or a PID reused by another process) is left running; the new daemon takes the next port. The phone URL (Tailscale → 3100) then needs that port free, so the owner-verified step-down is what normally keeps 3100.
- **Terminal command completion** depends on VS Code shell integration being active in that terminal (PowerShell, bash, zsh and fish are supported; it activates shortly after creation). Otherwise the outcome is truthfully Unknown. Multi-line commands use `sendText` (Unknown).
- **Natural-language guard:** a heuristic guard. It will not catch every sentence, and it deliberately lets anything with shell syntax through.
- **No command output returns to Incoming yet** (follow-up).

## WAS / IS / WILL BE

**WAS**
- Fresh Stadium code could reconnect to a stale detached Control Plane, forcing manual PID surgery through `~/.sideline/control-plane.json`.
- Reconnects re-dialled a dead port forever, and a hung connect could kill the retry loop.
- The selected Game was lost on restart.
- Terminal existed but could not be chosen as a Player in the Dispatcher; terminal-backed Plays were addressed by visible name.

**IS**
- **Freshness:** Control Plane build compatibility is verified automatically by deterministic build identity. A stale daemon is replaced safely: ownership proven, one election winner, instance-addressed step-down, lineage recorded.
- **Recovery:** every Stadium re-resolves and reconnects by itself, the selected Game survives, and Incoming and Game isolation continue.
- **Terminal:** a real exact-instance Player in the Roster and MANUAL dispatch. It has explicit shell-command semantics (Command; model and reasoning not applicable), truthful ownership (Coach-managed closes, adopted detaches) and truthful work state (shell-integration evidence, or Unknown), and it stays out of AUTO.

**WILL BE**
- The same freshness primitive protects packaged V1 upgrades, via installation lineage, and future remote or cloud topologies, via lease or credential ownership.
- The phone announces "Coach updating…" during a replacement.
- Terminal becomes a zero-token deterministic AUTO executor when command intent is explicit and Routing Settings policy allows it, with optional bounded command output returned to Incoming.
