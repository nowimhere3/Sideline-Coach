## Executive Verdict

# SMALL AMENDMENT REQUIRED BEFORE R1

The routing *brain* is already roster-general. Candidates come from the live roster, belief keys are open strings, UNKNOWN is first-class, priors never pool users, and the transport is the belief root.

The **resource nervous system is not.** Everything upstream of R1 is a closed two-provider world:

- `AlarmProvider = 'claude' | 'codex'`
- `AlarmWindow = 'five_hour' | 'weekly'`
- `HealthAuthoritySnapshot.providers: { claude?, codex? }`

S57.1 tells R1 to reuse it "per provider/window". It also implicitly treats **Player type = resource pool**, because it prices "the chosen provider's windows".

Left unamended, R1 will be built as `Record<AlarmProvider, …>`. That is exactly `ClaudeEconomics + CodexEconomics`. R2 would then freeze the same shape into the durable Film, and R6 and R8 would inherit it.

**The amendment is three specification rules (A1–A3, §10). It requires no code change to anything that exists today.** Stage 1A–2A (HealthAuthority, AlarmEngine, ResourcePolicy) stays exactly as it is. It becomes one *source adapter* feeding an open-keyed R1 snapshot.

Nothing else must change before R1. R3–R9 items are amendments to apply *when those slices are written* (§9). Pack modularity, a support manifest, a pack manager and roster telemetry are breadcrumbs (§11).

**Telemetry:** never required for pack selection or delivery. It stays opt-in, aggregate, closed-enum, and used only to prioritize what Sideline builds next (§6).

## 3. Recommended Team Discovery Model

**One ladder of *gates*, and separately two *knowledge* axes that never gate.** Only gates decide candidacy. Knowledge only changes belief strength. This is how "detected ≠ trusted" works without inventing a trust score.

### 3.1 Support Ladder (gates, in order)

| Level | Meaning | Where the fact already lives | Can be a seat? |
|---|---|---|---|
| L0 Unrecognized | A tool Sideline has never heard of | — | No. Invisible by definition |
| L1 Recognized, unsupported | Known ecosystem, no adapter in this build | **new** (watchlist, breadcrumb §11) | **No, never** |
| L2 Supported, not installed | Adapter exists; probe says absent | `PlayerDetectionState: 'not-installed'` + `InstallGuidance` | No |
| L3 Installed | Probe finds the executable | `'ready'` / `'authentication-needed'` | No |
| L4 Authenticated / reachable | Auth probe or live capability says signed in | `'authentication-needed'` vs `'ready'`; capability `authenticated`, `freshness` | No |
| L5 Operable | A real instance exists with a fresh model/effort catalog (controlled) or a provider-managed session (legacy) | roster instances; `ProviderCapabilitySnapshot`; `projectInstanceControls` | Yes, if L6 |
| L6 Eligible | Operable + autoEligible + roster state + Coach constraints + entitlement (S57.2) + Terminal/Scout separation | `routing-policy.ts` → R4 `eligibleSeats` | **Yes** |

### 3.2 Knowledge axes (never gates)

| Axis | Values | Source | Effect |
|---|---|---|---|
| **Researched** | exact node · effort-`*` · inherited (lineage) · baseline · none | `CapabilityPriorPack` | Sets the prior mean and strength; emits `PRIOR_ONLY` / `NEW_MODEL_INHERITED` |
| **Locally proven** | prior-only · thin · building · established | Routing Film (`nLocalEff`) | Evidence Strength (S57.1 §12) |
| *(orthogonal)* **Resource truth** | known · unknown | HealthAuthority coverage for the seat's pool | Price or `UNKNOWN` (S57.1 §18) |

**Rule:** research and proof never *admit* a seat and never *exclude* one. An operable, eligible, never-researched Player stays a candidate at baseline-prior strength. The engine is honest about it ("Early pick · still learning"), and the Coach can always route to it explicitly.

**Unavoidable human actions** (the entire list):

1. **Installing and signing in to provider tools.** Credentials and accounts belong to the human. The existing rule is that Coach never runs installs silently.
2. **Choosing telemetry consent** (S57.2 §15).
3. **Optionally naming a tool Sideline cannot recognize (L0).** Nothing can detect a tool nobody has described.

Everything else is discovered: models, efforts, transports, lineages, pack selection and resource truth.

## 4. Recommended Sideline Support Registry Model

**No new V1 runtime concept.** The registry already exists *de facto* and is correct in one essential way: **support is code shipped with the build.** An adapter launches local processes, parses provider CLIs and reads account limits. That can never be downloaded as data without becoming a code-delivery channel. So support is versioned with the app release, and there is nothing to add now.

**Breadcrumb: `SupportManifest` consolidation** (trigger: adding ecosystem #4). Fold the four parallel lists into one declaration per ecosystem:

```
SupportManifest {
  playerType, displayName, aliases, modelFamilies      // today: PLAYER_ADAPTERS + PLAYER_REGISTRY + MODEL_FAMILY_REGISTRY
  transports: controlled | legacy                      // hasControlledAdapter
  discovery: probe, auth probe, catalog reader
  routingPolicy                                        // createRoutingPolicies()
  resourcePool(seat) → ResourcePoolId | UNKNOWN        // A2 (§10) — the only piece needed now, as a function
  priorPackSegment: playerType                         // §5
}
```

"FooAI detected, unsupported" (L1) comes from a separate **recognition watchlist**: data listing known public agent CLIs Sideline does not yet support (id, display name, executable pattern). It is display and telemetry only. **Data can make a tool *recognized*; only code can make it *supported*.**

## 5. Recommended Capability-Pack Architecture

**Keep one pack *format*. Keep one shipped file in V1. Segment it by playerType later.**

| Option | Verdict |
|---|---|
| One global `priors.json` forever | Correct for V1 and harmless for any roster. Nodes are rooted at `playerType`, so a Claude-only install simply never matches `codex/*`. It fails only on update cadence (G5). |
| Modular per-provider packs now | Premature. It adds loader, versioning and signing work before a second publisher or cadence exists. |
| **Base pack + per-ecosystem segments, independently versioned (later)** | **Recommended scalable form.** Same schema, split on the existing `playerType` root. |

**Scalable flow (breadcrumb P1, Pack Manager):**

1. The app ships a base pack containing all segments for ecosystems this build supports.
2. The app periodically fetches the **public pack index plus every segment this build supports**. The fetch is **roster-blind**: the same bytes go to every install, so the request reveals nothing about the customer's Team and needs no telemetry.
3. It verifies a signature, keeps the last-good copy, and rolls back on failure. A segment for an ecosystem the build does not support is ignored, because data cannot create support.
4. The loader composes segments for the Players actually on the roster. It stamps a **per-segment `packVersion`** into each recommendation (a generalization of S57.1 §13 `priorPackVersion`).

**Invariants:**

- Packs are **published research only**. The customer's Film never enters a pack, and pack updates never touch the Film.
- A pack update that changes a node's mean resets nothing. Local evidence still dominates after a few reps.
- Inheritance rules are unchanged:
  - new model, known lineage → lineage ×0.5
  - unknown lineage → playerType node → baseline
  - unsupported ecosystem → **no seat** (it never reaches belief)

**Only one R3 accommodation is needed now** (applied at R3, not before R1): R3 loads the pack through a small `PriorPackSource` that returns segments and their versions, even though V1 has one file. That makes P1 a delivery change, not a belief-engine refactor.

## 6. Telemetry Recommendation

**Hybrid: C for delivery, A for prioritization. Reject B.**

| Option | Verdict | Why |
|---|---|---|
| **C: local discovery chooses packs; no telemetry needed** | **Adopt for all users** | The install already knows its roster locally. The roster-blind fetch (§5) delivers the right segments with zero data leaving the machine. |
| **A: telemetry helps Sideline prioritize support and research** | **Adopt, opt-in** | This is where telemetry has real leverage: "742 installs recognize FooAI", "31% of codex-pack installs see ≥1 unmatched model id → refresh codex segment". |
| **B: telemetry-enabled users get better or automatic pack selection** | **Reject** | Selection is a local computation, so telemetry adds no technical capability. Tying routing quality to data sharing would punish privacy-minded customers, weaken the consent choice (S57.2 §15 lets it be freely off), and cost trust for no gain. The legitimate kernel of Dad's idea is that telemetry lets Sideline **build** better packs and adapters sooner. **Everyone** receives those, consenting or not. |

**Fits S57.2 as-is:** same consent flag, outbox and closed-enum schema, and **no free-form strings**. Proposed events (breadcrumb W1):

- `team.daily_snapshot`
  - `dims.playerType` (closed enum: supported ids + watchlist ids)
  - `supportLevel` (L1–L6 enum)
  - `transport`
  - per-segment pack version
  - `lineagesMatched` (closed set from the shipped pack)
  - `unmatchedModelCount`
  - `resourceTruth` known/unknown
- `support.recognized_unsupported`: watchlist id, counts only.

**Never collected:** raw model ids or executable names outside closed enums, unknown tool names, prompts, reports, credentials, Film, per-node outcomes, receipts. S57.2's existing `play.dispatched` outcome event may inform product analytics, but it **must never feed a published prior automatically**. S57.1 §3 "nothing pooled across users" holds. Using aggregate outcomes for research would be a separate, explicit Coach decision (§12, deferred).

## 10. Minimum Changes Required Now

**No current implementation change is required. No existing code, test, prior or Stage 1A–2A contract changes.**

What is required is **three specification rules carried into the R1 Play and the R2 Play** as an additive S57.1 amendment:

- **A1 Open resource identity.** `RoutingEconomicsSnapshot` is keyed by `ResourcePoolId` (an open string), not `AlarmProvider`. Each pool carries `windows: { id: string; lengthMin: number; R?; T?; π?; price | 'unknown'; floor?; stale; policyLag }[]`, `evidence: 'known' | 'unknown'`, and `policy?: ProviderResourcePolicy` verbatim when a Stage 2A policy exists. π uses `lengthMin` from the descriptor, not an enum constant. `normalizeAlarmFacts` stays the single normalizer. R1 adapts its closed output at the boundary and never re-derives it.
- **A2 Pool belongs to the seat.** A pure `resourcePoolForSeat(seat) → ResourcePoolId | 'unknown'`, derived from the seat's playerType, transport and account, **never** from modelId or lineage. V1 mapping: `claude` seats → `claude`, `codex` seats → `codex`, everything else → `unknown`. A Claude model reached through AntiGravity maps to AntiGravity's pool (unknown), not Claude's.
- **A3 Film receipts are pool-keyed.** `ResourceReceipt` uses `pool` and `window` as open strings plus `windowLengthMin`. `decision` records the seat's `transport` and `pool`.

**Why before R1, not later.** R1 is the slice that *creates* the economics type. Every later consumer imports it: R2 receipts (durable), R6 pricing, R8 copy and R9 conditions. If R1 is written as `Record<AlarmProvider, …>`, the two-provider assumption spreads into five slices and one durable journal before anyone notices. Making it open now costs a few type names. Widening later would be recoverable (JSON strings stay valid), but it would cost a refactor across those slices. A1–A3 also add no behavior. With today's roster the snapshot contains exactly the claude and codex pools and produces the same numbers S57.1 §11.3 specifies.
