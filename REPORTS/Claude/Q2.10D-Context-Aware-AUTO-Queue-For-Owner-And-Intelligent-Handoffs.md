## Policy decisions

1. **Relevant context can outweigh idleness.** An idle context owner gets the follow-up even when a sibling is idle.
2. **A busy owner is a real decision, not a skip:**
   - a Play that *changes the Game* (implement / fix / apply / continue / refactor…, or not clearly read-only) → **Queue for owner**. Continuity and collision risk both favour waiting;
   - an *independent read-only* Play (review / summarise / check / explain…) **with a report to hand over** and an idle operable sibling → **handoff**;
   - the other option is always offered as the single alternative, and the human's pick is honoured in both directions.
3. **An owner with Plays already waiting** → the new Play queues behind them (FIFO), even if the owner is momentarily free.
4. **An owner that cannot take the Play** (benched, removed, unavailable, or Terminal) → never a silent reroute. The route states the reason ("Claude 1 owns this context but is on the bench.", "The Player that owns this context is no longer available.", "Terminal ran that work, and Terminal only runs exact commands."). It then hands off with context when there is something to hand over; otherwise it asks for Manual.
5. **Unknown owner** → normal AUTO, the sentence "Coach can't prove which Player owns this context.", and the referenced report still sent as context.
6. **New work** → Q2.10C AUTO unchanged, plus collision awareness.
7. **Terminal stays MANUAL-only** for natural-language Plays.
8. **Usage and cost stay out of scope:** resource scarcity remains Unknown.

## Context-affinity model

**`src/control-plane/context-affinity.ts`** (pure, scoped to one Game):

- **Evidence ranks:**
  1. **named-report** (strong): the Play names one of *this Game's* reports (filename, stem of 8+ characters, or path).
  2. **incoming-report** (strong): the Play refers to a report *and* the human is viewing one of this Game's reports in Incoming. The page sends `incomingReportPath` with both preview and dispatch.
  3. **latest-report** (medium): "that report / the recommendation / the findings…" with no viewed report → this Game's newest report.
  4. **latest-play** (medium): "continue / what you just built / now test…" → the most recent Play recorded in this Game.
- **Owner of a report:** explicit provenance (same Game only), otherwise the Ledger's single-active-play link, otherwise **Unknown**.
- **The Ledger is the memory.** No parallel store, no vector search.
  - New fields: `promptSummary` in recent history, `touches` (file-like references only, never the prompt).
  - Benched instances keep their history.
  - History and report links persist; activity is re-learned.

## Follow-up detection

- **Deliberately narrow wording:**
  - referring determiners (that / this / your / the latest / previous…) + report or work nouns;
  - a bare "the" only for report / recommendation / amendment / findings;
  - explicit continuation phrases ("continue", "as we discussed", "you found / built / wrote", "now test / fix…").
- **Verified as new work:** "Build a new export feature", "Add tests for the feature flags module", "Build the review screen for mobile", "Refactor the settings page", "Design an onboarding flow".
- **Verified as continuations:** the five brief examples.
- **Guards:** an open report never hijacks a non-report continuation, and a report path from another Game is never evidence.
- **Limits:** follow-up detection is not infallible. Wording only triggers a lookup of recorded evidence, and no evidence means Unknown.

## Queue design

**`src/control-plane/play-queue.ts`** (owned by the Control Plane):

- **Item:** `id`, `gameId`, exact `playerInstanceId`, playerType, prompt, resolved model/effort, playLabel, reason, context (report path, owner), `queuedAt`, `seq` (FIFO), state (`queued | dispatching | needs-attention`), attention message.
- **Enqueue:**
  - AUTO routes whose `action === 'queue'`;
  - MANUAL `whenBusy: 'queue'` for a busy Controlled instance (the phone's "Queue for …" button).
  - Response: `202 { status: 'queued', queuePosition, decision }`.
- **Release** (`ControlPlaneDaemon.drainQueue`):
  - **Triggers:** turn completed/failed/interrupted/unknown, capability updates, Game reconnect, retry, enqueue.
  - **Checks, in order:**
    - head of that exact instance is `queued`;
    - Game's authoritative Stadium connected and synchronized (otherwise wait — "Waiting for this Game to reconnect.");
    - still on the Team (else needs attention);
    - On Field (else "Claude 1 is on the bench. Put it back on field and try again — or cancel this Play.");
    - Controlled, not Terminal;
    - `busy` or Ledger working → wait;
    - ready → mark `dispatching` (persisted) → MANUAL dispatch to that exact instance with the stored model/effort.
  - **Outcomes:** success → removed; "still working / in flight" → back to queued; unknown outcome → needs attention ("Coach can't tell whether this queued Play started…"); anything else → needs attention with the reason.
- **Never:** a sibling, a re-route, or an automatic resend after an unknown outcome.
- **A needs-attention head blocks the items behind it.** Only the human clears it (Try again / Cancel).
- **API:** `GET /api/queue[?gameId]`, `POST /api/queue/:id/cancel`, `POST /api/queue/:id/retry` (all Game-scoped).
- **Status:** `status.queue` (friendly names, short first line, position, attention) and `capabilities[].work.queuedCount / needsAttention`. Work state shows **Queued** for a free-but-waiting instance. On Field stays eligibility only.

## Persistence / durability

- **`~/.sideline/play-queue.json`:** written atomically on every change. A freshness replacement uses the same directory, so the successor inherits accepted queued Plays.
- **Interrupted send:** an item found in `dispatching` after a restart becomes needs attention and is never resent.
- **`~/.sideline/work-ledger.json`:** debounced atomic save of history and report ownership. Restored entries are `unknown` until the Stadiums report activity, so context ownership survives replacement without fabricated work.
- **Proof:** automated test Q2.10D-15 runs a real daemon replacement on a new port. The queued Play is still listed, the Stadium reconnects, and the Play is released only to its exact instance after it becomes ready.
- **Live:** the running Control Plane now writes `work-ledger.json`. The queue file appears on the first queued Play.
- **Pre-Q2.10D history:** not recoverable, because the previous daemon never persisted it. That is why the live preview below correctly says Unknown for older Trend reports.

## Handoff context design

- **Built by the router from authoritative artifacts only.** Provider adapters are unaware of routing.
  ```
  [Sideline Coach handoff]
  You are continuing work previously handled by Claude 1 in this Game.
  Read this report before proceeding: Reports/Claude/Architecture-Amendment.md
  Previous Play: "Design the ledger architecture"
  ---
  <the human's Play>
  ```
- **Compact:** under 400 characters, with no machine ids, no report bodies and no histories.
- **Unknown owner with a known report:** "You are continuing earlier work in this Game. Read this report…".
- **Ledger and report hygiene:** the Ledger records the human's Play (summary, touches), not the preamble.

## Provenance

- **Format** (`src/report-provenance.ts`): an optional invisible line near the top of a report. As an HTML comment it renders as nothing in Markdown.
  `<!-- sideline-provenance: {"gameId":…,"clientRef":…,"playerInstanceId":…,"playerType":…,"provider":…,"model":…,"effort":…,"at":…} -->`
- **Parsing is strict:** malformed JSON or identities → Unknown.
- **Flow:** the Stadium parses it while scanning reports (`CoachReport.provenance`). The Ledger records it as `explicit-provenance`, but only for an instance of the same Game, and it outranks timing attribution.
- **Not yet done:** asking Controlled Players to write that line, via a prompt footer or a sidecar. Breadcrumbed as the next seam to avoid bloating this Play.

## Collision behavior

- **Signal:** file-like references (`src/x.ts`, `router.ts`, `migration.sql`…) extracted from every dispatched Play into Ledger `touches`.
- **Rule:** new work that names a file an instance is *currently changing* → **Queue for that instance** ("is changing src/control-plane/router.ts right now; queued so the edits don't overlap."), with "Run now on …" as the alternative.
- **No shared file** → no collision claimed (Unknown, not "safe"); parallel dispatch proceeds.
- **Busy-owner continuations** are treated as coupled by construction (policy 2).

## Routing changes

- **`computeContextAwareRoute`** (`src/routing-policy.ts`) layers on `computeAutoRoute`. Order: Game → intent → context owner → exact instance → work state / queue → provider → model → effort → transport.
- **`RoutingDecision` gains:** `action` (dispatch/queue/handoff), `context` (state, owner, evidence, report, note, collision), `playerName` (friendly), `alternative`, `contextPreamble`, `queuePosition`.
- **`ControlPlaneRouter.computeRoute`** is the single route function for `/api/status`, `/api/route/preview` and `/api/dispatch`, fed by `routeContextFor(gameId)`: that Game's Ledger, reports with provenance, friendly names, roster ids and queue counts. **Staged = actual.**
- **AntiGravity policy:** rationale now names the model actually chosen ("… · Gemini 3.8 Flash via AntiGravity"), never assuming Gemini.
- **Friendly names:** server summaries use contiguous names ("AntiGravity", "Claude 2"), never seat labels — a live-found bug, fixed.
- **Ledger truth fix:** a Controlled Player that reports anything but busy is no longer kept `working`. A benched-then-unavailable owner had frozen its queue.
