## 1. VERDICT

# GO WITH CONSTRAINTS.

**A controlled Player can survive a Coach reload safely.**

**The provider side:**
* Codex 0.154.0 resumes a thread by its id in a fresh `app-server` process.
* It enforces a single writer per thread across processes.
* It records an interrupted Play in thread history with the Play's correlation id.

**The Sideline side:**
* It needs one small per-Game record per controlled Player.
* A restore sequence re-proves the provider session before the Player can be dispatched to.
* Restore **never sends a Play.**

None of the stop conditions fires (see "Why not STOP" below).

### Constraints

| # | Constraint |
|---|---|
| **R1** | **Identity first, capability second.** Sideline identity is restored from Coach's own record, *synchronously* at activation, before the server starts. The provider session is a capability, re-proven asynchronously. The Player is dispatchable only after that proof. |
| **R2** | **One record per controlled Player, one writer.** The Player Control Host writes through a VS Code-free storage port. The key is `sidelineCoach.playerSessions.v1`, separate from provenance and never merged with it. |
| **R3** | **Authority is re-asserted on every open and every resume**: approval policy, sandbox, and working directory, sent explicitly and validated on echo. It is never inferred from provider persistence. The probe saw a resume without overrides come back with approval policy `on-request` instead of `never`. |
| **R4** | **The thread's captured Game root is validated before resume**, through a read-only `thread/read`. The probe showed that a working-directory override on resume silently re-homes a thread. |
| **R5** | **Restore and reconciliation never call `turn/start`.** Exactly once, or Unknown. |
| **R6** | **A write-ahead marker for the in-flight Play.** Its correlation id is written *before* the send and its turn id after acknowledgement. It is cleared only once the outcome is definite. |
| **R7** | **Absence is not proof.** A crash can leave an interrupted turn with no stored user message (probe B3). Failing to find the correlation id never proves the Play did not run. |
| **R8** | **Reload is never Leave Field.** Only an explicit human close (`TerminalExitReason.User`) removes a binding. Shutdown, extension-initiated disposal, and unknown reasons keep it. |
| **R9** | **One failure never poisons siblings.** Records are validated one at a time, restored one at a time, and a contradiction quarantines only the records involved. |
| **R10** | **The version gate and auth mode are re-checked at restore.** The outcome is Needs verification, Needs sign-in, or Needs decision (an API-key login would change billing). The binding is always kept. |
| **R11** | **Coach never deletes provider history.** `thread/delete` stays off the allowlist. Leave Field removes only the Sideline binding; the conversation stays in the user's Codex history. |

### Why not STOP

| Stop condition | Finding |
|---|---|
| Codex cannot resume the Stage 1.17 thread by provider id | **It can.** A fresh process resumed threads by id, and a new turn then ran on the resumed thread [LOCAL A5, B2, B4, B5] |
| Resume silently creates a new context | **It does not.** An unknown id returns an error (`no rollout found`); no thread is created [LOCAL A5] |
| Safe restore requires credentials | **No.** The provider's own login is reused; nothing is stored |
| Safe restore requires transcripts or prompts | **No.** Only pointers (§4) |
| Provider history cannot distinguish relevant outcomes, forcing a guess | **It distinguishes interrupted, completed, and failed turns by turn id.** Where evidence is missing, the Play stays Unknown (§20) |
| Identity collapses into provider identity | **It does not.** `instanceId` stays authoritative; the thread id is a pointer (§8) |
| Persistence conflicts with a future Stadium Bridge | **It does not,** because the host owns persistence through a storage port (§24) |

## 3. CURRENT LIFECYCLE MAP: WHAT SURVIVES A RELOAD

### 3.1 What happens today on a clean reload [CODE]

1. `deactivate()` calls `server.stop()`, then `playerControlHost.dispose()`.
2. That closes each control. `closeOwnedProcess` ends stdin, waits 750 ms, then runs `taskkill /T /F` if the child is still alive.
3. `PlayerRoster.dispose()` then disposes the presentations.
4. A new extension host activates. It starts with the provenance table only.

### 3.2 What survives

| Item | On reload | Evidence |
|---|---|---|
| Extension host process | Replaced | VS Code |
| `PlayerControlHost`, adapters, `PlayerRoster` maps and book | **Gone** (memory only) | [CODE] `extension.ts:128-135`, `player-roster.ts:56-68` |
| `codex app-server` child | **Exits.** On a clean reload, Coach ends stdin; the app-server exits in 17–106 ms (code 0), well inside the 750 ms grace, so `taskkill` is normally never needed. On an abrupt crash, the OS closes the pipe with the same end-of-file effect | [CODE] `codex-app-server.ts:449-462`; [LOCAL] every probe end-of-file exit took ≤ 106 ms, including one mid-turn |
| A turn active at that moment | **Not drained.** Recorded as `interrupted` in provider history | [LOCAL] B1 (end-of-file mid-turn), B3 (hard kill) |
| Provider thread (the rollout on disk) | **Persists.** Resumable by id *once it has content* | [LOCAL] A5, B2, B4 |
| Thread with no content yet (put on field, never sent a Play) | **Not resumable.** `no rollout found`, the same error as an unknown id | [LOCAL] A5 |
| Per-thread writer lock | **Held while a process has the thread loaded; released at exit** | [LOCAL] A7 refused while held; later resumes succeeded |
| Controlled presentation tab | **Gone.** `isTransient: true`, so VS Code does not revive it | [CODE] `player-roster.ts:152` |
| Legacy provenance | Survives in `workspaceState` | Stage 1.8 |
| **`instanceId` ↔ `threadId` binding** | **Lost. Memory only today** | Stage 1.17 report; [CODE] |
| Open browser page | Stays open. SSE reconnects, and a canonical refresh follows | Stage 1.11 |
| Report files and watcher | Files persist; the watcher is recreated | Stage 1.14 |

**Facts available after activation:**
* **Today:** only the legacy provenance table.
* **After Stage 1.18:** the controlled binding records too (§4). Everything else is rebuilt from the provider and the Stadium.

### 3.3 An existing reload hazard to guard against

If VS Code delivers `onDidCloseTerminal` for the transient tab *during shutdown*, Stage 1.17's `retireTerminal` treats it like a human close (`player-roster.ts:190-204`). Today that costs nothing, because there is nothing to delete.

Once bindings persist, that same path would erase them on every reload. **R8 closes this.** VS Code reports *why* a terminal closed:
* `TerminalExitStatus.reason` is one of `Shutdown = 1` (*"The window closed/reloaded"*), `Process = 2`, `User = 3`, or `Extension = 4` [OFFICIAL, installed `@types/vscode`].
* Only `User` means Leave Field.

## 4. EXACT PERSISTENCE REQUIRED

### 4.1 The Stage 1.16 shape is not enough

The proposed shape was `{instanceId, playerType, providerSessionId}`. Evaluated against Stage 1.17 and the probe, it has four gaps:

1. **No seat.** The label `Codex 2` and the seat reservation cannot come back without it. Stage 1.7's provenance stores the seat for exactly this reason.
2. **No adapter discriminator.** What a session reference means depends on the adapter. One Player type could later have a Tier S and a Tier H adapter, with different references.
3. **It cannot tell "nothing to lose" from "lost".** Codex answers `no rollout found` both for a thread that never ran a turn and for one that is gone [LOCAL A5].
4. **It cannot reconcile an uncertain Play.** Nothing records which Play was in flight [LOCAL B1, B3].

### 4.2 The amended record (one per controlled Player)

```json
{
  "instanceId": "codex-7f3a91c2",
  "playerType": "codex",
  "seat": 2,
  "adapter": "codex-app-server",
  "sessionRef": "01a08f91-1f2e-7833-8f14-0d13253745b9",
  "historyExpected": true,
  "pendingPlay": { "clientRef": "5d7c…-uuid", "turnRef": "01a0…" }
}
```

`pendingPlay` is `null` when nothing is uncertain. `turnRef` is absent until the provider acknowledges the Play.

| Field | Why it is required | Evidence |
|---|---|---|
| `instanceId` | Sideline identity, which stays authoritative | — |
| `playerType` | Chooses the adapter family. Must match the id prefix | Existing identity rule |
| `seat` | Restores the same label and reserves the seat | Stage 1.7 precedent; missing from the 1.16 shape |
| `adapter` | Tells Coach how to interpret `sessionRef` | Stage 1.16 tiers |
| `sessionRef` | The provider session pointer. Opaque to Coach | [LOCAL] resume by id |
| `historyExpected` | Becomes `true` once any Play is sent. It separates "no context existed" (safe to open a fresh thread) from "context is gone" (a human decision) | [LOCAL] A5: identical errors for both cases |
| `pendingPlay.clientRef` | Finds the Play in history when the acknowledgement was lost | [LOCAL] B1: `userMessage.clientId` equals Coach's `clientUserMessageId` |
| `pendingPlay.turnRef` | Finds the Play when the user message was never persisted | [LOCAL] B3: an interrupted turn with **no** items |

### 4.3 What is never persisted

* Transcripts, prompts, Play text, or report contents.
* Tokens, credentials, or auth mode.
* Labels, model, effort, or runtime version. These are observed again at every open.
* PIDs, process handles, or terminal handles.
* The Game root. It is implicit in the per-Game store.
* Authority. It is fixed by Coach's code in Stage 1, and becomes persisted *policy* only when a human can choose it.

### 4.4 Scope, key, and validation

**Scope:**
* Per Game (`workspaceState`), machine-local, never synced, never committed.
* One record per controlled Player, about 250 bytes each.

**Key:** `sidelineCoach.playerSessions.v1`. It is separate from `sidelineCoach.playerProvenance.v1`, because provenance and provider-session binding are different concerns.

**Validation is per record.** A record must have exactly the seven keys, and:
* `instanceId` matches `^(claude|codex|antigravity)-[0-9a-f]{8}$`, with its prefix equal to `playerType`;
* `seat` is a positive safe integer;
* `adapter` is a registered adapter id;
* `sessionRef` is a string of 1–200 characters;
* `historyExpected` is a boolean;
* `pendingPlay` is `null` or `{clientRef: string, turnRef?: string}`.

**Rejection is per record.**
* An invalid record is dropped alone; its siblings are unaffected.
* A top-level value that is not an array is read as empty. The next legitimate write replaces it.
* This deliberately differs from Stage 1.7's provenance loader, which discards the whole table if any single record is malformed (`player-roster.ts:251-258`).

## 5. STORAGE OWNER

### The owner: the Player Control Host, through a VS Code-free storage port

```text
interface BindingStore {            // VS Code-free
  load(): unknown;                  // synchronous read of the raw value
  save(records): Promise<void>;     // ordered, awaited writes
}
Stage 1.18 implementation:  WorkspaceStateBindingStore  (extension side, wraps context.workspaceState)
Stadium Bridge later:       a file-backed store per Game  (§24)
```

### Why the host and not `PlayerRoster`

* **The host already sees the delivery lifecycle,** which is where the write-ahead marker is written (R6).
* **The host already owns transport truth** (Stage 1.17's contract line).
* **Owning persistence behind a port** keeps the Stadium Bridge move cheap: only the store implementation changes (§24).
* **`PlayerRoster` keeps sole ownership of legacy provenance.** Two keys and two owners match the two concerns. The records are never merged.

### Single writer, ordered writes

Writes go through one promise chain, the same pattern as today's provenance `writeChain`.

| Moment | What is written |
|---|---|
| Open succeeds | New record: `historyExpected: false`, `pendingPlay: null` |
| First SEND, before `turn/start` (write-ahead, awaited) | `historyExpected: true`, `pendingPlay: {clientRef}` |
| Provider acknowledges the Play | `pendingPlay.turnRef` |
| Turn completion observed (any status), or reconciliation reaches a definite outcome | `pendingPlay: null` |
| A fresh thread replaces a thread that never had content (§8) | New `sessionRef`, `historyExpected: false` |
| Leave Field, or a contradiction drop | Record removed |
| Reload, deactivate, or crash | **Nothing.** The record stays as it was |

**If the write-ahead fails, the Play is refused** with *"Coach couldn't record this Play safely."*
* Without the marker, a reload during the Play could not honestly report its outcome.
* Refusing is honest, and such failures are rare.
* No resend is ever involved.

## 6. RESTORE OWNER

**Three owners, one sequence:**
* **The Player Control Host orchestrates** restore.
* **`PlayerRoster` reconstructs** Sideline identity.
* **The adapter performs** the provider-specific resume, validation, and reconciliation.

```text
activate()
 1. host = new PlayerControlHost(new WorkspaceStateBindingStore(workspaceState)); register codex adapter
 2. PlayerRoster constructor (synchronous part):
      loadProvenance()                          ← legacy, unchanged
      plan = host.planRestores()                ← pure: per-record validation + contradiction check
      for each planned record:
        book.adopt(instanceId, playerType, seat)   (seat taken? → next free seat; identity unchanged)
        controlState = 'restoring'; create a fresh transient tab "Resuming…" (not focused)
      fire onDidChange
 3. CoachServer starts → the first status projection already contains every restoring Player
 4. For each Player, independently and asynchronously:
      host.restore(instanceId, {gameRoot, authority})  →  adapter restore sequence (§7)
      → Ready | NeedsVerification | NeedsSignIn | NeedsDecision(reason) | Failed
      PlayerRoster updates controlState, fires onDidChange → SSE status → browser converges
```

### `PlayerRoster` needs a distinct `adoptControlled()` path

Controlled Players must never pass through the legacy terminal funnel. That funnel's PID and start-time matching (`decidePendingMatch`) has no meaning for them.

### Why a controlled Player adopts identity immediately, unlike Stage 1.7's legacy PENDING

**Legacy restore proves something different.** It must prove a revived *terminal* is the same shell process, because a terminal named `Codex 2` can impersonate a Player.

**A controlled Player has no terminal to impersonate.** Its identity record is Coach's own. What the provider must prove is only the *capability*: that this conversation, in this Game, under this authority, can be driven.

**The browser forces this choice too.** It clears a selected `instanceId` that is absent from a render (`index.html:428-440`). If identity waited for provider proof, the phone would lose its selected target on every reload.

## 7. ADAPTER RESUME SEMANTICS (Codex 0.154.0)

### 7.1 Observed behaviour

The disposable probe [LOCAL] used only threads it created itself, in scratch folders, and deleted them afterwards:
* Codex's session store held 57 files before and after, and its index 38 lines before and after.
* `auth.json` was untouched.
* No probe process was left behind.
* The human's live Player was never touched.

It spent three deliberately tiny low-effort turns. The in-flight question could not be answered honestly without them.

| Call | Result |
|---|---|
| `thread/resume {threadId}`, fresh process, thread **with** content | OK. The same `thread.id`, with `thread.cwd` (captured), `cwd` (effective), `model`, `reasoningEffort`, `approvalPolicy`, `sandbox`, and status `idle` |
| The same call, thread that **never ran a turn** | `-32600 no rollout found for thread id …` |
| The same call, an id that **never existed** | **The same** `-32600 no rollout found …` |
| The same call, again in the same process | OK (rejoins) |
| The same call, in a **second process** while another holds the thread | `-32600 thread … already has an active writer` |
| With a `cwd` override pointing at another folder | OK. The **effective `cwd` silently becomes the override**, while `thread.cwd` keeps the original. With no turn run, the override did not persist to the next resume |
| **Without overrides**, on a thread whose turn had run | `approvalPolicy` came back as **`on-request`** instead of `never`, and effort as `null` |
| `turn/start` after resume | OK. A normal turn ran and completed on the same thread id in ~3.3 s |
| `thread/turns/list {itemsView: "full"}` | Turn id, status, and items. `userMessage.clientId` equals Coach's `clientUserMessageId` whenever the user message was stored |
| `thread/read {threadId}` | Read-only metadata, including the captured `cwd`. It does not load the thread |

### 7.2 Resume parameters and response

**Request:**
```text
thread/resume { threadId, cwd: <Game root>, approvalPolicy: "never",
                sandbox: "danger-full-access", excludeTurns: true }
```
* `threadId` is the only required field.
* `cwd`, `approvalPolicy`, and `sandbox` are Coach re-asserting its authority (R3).
* `excludeTurns: true` avoids hydrating the whole history. A Player that has received 10,000-character Plays has a large history, and the schema itself says full hydration *"is deprecated for paginated threads; use this with `thread/turns/list`"* [OFFICIAL].

**Response fields and what Coach does with each:**

| Field | Rule |
|---|---|
| `thread.id` | Must equal `sessionRef` |
| `thread.cwd` (captured) and `cwd` (effective) | Must both equal the Game root |
| `approvalPolicy` | Must be `never` |
| `sandbox.type` | Must be `dangerFullAccess` |
| `thread.status` | Must not be `systemError` (expect `idle`) |
| `model`, `reasoningEffort` | Presentation only. Effort may be `null` |

**The answers the brief asked for:**
* **Working directory.** An override changes only the *effective* directory, and silently. That is why R4 validates the captured one first.
* **Model and effort.** Reported, never validated.
* **Approval and sandbox.** Must be sent explicitly, because the probe's resumes without overrides fell back to a default approval policy [LOCAL].
* **Previous context.** Codex restores the thread history: prior turns are listed, and new turns run on the same thread. That the *model* actually recalls earlier Plays is proven only by the human test (§26).
* **Which id is authoritative.** The same UUIDv7 thread id stays authoritative. Resume never mints a new one.

### 7.3 The adapter's restore sequence

1. **Spawn a fresh `app-server`,** resolved exactly as Stage 1.17 does at open.
2. **`initialize`, then the version gate.** An uncertified version gives **Needs verification**. Stop there: no thread calls.
3. **`account/read`.**
   * `chatgpt`: continue.
   * No account: **Needs sign-in**.
   * `apiKey`: **Needs decision** (billing would change).
4. **`thread/read {threadId}`.**
   * `no rollout found`: **Missing** (§8, §13).
   * Any other error: Failed / Unknown.
   * Success: validate the thread id, `ephemeral: false`, and the **captured** `thread.cwd` against the Game root. A mismatch is a **Contradiction**.
5. **`thread/resume`** with the request in §7.2.
   * `already has an active writer`: retry with bounded backoff (about 10 s in total). If it persists: **Needs decision** — *"the previous Codex process is still running"*.
   * `no rollout found`: **Missing**.
   * Success: validate the echo (§9).
6. **If `pendingPlay` is set,** reconcile it (§20) with `thread/turns/list {threadId, limit: 10, sortDirection: "desc", itemsView: "full"}`.
7. **Bind the new control handle to the same `instanceId`.** The Player is now **Ready**.

**The allowlist grows from 3 methods to 7:** `initialize`, `thread/start`, `turn/start`, plus `account/read`, `thread/read`, `thread/resume`, `thread/turns/list`. It still never includes `thread/delete`, `fs/*`, or `command/exec`.

**Contract changes, both small and provider-neutral:**
* `PlayerControlFactory` gains `restore(request, binding)`, returning the control plus a reconciliation result.
* `PlayerControl.deliver(play, clientRef)` takes a **host-minted** `clientRef`. The host has to know it *before* the send in order to write ahead. C9's same-id retry after `-32001` is unchanged.

## 8. SIDELINE IDENTITY RECONSTRUCTION

| Question | Answer |
|---|---|
| **Who reads the bindings?** | `host.planRestores()`, synchronously (`workspaceState.get` is synchronous). It is called from `PlayerRoster`'s constructor after `loadProvenance()`, before the server starts |
| **Who owns reconstruction?** | `PlayerRoster` owns identity. The host owns the records and the provider restore |
| **When during activation?** | Identity adoption is synchronous at construction. Provider restore is asynchronous afterwards |
| **How are seats reserved?** | `book.adopt(instanceId, playerType, seat)` makes the identity live immediately. If the seat is already taken (by legacy PENDING provenance or another restored record), the Player gets the next free seat. The label changes; the identity does not; the record is updated. Only corruption can cause this, because one allocator writes both tables |
| **How are labels regenerated?** | From type plus seat (`fieldLabel`), with the controlled suffix and state, e.g. `Codex 2 · Controlled · Resuming…`. Never read from storage |
| **How are exact instance ids restored?** | Taken verbatim from the record. `adopt` refuses an id that is already live; that is a contradiction and the record is skipped |
| **Does `PlayerRoster` need a distinct method?** | **Yes: `adoptControlled(record)`.** It creates the identity, a fresh presentation, and the `restoring` state. It never touches the legacy terminal funnel |

**The planner (a pure function):**
* drops unreadable records;
* quarantines contradictions (§15);
* keeps records whose adapter is not registered, as **Needs verification**, without contacting any provider;
* restores the rest.

**Dispatchability comes from `PlayerRoster.resolve()`, not from the book:**

| Control state | `resolve()` returns | HTTP |
|---|---|---|
| `restoring` | `pending` | Existing 409, *"That Player is reconnecting — try again in a moment."* |
| Needs verification, Needs sign-in, Needs decision | New `unavailable` state carrying a human reason | 409 |
| Ready | `live` / `controlled` | — |

**The Missing branch:**
* **`historyExpected: false`** (no Play was ever sent):
  * The adapter opens a fresh thread with Stage 1.17's full open validation, and the host rewrites `sessionRef`.
  * The tab says *"No Plays had been sent yet — Coach opened a new conversation for Codex 2."*
  * This is not silent, and no context is lost.
* **`historyExpected: true`**:
  * **Needs decision:** *"Can't resume Codex 2 — its conversation is no longer available."*
  * The identity, seat, and record stay until the human takes the Player off the field.
  * An explicit **Start Fresh** is later work, not part of the next Play.

**The high-water rule is unchanged.** `adopt` raises the per-type high-water mark to at least the restored seat. Stage 1.7's documented limitation remains: the mark is not persisted, so after a reload it restarts from the highest restored or pending seat.

## 9. PROVIDER-SESSION VALIDATION

| Check | Source | On failure |
|---|---|---|
| Adapter registered for the record | `record.adapter` against the host registry | Needs verification (kept) |
| Provider version certified | `initialize.userAgent` | Needs verification (kept; no thread call) |
| Auth mode is `chatgpt` | `account/read` | Needs sign-in, or Needs decision (API key) |
| Thread exists | `thread/read` | Missing → §8 rules |
| Thread id matches the record | `thread/read` and the resume response | **Contradiction** |
| Thread is not ephemeral | `thread/read` | **Contradiction** |
| **Captured** cwd equals the Game root | `thread.cwd` | **Contradiction** ("belongs to another folder") |
| Effective cwd equals the Game root | resume `cwd` | **Contradiction** |
| Approval policy is `never` | resume `approvalPolicy` | **Contradiction** |
| Sandbox is `dangerFullAccess` | resume `sandbox.type` | **Contradiction** |
| Thread status is healthy | resume `thread.status` | Failed |
| Single writer | resume error `already has an active writer` | Bounded retry, then Needs decision |
| Model / effort | resume response | **Never validated.** Presentation only |

**On any Contradiction:**
* The fresh `app-server` is closed immediately. No turn is sent.
* The Player stays visible as **Needs decision**, with its reason.
* Its record is kept, so the human can see the problem and dismiss it.
* A contradiction is never treated as "close enough".

## 10. PRESENTATION RESTORATION

* **Always a new transient Pseudoterminal.** The old object died with the extension host, and `isTransient` prevents revival.
* **Created without focus.** Stage 1.17 calls `show(true)` on open; restore should not call `show` at all, so a reload does not grab the terminal panel.
* **What the tab shows:**
  1. **First:** `CODEX 2 · CONTROLLED` and `Resuming the same conversation…`
  2. **Then exactly one of:**
     * `READY · same conversation · runtime 0.154.0 · <model> · <effort or "default effort">`
     * a previous-Play line (§20): `Last Play before restart: Interrupted — it may have made partial changes`, or `Completed`, or `Failed: …`, or `Unknown — check the Game before sending it again`
     * a Needs-… message stating the one available human action: *"Close this tab to take Codex 2 off the field."*
* **The tab never carries identity.** Closing it for reason `User` is Leave Field (§14).
* **No transcript is replayed** into the tab in this stage.

## 11. BROWSER RECONNECTION BEHAVIOUR

**No browser-local restoration logic. The server and `PlayerRoster` stay canonical.**

**The sequence:**
1. Reload.
2. SSE drops. The browser shows Reconnecting and disables mutations (the Stage 1.11 contract).
3. The new server starts *after* `PlayerRoster` has adopted all identities (R1).
4. The SSE `hello` triggers the canonical status refresh. Restored Players are already present as `Resuming…`, so the selected `instanceId` survives.
5. Each restore outcome fires `PlayerRoster.onDidChange`, which reaches the browser through the existing `player-roster-change` broadcast (`server.ts:145`). The browser refreshes and the label turns Ready.

**The projection:**
* Controlled instances gain a `controlState` field (`restoring`, `ready`, `needs-verification`, `needs-sign-in`, `needs-decision`) and a short `stateMessage`.
* The label suffix is built server-side, e.g. `Codex 2 · Controlled · Resuming…`.
* The browser keeps rendering labels as it does today; no new browser logic is required. Disabling non-ready options is optional polish.

**Dispatching to a restoring or unavailable Player** returns a 409 with the reason, which the browser shows as a toast. Nothing is queued.

## 12. MULTIPLE-PLAYER BEHAVIOUR

* **Independence.** Each record gets its own `app-server`, thread, writer lock, and outcome. One Player's failure never waits on, cancels, or changes another.
* **Order.**
  * Identity adoption is synchronous, in a deterministic order: by type, then seat.
  * Provider restores run concurrently, limited to three at a time.
  * Restore order does not affect correctness, because every binding is exact by `instanceId`.
* **Seats.** Each Player keeps its own seat. On a collision, only the later record moves to the next free seat.
* **High-water.** If Codex (seat 1) and Codex 3 are restored, the next new Codex gets seat 4.
* **Duplicates and corrupt records:** §15 and §4.4.
* **Isolation proof** is built into the human test (§26). Play A goes only to Codex 2; after reload, Codex (seat 1) knows nothing about it.

## 13. STALE-RECORD CLEANUP

| Event | The record |
|---|---|
| Human closes the controlled tab (reason `User`) | **Removed** (Leave Field, §14) |
| A future "Leave Field" button | **Removed** |
| Window reload or VS Code close (reason `Shutdown`, or `deactivate`) | **Kept** |
| Coach disposes the tab itself (reason `Extension`) | **Kept** |
| Close reason `Unknown` | **Kept.** Failing toward identity costs only a Player reappearing, which the human can close again |
| Provider child crashes while Coach runs | **Kept** (§22) |
| Resume finds Missing, and `historyExpected` is `false` | **Kept.** `sessionRef` is replaced by the fresh thread |
| Resume finds Missing, and `historyExpected` is `true` | **Kept** as Needs decision, until the human leaves |
| Contradiction or duplicate | **Kept** and quarantined as Needs decision, until the human leaves |
| Unreadable record | Dropped at the next write, because it cannot be shown |
| Game folder deleted | Its per-workspace storage is orphaned along with it. Nothing to do |
| Codex version changed | **Kept** as Needs verification |

**Rule.** A record disappears only through an explicit human act, or because it is unreadable. **Elapsed time never deletes a record.** That is Stage 1.7's "no timers" principle.

## 14. EXPLICIT LEAVE FIELD SEMANTICS

**Trigger in Stage 1.18:** the human closes the controlled Player's tab, i.e. `terminal.exitStatus?.reason === TerminalExitReason.User`. A future Coach button maps to the same operation.

**Effects, in order:**
1. Mark the Player as leaving.
2. Close the channel (end stdin). An active turn is interrupted; the human chose to leave.
3. Remove the binding record (awaited).
4. Retire the identity. Seat rules are unchanged.
5. Fire the change event.

**Leave Field never:**
* deletes the provider conversation (R11);
* resends anything;
* touches a sibling.

**These are not Leave Field:** reasons `Shutdown`, `Extension`, and `Unknown`; `deactivate`; any crash.

**Implementation note.** `PlayerRoster`'s close listener must read the exit reason before it decides anything, and the dispose path must never remove records.

## 15. DUPLICATE-BINDING SAFETY

* **Provider layer (the second line of defence).** Codex refuses a second process on a loaded thread: *"already has an active writer"* [LOCAL A7].
* **Sideline layer (the primary rule).**
  * The planner refuses two records with the same (`adapter`, `sessionRef`), and two records with the same `instanceId`.
  * **Both** records are shown as Needs decision (*"Two Players claim the same Codex conversation"*). Neither is restored, and neither contacts the provider. **Ownership is never guessed.**
  * Once the human takes one off the field, the other restores at the next activation.
* **At bind time,** `host.open` refuses a `sessionRef` that is already bound to another instance. This is defensive; fresh threads cannot collide.
* **Across VS Code windows.** Two windows on one Game through different workspace identities use separate stores. The writer lock stops the second from resuming, which gives Needs decision, never a takeover.

## 16. VERSION-GATE BEHAVIOUR

**The rule.** The same exact-version gate as Stage 1.17 (`CERTIFIED_VERSION = '0.154.0'`), applied **before any thread call**.

**If Codex was upgraded while Coach was off:**
* The record is kept, and the Player shows **Needs verification**: *"Codex was updated to X. Coach needs to verify this version before it can resume Codex 2."*
* There is no resume through an uncertified version, no deletion, and no fallback to the legacy path.

**Recovery.** Certify the new version (code update, conformance run, schema diff). The next activation then restores the Player.

**A second reason to gate before touching threads:** a provider upgrade may also change the stored history format (e.g. `historyMode` `legacy` versus `paginated`).

## 18. IN-FLIGHT PLAY BEHAVIOUR

### What Codex 0.154.0 actually does [LOCAL]

| Scenario (as modelled) | What the provider did | History after resume |
|---|---|---|
| **Stdin closed right after `turn/start` was acknowledged.** Covers a clean reload (Coach ends stdin) and an abrupt extension-host crash (the OS closes the pipe) | **Did not drain the turn.** No `turn/started` or `turn/completed` was emitted. Exited with code 0 in 106 ms | The **same turn id**, status **`interrupted`**, `completedAt` set. The user message **was stored**, with `clientId` equal to Coach's `clientUserMessageId`. No agent message |
| **Provider process hard-killed right after the turn started.** Covers a provider crash, and Coach's own `taskkill` fallback | `turn/started` had already been emitted. Exited with code 1 in 169 ms | The **same turn id**, status **`interrupted`**, `completedAt` null, and **no items at all**: the user message was never stored |
| **A turn completing normally** | `turn/completed` with status `completed` | Status `completed`, a user message with `clientId`, and an agent message |

### What that means

* **A reload never finishes the Play in the background.** In both cases modelled, the provider stopped the turn within 0.1–0.2 s and recorded it as interrupted.
* **"Interrupted" is definite about the turn, not about its side effects.** Commands or file edits made before that point may already have happened.
* **A turn that finished just before the reload shows `completed`.** Coach simply missed the notification.
* **So the in-flight Play is reconciled from history after resume** (§20). It is never resent, and never assumed to have failed or succeeded.
* **Not modelled: a reload after Coach's write but before the provider received it (acknowledgement loss).** If the request never arrived, no turn exists; if it arrived, one of the rows above applies. Without a turn id, Coach cannot tell these apart, so the outcome is **Unknown**.
* **Stage 1.17's clean-reload path fits these results.** End of stdin, a 750 ms grace, then `taskkill` if needed. In every observed case the provider exited well inside the grace period, so a clean reload records the turn as `interrupted` with its user message stored.

## 19. EXACTLY ONCE / UNKNOWN PRESERVATION

**Rules:**
1. **Restore never calls `turn/start`.** Reconciliation only reads history (`thread/turns/list`).
2. **The pending marker is written before the send.** If it is still present after a reload, it means *"Coach cannot confirm what happened"* until evidence arrives.
3. **Definite outcomes come only from provider history:** Completed, Failed, or Interrupted.
4. **Everything else stays Unknown, visibly,** until the human sends a new Play (which replaces the marker) or takes the Player off the field.
5. **The only automatic retry anywhere is unchanged:** `-32001` at delivery, which proves ingress rejection.
6. **Retrying a resume is safe,** because resume executes nothing.
7. **The human decides whether to resend.** Coach may say *"Unknown — check the Game before sending it again."* It never offers "Retry" as a default action.

**Prohibited:**
* resending the last Play;
* inferring failure because Coach disappeared;
* inferring success because the resume succeeded;
* treating a missing `clientId` as proof the Play did not run.

## 20. OUTCOME RECONCILIATION

### What exists today, before a reload [CODE]

All of these are in memory only:
* `clientUserMessageId`, minted per SEND inside the adapter (`codex-app-server.ts:283`);
* `turnRef`, from the `turn/start` response (`:299`);
* `activeTurnRef`, from notifications.

### What Codex exposes [LOCAL]

* **`clientUserMessageId` is persisted,** and appears in history as `userMessage.clientId` (B1, B5). That settles Stage 1.17's open question about persistence. Whether Codex de-duplicates by it is still unobserved; Coach never needs it, because it never resends.
* **A turn can be found after resume by its id** (B2, B4).

### The algorithm

The adapter runs it after a successful resume, and only when `pendingPlay` is set:

```text
turns = thread/turns/list {threadId, limit: 10, sortDirection: "desc", itemsView: "full"}
if pendingPlay.turnRef:
    t = turns.find(id == turnRef)            (page further if absent; bounded)
    completed   → Completed
    failed      → Failed (turn.error.message)
    interrupted → Interrupted
    inProgress  → Unknown   (cannot be live in a fresh process)
    not found   → Unknown
else (acknowledgement never arrived):
    t = turns.find(any userMessage.clientId == clientRef)
    found       → the same status mapping as above
    not found   → Unknown   (B3: a started turn can exist without its user message)
definite → clear pendingPlay
Unknown  → keep it (shown once; replaced by the next SEND)
```

### When the outcome becomes definite, and when it must stay Unknown

| Evidence | Outcome |
|---|---|
| Turn found by `turnRef` or `clientRef`, with status `completed`, `failed`, or `interrupted` | **Definite** |
| `turnRef` known, but that turn is not in history | **Unknown** |
| No `turnRef`, and no user message carries `clientRef` | **Unknown**, even if some unmatched interrupted turn exists |
| Resume itself failed (missing, contradiction, version, auth) | **Unknown.** No evidence can be read |
| No `pendingPlay` | Nothing to reconcile |

**Never infer an outcome** by recency ("the newest turn must be mine"), by matching the Play's text, or by elapsed time. The stored user message does contain the Play text, but text matching is deliberately avoided: `clientRef` and `turnRef` are exact, and Coach neither needs nor stores the text.

## 24. STADIUM BRIDGE IMPLICATIONS

**Question:** would this binding still make sense if the Player Control Host moved into a Stadium Bridge?

**Yes.**
* **The host already owns the records** through the `BindingStore` port. Only the store implementation changes: `workspaceState` becomes a per-Game file store owned by the Bridge.
* **The record holds nothing tied to VS Code.** No handles, no PIDs, no paths; the Game root is implicit in the store's scope.
* **Restore is a host operation,** callable with no VS Code at all.

**What changes when the Bridge arrives (not now):**
* **The Game key becomes explicit.** `workspaceState` scopes by VS Code workspace; a Bridge needs its own Game identity, such as the Game root or repository identity.
* **Identity and seat ownership may move with the host,** because the Bridge holds Players across windows. `PlayerRoster` then becomes a client-side projection.
* **With a surviving Bridge, a VS Code reload no longer stops the `app-server` at all.** In-flight Plays keep running, and reconciliation is needed only when the Bridge itself restarts.

**Avoided, because each would have made extraction expensive:**
* storing bindings in VS Code-only `PlayerRoster` code;
* storing process handles;
* tying identity to the terminal lifecycle.
