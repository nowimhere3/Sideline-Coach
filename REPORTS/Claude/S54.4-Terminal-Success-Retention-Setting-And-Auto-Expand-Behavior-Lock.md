## WHAT CHANGED

**Preference** (`src/running-players.ts`)
- `CoachPreferences.terminalRetention` is a stable enum: `'30s' | '5m' | '30m' | 'until-dismissed'`, default `'5m'`.
- `isTerminalRetention` guards it.
- A missing, malformed or unknown stored value loads as `'5m'`. Legacy preference files are safe, and the other fields are preserved.

**Daemon** (`src/control-plane/daemon.ts`)
- `POST /api/preferences` accepts `terminalRetention` and persists it.
- Anything outside the four values returns 400 with a plain message and changes nothing.
- It follows the same pattern as the other preference fields and leaves them untouched.

**Browser** (`src/public/index.html`)
- The provisional hard-coded 5-minute constant is gone. There is now one source: `terminalRetentionMs()`, reading `preferences.terminalRetention` with a safe fallback to 5 minutes.
- It is applied at read time to the existing S54.3 `terminalEvidence` record. The record stores no lifetime, so a changed setting applies immediately and a stale stored value can never override it. There is no second store.
- `until-dismissed` gives an infinite lifetime and schedules no wake-up timer at all.
- The wake-up timer is keyed by (play, lifetime), so changing the setting schedules its own.
- Only `completed` evidence is ever timed. `failed` and `unknown` code paths are unchanged.
- The Settings card **Terminal Success Retention** follows the existing radio-fieldset convention (as Running Players). It reads "How long successful Terminal output stays available after the command finishes. Failed commands stay until dismissed or the next Play." It has no jargon.
- Gating: it shows only while Dev Mode **and** View Player Terminal are on, because the evidence exists only under both. It is independent of Advanced Player Discovery.

## ONE THING TO CONFIRM (auto-expand)

This Play's contract says Dad likes the current "auto-open" behavior: desktop half-height and mobile full-screen. **I could find no auto-expand code in the source.** Here is what actually opens the console:

- The **only** place a console gets opened is the human's **Expand** click (`consoleExpandedByInstance.add`, exactly one call site).
- That open state is per Player, held in page memory, and carries into that Player's next Plays (LPT-29). So after Dad clicks Expand once, later commands on that Player open already-expanded, which reads as "auto-opens".
- The sizing is the existing responsive CSS: `.play-console` is `height: 50vh` (desktop, embedded) and `position: fixed; inset: 0` at **≤619 px** (mobile, full-screen).

Consequences:

- I froze **that**, not a new feature. I added no toggle, no breakpoint and no expand logic.
- After a **page reload**, or for a Player Dad has never Expanded, the console opens on the first Expand click.
- If Dad has seen a console open with **no click at all** (fresh page, never-Expanded Player), then something I did not find opens it. Please tell me and I will chase it. Otherwise the lock is exactly what the field approved.
