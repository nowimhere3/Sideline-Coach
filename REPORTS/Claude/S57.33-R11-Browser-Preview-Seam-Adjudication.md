## Verdict: GREEN WITH CORRECTIONS

AGY is mostly right. Local Preview is a small seam: no daemon proxy is needed, `Game + Stadium` is the right identity, and Remote belongs in V2. The report has four problems, the most important being that the preview link only works for some viewers. Findings are based on the AGY report plus targeted source reads.

## What was checked in the source

- **The daemon runs in the Stadium's environment.** `src/extension.ts:143` spawns `out/control-plane/daemon.js`. The daemon listens on `127.0.0.1` only (`daemon.ts:1172`), and the Stadium connects to `ws://127.0.0.1:3100` (`stadium-client.ts:229`). In WSL, SSH or Codespaces, the daemon and the Game's dev server sit on the same side.
- **The extension runs where the workspace is.** `package.json` sets no `extensionKind` and uses `main`, so in remote setups it runs in the remote extension host — where `asExternalUri` must be called from.
- **The daemon can host an iframe.** It serves `index.html` with no CSP (`daemon.ts:~5498`). The legacy `src/server.ts:952-955` sets `X-Frame-Options: DENY` and `default-src 'self'`, which would block one. The preview view must live on the daemon UI, not the legacy server.
- **Nothing is built yet.** No webviews, `asExternalUri`, `openExternal` or `simpleBrowser` calls exist, as AGY said.

## Answers to the 8 questions

1. **Is the Local Preview seam sound?** Yes, once the corrections below are applied.
2. **Is `Game + Stadium → PreviewEndpoint` the right abstraction?** Yes, and it's stronger than AGY argued. Port forwarding and port ownership only exist per Stadium environment, so `Game → Port` is wrong once a remote setup is involved. See correction 1 for one more rule.
3. **Is `asExternalUri` the right bridge?** Yes, called on the Stadium side (which is the case here). Note:
   - On WSL/SSH it can return a *different* local port than the dev server's.
   - On Codespaces it returns an authenticated `*.app.github.dev` URL.
   - The forward only lasts as long as the VS Code window — another reason to key it by Stadium.
4. **Is V1 correctly scoped with no daemon proxy?** Yes. V1 must not forward HTTP or WebSocket traffic to any Game port.
5. **Do the viewport presets work over the same running app?** Yes, as presentation only:
   - Use one iframe whose width changes, not three at once (three iframes = three copies of the app, each with its own state and live-reload connection).
   - Resizing triggers the app's CSS responsive layouts but doesn't emulate a device: no touch, no mobile browser identity, no retina scaling. Label the presets as approximate.
6. **Is an external browser fallback needed?** Yes, and it can't appear only on failure. A page can't reliably detect a blocked cross-origin iframe (`X-Frame-Options` / `frame-ancestors`), and Codespaces login cookies may fail inside an iframe. "Open in new tab" must always be visible.
7. **Did AGY miss a blocker?** No blocker that changes the architecture, but four corrections that change the design (below).
8. **Should Remote / Send to Phone stay V2?** Yes. AGY's reasoning holds (localhost exposure / SSRF, host checks, root-relative assets, live-reload sockets), and it also follows from correction 1: the phone has no valid URL to open.

## Corrections to AGY

1. **The preview URL only works for some viewers (most important).** `externalUrl` is valid only in a browser on the machine running VS Code. The Sideline dashboard is also viewed from a phone over the relay; handing that viewer the URL gives a broken iframe. The daemon must check who is asking (it already distinguishes principals, `daemon.ts:1832`). Remote viewers get `{ available: false, reason: 'remote-viewer' }` and a "Preview is on your computer" note — never a URL.
2. **Level 1 discovery doesn't exist.** There is no `vscode.workspace.onDidChangePortAttributes`, and no stable API lists forwarded ports. `registerPortAttributesProvider` only fires in remote auto-forward flows, never on local Windows. Discovery must be:
   - a URL or port declared in `.sideline/game.json`,
   - then a port Dad already confirmed,
   - then candidates from `package.json` scripts and framework defaults (plus a literal `port` in `vite.config`), each probed.

   Reading "Local: http://localhost:5173" from VS Code terminals is optional; it misses dev servers AI Players start outside VS Code terminals.
3. **Port ownership.** If Game A runs Vite on 5173 and Game B's Vite falls back to 5174, a probe from Game B finds Game A's app on 5173. A detected port needs an ownership check: the listening process's command line should include `<rootFsPath>/node_modules/...` (Win32_Process on Windows, `/proc/<pid>/cmdline` on Linux). Otherwise ask Dad to confirm once and remember it. A declared URL skips the check.
4. **Probe `localhost`, not `127.0.0.1`.** On Node 17+, Vite often listens only on `::1`, so a probe to `127.0.0.1:5173` is refused. Probe both address families and store `http://localhost:<port>`. Cookie scope depends on host spelling (ports don't count, but `localhost` vs `127.0.0.1` does); where safe, load the preview shell with the same host spelling as the Game's URL, or the Game's login cookies may break in the iframe.

Smaller points:

- **Pull, don't push.** Resolve the endpoint when Dad clicks (daemon→Stadium request with a short cache) instead of pushing `game.preview.snapshot`. No polling, nothing goes stale.
- **"Open in new tab" is a plain link** (`<a target="_blank" rel="noopener">`). AGY's `vscode.env.openExternal` from the web UI would need a UI→daemon→Stadium round trip. `openExternal` belongs only to the VS Code command.
- **`stadiumType` propagation is off the critical path.** The Stadium resolves the URL itself. Defer it or ship it as a trivial add-on.
- **Scheme allowlist.** A declared `previewUrl` must be `http:` or `https:`. `openExternal` or an iframe with `javascript:`, `file:` or custom schemes is a real hazard.
- **Wire shape.** Send `endpoints: PreviewEndpoint[]` with one marked primary, even if V1 uses only one, so a frontend + API or Storybook needs no protocol change later.
- **Codespaces risk, unconfirmed.** Recent Vite versions reject unknown hosts ("Blocked request… not allowed"), which may hit `*.app.github.dev`. If so, show a plain-language hint. Sideline never edits the Game's config.

## Canonical architecture

```text
Stadium (extension host, same environment as the Game's dev server)
  resolvePreview(gameId):
    candidates = declared → remembered → package.json/framework defaults
    probe localhost (both address families) + ownership check (process path under rootFsPath)
    clientUrl = asExternalUri(localUrl)          // valid for the VS Code client machine only
  → PreviewEndpoint { gameId, stadiumId, localUrl, clientUrl, port, source,
                      ownership: 'declared'|'verified'|'confirmed', status, observedAt }

Daemon (no proxy)
  GET /api/games/:gameId/preview
    local principal  → ask the primary Stadium's resolvePreview → endpoint
    remote principal → { available:false, reason:'remote-viewer' }
  endpoints cleared on Stadium disconnect

Dashboard (daemon-served index.html)
  Preview view: one iframe(src=clientUrl), presets Desktop / Tablet 768×1024 / Phone 390×844 (+ rotate)
  Always-visible "Open in new tab ↗" link; empty state "Your app isn't running yet"

VS Code: coach.previewInBrowser → resolvePreview → openExternal(clientUrl)
```

## Exact V1 boundary

**In:**
- Local Windows, WSL/SSH, and Codespaces with an external tab (iframe where it works).
- One primary endpoint per Game and Stadium.
- Presets, always-visible external link, VS Code command.
- Discovery by declared URL, remembered port, or verified candidate.

**Out:**
- Any proxying through the daemon or relay.
- Send to Phone.
- Starting or stopping dev servers.
- Multi-device mirroring.
- Standalone daemon without VS Code.
- `stadiumType` wire propagation (optional).

## Smallest implementation sequence

1. **Pure module `src/preview-discovery.ts`** (no `vscode` import): candidate ranking, probe on both address families, ownership check, scheme allowlist, `PreviewEndpoint` type, unit tests.
2. **Stadium:** `resolvePreview` handler using `asExternalUri`, remembered confirmation stored per Game, `coach.previewInBrowser` command.
3. **Protocol and daemon:** `game.preview.resolve` request type in `protocol.ts`; `GET /api/games/:gameId/preview` gated to the local principal; clear endpoints on disconnect.
4. **Dashboard:** Preview view with iframe, presets, external link, and empty / offline / remote-viewer states.
5. **Field proof:** see gates below.
