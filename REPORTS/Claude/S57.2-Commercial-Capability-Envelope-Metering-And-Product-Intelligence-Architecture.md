## 1. Executive Verdict

**Yes, this is feasible without a major refactor.** Every capability Dad listed that actually exists funnels through a small number of choke points. Most of them are in one file, `daemon.ts`. The architecture below adds one read-only authority, one gate interface and three small local stores. It changes no feature internals.

The most important recon findings:

1. **Mobile Remote has one choke point.** Every phone request goes relay → `RelayClient` → `InProcessRemoteAdapter` → **`ControlPlaneDaemon.dispatchRemoteRequest()`**. Both servers bind to `127.0.0.1`, so there is no LAN path around it. The natural "session" signal is the phone's **`/api/events` SSE stream**, which the daemon already tracks per principal in `sseClients`.
2. **Games have two admission paths.** One is explicit **Add Game** (`runAddGame`). The other is *implicit auto-registration*: any VS Code window with the extension registers its workspace as a Game (`extension.ts` → `registerGameInRegistry`, and Stadium `setGame` → `recordKnownGame`). A Game limit that counts auto-registered windows would burn slots whenever Dad opens a random folder. The gate therefore belongs at **admission on first Play or explicit Add**, not at registration.
3. **Scout has one execution choke point per side.** On the Stadium side it is `StadiumClient.deliverScout()`. On the Control Plane side it is `ControlPlaneRouter.dispatch()` plus the Dev-only `/api/scout/formation-run`. A "Scout" *is* a Formation today (`ScoutPlayerAdapter.execute` → `runScoutFormation`). "Strong Scout" and "A-Team reconciliation" are **not runtime tiers**. A-Team reconciliation is an ordinary Player Play.
4. **The router already has the right seam for S57.1.** `ControlPlaneRouter.setCandidateEnricher()` is where entitlement joins the candidate set, so "one brain" survives cleanly.
5. **"Coach Refresh" is two different things.** Scout depth-chart maintenance (`runCoachRefresh`, via `ScoutBootstrapService`) and Coach Routines' "Coach Refresh" handoff that Dad sees in the UI copy. This must be disambiguated before capability IDs are frozen.
6. **Autofill and Wires: NOT FOUND** in source. They are reserved as capability IDs with no gate points.
7. **The relay's enrollment header is the only existing server-side entitlement seam.** Production relay requires `ENROLLMENT_KEY`, and machines are provisioned by a hand-placed `~/.sideline/remote/beta-enrollment.json`. This is a **launch question for Remote itself** (§21 Q1), independent of commercialization.
8. **There is no install/account identity and no product telemetry.** The only durable IDs are `hostPublicId` (created only when Remote is enabled) and per-phone `deviceId`s.

**Launch impact is nearly zero code.** Before launch I recommend one tiny change (a durable `installId`) plus four decisions. Everything else can be breadcrumbed or deferred (§19, §22).

Four concepts, kept separate: **Capability** (what), **Grant** (how much, from where), **Usage** (how much used), **Decision** (may I, now).

## 5. Feature-Gate Contract

One service, three verbs, one ask. **Feature code never sees grants, licenses or plans.**

```ts
interface FeatureGate {
  /** Pure read. "May I execute this capability now?" No side effects. */
  check(capability: CapabilityId): GateDecision;

  /** Count meters: check + record one idempotent consumption. Re-calling with the same key is a no-op. */
  charge(capability: CapabilityId, idempotencyKey: string, units?: number): GateDecision;

  /** Release/refund (e.g. Game archived, Scout rejected before start). Idempotent. */
  release(capability: CapabilityId, idempotencyKey: string): void;

  /** Duration meters: the Remote minute meter is the only V1 user. */
  readonly minutes: DurationMeter;                   // §7
}
```

Rules:

1. **Gate at the entry, not inside the feature.** Once allowed, the feature runs exactly as today.
2. **Entitled ≠ Available ≠ Recommended.** The gate answers only *entitled (and has allowance)*. Runtime readiness stays with its current owner (Scout `capability.state`, relay stats). Recommendation stays with S57.1. UI and routing combine the three explicitly:
   ```
   scoutOptionVisible = gate.check('scout.play').allowed && scoutCapability.state === 'ready'
   scoutRecommended   = scoutOptionVisible && S57.1 net value > margin
   ```
3. **Deny copy is capability-named** ("Scout Plays are used up until Oct 1."), never plan-named ("Upgrade to Pro"). Upgrade UI is a separate, deferred consumer of `GateDecision`.
4. **Unknown capability id** is a programming error: throw in tests, and in production allow with a warning. Core must never break on a catalogue bug.
5. **Reserved capabilities** return `reason: 'reserved', allowed: true` until they get a gate point.
6. **Facets:** `check(facet)` uses the facet's own grant if one exists, otherwise its `parent`'s.

## 6. Allowance / Usage Model

### 6.1 One store, four meter kinds

| Meter | Examples | Stored as | Consumption |
|---|---|---|---|
| `flag` | `routing.intelligent`, `alerts.advanced` | nothing | none, entitlement only |
| `count` | `scout.play`, `scout.maintenance`, `routines` (if ever) | per grant+period: `consumed` + recent idempotency keys (last 500) | `charge(key)` |
| `minutes` | `remote.access` | per grant+period: merged **minute-index intervals** `[[a,b],…]` | union of minute buckets (§7) |
| `ceiling` | `games.active` | a **set** of member ids | `charge(gameId)` adds, `release(gameId)` removes; `used = set size` |

### 6.2 Periods

`periodKey(grant.period, now)`:

- lifetime → `'lifetime'`
- daily → `'dYYYY-MM-DD'` (local day)
- monthly calendar → `'YYYY-MM'`
- monthly anchored → cycle index from the anchor
- rolling N days → the last N daily buckets are summed (daily sub-buckets kept for N days)

The `resetsAt` shown to Dad is the next boundary.

### 6.3 Multiple grants (stacking)

- `unlimited` dominates.
- Otherwise, consumption draws from the grant that **expires soonest** first (promo before base), and each grant has its own bucket.
- `remaining = Σ remaining(valid grants)`.

This handles lifetime trial minutes, promotional top-ups, monthly base allowance and manual overrides with one rule.

### 6.4 Journal (support-grade, not a financial ledger)

- Every `charge`/`release` appends a `UsageReceipt` to `usage-journal.jsonl`, rotated at 1 MB with 3 kept.
- Counters in `usage.json` are the fast path. If `usage.json` is corrupt, rebuild by replaying the journal for current periods.
- **Idempotency** comes from the receipt `id`. **Restart-safety** comes from atomic writes plus the journal. **Double-count resistance** comes from idempotency keys and minute-set semantics.
- Support can read the journal: "3 Scout Plays on Oct 2 at …, clientRefs …".

### 6.5 When a count is charged

- `scout.play`: charged when the Stadium **accepts** the dispatch (`handleDispatchAccepted` for the Scout target), keyed `scout.play:<clientRef>`. A rejected or unavailable Scout is never charged. A Formation that fails with *zero receivers started* is released, keyed on the same id. Anything else is support's call.
- `scout.maintenance`: charged at `authorizeAndStart/refresh` acceptance, keyed by the session start id.

## 7. Mobile Remote Metering Architecture

### 7.1 Definition: one Remote Minute

> **A Remote Minute is one wall-clock minute (UTC minute index) during which at least one paired phone was connected to this Sideline**, meaning at least one of:
> - a `remote-device` `/api/events` SSE stream was open at any instant of that minute, or
> - an authenticated `remote-device` request (non-public, non-pairing) was handled in that minute.
>
> Minutes are counted **once per install**. Two phones, three tabs or ten reconnects inside the same minute still count as one minute.

Why this definition:

- **Fair.** It measures time the phone is actually attached. Mobile browsers suspend background tabs, the relay then cancels the stream, and the adapter's `cancel()` closes it.
- **Explainable.** "Time your phone was connected."
- **Cheap.** It observes signals the daemon already has, with no Mobile changes.
- **Double-count proof.** Set semantics over minute indices.

It deliberately does not use:

- **Relay connection time:** the host tunnel is up even when no phone is.
- **Activity-only time:** watching a Play stream on the phone is real use and generates no requests.
- **Foreground time:** it would need client beacons, which are Mobile internals.

### 7.2 Three separate owners

| Role | Owner | Changes? |
|---|---|---|
| **Allowance authority** | `EntitlementSnapshot['remote.access']` | new, read-only |
| **Usage meter** | `RemoteMinuteMeter` (a `DurationMeter`) in `UsageStore` | new, observer only |
| **Runtime session state** | `sseClients`, `RelayClient`, `DeviceRegistry` | **unchanged** |

### 7.3 Lifecycle

| Event | Hook (daemon only) | Meter action |
|---|---|---|
| Relay enable | `syncRelayClient()` `wanted` | **Gate:** `check('remote.access')`. Not entitled → do not start the tunnel. The Settings toggle shows the deny sentence |
| Pairing (QR) | `POST /api/pairing/create` | **Gate:** `check`. Exhausted → the desktop says so *before* Dad scans. Pairing itself is never metered |
| Stream open | `handleSseConnection()` when `principal.kind === 'remote-device'` | `meter.open(streamKey)` → marks current minute |
| Request | `dispatchRemoteRequest()` (non-public paths) | **Gate (continue):** `check` (cheap snapshot read). `meter.touch()` marks current minute |
| Heartbeat | existing 15 s SSE heartbeat is transport; the meter keeps its own **60 s checkpoint** while ≥ 1 remote stream is open | persist `openInterval.lastMinute` |
| Reconnect | new SSE open | falls in the same or next minute, so the interval merges |
| Stream close | `removeSseClient()` for a remote principal | `meter.close(streamKey)`; the interval ends when the last stream closes and no request arrives within 60 s |
| Daemon restart / crash | startup | any open interval is closed at its **last checkpoint minute** (≤ 1 minute under-count, never an over-count) |
| Clock skew | — | minute indices below the last recorded index are ignored (no negative time, no replay) |

### 7.4 Exhaustion and grace

- When `remaining` reaches 0 while connected, a **grace window** starts (`grant.graceMinutes`, default 5). The phone gets a one-line SSE `status` notice ("Remote time is almost up").
- After grace, `dispatchRemoteRequest` answers authenticated requests with **HTTP 403 `{ code: 'remote-allowance-exhausted', message }`** (HTML page for `/` requests, like `UNPAIRED_HTML`). Remote SSE streams are closed.
- **Never interrupted:** Plays already dispatched (they run locally), the local desktop UI, pairing records, and device tokens. Dad keeps his paired phone. It works again at `resetsAt` or after a new grant.
- Unlimited profiles skip grace and exhaustion entirely.

### 7.5 Relay-side enforcement (later, optional)

Local metering is the product gate. The relay is the only component the vendor pays for. Later, the per-install license can replace the shared enrollment key in the existing `x-sideline-enrollment` slot, letting the relay refuse revoked or abusive hosts. **No second credential seam.** This is anti-abuse, not metering.

## 8. Game Limit Architecture

### 8.1 What counts

A Game counts against `games.active` once it is **admitted**. Admission happens on the first of:

1. an explicit **Add Game** that resolves a repository (`runAddGame`, after `recordKnownGameFromPicker`), or
2. the **first Play dispatched** to that Game (`ControlPlaneRouter.dispatch`, before routing).

Auto-registration (a VS Code window opening a folder) **never** admits. Otherwise every folder Dad opens would silently burn a slot.

### 8.2 Gate mechanics

```
admit(gameId):
  if admittedSet.has(gameId) → allow            // idempotent; existing Games never re-gated
  decision = gate.charge('games.active', gameId) // ceiling meter: set add if size < limit
  allow or deny("You're using all N Game slots. Archive a Game to make room.")

archive(gameId) → gate.release('games.active', gameId)   // frees a slot; the repository is never touched
restore(gameId) → nothing; admission recurs on next Play/Add
```

### 8.3 Guarantees

- **Never corrupts existing Games.** Game identity, registry, files, ledger, reports and Film are untouched. The only effect is a *refusal to dispatch a new Play* to a non-admitted Game, with a clear sentence.
- **Grandfathering.** When gating first activates (the migration stage), `admittedSet` is seeded with every Game that has ledger/Film history or is currently known and not archived, **even if that exceeds the limit**. Downgrades never lock an already-admitted Game. They only block *new* admissions until the count falls below the limit.
- **Independent of the registry durability gap.** The admission set is durable in `usage.json`, so the pre-existing fact that Control Plane archive state is memory-only (§2.2) does not affect counting.

### 8.4 Code touch

Two call sites: the top of `router.dispatch`, and `runAddGame` after successful pick resolution. One release call sits in the `/api/game/archive` handler. `StadiumRegistry`, `game-identity` and the extension are not changed.

## 9. Scout Optionality

Scout stays **an optional Play in the playbook**. Three independent predicates:

```
scoutExecutionAllowed      = gate.check('scout.play').allowed                 // ENTITLED (+ allowance)
scoutRuntimeReady          = scout capability.state === 'ready' && on field    // AVAILABLE (unchanged owner)
existingScoutIntelAvailable= fresh Scout report exists for this Game           // NEVER GATED
```

| State | Routing behavior |
|---|---|
| Not entitled | The Scout seat is marked `entitled: false` by the candidate enricher. AUTO never picks it. S57.1 generates no `scout-first` option. Explicit `Scout this play` → router refuses with the deny sentence |
| Entitled, unavailable | Today's behavior (Scout unavailable message, AUTO skips) |
| Entitled, available, not recommended | S57.1 shows no Scout option, or only in Dev ranking |
| Recommended | S57.1 `scout-first`. Charged on acceptance |

**Existing Scout intelligence stays usable.** Reports, Incoming, handoff preambles, S57.1's `existing-intel` tier and possession value are read paths and are never gated. A lapsed account keeps its mapped terrain.

Choke points:

## 10. Intelligent Routing Integration

### 10.1 Answer to "where does gating happen?"

**B: an input capability set to `recommendRoute()`, applied inside the one brain at candidate generation (S57.1 step [3]) and option synthesis (step [7]), plus one execution gate in `router.dispatch` for explicit routes.**

- **Not A.** Gating *before* `recommendRoute()` needs a second code path for non-entitled users. That is the fork S57.1 forbids.
- **Not C alone.** Candidate filtering can remove the Scout seat, but it cannot remove *option kinds* (wait-for-reset, next best) or *surfaces*.

### 10.2 S57.1 amendment (additive only)

### 10.3 Behavior

| Capability off | Effect inside the same engine |
|---|---|
| `intelligent` | **Basic profile.** `primary = baseline` (the existing AUTO decision S57.1 already carries), no alternatives, no Dad chip, no Dev rationale. AUTO dispatches exactly as today. **This is the fallback, and it is not a second brain.** It is the baseline S57.1 retains as its cold-start and golden-corpus reference |
| `economics` | Prices neutral 1.0, labeled `not-entitled` (distinct from `unknown`); no resource reason codes |

## 12. Offline Entitlement Model

Smallest robust design: **signed, cached, time-boxed, and fail-soft to Core, never fail-closed.**

```ts
interface SignedEntitlement {
  v: 1; licenseId: string; installId: string;     // bound to install
  profileLabel: string;                           // display only
  grants: CapabilityGrant[];
  issuedAt: number; refreshAfter: number; expiresAt: number;
  keyId: string; sig: string;                     // Ed25519 over canonical JSON
}
```

| Condition | Behavior |
|---|---|
| Valid (`now < refreshAfter`) | use grants |
| Needs refresh (`refreshAfter ≤ now < expiresAt`) | use grants; refresh attempts in the background (backoff); `validity: 'grace'` |
| Expired (`now ≥ expiresAt`) | fall back to the **built-in default profile** (`validity: 'expired-fallback'`). Core always works; the Settings line says "Reconnect to restore your access." |
| Signature invalid / installId mismatch | ignore the file, use the default profile, log symbolically |
| Backend unreachable | nothing changes until `expiresAt` |
| Clock rolled back (`now < lastSeenAt − 1 day`) | treat as `grace`, never extend `expiresAt` |

Suggested windows, all data in the signed document and not code: monthly subscriptions refresh after 7 days and expire after 30. Founder/lifetime refresh after 30 days and expire after 365.

Security posture: the public verification key is pinned in the build, with `keyId` supporting rotation. There is no obfuscation, no hardware fingerprinting, and no kill switch. Local usage counters are editable by a determined user. That is accepted; backend usage summaries allow anomaly detection later.

## 14. Product Telemetry Event Model

**Principle:** telemetry tells us WHAT; users tell us WHY. Events describe *behavior*, never *content*.

```ts
interface ProductEvent {
  v: 1;
  eventId: string;                 // uuid; dedupe key
  name: ProductEventName;          // closed enum
  at: number;                      // rounded to the minute
  installId: string;               // pseudonymous (never hostPublicId, deviceId, email)
  appVersion: string; platform: 'win32' | 'darwin' | 'linux'; surface: 'desktop' | 'remote';

```

**Event catalogue (initial):**

| Area | Events |
|---|---|

## 15. Analytics Delivery Model

- **Emit:** `telemetry.emit(event)`. Synchronous schema validation, then an async append to `~/.sideline/telemetry/outbox.jsonl`. Wrapped in try/catch and never awaited on a hot path.
- **Consent:** preference `telemetry: 'on' | 'off'`. When off, `emit` is a no-op: nothing is written and nothing is sent.
- **Buffer:** at most 5 000 events or 2 MB, whichever comes first. Drop oldest.
- **Flush:** a batch of ≤ 200 every 15 minutes, on daemon stop (best effort, 2 s budget), and on the next start.
- **Retry:** exponential backoff 1 min → 6 h. Events older than 7 days are dropped. Batches are idempotent by `batchId`.
- **Isolation:** separate from `EntitlementAuthority` and license refresh. Different endpoint, different failure domain. **Analytics failure never influences entitlement and vice versa.**
- **Transport:** pluggable. It ships as a no-op sender until a backend exists, so events can be verified locally in Dev Mode ("Telemetry preview").

## 16. Privacy Boundary

**Prohibited in any product telemetry payload, always:**

- source code, file contents, diffs, repository names/URLs/paths, branch names, commit messages
- Play prompt text, prompt fingerprints/hashes, Strategy Board text, routine instructions
- report bodies, report filenames/paths, Scout report text, Scout objectives
- terminal output, commands, Player transcripts, activity summaries
- credentials, tokens, enrollment keys, OpenRouter keys, cookies, device tokens, pairing codes/secrets
- `hostPublicId`, `deviceId`, device labels, account email, IP addresses (the backend must not log them against events)
- Game names/display names/gameIds, model prompts, provider account identifiers
- precise timestamps finer than a minute; exact durations finer than 10 s

**Enforcement:**

- **Schema allowlist.** Every string field is a closed enum. There are **no free-form strings** in `ProductEvent`.
- The runtime validator rejects any event that has an unknown field or a non-enum string. Validator tests run in CI.
- Counts are small integers.
- Events are built from typed facts at seams, never from logs or UI text.

2. **What is "Core"?** Is Remote (as a trial), Scout or Routines part of the free experience? This is packaging, and it can wait for data, but it decides the `core` profile contents.
3. **"Coach Refresh" naming.** Routines' Coach Refresh vs Scout maintenance "Coach Refresh V0.1". Which one keeps the name, and which capability IDs do they map to?
4. **Autofill and Wires.** Not found in source. Are they the Routine handoff on Copy and something unbuilt, or future features? Until answered they remain `reserved` IDs.
5. **Game admission rule.** Confirm "a Game counts once you add it or send it a Play" (recommended), rather than on window open.
6. **Remote minute fairness on Android.** If field data shows background tabs holding SSE open for long periods, add an attended-idle cutoff (for example a visibility beacon). That would be the first change requiring a small Mobile UI hook.
7. **Telemetry consent: opt-in vs opt-out.** A legal/product call that affects data volume. It must be settled before C7 ships.
8. **Founder grant delivery.** License key entry vs account sign-in. This must exist *before* any build flips `DEFAULT_PROFILE` to `core`, or early customers would be downgraded.
9. **Tamper posture.** Local counters are user-editable by design (no DRM). Confirm that is acceptable.
10. **Pre-existing, non-commercial:** Control Plane archive state is memory-only and a reconnecting window un-archives its Game. It doesn't affect this design (admission is separately durable), but Dad may want it fixed on its own merits.

## 22. Final Architect Verdict

**Do almost nothing now. Launch.**

Before launch:

1. **Add the `installId` file** (C0, about 30 lines, Codex · Medium). It is the one thing that can't be backfilled.
2. **Decide Remote public enrollment** (Q1). It is a Remote launch question you need anyway.
3. **Keep a record of launch buyers** so Founder licenses can be issued later.
4. **Reserve telemetry in the privacy policy.**

While building S57.1, pass a `capabilities` parameter into `recommendRoute()` (default all-true). Keep Dev Mode as presentation only.

After launch, when public users arrive, build C1 → C2 → C3 in order. Under the `unlimited` default they change nothing, and they start recording the real usage that will tell you where Free, Pro and higher tiers should sit. Then add C4/C5 enforcement, C6 licenses and C7/C8 telemetry as packaging decisions demand.

The capabilities that actually exist gate at nine points, all in two files (`daemon.ts`, `router.ts`). Mobile, Scout, Formation, the Stadium and the routing brain never learn what a plan is.
