# Recommendation Contract

`recommendRoute(input)` is pure and deterministic. The clock and every input are injected. There is no `Math.random`, no `Date.now()` and no I/O, and numbers are rounded to 6 decimals.

**Input:**
- `now`, `gameId`, `clientRef?`
- `profile`: task class, difficulty, role, urgency (V1: `normal`), Scout need, follow-up kind, hashed touch keys, and whether this is a post-Scout continuation
- `authority`: mode plus constraints
- `baseline?`: the existing router's decision
- `seats` (R4), `economics` (R1), `priorPack`, `filmIndex` (R5), `baselinePreference` (`PROVIDER_PREFERENCE`)
- `possession` evidence and `scout` evidence
- `capabilities` (default all-true), `posture` (default BALANCED `coach-default`)

**Output (`RoutingRecommendation`):**
- Identity: `id` (`rec_<sha256>`), engine, weights and prior-pack versions, `computedAt`, and the profile (no prompt)
- `authority {mode, lockedBy, advisoryOnly}` and `capabilities`
- The options: `baseline`, `primary`, `nextBest` (differs in playerType or lineage), `waitOption`, `scoutOption`, and the ranked `candidates` (≤ 12)
- `strength {recommendation: clear|lean|toss-up, evidence: prior-only|thin|building|established}` and `baselineAgreement`
- `possession {max, seats[]}`, a `scout` summary (intel, P_runs, P_right, net value, verdict, blockedBy), `scarcity` (ResourcePolicy verbatim per pool), and `unknowns[]`

Each **`RouteOption`** carries:
- `kind` (send | queue | handoff | scout-first | wait-for-reset), `target` (playerType/lineage/modelId/effort; **no instance**), and `route` (the exact executable instance/model/effort a later `optionToDecision` would send)
- `resourcePool` and `belief` (evidence, source, nPrior, nLocalEff, pooled, drift, burn confidence, duration)
- `scores`: utility, firstPass, q, cost (units, neutral flag, priced burn, reacquisition, effective, per-window price/π/floor/burn/cost), possession, delay, risk, interrupt, σ_U
- `reasons`

**Intentionally not in R6:**
- `dad` view (R8: "do not invent Dad UI copy")
- Dev `narrative` strings (R7)
- `optionToDecision` (R8: the single advice → decision bridge; not needed while nothing consumes advice)
- `calibratedFirstPass` (R10)

# Candidate Flow

1. The router fixes its decision exactly as before.
2. At `play-dispatched`, the router attaches `shadow` facts:
   - The static-AUTO **baseline** is the actual decision object under AUTO.
   - Under MANUAL it is a recomputation through `computeRoute`, the same side-effect-free computation the staged preview runs on every keystroke. Queue releases get none: the Play was already routed.
3. The daemon runs `eligibleSeats(candidates, {authority: 'auto', availability: 'taking-plays'})`:
   - Envelope constraints narrow the seats under AUTO, so locked dimensions are never re-ranked.
   - MANUAL ranks the unconstrained AUTO set ("Sideline would have picked…").
4. Scout and Terminal seats are excluded from Player ranking. Each remaining seat expands over its live catalog, models × supported efforts (a legacy seat is one provider-managed target).
5. Each target is scored, and the best seat per target is kept: higher utility, then more possession, then a ready seat, then the stable instance order.
6. Option kind:
   - a ready seat → `send`, or `handoff` when another seat owns the context
   - a busy seat → `queue` only when it is the context owner (existing Q2.10D semantics)
   - a busy non-owner → no option

# Belief Integration (R3 / R5)

- Every target is scored by `computeBelief({playerType, modelId, effort}, {taskClass, difficulty, role: 'player', gameId}, priorPack, filmIndex, now, {baselinePreference, resourcePool: seat pool})`. Instances are never statistical units.
- `filmIndex` is always `buildAttributedFilmIndex(events, pack, now)`, R5's single seam. The daemon caches it per Film length and minute.
- `q = firstPass.mean` (`lo` under SURE). σ_q is derived from the 20th–80th percentile band.
- `evidence` and the PRIOR_ONLY / THIN_EVIDENCE / NEW_MODEL_INHERITED / DRIFT_SUSPECTED codes come straight from the belief.
- The researched priors are R3's, unchanged. Film overtakes them per the R3 contract.
- A future unranked Player type gets S57.9's 0.55 / 2.

# Economics Integration (R1)

- Economic identity is the **seat's** `resourcePool`, from R4/R1 `resourcePoolForSeat`. It is never inferred from a model name.
- Per burn window, cost goes through **R1's own `estimatePoolEconomicCost`**:
  - pace price
  - Dad's LOW/CRITICAL floor only while scarcity outlasts the Play
  - split at reset, with post-reset burn at 1.0
- Interrupt risk follows §11.2: 0.9 if p50 pre-reset burn exceeds R, 0.5 if p75 does.
- UNKNOWN price: neutral 1.0, Risk +0.1, and a `RESOURCE_UNKNOWN` reason. The seat stays eligible.
- The daemon reads current economics through one accessor over `RoutingEconomicsReader.read()`. **No Film receipt is ever read.** A test feeds a Film whose receipts say "1% left" against a stale R1 snapshot, and the result is UNKNOWN, never scarcity.
- **Cold start (S57.7 §531, ratified):** every R0 node has `burn: null`, so burn is UNKNOWN until isolated Film exists.
  - An UNKNOWN-burn option is charged one **neutral, equal** cost: the median known option cost, else `0.10`. It carries `neutral: true`, the Film digest records `cost: 'unknown'`, and Risk gets +0.1.
  - Because the cost is equal across options, it never flips a ranking. It never counts as saved burn for Scout ROI.
- Utility follows §5.4 exactly:
  - `C_eff = C_play·(1+(1−q)·0.6)`
  - `U = q − λ_c·C_eff − λ_d·urgency·D − λ_r·Risk`, with the posture table verbatim

# Possession

- **Tiers (§9.1), from existing evidence only:**
  - `active`: the owner is currently working
  - `owner-strong` / `owner-medium`: the owner `resolveContextOwner` named in R5's dispatch evidence
  - `game-recent`: the seat's Ledger Plays overlap this Play's hashed touches, via the Film's `touchKeys` or the Ledger's live touches
  - `game-only`, `none`
- **Value:** base · 0.5^(age/240 min) · continuity.
- **Continuity is UNKNOWN (0.7)** and labeled `session-continuity` in `unknowns`. No canonical provider-session identity is observable (S57.1 §18.3 open fact 1), and none was invented.
- **Reacquisition:** `(maxPossession − p)·reacq(taskClass)·pricedBurn`, cut 50% by fresh Scout intel (§9.5). It is monotone: more possession never costs more (tested).
- **Possession never forces a route.** A test with an owner seat and a much stronger non-owner recommends the non-owner as a `handoff`. The owner shows zero reacquisition; the non-owner pays it.
- **No new store.** A Film `possession {tier, value}` of the chosen seat is written on the decision (S57.1 §7).

# Wait / Reset

A `waitOption` is synthesized only under all of these conditions (§15.5):
- the primary's own pool window has a **known** horizon (not stale, `resetsAt` known)
- 5H: T ≤ 90 min, and interrupt risk ≥ 0.5 or waiting improves U by ≥ 0.02
- Weekly: only under CONSERVE, urgency ≠ now, T ≤ 36 h
- the `schedule` capability is on

Its `wait {pool, window, resetsAt, cycleToken}` is data only. No DeferredPlay, no PlayQueue change, no scheduling (R9).

# Selection, Strength, Reasons

- **Strength (§12.1):** Δ = U₁ − U₂ against σ_Δ, a first-order combination of q uncertainty and burn IQR. Clear at > 2σ, lean at > 0.5σ, otherwise toss-up.
- **Toss-up stability (§5.4):** a toss-up keeps the baseline AUTO choice (`TOSS_UP_KEPT_BASELINE`). Tested in both directions: whichever option is the baseline stays.
- **Reasons:** the S57.1 §13 codes, emitted in one fixed priority order. `COACH_LOCKED` leads under advisory. Two additive codes:
  - `SPECIALIZED_ROUTE_KEPT`: a Scout-reconnaissance or Terminal baseline is kept as today
  - `BASELINE_ONLY`: the basic profile
- **Advisory:** `advisoryOnly` is true under MANUAL or any explicit envelope lock (player / instance / model / effort / model-exclusion / scout-directive / route-shorthand). A control title is not a lock.

# Interpretations For Coach (small, bounded, frozen in `r6-weights-1`)

1. **P_runs from READY.** The daemon sees Combine only as the Scout seat's `ready` projection; Combine totals live in the Stadium. READY maps to 0.9 (the §10.5 value); anything else means no Scout option. A later seam could pass real Combine completion rates.
2. **Neutral UNKNOWN burn** is the median known option cost, else 0.10, applied equally. This follows S57.7 §531. It only scales reacquisition and the repair term and is never saved burn.
3. **Scout parameters:**
   - `reconPrior` by task class: architecture 0.30, implementation 0.20, default 0.20, quick 0.05. S57.1 names "hard architecture 0.30" without a non-hard value.
   - The quality lift applies to hard **or** architecture Plays.
4. **Saved burn is priced across every burn window** (Σ price·burn), generalizing §10.2's "price(primary provider)·savedBurn". §10.5 reproduces.
5. **Reacquisition charges `burn_p50` at the target's own window prices.**
6. **Unknown duration:** the Play is priced as finishing before the reset (floor applies, no split). A queued owner's delay is UNKNOWN (+Risk), not guessed.
7. **Owner confidence mirrors `resolveContextOwner`** (latest-play and wording → medium; named/Incoming report → strong). This differs from S57.1 §9.1's prose, which put latest-play in `owner-strong`. Source truth won. Test R6-9 pins the mapping to the source.
8. **Only the `cheap-formation` Scout tier is executable today.** `strong-scout` and `a-team-reconciled` are defined but never offered.
9. **Specialized baselines** (Scout reconnaissance, Terminal) are kept with strength `toss-up`, because no statistical separation exists.
10. **Posture is BALANCED `coach-default`.** There is no posture preference yet.
