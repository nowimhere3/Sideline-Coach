## Verdict: GREEN WITH CORRECTIONS

AGY's diagnosis is right, and so is Policy D's shape: periodic reads, a backstop for stale data, show UNKNOWN instead of old numbers, and handle expiry. But targeted source reading found one defect that would stop Policy D from working as written, plus two wiring errors:

1. **Staleness is measured from the wrong timestamp (critical).** `HealthAuthority.ingest()` and `ingestClaudeUsage()` return early when the new values match the old ones, so `observedAt` only moves when the numbers **change** (`health-authority.ts:143-147, 169`; confirmed by the existing note at `claude-usage-reader.ts:93-104`). `AlarmEngine` measures staleness from `observedAt` (`alarm-engine.ts:256-257`). **So a successful read that returns the same numbers never makes the data fresh.** With Policy D as written:
   - If Dad stops using Codex for 30 minutes, every read succeeds but the scoreboard still turns UNKNOWN.
   - The stale-triggered read also succeeds with the same numbers, so it can't clear UNKNOWN either.
   - Applying the same UNKNOWN rule to Claude would break Claude the same way when idle. Claude's `alarm:stale` already misfires today after 30 idle minutes.
2. **`alarm:stale` can't be the healing trigger.** It is only emitted when `enabled && notifyOnThreshold` (`alarm-engine.ts:144-148`). If Dad turns alarm notifications off, healing silently stops.
3. **`pruneExpired()` should not run on a timer.** It moves `observedAt` forward (`health-authority.ts:198, 206`), so pruning would look like a fresh reading. Removing a window at the reset moment also leaves a gap that the AlarmEngine would report as a false "stale" alert and routing would read as missing data. Expiry belongs in the read-time projection instead (§5).

With those corrected, the repair is small, and one freshness definition serves the AlarmEngine, routing economics, the API and the UI.

## 1. Canonical freshness architecture

Three separate facts, kept separate:

| Fact | Meaning | Owner |
| :--- | :--- | :--- |
| `observedAt` (existing) | Last time the stored numbers **changed** | `HealthAuthority` |
| **`verifiedAt` (new)** | Last time a trusted source **confirmed** the numbers, changed or not: a reader read or a Stadium push | `HealthAuthority` |
| Window `resetsAt` (existing) | When the provider's window ends; after it, that number is outdated no matter how recently it was confirmed | Provider fact |

- `HealthAuthority` keeps the raw last-known numbers **and** `verifiedAt`, both saved to disk. It never deletes numbers because they are old.
- **One pure function** decides trust: `providerFreshness(state, now, maxStaleAgeMinutes)`, exported from `health-authority.ts`. It returns `{ current, verifiedAt, staleAfter }`, with `staleAfter = (verifiedAt ?? observedAt) + maxStale`. The `observedAt` fallback covers snapshots saved before this change and is the conservative choice.
- `normalizeAlarmFacts` (`alarm-engine.ts:256`) uses that function. Routing economics already goes through `normalizeAlarmFacts` (`routing-economics.ts:80`), so it inherits the fix. Result: one freshness rule, not three.
- The daemon attaches a derived, never-saved `freshness` block to what the browser receives. **The browser compares one server-supplied timestamp and does no `maxStaleAgeMinutes` math.**

Separation of concerns:

```text
AlarmEngine                → evaluates and alerts only (unchanged role; stale anchor fixed)
UsageFreshnessCoordinator  → consumes freshness/reset deadlines; asks for a read
CodexUsageReader           → owns acquisition, schedule, backoff, in-flight join
HealthAuthority            → owns facts + verifiedAt; freshness function is pure
```

This is stronger than giving AlarmEngine the power to trigger reads, and stronger than reacting to `alarm:stale`. Healing never depends on Dad's notification settings.

## 2. Exact Codex polling policy

**Yes, add periodic reads.** Only a read of the provider's usage endpoint can see Codex use from the native VS Code extension, the web, or another device. Nothing local detects it.

- **How often:** Dad's existing **Settings → AI Usage → "Refresh every"** choice (`aiUsageRefreshMinutes`: 3/5/10/15, default 5).
  - That setting is presented as AI usage in general but only drives Claude today. Applying it to Codex honors what Dad chose; it isn't copying Claude for its own sake.
  - The daemon's preferences handler (`daemon.ts:3424`) calls `codexUsageReader.setCadenceMinutes` alongside Claude's.
  - Cost at the 5-minute default: one ≤10 s `codex app-server` process every 5 minutes, about 288 a day. That's negligible, and it's what makes the invariant hold.
- **Start/stop:**
  - `CodexUsageReader.start()` does one read immediately, then schedules. Call it from `daemon.start()` right after `claudeUsageReader?.start()` (`daemon.ts:1032`).
  - `stop()` clears the timer and any pending activity timer. It is already called on both stop paths (`daemon.ts:1114, 1280`). It must also stop scheduling after an in-flight read finishes.
  - All timers are `unref`'d.
- **Relation to activity-triggered reads:**
  - Keep the existing rollout-file watcher and its debounce (15 s settle, 90 s spacing). It stays the fast path for CLI use.
  - **Any finished read** (scheduled, activity, manual, or coordinator) restarts the periodic countdown from that moment, the same "one chain" rule as `ClaudeUsageReader.scheduleNext`. There is never a second polling loop.
  - Two reads that overlap share one process (the existing `inFlight` join).
- The file header ("no background polling loop") and the `refresh()` doc comment ("Never background polls") must be corrected.

## 3. Exact stale→reacquisition flow

```text
HealthAuthority change (or daemon start / preference change)
  → UsageFreshnessCoordinator re-arms ONE timer at the earliest of:
       codex.staleAfter                               (stale deadline)
       earliest future Codex window resetsAt + 30 s   (reset deadline)
  → timer fires → codexUsageReader.requestRead('stale' | 'reset')
       · joins an in-flight read
       · refused while the reader is in backoff (§6) or a read started < cadence ago ('stale' only)
  → success → HealthAuthority.ingest sets verifiedAt (and numbers if changed) → onChange → re-arm
  → failure → reader backoff governs; freshness stays expired → UI shows UNKNOWN
```

- **At most one coordinator read per deadline.** After firing, the timer re-arms only on the next `HealthAuthority` change or preference change, so a broken CLI can't cause repeated process launches.
- While the periodic reads succeed, the stale deadline never arrives. It exists as a safety net: after sleep/resume, if the polling chain dies, or after backoff.
- **The reset deadline is the useful part for Codex.** When a Codex 5-hour window rolls over, Sideline re-reads within about 30 s instead of showing UNKNOWN until the next scheduled read. This also answers Q5.
- The coordinator is Codex-only in this Play. Claude already refreshes itself; plugging Claude into the coordinator later is a separate choice.

## 4. Canonical UNKNOWN projection rule

For each provider window, show the numbers **only if all of these hold**:

1. `freshness.current === true` **and** `now < freshness.staleAfter` (browser clock, compared against the server-supplied time);
2. the window exists with a finite used percentage;
3. the window's `resetsAt` is **null or absent** (no expiry) **or** later than now.

Otherwise the window shows **UNKNOWN**, with the reason `stale` / `expired` / `missing`. The UNKNOWN display the scoreboard uses for missing windows already exists, so this changes where the data comes from, not how it looks.

- **Where the numbers come from:** the daemon adds `freshness: { claude?, codex? }`, each `{ current, verifiedAt, staleAfter }`, to `GET /api/ai-health`, to the `POST /api/ai-health/refresh` response, and to the SSE `ai-health` broadcast (`daemon.ts:541`). It re-broadcasts when `maxStaleAgeMinutes` changes.
- **UI:**
  - `aiScoreboardCodexWindows` and `aiScoreboardClaudeWindows` (`index.html:5986-5994`) take that provider's freshness; if it isn't current, both windows are `undefined`.
  - Codex also gets `checkExpiry: true`, as a backstop, as Claude already has.
  - The Copy text reads the same functions, so it also says UNKNOWN.
- **Required for Claude too.** The rule is shared, and without `verifiedAt` Claude would go UNKNOWN whenever Dad is idle. `verifiedAt` is set inside `HealthAuthority` itself, so Claude needs **no reader change**.

## 5. Expiration / pruning rule

- **Expired and stale are different, and both show UNKNOWN.**
  - Expired: the provider window has rolled over, so the number is definitely out of date, even if it was confirmed a minute ago. The fix is to re-read now (the reset deadline).
  - Stale: Sideline hasn't confirmed the number recently, but it may still be right. The fix is to re-read, subject to backoff.
- **Where expiry is enforced:** at read time, in the projection (§4, rule 3). The ingest merges already drop expired windows when new data arrives (`mergeCodexRateLimitInfo`, and the Claude merge's prune flag).
- **`pruneExpired()` stays unscheduled.** Running it on a timer would (a) move `observedAt` forward, making pruned data look freshly observed, and (b) open a gap at every reset that the AlarmEngine would report as `alarm:stale` and routing would treat as missing. If it's ever used, it must stop moving `observedAt` and must never touch `verifiedAt`. That is a separate hygiene item, not part of this Play.

## 6. Failure / backoff rule (CodexUsageReader)

| Situation | Next scheduled read |
| :--- | :--- |
| Success | cadence; failure count reset |
| Failure n (`timeout`, `process_error`, `rpc_failed`, `malformed_response`, `no_limits`) | `min(60 min, cadence × 2^(n−1))`, so a single failure retries at the normal cadence |
| `cli_not_found` | 60 min immediately |

- **Manual Refresh** ignores backoff (Dad explicitly asked) and resets it on success.
- **Activity-triggered reads** skip the `cli_not_found` hold, because a growing rollout file proves the CLI exists. They still respect the 90 s spacing.
- **Coordinator reads** always respect backoff.
- The reader's status (`idle` / `ok` / `unavailable` plus `code`) is already exposed as `acquisition.codex`. Add `nextAttemptAt` for diagnostics only; no new UI surface.
- Failures never touch `HealthAuthority`. The numbers age normally, and §4 turns them to UNKNOWN once `staleAfter` passes. That's the "visibly unavailable" outcome.

## 7. Codex reset semantics (Q5)

- **Codex doesn't need Claude's idle translation.** Claude's usage API reports a post-reset idle window as `{utilization: 0, resets_at: null}`, which Sideline translates on purpose. Codex's `account/rateLimits/read` returns native `primary`/`secondary` windows (`usedPercent` 0–100, `windowDurationMins`, `resetsAt` in Unix seconds), and Sideline stores them as-is (`health-authority.ts:450-510`). No source code shows a special Codex idle shape, so none is needed.
- **Codex does need two protections:**
  1. **Reset handling:** after `resetsAt`, the window shows UNKNOWN (expired). The coordinator's reset deadline (§3) re-reads right away, so the gap is seconds. This is Claude-equivalent behavior with no provider-specific translation.
  2. **Null reset time:** a window with a finite `usedPercent` but a null or absent `resetsAt` is a **valid current fact**, not an expired one. `resolveCodexWindows` turns a missing reset into `resetsAt: 0` (`health-authority.ts:579`). If any projection runs expiry checks on that value, a genuine "0 % used" would show UNKNOWN. The projection must check expiry against the raw window, or the `?? 0` must go.
- **Not verifiable from source:** what Codex actually returns right after a reset. A field capture of one idle read (no secrets) should become a test fixture.

## 9. Required tests

1. **Unchanged reads still count as fresh:** an unchanged Codex/Claude read moves `verifiedAt` forward, not `observedAt`, and fires `onChange`. The refresh outcome stays `unchanged`.
2. **Idle is not stale:** reads succeed every 5 minutes with identical numbers for 45 simulated minutes, and there is no `alarm:stale`, freshness stays current, and the scoreboard keeps showing numbers. Covers Claude and Codex.
3. **Codex polling lifecycle:** `start()` reads immediately, then at the cadence. Activity and manual reads restart the countdown, and there is never more than one pending timer. `stop()` stops everything, including after an in-flight read. A cadence preference change takes effect.
4. **External use shows up:** with no rollout-file growth, a scheduled read picks up new numbers (the VS Code native extension case).
5. **Backoff:** the failure sequence gives cadence, 2×, 4×, …, capped at 60 min. `cli_not_found` goes straight to 60. Success resets it. Manual Refresh ignores it. Coordinator reads respect it. Launch count stays bounded when the CLI is broken.
6. **Coordinator:** it re-reads once when `staleAfter` passes; it re-reads about 30 s after a known `resetsAt`; it doesn't depend on alarm notification settings (alarms disabled still heals); it fires one read per deadline.
7. **UNKNOWN projection:** stale, expired and missing windows show UNKNOWN in both the scoreboard **and** the Copy text. A current window shows its numbers. A null-reset window with `usedPercent: 0` shows 0 % used, not UNKNOWN.
8. **Routing / AlarmEngine regression:** the existing alarm and routing-economics suites pass with the new staleness anchor; a snapshot saved before this change (no `verifiedAt`) falls back to `observedAt`.
9. **Scoreboard contract tests:** update any test asserting "an unchanged refresh broadcasts nothing" (comment at `daemon.ts:1943`). The new contract: unchanged reads update freshness, never numbers or `observedAt`.

Field proof (Dad):
- Use Codex only in the native VS Code extension. Within one cadence plus about 10 s, Sideline should match the native display.
- Leave everything idle for 45 minutes. There should be no stale alert and the numbers should stay shown.
- Make the CLI unavailable. After `maxStaleAgeMinutes`, Codex should show UNKNOWN, process launches should stay bounded, and restoring the CLI should heal it within one cadence.
