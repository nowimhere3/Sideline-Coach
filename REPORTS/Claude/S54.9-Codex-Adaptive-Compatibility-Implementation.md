## WHAT WAS BUILT

### 1. Pure contract module — `src/player-control/codex-contract.ts` (new)

`REQUIRED_CONTRACT` declares exactly what the adapter reads or writes: **99 items**. 8 client methods, 5 server notifications, 5 server requests, 22 definitions' fields, 10 enum values, and 3 tagged-union variants with their fields. `checkSchemaContract(files)` returns `{ ok: true }` or `{ ok: false, missing: [...] }`. It has no filesystem, process, network, VS Code, launch, or routing code, and a test enforces that. Input that is not a schema simply reports what is missing; it never throws. The checker is a port of the S54.8 evidence script, and it gives 99/99 against the real 0.155.1 schema and names `TurnStartParams.clientUserMessageId` when I delete it.

### 2. Adaptive gate — `src/player-control/codex-app-server.ts`

The two `certified.includes(runtimeVersion)` gates (open and restore) are replaced by one `verifyCompatibility()` that runs right after `initialize`, before `account/read` and every thread call:

| Order | Situation | Outcome |
|---|---|---|
| 1 | Runtime contradiction already latched for this binary + version | `needs-verification` |
| 2 | Version on the known-bad list | `needs-verification`, regardless of schema |
| 3 | Seeded proven version (`0.154.0`, `0.155.1`) | pass, no probe |
| 4 | This exact binary + version proven earlier in this process | pass, no probe |
| 5 | Otherwise: bounded probe | pass → Ready and cached; missing items → `needs-verification` naming them; probe cannot run / times out / bad output → `needs-verification`, "compatibility unproven" |

An **unparsable version string is not a failure** — the probe decides (`0.999.0-alpha.1` and `weird-build` both reach Ready when the contract passes). The version regex now also accepts pre-release suffixes so they display truthfully.

### Exact contract probe

`<the same resolved launch> generate-json-schema --out .` run in a private `mkdtemp` directory as the working directory.

- Uses the launch the adapter already trusts (`resolveLaunch`, including the Windows `node + codex.js` and `cmd` shim variants). There is no second binary lookup.
- Bounded: 20 s timeout (process tree killed, awaited before cleanup), at most 1,000 directory entries, 16 MB per file, 32 MB total. It loads only the 7 named schema files, never a directory walk.
- No model turn, no `thread/start`, no Game or user-config touched, `CODEX_API_KEY` stripped from its environment. The temp directory is always removed.
- Invalid JSON, empty output, non-object output, a non-zero exit, a spawn error, or a timeout all give "compatibility unproven".

### Cache policy

In-process only (`CodexCompatibilityRegistry`), nothing persisted, no database. "Proven" means *this exact binary + version already satisfied the contract*. The key is `[version, command, args, shell, path + size + mtime of every launch file]`. Concurrent restores of one binary share one probe. A failed verdict is **never** cached, so the next attempt genuinely re-probes.

**Honest caveat:** the two seeded versions are matched by version string alone, because the seed is release-time certification with no binary to stamp. Only *dynamically* proven entries are binary-bound. On the default Windows launch the stamp covers `codex.js` and `node`, not the native vendored binary behind it; a version change still re-keys.

### Known-bad policy

`KNOWN_BAD_VERSIONS` exists and is **empty**. It is checked before the seed, so it wins over both the seed and a passing schema (test CC-11). `knownBadVersions` and `certifiedVersions` remain injectable through `LaunchOptions`.

### First-turn tripwire

Schema shape is not behaviour. Until a binary + version completes one clean real turn in this process, the tripwire is armed. It is armed for probe-proven versions **and for `0.155.1`**, whose real turn has never been observed. Only `0.154.0`, which is field-proved, starts disarmed. It latches on:

- `turn/start` acknowledged without a turn id → control state `needs-verification`, outcome stays `unknown`;
- `turn/completed` with no turn identity, or an unrecognised status (previously silently reported as "completed").

A latch lasts for the process. It benches that control, refuses later Plays with `needs-verification`, and makes reopening the same binary + version fail closed with the reason. A first clean completion disarms it. Lifecycle handling is not redesigned; the existing `unknown` / `lost` behaviour is unchanged for the disarmed field-proved version.

### Dad vs Dev messaging

- Dad-facing `message`: **`Codex needs attention. Try again.`** No version, "certified", provider, or contract wording (verified against every one of the 99 missing-item cases).
- Dev-facing `diagnostic`: `Installed version: 7.42.0 · Compatibility: incompatible · Reason: required contract missing: TurnStartParams.clientUserMessageId`. Compatibility is `verified` / `unknown` / `incompatible`.
- `ControlOpenError` and `ControlOpenOutcome` gained an optional `diagnostic` (restore already had one). `PlayerControlHost.open()` and the roster's add-Player result carry it through.
- Not built: a "Checking Codex compatibility…" caption. The gate lives inside the adapter, so the roster cannot see the moment the probe runs, and the existing "Resuming the same conversation…" state covers it. This is a copy-only follow-up.

### Try Again behaviour

`restoreControlled()` no longer performs `reopenFresh()` after a `needs-verification` restore, because that second attempt spawned Codex again and hit the same deterministic verdict. Other restore failures keep their one bounded fresh-open. Together with the adaptive gate this means Try Again can now genuinely recover a newly updated compatible Codex. It re-runs the probe, a failed probe is never cached, and the Player is not re-benched by a static string (tests CC-22 and CC-23, driven through the real `PlayerRoster` with a fake factory). Both existing `needs-verification` sources (`structured-print.ts` contract checks and "adapter not registered") are also deterministic, so the skip is safe for them too.

## SECOND REVIEW BEFORE PASS

1. **Can a random unknown version bypass contract verification?** No. Only the seeded versions (`0.154.0`, `0.155.1`) skip the probe; every other version needs its own passing probe or a same-binary proof. *(The seed is version-string-only; see the cache caveat.)*
2. **Can missing schema items still result in Ready?** No. All 99 items are proven individually to block.
3. **Can the probe weaken cwd / authority / session checks?** No. It is a separate process in a temp directory, and every per-open check runs after it, proven in CC-14/15.
4. **Can a failed probe silently fall back to dispatch?** No. It returns `needs-verification` before `account/read` or any thread call.
5. **Can a new binary reuse another binary's proof?** For probe-proven entries, no (key includes launch and file stamps). **For the two seeded versions, a different binary reporting that same version string would inherit the seed.** That is inherent to seeding by version and is the documented residual.
6. **Can Dad-facing UI leak internal version plumbing?** Not on the Roster card or state message (`Needs attention: Codex needs attention. Try again.`). **One nuance:** the roster also writes `Diagnostic: …` into that Player's own console pane via the existing restore-diagnostic path. That is a pre-existing pattern, is technical, and is not gated by Dev Mode. If Dad should never see it there, a Dev-Mode gate is a small follow-up.
7. **Can Try Again now genuinely recover a compatible update?** Yes (CC-22, plus real 0.155.1).
8. **Can a behaviour-only contradiction after schema proof fail closed?** Yes for the tripwire cases; see remaining unknowns for what is not covered.

No unresolved YES caused by this implementation.

## REMAINING UNKNOWNS

- **A real `turn/start` on 0.155.1 is still unobserved** (needs a model turn). The two-step field proof above closes this.
- **`generate-json-schema` is marked experimental by Codex.** If it changes, unseeded future versions fail closed as "unproven" (safe, but such a Player is benched until the contract table or probe is updated). Seeded and already-proven binaries are unaffected.
- **Tripwire scope is small by design.** Not covered: a provider that acknowledges a turn but never sends `turn/completed`, and behaviour drift that shows only mid-stream. The existing lost/unknown handling still applies.
- **Static conformance proves shape, not meaning.** The 0.154.0 `thread/read` change was behavioural; the layered defence (probe, unchanged runtime checks, tripwire) reduces but does not eliminate this.
- **`REQUIRED_CONTRACT` must grow with the adapter.** CC-21 catches new RPC methods, notifications and server requests, but a newly read *field* or *enum value* still needs a manual contract entry.
- `test/coach-routines-v0.1-add-edit-and-repository.test.mjs` "V01-4" is **flaky on its own** (ECONNRESET on a local HTTP fetch; failed 1 of 3 solo runs) and never touches Codex or player-control.
