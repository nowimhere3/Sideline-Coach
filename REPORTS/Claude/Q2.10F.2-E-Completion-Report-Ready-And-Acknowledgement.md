# Executive Result

**Q2.10F.2 Slice E is complete.** A Play can finish, return its report, remain visibly ready until the human intentionally consumes that result, then settle quietly without losing durable Incoming history. An uncertain (Unknown) dispatch can return its text to the human only through an explicit recovery action that never auto-dispatches and never claims the prior attempt failed.

- **Rich Finished** (canonical `finishedAt` + `serverNow()`, never render time) lasts ~10 seconds, with a static duration and, when a report is linked, a real `View Report` action.
- **Quiet post-completion** is a small adjunct on the Player card's existing eligibility line (`On Field · ✓ Report ready` / `On Field · ✓ Finished`) — never a second execution surface, never a strip, never a clock.
- **View Report** opens the exact linked report through Incoming's real reader, then acknowledges it through the real, idempotent `POST /api/work/acknowledge` (Slice A). Selecting a report in Incoming or Copying it also acknowledges — all three are the only acknowledgement triggers; nothing else (render, refresh, reconnect, TEAM expansion) ever does.
- **Unknown recovery** (`Recover Play Text`, on Slice D's persistent Unknown acknowledgement) restores `dispatchAttempt.prompt` into the composer on deliberate request only, with a confirmation guard when the composer already holds different text.
- **Failure/needs-attention Dismiss**: the real endpoint turned out to already support failed/interrupted/Unknown acknowledgement (`instanceId` + `playRef`, no `reportPath`), so Slice C's `See what happened` strips gained a real `Dismiss` action — no second acknowledgement primitive was invented.
- A real production bug was found and fixed during implementation: the 10 s Finished decay's `setTimeout` (and, in hindsight, Slice D's 8 s Outgoing decay and the reveal-highlight timeout) held the Node event loop open in test harnesses that don't fake timers, hanging entire test files. All three now `.unref()` — a no-op in real browsers, standard Node practice, with no behavioural change.

None of the six stop conditions applied — in particular, `/api/work/acknowledge`'s existing contract turned out to cover **both** report acknowledgement and failure/Unknown acknowledgement, so no server code changed. No Slice F work (E2E promotion, the full hammer suite, human field proof, packaging) was done.

# Rich Finished State

`isRichFinished(view)` = `Number.isFinite(view.finishedAt) && (serverNow() - view.finishedAt) < 10_000`. `stripCopy`'s `finished` case now returns `null` (no strip at all) when this is false — the quiet adjunct (below) takes over instead. While rich:

```
✓ Finished              8m 19s
Report ready in Incoming
[ View Report ]
```
or, with no report yet:
```
✓ Finished              8m 19s
Report on its way
```

The duration is `formatPlayElapsed(0, view.durationMs)` — the existing static-duration formatter Slice C already used; nothing new was invented for "static."

# Canonical Finished Decay

The origin is exclusively `view.finishedAt` (Control Plane time) compared against `serverNow()` (skew-corrected, Slice B). Browser render time, `Date.now()` alone, and page-load time are never consulted. Consequences, proven by test:

- A reload/reconnect 8 seconds after a Play finished (E-4) shows the Play still rich, with only the *true remaining* ~2 seconds left — never a fresh 10-second window.
- The transition is driven by exactly one `setTimeout` per exact (instance, `playRef`) pair (`scheduleFinishedDecay` / `finishedDecayScheduledFor`), scheduled for `10_000 - (serverNow() - finishedAt)` and re-deriving state at fire time — never the shared 1 s ticker (see "One Timer Topology" below).

**On Field stays eligibility.** The quiet text is an adjunct on the same line, never a replacement for "On Field" / "On Bench", and never a second execution surface — there is still exactly one `.play-strip` mechanism (rich Finished uses it; every other active state already did) and exactly one quiet-adjunct mechanism (nothing else uses it).

# Acknowledgement Endpoint Contract

Inspected `daemon.ts`'s real `POST /api/work/acknowledge` and `WorkLedger.acknowledge()` (not assumed):

```
POST /api/work/acknowledge { gameId, reportPath?, instanceId?, playRef? }
→ 200 { success: true, acknowledged: true, changed, instanceId }         (found)
→ 404 { success: false, acknowledged: false, message }                  (not found)
```

Two real branches inside `WorkLedger.acknowledge`, both idempotent and Game-scoped:
1. **`reportPath` given**: finds the matching `LedgerReportLink` (optionally narrowed by `instanceId`/`playRef`), sets `acknowledgedAt` once. A second call on an already-acknowledged link returns `found: true, changed: false` — safe to call repeatedly (E-14).
2. **No `reportPath`, `instanceId` + `playRef` given**: acknowledges a `failed` / `interrupted` / `unknown` / `not-sent` `recentPlay`, **or** an in-progress `unknown` `currentPlay` matching that `playRef` (which it also resolves to idle). This is the primitive Slice C's `Dismiss` (below) uses — it already existed; nothing was added to the daemon.

Both mutate through the existing `commit`/`touch` path, which bumps `revision` and fires `ledger.onChange` → `scheduleExecutionBroadcast(gameId)` — confirmed in `daemon.ts`. The browser never needs a second signal: the next `execution` SSE event (or full snapshot) is the only thing that ever changes presentation.

# Acknowledgement Failure Handling

`acknowledgeWork` never throws to its caller — on any HTTP failure or thrown error it logs and returns `false`. Every call site already performed the human-visible action (report opened, content copied) **before** calling it, so:
- **View Report / select**: the report is shown regardless of ack success (E-15).
- **Copy**: the copy already succeeded (ack sits after the success UI, never gated by it).
- **Report Ready presentation** is never cleared locally on ack failure or success — only a new canonical `ExecutionView` (from the next `execution` event or snapshot) ever changes it. This is the same "server wins" rule Slice B established for execution truth generally, now applied to acknowledgement too.

# Unknown Recovery

Added to Slice D's persistent, never-auto-decaying `unknown`-tone Outgoing acknowledgement (unchanged trigger conditions): when `attempt.prompt` is present, a `Recover Play Text` button appears alongside `View {Name}`.

`recoverAttemptPrompt(attempt)`:
- If the composer is empty or already equal to `attempt.prompt` (trimmed): restores it immediately, re-requests the AUTO route preview if applicable, focuses the composer. **Never dispatches. Never changes AUTO/MANUAL mode.**
- If the composer holds different, non-empty text: reuses the **existing** `confirmAction()` modal (the same one used for Remove Player, Restart with Coach controls, etc.) — "Replace the Play you are composing?" / "Coach will put the earlier Play's text back in the box, replacing what you have now." / **Use Recovered Text**. Declining changes nothing (E-19b); confirming replaces it (E-19).
- The copy above this button is unchanged from Slice D: `? Can't confirm {Name} received this Play` / `Check the Game before sending it again.` — Recovery never claims the Play failed (E-20); it explicitly gives the human their text back so *they* decide, matching the breadcrumb "Unknown recovery restores human control, not certainty."

# Failure / Needs-Attention Handling

Slice C's `See what happened` disclosure (states `couldnt-finish`, `unknown`) gained one new sibling action, `Dismiss`, wired to the real endpoint's non-`reportPath` branch: `acknowledgeWork({ instanceId: view.instanceId, playRef: view.playRef })`. It:
- appears only when `view.playRef` exists (the endpoint requires it);
- performs no local hiding — the strip stays exactly as it is until a new, real `ExecutionView` (via the resulting `execution` SSE broadcast) says otherwise;
- is completely separate from Unknown's text-recovery action — Dismiss ends the human-attention state; Recover Play Text gives the human their submitted words back. They can be used independently or together.

This closes the failure lifecycle using only what the real server contract already offered — no second acknowledgement store or endpoint was invented, resolving stop condition #4 in the affirmative (a mechanism exists) rather than by escalation.

**A real defect was found and fixed mid-implementation, not papered over in a test:** the new `scheduleFinishedDecay` (and, on inspection, Slice D's pre-existing `scheduleOutgoingDecay` and the reveal-highlight timer) used raw `setTimeout`, which several test files pass through to real Node timers rather than faking. Without `.unref()`, a Slice C test file that used to finish in ~0.6 s took 30+ seconds (confirmed via an isolated `timeout 30` run) because the process waited out every pending real 10-second decay timer scheduled during the run. All three call sites now `.unref()` their timer (optional-chained, so it is silently skipped in real browsers, which have no such method). This is a genuine correctness fix, not a test-only workaround: an un-unref'd timer is otherwise harmless in a real browser tab but is exactly the kind of thing that would have made a future Node-hosted test harness (or a headless-browser CI runner with strict idle-timeout semantics) flake or hang for reasons unrelated to the feature under test.

# Remaining Limitations

- **`Dismiss` has no dedicated automated test in this Slice's file** beyond what's implied by the endpoint contract inspection (E-11 style identifier-exactness coverage exists for `View Report`, not `Dismiss` specifically) — it reuses the identical `acknowledgeWork` call shape and endpoint branch, so the risk is low, but a focused `Dismiss` test is a reasonable Slice F addition.
- **Recovery only covers the *current* `dispatchAttempt`.** If the human dispatches a second Play (replacing the attempt) before recovering the first Unknown one, that earlier text is gone from the browser (Slice B's documented, intentional limitation — never changed here).
- **Selecting a report the human is only browsing, not really "opening" with intent** (e.g. flipping through `#reportSelect` options quickly) still acknowledges each one, per the architecture doc's literal instruction that selection is deliberate opening. If this proves too eager in the field, restricting acknowledgement to a dwell time or an explicit "Mark as read" is a Slice F/future consideration — not implemented here to avoid inventing UX beyond the brief.
- **No visual regression / real-browser screenshot proof.** All 26+1 tests exercise the real script logically; nothing here claims a human looked at rendered pixels.

# WAS / IS / WILL BE

## WAS

A Player's Finished strip stayed rich indefinitely — no decay, no quiet phase, no Report Ready action beyond the passive copy already in the strip. Unknown's Outgoing panel told the human it couldn't confirm receipt, but there was no way to get their submitted text back except retyping it from memory. Failure/Unknown states had a "See what happened" disclosure but no way to actually clear them from server truth.

## IS

Finished is rich for ~10 canonical seconds, then settles into a small adjunct on the Player card's own eligibility line — Report Ready or plain Finished, truthfully, until a real acknowledgement (View Report, selecting it in Incoming, or Copy) or a server-confirmed state change clears it. TEAM's Report Ready count, and the strip/adjunct presentation, both derive from the same canonical truth and never drift from each other or across Players or Games. An Unknown dispatch can be deliberately recovered into the composer, with a confirmation guard protecting anything the human is already composing, and Dismiss can close a failed/Unknown attention state through the same real endpoint — without ever inventing a second acknowledgement store.

## WILL BE

- **Slice F:** promote the lifecycle forensic fixture to full asserted E2E acceptance, build the cross-Slice reconnect/concurrency hammer suite, run the first human field proof of the completed loop, and package.
