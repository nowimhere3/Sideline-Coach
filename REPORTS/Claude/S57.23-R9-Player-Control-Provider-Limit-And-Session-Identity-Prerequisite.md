# Verdict

**PLAYER CONTROL PREREQUISITE GREEN.**

Both facts S57.22 found missing are now canonical Player Control truth. Both are proven with deterministic tests and with the certified provider contract.

1. **Provider-limit interruption.** A turn now carries an optional structured `blocker`, set **only** from provider-emitted structured evidence scoped to that exact turn. It reaches the Work Ledger with the Play's outcome.
2. **Session-identity precondition.** A dispatch may carry `expectedSessionKey`. Player Control proves `currentSessionKey === expectedSessionKey` **before** the write-ahead marker and **before** any provider send, and otherwise refuses with `session-changed`.
   - When `reopenFresh()` gives the same `instanceId` a new conversation, the key changes and an old-key continuation is refused before anything is sent.

What did not change:
- R9 DeferredPlay was not implemented, and there is no Schedule UI.
- AUTO and MANUAL routing, the PlayQueue, R8, recommendations and provider selection are unchanged.
- A dispatch without `expectedSessionKey` behaves exactly as before.

# Part 1 — Structured Provider-Limit Interruption

## Contract

`ControlEvent` `turn` gains an optional `blocker?: ProviderLimitBlocker`, defined in `player-control/contract.ts`:

```ts
interface ProviderLimitBlocker {
  kind: 'provider-limit';
  pool: string;            // R1 pool identity ('codex' | 'claude')
  window?: string;         // only when the provider named it for this refusal
  resetsAt?: number;       // Unix seconds, only when the provider stated it for this refusal
  evidence: 'codex-turn-error' | 'claude-rate-limit-event';
  providerCode: string;    // 'usageLimitExceeded' | 'rateLimitExceeded' | 'rejected'
}
```

This keeps the Coach's semantic and adds two fields for auditability: `evidence` and `providerCode`. `parseProviderLimitBlocker` validates the blocker at every process and storage boundary and drops anything malformed.

## Codex — certified, not assumed

**Probe.** Ran `codex app-server generate-json-schema` from the installed **codex-cli 0.157.1**. This is the repo's own certification method (CODEX-COMPATIBILITY-CONTRACT). It ran into the scratchpad with no model turn, no thread and no account use.

**Real wire shape (VERIFIED):**
- `Turn.error: TurnError | null`, which the schema describes as *"Only populated when the Turn's status is failed."*
- `TurnError { message: string; codexErrorInfo?: CodexErrorInfo | null; additionalDetails?; misalignment? }`
- `CodexErrorInfo` is a `oneOf`. Its string variants include `usageLimitExceeded` and `rateLimitExceeded` (and, among others, `contextWindowExceeded`, `serverOverloaded`, `unauthorized`); object variants carry `httpStatusCode`.
- **`TurnError` carries no `resetsAt` or window.** Those exist only in the account-level `RateLimitSnapshot`, so the Codex blocker states neither. R9 must take the horizon from R1 economics for pool `codex`.

**Certification.**
- `REQUIRED_CONTRACT` gains `TurnError: ['message', 'codexErrorInfo']` and the enum values `CodexErrorInfo: usageLimitExceeded, rateLimitExceeded`.
- The **full** updated contract passes against the real 0.157.1 schema: `checkSchemaContract(...) → {"ok": true}`.
- Following the breadcrumb's FUTURE WIDENING rule, a probed version missing these items now fails closed as `needs-verification`, like every other certified field.
- Seeded versions 0.154.0–0.156.1 skip the probe. Reading the field is purely defensive: an exact string match or nothing, so a version without it simply produces no blocker.
- The two definitions are saved verbatim as `test/fixtures/codex-0.157.1-turn-error.schema.json`.

**Mapping (`codexProviderLimitBlocker`).**
- Applies only to a `failed` turn.
- Only when `turn.error.codexErrorInfo` is **exactly** `usageLimitExceeded` or `rateLimitExceeded`. The result is `{kind, pool: 'codex', evidence: 'codex-turn-error', providerCode}`.
- `message` is never read for this. Neither is the account rate-limit snapshot.

## Claude — turn-scoped provider evidence

**Provider declaration (VERIFIED from Claude Code 2.1.283's bundled SDK schema):**
- `rate_limit_event { rate_limit_info, uuid, session_id }` is described as *"Rate limit event emitted when rate limit info changes."*
- `rate_limit_info.status` is one of `allowed | allowed_warning | rejected`, with optional `resetsAt` (int), `rateLimitType` (`five_hour | seven_day | seven_day_opus | …`) and `overageStatus`.
- The bundled docs state that allowed overage covers a `rejected` limiter ("nothing will be cut off").

**Turn correlation (VERIFIED by adapter structure):**
- Each Claude Play is exactly one `claude -p --resume <session>` process, and its stream is that Play's run.
- The adapter already refuses a run whose `init` names another session.

**Rule (`claudeLimitRejection` plus the run loop).** The latest `rate_limit_event` in *this Play's run* sets or clears the candidate. It counts only when all of these hold:
- the frame's `session_id` equals this Player's conversation;
- `status === 'rejected'`;
- overage is not `allowed` or `allowed_warning`.

The blocker is attached only when the Play did not complete (`failed`, or `unknown` with no result). It carries `window` and `resetsAt` from that frame; a millisecond reset is normalized to seconds.

**Never blocked:**
- a completed Play
- `allowed` or `allowed_warning` telemetry
- a frame for another session
- a rejection followed by a recovery in the same run
- failure text such as "usage limit reached"

## AntiGravity and others

There is no structured proof, so `blocker` is always absent (tested with a failure whose text reads "quota exceeded").

# Part 2 — Blocker Recorded With the Outcome

This rides the existing path: control event → `PlayerRoster` turn event → Stadium `turn.changed` → daemon → `InstanceWorkLedger.recordTurn`. There is no second ledger.

- `PlayerTurnEvent` gains optional `blocker` and `sessionKey` (the digest of the conversation the turn ran in). Both are set for controlled Players only.
- `TurnRecord` accepts both as untrusted input.
- `LedgerRecentPlay` gains optional `blocker` and `sessionKey`, validated by `turnOutcomeEvidence`:
  - a blocker is kept only on a Play that did not complete;
  - malformed values are dropped.
- **Historical records stay valid.** `restore()` re-validates only these optional fields and drops them if malformed. Records without them are untouched (tested).
- Serialization and restore round-trip the blocker.

# Part 3 — Session-Identity Precondition

**Key.**
- `providerSessionKey(sessionRef)` in `contract.ts` is the single definition, an 8-hex SHA-256 digest. `player-activity.sessionKeyFor` now delegates to it, so the activity key and the precondition key cannot drift.
- Raw provider session ids never leave Player Control.
- A restored conversation keeps its key. A fresh conversation always gets a new one.

**Exposure before dispatch.**
- `PlayerControlHost.sessionKey(instanceId)` returns the key only while the live control and the durable binding agree on the conversation.
- `PlayerRoster.getRoutingCapabilities()` projects it as the optional `PlayerRoutingCapability.sessionKey`. That projection is observational; the authoritative check is at send time.

**Enforcement.**
- **`PlayerControlHost.deliver(..., preconditions?)`:** a mismatch returns `refused / session-changed` **before** the write-ahead `pendingPlay` is persisted and before `control.deliver` is called. Nothing reaches any provider.
- **Stadium `executeDispatch`:** a Play carrying `expectedSessionKey` may only reach a **live controlled** Player. Legacy terminals, pending or unavailable Players, Scout and terminal names are all refused with `reason: 'session-changed'`. For a live controlled Player the key is passed to the host, and the host's refusal reason is forwarded.
- **Protocol:** `DispatchRequestParams.expectedSessionKey?` and `DispatchRejectedParams.reason?`, both optional.
- **Router:** `DispatchOptions.expectedSessionKey?`. A session-bound Play must be:
  - a valid key;
  - `routingMode: 'manual'`;
  - one exact non-Scout `playerInstanceId`, with no terminal name;
  - **never queued** (`whenBusy: 'queue'` and queue releases are refused with `reason: 'session-bound-invalid'`).

  It is forwarded in the `dispatch.request` frame, and a Stadium `session-changed` rejection surfaces as `DispatchResult.reason`. Without the option, the frame is byte-for-byte what it was (tested).

**The critical proof (R9P-9, through the real `PlayerRoster` self-healing path):**
1. A restored conversation keeps its key, which is also projected in the routing capability.
2. The provider channel is lost and restore fails. The roster's real crash path calls `reopenFresh()`, which opens `fresh-conversation-N` for the **same `instanceId`**.
3. The key changes, as shown in both `host.sessionKey` and the routing capability. The `instanceId` and model are unchanged.
4. `deliver(..., { expectedSessionKey: <original> })` returns `refused / session-changed`, and **no send occurred**. The same call with the new key is accepted.

# Notes For R9 (implementation map, not implemented here)

1. **Arm-time identity.** R9 should record `sessionKey` from the interrupted Play's own Ledger record (`LedgerRecentPlay.sessionKey`, the conversation the Play ran in), not merely from the Player's current capability.
2. **Codex horizon.** A Codex blocker has no `resetsAt`, so R9 takes the reset horizon from R1 economics for pool `codex`. A Claude blocker may carry one; R9 still revalidates against fresh R1 truth.
3. **One decision for R9:**
   - A session-bound continuation is refused rather than queued, because a released PlayQueue item carries no session precondition. That is today's fail-closed behavior.
   - The R9 brief says "If that same Player is busy then normal PlayQueue may own the wait". That would need the precondition to travel with the queued item: an additive, optional `QueuedPlay.expectedSessionKey` carried into the release.
   - Otherwise R9 must wait out a busy Player itself. PlayQueue semantics were not changed here.
