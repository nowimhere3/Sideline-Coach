## What was built

### The contract (Coach decision, honored)

- R9 does **not** extend the PlayQueue with `expectedSessionKey`. It keeps a separate intent that it owns: "continue *this* interrupted task on *this* Player in *this* conversation after *this* reset."
- **What is sent:** a single fixed instruction, `CONTINUE_TASK_PROMPT` = *"Continue the current task from where you were interrupted."*
- **What is never done:**
  - The original prompt is never replayed.
  - No transcript or prompt is stored.
  - Another Player is never substituted.
  - Nothing goes into the PlayQueue.

### Arm: `continuationEligibility` (`src/control-plane/deferred-play.ts`)

A Player is schedulable only when **all** of these hold:

| Check | Source of truth |
|---|---|
| The latest Play for that exact instance carries a structured `ProviderLimitBlocker` | Work Ledger `recentPlays[0].blocker` (S57.23; failure text never counts) |
| That Play did not complete (no `completed`/`partial`) | Ledger outcome |
| The Player is a Controlled Player (not terminal, direct-shell or Scout) | routing capability |
| The interrupted Play recorded its own `sessionKey` | Ledger |
| The Player is **still in that conversation** (`capability.sessionKey === play.sessionKey`) | Player Control |
| The Player is not already working | Ledger `currentPlay` |
| A reset horizon is known | the refusal's own `resetsAt` (Claude) if R1 has that window, otherwise R1's exhausted windows for the refused pool (Codex names no reset) |

Refusals come back as structured reasons (`no-interruption`, `not-controlled`, `no-session`, `session-changed`, `player-working`, `reset-unknown`). Each one maps to a Dad-readable 409 message.

- **Idempotent:** the key is `gameId | playerInstanceId | interruptedClientRef`. A double click or a browser retry returns the same intent (`created: false`).
- **Server-verified:** `interruptedClientRef` must still be the Player's latest Play.

### Store: `~/.sideline/deferred-plays.json`

- A separate file with its own versioned schema. It holds references only:
  - instance, sessionKey, interrupted clientRef/turnRef, blocker, reset condition, model/effort, state, attempt
  - no prompt and no transcript
- **Atomic write:** tmp file, then rename.
- **Corrupt file:** renamed to `*.corrupt.bak`, a warning is logged ("nothing from it will fire"), and the book starts empty.
- **Invalid records are dropped:** a bad sessionKey, an unparseable blocker, or `firing` without a write-ahead attempt.
- Terminal records are pruned after 50.
- **States:** `waiting` (`waitingFor`: reset · recovery · player · game), `firing`, `handed-off`, `needs-attention`, `cancelled`.

### Wake: `DeferredPlayScheduler` (`src/control-plane/deferred-play-scheduler.ts`)

Every wakeup means **check now**, never "send now." Wakeups come from:

- `alarm:reset_boundary_reached` / `alarm:recovered` for the pool
- a fallback timer at horizon + 2 min, plus one at the end of the 30-min recovery grace. The AlarmEngine only emits when alarm preferences are on, so the fallback timer is required.
- startup reconciliation, so a reset missed while Coach was closed is not a failure
- existing event seams, with no polling:
  - the health/economics change callback
  - terminal `turn.changed` for that instance (the Player is free)
  - registry `capabilities-updated` / `game-connected`

Evaluation is single-flight per record. Racing wakeups (alarm + recovered + timer + health) produce one send (R9-5).

### Revalidate: `revalidateContinuation` (fresh truth each time)

1. **Before the horizon** → keep waiting (reset).
2. **Resource truth for each armed window must be:**
   - present
   - not stale
   - a **new cycle**: `resetsAt` advanced by more than 15 min, so a stale or unchanged reading is never taken as a reset
   - recovered to ≥ 5% and not at the CRITICAL floor

   Before the 30-min grace ends it keeps waiting for recovery. After that it goes to needs-attention ("reset couldn't be confirmed" / "UNKNOWN" / "too little recovered").
3. **Game** offline or its roster not synchronized → wait (game).
4. **Player** no longer on the Team, benched, not controlled, unavailable or needs-verification → needs-attention.
5. **Conversation:** `sessionKey` changed → needs-attention ("no longer in the conversation").
6. **Player busy** → wait (player). R9 keeps ownership; nothing goes to the PlayQueue.
7. **Player moved on:** the latest Play is no longer the interrupted one, or it completed → needs-attention ("worked on something else"). This check also makes the send idempotent after an uncertain send.
8. Otherwise **ready**.

### Send: exactly once or needs-attention

- **Write-ahead:** `beginFiring` persists `attempt.clientRef` (`ref_dp_…`) *before* dispatch.
- The router gained an internal `clientRef` option so the persisted correlation is the one the Stadium and Ledger see. It is only honored when well-formed and not already in flight.
- **Dispatch:** `router.dispatch({ routingMode: 'manual', playerInstanceId, expectedSessionKey, model, effort, prompt: CONTINUE_TASK_PROMPT, clientRef })`. This passes S57.23's `session-bound-invalid` rules: manual, exact instance, never queued. Player Control then enforces `expectedSessionKey` before anything is sent.

| Router outcome | Result |
|---|---|
| accepted (`received`) | `handed-off` (turnRef kept). R9's ownership ends and the Player's strip shows the Play as usual |
| `busy` (in-flight guard, or the Stadium's pre-send `busy` refusal, now forwarded) | proven no-send → back to `waiting` (player) |
| `session-changed` | `needs-attention` |
| `unknown` (no ack) | `needs-attention`, never retried automatically |
| any other refusal | `needs-attention` with the reason ("Nothing was sent") |

**Restart while firing:** only Ledger evidence of that exact `attempt.clientRef` (in `currentPlay` or `recentPlays`) proves it landed → `handed-off`. Anything else → `needs-attention` ("Coach restarted while sending…"). There is never a blind resend.

**Retry:** Retry first checks Ledger evidence of the last attempt. It then runs every check again, and does not bypass freshness or the moved-on check (R9-6, R9-8).

### Use another Player (explicit human action only)

`POST /api/deferred-play/use-another` `{gameId, fromInstanceId, interruptedClientRef, toInstanceId}`:

- **Validation:** the interruption must still be the latest Play and carry a blocker.
- **Refused (409)** while a continuation is scheduled or already handed off. It is never both.
- **Target:** must be a different, ready, non-Scout, non-terminal Player.
- **Path:** the **existing** router with MANUAL exact dispatch. It carries the existing handoff preamble (`buildHandoffPreamble`: owner, the previous Play summary, the interrupted Play's own report if attributed, reason `owner-unavailable`) plus the bounded instruction `HANDOFF_AFTER_LIMIT_INSTRUCTION`: inspect the working tree and the task/report context, work out what is already done, and continue from the proven state without redoing completed work.
- It sends no `expectedSessionKey`, because it is a different conversation by design.

### Routes (default-deny table updated)

`remote-routes.ts` classifies all of these as `remote-mutate`:

- `POST /api/deferred-play`
- `POST /api/deferred-play/use-another`
- `POST /api/deferred-play/:id/(cancel|retry)`

Cancel and retry check that the record belongs to the given `gameId`.

### Status projection

- `status.continuations[]`: an offer on the interrupted instance only. It carries the interrupted clientRef, `limit` (provider code), `resetsAt`, and `alternatives [{instanceId, name}]`. It is hidden once an intent exists.
- `status.deferredPlays[]`: active intents (`waiting`/`firing`/`needs-attention`) with `waitingFor`, `resetsAt` and the attention text.
- No `sessionKey` reaches the browser.

### UI (Player-centric only)

The controls appear only inside the exact Player's strip, in the same line style as the PlayQueue. There is no global Schedule control, and nothing sits beside AUTO/MANUAL or Refresh/+Path (R9-11).

- **Offer:** `Rate limit reached · Resets 3:19 AM` (or "Usage limit reached") `[Schedule after reset] [Use another Player]`. **Use another Player** expands into `[Send to <name>]` choices.
- **Scheduled:** `Scheduled · continue after reset · 3:19 AM [Cancel]`. Variants: "continues when this Player is free", "waiting for this Game to reconnect", "reset reached, confirming usage…".
- **Firing:** `Continuing the task now…` (no Cancel mid-send).
- **Attention:** `Needs attention · <reason> [Retry] [Cancel]`.

## Coach notes / residual risks

1. **Codex horizon depends on R1.** Codex's turn error names no reset. If R1 is stale when the refusal lands, Schedule is not offered. This is the conservative choice and can be revisited with field evidence.
2. **The recovery grace (30 min)** is a named constant (`DEFERRED_PLAY_CONSTANTS.recoveryGraceMs`). A provider that is slow to publish new-cycle usage may send Dad to Needs attention, and then Retry. It never fires on unproven truth.
3. **After `handed-off`** the continuation is an ordinary Play on the Player's strip. If that Play hits the limit again, a fresh Schedule offer appears. It does not re-arm automatically.

## Breadcrumbs (recorded, NOT built)

- **Generic scheduled first prompts.** Scheduling a *new* Play, one that is not a continuation, for later is a different product: a new-Play prompt store, authorization and consent. R9 deliberately stores no prompt.
- **Arbitrary-time scheduling.** R9's only horizon is a provider reset proven by truth. "Run at 7 PM" or calendar scheduling needs its own intent model and UI and must not reuse the reset revalidation.
- **Teach scheduling the first 3–5 times.** A lightweight explainer on the first few offers ("Coach will send *continue* to this same Player after the reset, only if it's safe"), then quiet. This needs a per-user counter preference, so it was not built here.
