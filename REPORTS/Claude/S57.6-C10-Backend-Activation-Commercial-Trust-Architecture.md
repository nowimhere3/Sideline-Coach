## 1. Executive Verdict

**ARCHITECTURE READY.** C10 is small:

- **one** stateless API service (a `backend/` sibling of the existing `relay/`, reusing the repo's already-pure `src/commercial` and `src/telemetry` modules);
- **one** managed Postgres database;
- **one** managed-KMS signing boundary holding non-exportable Ed25519 keys (ACTIVE + STANDBY for licenses; a separate pair for relay credentials).

**Recommendation: build none of C10 today.** Nothing in C0–C9 becomes expensive to retrofit by waiting:

- `DEFAULT_PROFILE` is `unlimited`, so no customer needs a license yet.
- Telemetry is OFF and has no sender.
- The relay keeps working on its existing enrollment key.

The only "do now" item is unrelated to C10: the one-line **Scout Roster Refresh** spelling fix (§19).

**Four contract changes to S57.2 are justified by security analysis (§14):**

1. Activation returns a **refresh token**, and refresh must present it. Without it, anyone who learns a `licenseId` + `installId` could mint that install's entitlement.
2. Activation and refresh can also return a **relay credential**.
3. A **deactivate** call supports seat transfer.
4. **Usage summaries** are authenticated and batched.

**Remote trust migration (§10):** keep the existing `x-sideline-enrollment` header as the only host credential seam. Its value evolves from today's shared beta key to a **backend-signed relay credential bound to the host's existing Ed25519 `hostPublicId`**. The relay verifies it offline against pinned public keys, and binds it at the existing `hello` step, so a stolen credential is useless without the host's private key. The relay never calls the backend. QR pairing, domain, SSL, transport and phone pairing are untouched.

**COACH REVIEW REQUIRED: five decisions (§21).** None blocks this architecture: every one is designed as data or behind a clean seam. They are seat/transfer policy, license windows and revocation latency, hosting/KMS commitment, telemetry identity linkability, and public-relay eligibility for unactivated installs.

## 4. Minimum Deployable Backend

**One service, one database, one signer boundary. No microservices.**

```
                   ┌───────────────────────── C10 (future) ─────────────────────────┐
Sideline client ── HTTPS ──► sideline-api (Fly app, stateless, ≥2 machines OK)       │
                   │            ├─ /v1/licenses/*  /v1/relay … (activation, refresh)  │
                   │            ├─ /v1/events  /v1/usage/summaries (opt-in only)      │
                   │            ├─ /v1/keys (public keys, informational)              │
                   │            └─ /v1/admin/* (operator CLI only)                    │
                   │                 │ SQL                    │ sign(keyId, bytes)    │
                   │          managed Postgres           managed KMS (Ed25519,        │
                   │          (backups, PITR)            non-exportable, IAM sign-only)│
                   └───────────────────────────────────────────────────────────────────┘
Existing relay (Fly app "mysidelinecoach-relay") ── verifies relay credentials OFFLINE with pinned public keys; never calls C10.
```

- **Code layout:** `backend/` beside `relay/`. It imports the canonical payload and validation from `src/commercial/license.ts` and `src/telemetry/events.ts`, the same way the relay imports `src/control-plane/host-identity.ts`. That gives **one schema, not two**.
- **Hosting:** Fly.io can host the API app (Dad already operates Fly). Keep it a **separate Fly app from the relay**. The relay stays a single in-memory machine with no database or KMS reach, which keeps the relay's blast radius tiny.
- **Datastore:** any managed Postgres with point-in-time recovery and backups.
- **Signer:** Fly has no KMS. The private keys must live in a managed KMS/HSM that supports **non-exportable Ed25519 signing**. Google Cloud KMS offers Ed25519 signing keys. Other vendors' current Ed25519 support must be verified at build time. The API holds only a *KMS client credential scoped to `sign`*, never key bytes.

This is a hosting commitment → Coach Review §21.3.

## 5. Activation-Code Architecture

| Aspect | Design |
|---|---|
| **Format** | `SLC-XXXXX-XXXXX-XXXXX-XXXXX` using the existing unambiguous alphabet `23456789ABCDEFGHJKMNPQRSTVWXYZ` (30 symbols). 19 random chars (≈ 93 bits) + 1 check char (client-side typo rejection before any network call) |
| **Generation** | CSPRNG on the backend (operator CLI or billing adapter). Shown **once** to the operator |
| **Storage** | `codeHash = HMAC-SHA256(pepper, normalizedCode)` (pepper held as a managed secret, rotatable with a version tag) + `last4` for support. **No plaintext at rest** |
| **Kinds** | `license` code: redeems into one existing license (V1). `campaign` code: each redemption mints its own license; has `maxRedemptions` (future promotions) |
| **Redemption semantics** | A `license` code is **reusable by the same customer up to the license's `maxInstalls` seats**. Each new `installId` creates a binding. Seat count and transfer are data; the values are Coach Review §21.1 |
| **Install binding** | `(licenseId, installId)` unique. Re-activating the same install is idempotent: same binding, fresh entitlement, same refresh token (or rotated; see §6) |
| **Idempotent retries** | Keyed by `(codeHash, installId)`. A retry after a timeout returns the same binding and a newly signed entitlement with the same grants |
| **Expiry** | Optional `redeemBy` on codes (data). Founder codes: none by default |
| **Revocation** | `license.status = revoked` → activate and refresh refuse. Cached entitlements run until `expiresAt` (§7). Codes can be disabled independently of the license |
| **Lost machine / reinstall** | Same `~/.sideline` kept → same `installId`, nothing to do. Wiped machine → new `installId` → needs a free seat. Freeing seats is operator `binding release` today; self-serve `deactivate` is policy (§21.1) |
| **Abuse resistance** | ~93-bit codes make enumeration infeasible. Server-side limits: per IP, and globally on failures (§11). Uniform `invalid-code` response (no oracle for "revoked" vs "unknown" before a hash match) |
| **Operator recovery** | Lost code → operator re-issues a new code for the same license (old one disabled). No license change |

## 6. License Record Model and Issuance

**Canonical backend records** (field detail in §13):

- **`license`**:
  - `licenseId` (`lic_` + 20 base32)
  - `status` (`active | suspended | revoked`)
  - `profileLabel` (display)
  - `grantsTemplate` (the capability grants, as data)
  - `term` (`lifetime` | `subscription` with `currentPeriodEnd`)
  - `windows` (`refreshAfterDays`, `expiresAfterDays`)
  - `maxInstalls`
  - `source` (`manual` | `billing` | `campaign`, with operator or commerce reference)
  - timestamps
- **`install_binding`**:
  - `(licenseId, installId)` pair
  - `refreshTokenHash`
  - optional `hostPublicId`
  - `status` (`active | released`)
  - `boundAt`, `lastRefreshAt`
- **`issuance`**: an audit row per signed entitlement (`licenseId, installId, keyId, issuedAt, refreshAfter, expiresAt, grantsHash`). It does **not** store the full entitlement.

**Grant resolution** turns `grantsTemplate` into concrete `CapabilityGrant[]` with **stable grantIds** (`<licenseId>:<capability>:<n>`), and uses the license start as the monthly anchor (`period.anchor`).

**This is a hard rule:** the local `UsageStore` keys buckets by `grantId`. Changing grantIds on refresh would silently reset usage.

**Issued entitlement:**
- `issuedAt = now`
- `refreshAfter = now + refreshAfterDays`
- `expiresAt = min(now + expiresAfterDays, term end)`
- signed by the ACTIVE key via KMS over `canonicalEntitlementPayload()`, the exact C6 function.

## 7. Signing, KMS and Key Rotation

| Aspect | Design |
|---|---|
| **Where signing happens** | Inside the managed KMS only. `sideline-api` sends `sign(keyVersion, canonicalBytes)` and receives a 64-byte signature. Keys are created **non-exportable** |
| **Key families** | `ent-*` for entitlements, `rly-*` for relay credentials. Separate KMS keys so compromise and rotation are independent. **Domain separation:** relay credentials sign `"sideline-relay-credential-v1\n" + payload`; entitlements keep the existing C6 bytes (unchanged for interop) |
| **States** | `standby → active → retiring → retired`, plus `compromised`. Exactly one ACTIVE per family |
| **Day one** | Create ACTIVE + STANDBY for each family. The first C10 client build pins **both** entitlement public keys (`PINNED_ENTITLEMENT_KEYS`). The relay pins both relay public keys (config) |
| **Publication** | `GET /v1/keys` lists public keys and states **for operations only**. Clients trust **only pinned** keys and never fetch trust |
| **Planned rotation** | Promote STANDBY → ACTIVE (already pinned everywhere) and create a new STANDBY. The next client build pins {new ACTIVE, new STANDBY, retiring}. Licenses signed by the retiring key stay valid until they expire. Refresh re-signs with the new ACTIVE. Unpin the retiring key only after max license lifetime (Founder: 365 d) **and** client-update adoption |
| **Compromise** | 1. Disable the compromised key version in KMS (signing stops instantly). 2. Promote STANDBY. 3. Set `refreshAfter` in the past for all bindings (next refresh re-signs). 4. Ship a client build that removes the compromised keyId. Updated clients then treat old licenses as `invalid` → built-in default + automatic refresh via refresh token, so there is no user action. 5. Rotate the relay keys the same way (relay config redeploy) |
| **Signer authorization** | KMS IAM: the API's service identity has `sign` on the ACTIVE key versions only. The operator (Dad) has key admin with MFA, used only in a written rotation ceremony. No other principal |
| **Audit** | KMS audit logs plus the `issuance` table plus the `operator_audit` table |

## 8. Founder / Manual Issuance

**Surface:** a small **operator CLI** (`backend/cli`) run on Dad's machine. It calls `POST /v1/admin/*` authenticated by an operator token: high-entropy, stored only in Dad's password manager, **hashed** server-side, rotatable, and optionally IP-allowlisted. There is no portal.

```
sideline-admin license create --profile founder --label "Founder access" --max-installs <N> [--note "<operator note>"]
  → licenseId + activation code (printed once)
sideline-admin code reissue <licenseId>        # old code disabled
sideline-admin binding list|release <licenseId> [installId]
sideline-admin license revoke|suspend|restore <licenseId> --reason <enum>
sideline-admin key status                      # read-only; rotation is a documented ceremony, not a CLI shortcut
```

- **`founder` template:** every capability `unlimited`, term `lifetime`, windows refresh 30 d / expire 365 d (proposed; §21.2).
- **Delivery:** Dad sends the code by his own channel (email or DM). C10 stores no customer email in V1. A customer reference is an optional operator note, and customer records stay in Dad's purchase records (S57.2 §19).
- **Every admin call writes `operator_audit`.** The token never appears in logs.

Founder delivery must exist before any build flips `DEFAULT_PROFILE`. This path (plus C10.6 client activation) satisfies that.

## 9. Future Billing Adapter

```
Provider webhook (Stripe / PayKickstart / PayPal / Google Wallet / …)
   → BillingAdapter<provider>: verify provider signature, normalize
   → CommerceEvent { provider, externalEventId (idempotency), kind: purchase|renewal|cancel|refund|change,
                     externalCustomerRef, offeringRef, periodEnd? }
   → LicenseService (internal, vendor-neutral):
        grantLicense(offeringRef, source)  → license + activation code (delivered by the adapter's mailer, future)
        renew(licenseId, periodEnd)        → extends term; next refresh carries it
        cancel(licenseId, atPeriodEnd)     → term ends; entitlement lapses at expiry
        refund(licenseId)                  → revoke (policy §21.2)

```

- `offeringRef → grantsTemplate` is a **data table** (`offerings`). That is where packaging lives, and C10 defines none.
- Sideline never talks to a provider. `commerce_refs` stores `(provider, externalRef, licenseId, lastEventId)` for idempotency.

## 10. Remote Relay Trust Migration

### 10.1 Current truth

Upgrade → shared `ENROLLMENT_KEY` check → nonce challenge → `hello` proves possession of a **self-generated** Ed25519 host key → the relay routes `h-<hostPublicId>` traffic.

Anyone holding the shared key can register any self-made host identity. That is acceptable for Dad, Founders and beta, but it is not a public-commercial trust root.

### 10.2 After C10: what proves a host may use the public relay?

**A backend-signed relay credential, bound to the host's existing `hostPublicId`, carried in the existing `x-sideline-enrollment` header, verified offline by the relay.**

**Relay credential (compact, minimal):**
```
header value = "v1." + base64url(payload) + "." + base64url(sig)
payload = { "k": keyId, "h": hostPublicId, "r": credentialId (random, for denylist), "iat": ms, "exp": ms }
sig     = Ed25519_rly( "sideline-relay-credential-v1\n" + canonical(payload) )
```

- It contains **no** licenseId, installId, grants, email or plan. The relay learns only "this hostPublicId is eligible until exp".
- **Issuance:** activate or refresh with `hostPublicId` (sent once Remote has created the host key) returns `relayCredential`, **only if** the license's grants entitle `remote.access`. Remote *minutes* stay local (C4).
- **Lifetime:** `exp = entitlement.expiresAt`. It refreshes with the license, so backend outage tolerance equals license tolerance.
- **Client:** it stores `~/.sideline/entitlement/relay-credential.json` (0600). The existing bootstrap resolution prefers it over `remote/beta-enrollment.json`, and the existing `RelayClient` puts it in the same header. **No transport, pairing, QR or domain change.**

**Relay verification (future, small):**
1. At upgrade (still before any challenge): parse. On failure, fall back to the legacy shared-key comparison while `LEGACY_ENROLLMENT` is enabled. Verify the signature against pinned `RELAY_CREDENTIAL_KEYS` and check `exp` (±5 min skew) and the optional denylist. Keep the claims on the pending socket.
2. At `hello`: require `claims.h === hello.hostPublicId`. A stolen credential is useless without that host's private key.

**Why this one** (the alternatives are the ones the Play asked to be evaluated):

| Approach | Theft/replay | Rotation | Backend outage | Revocation | Privacy | Simplicity | Verdict |
|---|---|---|---|---|---|---|---|
| Keep the shared key | copy-and-use | redeploy all hosts | n/a | none per host | ok | trivial | legacy only |
| License-derived enrollment secret (HMAC per license) | replayable by anyone holding it | backend + relay must share the HMAC secret | relay needs a shared secret | per license | relay can link to license | medium | ✗ |
| Short-lived backend token (minutes) | low | automatic | **Remote breaks during backend outages**, and reconnects need the backend | fast | ok | medium | ✗ (fails "backend outage ≠ product failure") |
| Relay presents the full SignedEntitlement | bound to installId, not the host key → replayable | client keys | ok | at expiry | **relay sees grants and licenseId** | medium | ✗ |
| **Signed relay credential bound to hostPublicId (recommended)** | needs the host private key | pinned active + standby, config redeploy | none until `exp` | at `exp` + emergency denylist | minimal claims | small verifier + dual-accept | ✅ |

### 10.3 Staged migration (not implemented)

| Stage | Relay | Clients | Effect |
|---|---|---|---|
| R0 (today) | shared key | beta file / env | unchanged |
| R1 | **dual-accept**: credential **or** shared key | activated installs send the credential | Founders move over transparently |
| R2 | per-host denylist and metrics show legacy usage near zero | — | readiness check |
| R3 | `LEGACY_ENROLLMENT=off` (or internal-only key rotated) | unactivated installs no longer reach the public relay | only if §21.5 decides that |

**Reconnects** reuse the credential (no backend). **Rate limiting** stays in the relay's existing per-IP limiter, plus a future per-`hostPublicId` connect-churn limit.

## 12. Product Event Ingest and Usage Summaries

### Events (`POST /v1/events`)

- **Sent only when consent is `on`.** The client transport replaces `NOOP_TRANSPORT` only then. With consent off, nothing is sent (unchanged C7/C8 behavior).
- **Validation:** every event goes through the **same** `validateProductEvent` module. Any unknown field or non-enum string rejects the batch (`422 schema`). Only counts are logged.
- **Idempotency:** `batchId` (the C7 deterministic hash) primary key, plus per-event `eventId` primary key, both `ON CONFLICT DO NOTHING`. Retries are safe.
- **Storage:** an append-only `product_events` table with only schema columns. IP addresses are never stored with events, and application logs never include payloads.
- **Retention:** raw events for a bounded period, aggregates longer (§21.4).
- **Isolation:** separate route, separate rate limits and separate tables. No foreign keys between telemetry and licenses. **An events outage never touches activation or refresh, and vice versa.**

### Usage summaries (`POST /v1/usage/summaries`)

- **Purpose:** commercial intelligence, anomaly detection, and future account views.
- **Not authoritative:** local `UsageStore` + signed grants remain the only runtime gate.
- **Authenticated** with the binding's refresh token (forged summaries for other installs are rejected).
- **Batched, idempotent:** monotonic upsert of `(installId, grantId, periodKey) → max(used)`.
- **Guardrail (design rule):** no C10 endpoint ever returns an allow/deny, remaining allowance, or dispatch decision derived from summaries. A test asserts the API surface has no such field. This prevents drift toward server-authoritative dispatch.
- **Timing:** sent opportunistically with refresh. Summaries are part of the license relationship, not telemetry; whether they require their own consent is part of §21.4.

| `POST /v1/licenses/activate` | `{activationCode \| accountToken, installId}` → `SignedEntitlement` | `{activationCode, installId, hostPublicId?, clientVersion}` → `{entitlement, refreshToken, relayCredential?}` · errors: `invalid-code`, `seats-exhausted`, `license-inactive`, `rate-limited` | A refresh proof is needed (see refresh). Without a possession proof, anyone who learns them could mint that install's entitlement |

| `POST /v1/admin/*` | — | operator-token CLI endpoints (§8) | Founder issuance |

**Client refresh semantics (C6-compatible, no DRM):**
- **When:** at or after `refreshAfter`, plus opportunistically once a day, with backoff 1 h → 24 h.
- **On success:** atomically write `license.json` and `relay-credential.json`.
- **On failure:** keep using the cached license until `expiresAt`. After that, fall back to `DEFAULT_PROFILE` (today `unlimited`, so no user impact) and keep retrying.
- **Revocation latency** ≤ the remaining `expiresAt` window (§21.2).
- **Clock:** the existing C6 high-water rollback rule applies.
- **The refresh token** is 256-bit, stored hashed server-side, rotated on each successful refresh with a one-previous-token grace window, and sent only to C10.

| # | Threat | Likelihood × impact | Mitigation (proportionate) |
|---|---|---|---|
| 1 | **Operator credential compromise** (can mint licenses) | med × high | Token hashed server-side and rotatable; MFA on Fly, KMS and DB consoles; IP allowlist option; `operator_audit`; KMS admin separate from API sign role |

| 5 | **Log leakage** of codes, tokens or content | med × med | Symbolic logging only (§17); request bodies never logged; redaction tests |
| 6 | **Relay credential theft** | low × low | Bound to hostPublicId (needs the host private key); expiry; denylist |

| 8 | **Code enumeration** | low × med | ~93-bit codes, rate limits, uniform errors |
| 9 | **Forged usage summaries** | low × low | Refresh-token auth; advisory only |
| 10 | **Entitlement forgery** | very low × high | Ed25519 plus pinned keys (C6); no fetched trust |
| 11 | **Private key compromise** | very low × high | Non-exportable KMS keys, least-privilege IAM, standby key, compromise runbook (§7) |

| 13 | **Backend outage** | med × low | Local-first: nothing stops until `expiresAt`; the relay is independent |
| 14 | **Clock rollback** | low × low | Existing C6 high-water rule; server time for issuance |

## 17. Logging and Observability

- **Never log:**
  - activation codes (only `last4` after hashing) and refresh tokens
  - operator tokens and KMS credentials
  - private keys and full signed entitlements or relay credentials
  - device cookies and pairing secrets
  - prompts, code, repo paths, reports and terminal output
  - request bodies
  - IP addresses beyond the edge rate-limiter's hashed client key (the pattern the relay already uses)
- **Log (symbolic JSON):**
  - `request_id`, route, status, latency
  - `result` enum (`activated`, `refreshed`, `invalid-code`, `seats-exhausted`, `revoked`, `signer-unavailable`, `rate-limited`, `schema-reject`)
  - `license_id` (not secret), `key_id`, `family`
  - event batch sizes
- **Metrics / alerts:**
  - activation success/failure ratios, invalid-code spikes
  - signer latency and errors
  - refresh backlog
  - ingest rejects
  - key-state drift (exactly one ACTIVE per family)
  - legacy-enrollment usage on the relay (R2 readiness)

## 18. No-DRM Rule (preserved)

- **No** hardware fingerprinting, anti-debugging, obfuscation-as-trust, kill switches, always-online checks or hostile lockouts.
- `installId` is a random file.
- Local counters stay user-editable.
- Expiry falls back to the built-in default, never to a lockout.
- Revocation is bounded by expiry windows, not by forced online checks.

### Test strategy (written before implementation)

- **Deterministic activation:** injected clock and CSPRNG. Retry idempotency. Bad, revoked and expired codes. Seat exhaustion. Binding uniqueness.
- **Interop:** a backend-signed entitlement verifies in the **real** C6 `LicenseFileSource`. Canonical-bytes golden vectors. Unknown and retired keyIds. Active/standby rotation keeps pre-rotation licenses valid. A compromised key is refused after the client update.
- **Refresh:** offline for days (cached use), expiry fallback, malformed responses never overwrite `license.json`, rollback.
- **Relay:** credential parse/verify/expiry; hello-binding mismatch rejected; dual-accept; the backend down during reconnects still works.
- **Ingest:** schema property tests (fuzzed free-text never accepted), batch/event idempotency, size and rate caps, consent-off → zero requests.
- **Isolation:** kill the ingest dependency and activation still works, and vice versa. Log-redaction scans (no code, token or body patterns).

### COACH REVIEW REQUIRED

**21.1 Seats and transfer.**
- **ISSUE:** how many installs one license may activate, and how a customer moves machines.
- **SOURCE TRUTH:** activation binds `installId`, which is random and file-based (C0). A wiped machine gets a new id.
- **WHY IT MATTERS:** it defines customer rights and support load.
- **OPTIONS:**
  - (a) Fixed N seats, operator-only release.
  - (b) N seats plus self-serve `deactivate` from the old install, and operator release for dead machines.
  - (c) Unlimited installs with abuse monitoring.
- **RECOMMENDATION:** (b), with N as per-license data (Founder N set by Dad).
- **IMPACT:** (a) means the most support tickets, (c) the most leakage, (b) is balanced and adds one endpoint.
- **DECISION NEEDED:** Which option, and what N for Founders?

**21.2 License windows and revocation latency.**
- **ISSUE:** `refreshAfter` / `expiresAt` defaults decide how long a refunded or revoked license keeps working offline.
- **SOURCE TRUTH:** C6 honors `expiresAt`, and S57.2 suggested 7 d / 30 d (monthly) and 30 d / 365 d (Founder/lifetime).
- **OPTIONS:**
  - (a) Adopt those.
  - (b) Shorter (for example 3 d / 14 d monthly).
  - (c) Longer, for maximum offline friendliness.
- **RECOMMENDATION:** (a), with refunds revoked at next refresh and expiry as the hard bound.
- **IMPACT:** a trade between offline tolerance and revocation lag. There is no DRM either way.
- **DECISION NEEDED:** Adopt the S57.2 windows?

**21.3 Hosting and KMS commitment (irreversible infrastructure).**
- **ISSUE:** where the API, database and signer live.
- **SOURCE TRUTH:** the relay is on Fly (`mysidelinecoach-relay`), and Fly has no KMS.
- **OPTIONS:**
  - (a) API on Fly + managed Postgres + Google Cloud KMS (Ed25519).
  - (b) Everything on one hyperscaler (verify Ed25519 KMS support).
  - (c) API on Fly with the key in Fly secrets. **Not recommended:** raw key bytes in app memory violate the custody requirement.
- **RECOMMENDATION:** (a).
- **IMPACT:** (a) adds one cloud account but keeps Dad's existing Fly operations. (b) means one vendor but migrates operations.
- **DECISION NEEDED:** Approve (a), or name the preferred provider, before C10.2.

**21.4 Telemetry identity linkability (privacy).**
- **ISSUE:** C7/C8 events carry `installId`, the same id licenses bind to, so C10 could join usage analytics to a known customer license.
- **OPTIONS:**
  - (a) Keep `installId` (linkable; richer commercial analysis).
  - (b) A separate random local `telemetryId` for events (unlinkable). Usage summaries, which are part of the license, stay linked.
  - (c) (b) plus a separate consent for usage summaries.
- **RECOMMENDATION:** (b). It matches the "behavior, never identity" spirit, and costs one small client change before C10.8 ships.
- **IMPACT:** (a) is a privacy-policy disclosure burden, (b) a small client change, (c) adds another consent toggle.
- **DECISION NEEDED:** Linkable or unlinkable telemetry? Also: raw-event retention (recommendation: 13 months, aggregates indefinitely).

**21.5 Public relay eligibility for unactivated installs.**
- **ISSUE:** after R3, may an install without a license use the public relay?
- **SOURCE TRUTH:** today only holders of the shared key can connect.
- **OPTIONS:**
  - (a) Activated installs only.
  - (b) Also issue a free "Remote trial" credential by activation of a campaign code.
  - (c) Keep a legacy/open path.
- **RECOMMENDATION:** (a), plus (b) later if packaging wants a Remote trial.
- **IMPACT:** it decides whether Remote can ever be a free taste without activation.
- **DECISION NEEDED:** Choose before stage R3. Not needed for R1.
