# Verdict

## SECURITY REVIEW: GREEN WITH REQUIRED FIXES

S5 implements the S57.45 security boundary faithfully. I found no way for a browser to choose a host, port or target. There is no generic localhost or SSRF capability. No credential crosses between the `h-` and `p-` origins. Stale Stadium and StaticPreviewServer state fails closed. The authorization boundary is **sound**.

There is one required fix, and it is about failure semantics, not authorization. Once response headers have been sent, an upstream failure or a revocation ends the phone's response as if it had completed (or leaves it open), instead of aborting it. Details are in MF-1. It is small and needs no new architecture.

# 3. MUST-FIX

## MF-1: A post-head upstream failure or revocation must abort the phone's response, never "complete" it

**Defect.** In `RemotePreviewGateway.forward` (`remote-preview-gateway.ts:325-381`), once `headSent` is true:

- **`fail()`** (upstream `timeout` or `error`) only calls `abort()`. That destroys the upstream and resolves, but it **never ends or aborts the downstream**. The phone's response stays open, and the adapter and relay in-flight entries remain until the browser gives up.
- **`revokeAll()`** calls each `abort`, which has the same effect. `upstreamRes.destroy()` fires `close` only after `settled` is already true, so the `close` handler does nothing. S5-18 asserts only `gateway.stats.inflight === 0`, never the downstream state.
- **Incomplete upstream `close` and upstream `error`** call `res.end()`. The adapter then sends a clean `end` frame, and the relay calls `res.end()` on a response whose declared `Content-Length` was never met. The browser receives a truncated asset through a "successful" 200, or hangs waiting for the missing bytes on keep-alive.

**Realistic trigger.** The field-typical case is Dad's Game window reloading or switching Games while an image streams: `dispose()` calls `closeAllConnections`, and the upstream closes incomplete. A static-file read error mid-stream triggers it the same way.

**Why it is required for R13.** S57.45 §F2 requires "never partial content". A truncated JS, CSS or WASM body that looks complete is exactly the corruption R13 set out to prevent, and the leaked in-flight entries break the "fail closed" lifecycle.

**Smallest fix (no new architecture):**

1. **Adapter** (`remote-dispatch.ts`, the `res.destroy()` / `cancel` path). When `destroy()` is called **after** `headSent`, emit `{ t: 'error', id, code: 'aborted' }` instead of `{ t: 'end' }`. The relay already maps a post-head `error` to `res.destroy()` (`reference-relay.ts` `onResponseFrame`), which the browser sees as a network failure rather than a completed body. Pre-head behavior is unchanged. `daemon.ts` does not currently call `res.destroy()` on the app surface (`grep` finds only socket and `req` destroys), so app-surface behavior does not change. The worker must re-confirm this with `grep -a`.
2. **Gateway** (`forward`). Add `destroy()` to `PreviewResponseLike`. Every post-head termination that is not a clean upstream `end` must call `res.destroy()`, never `res.end()`. That covers `fail()` after `headSent`, `abort()` from `revokeAll`, upstream `error`, incomplete `close`, and the byte-counter overflow. The downstream `close` listener must not double-abort (guard with `settled`).
3. **Gateway timeout scope.** `UPSTREAM_TIMEOUT_MS` must not fire while the stream is deliberately paused for tunnel backpressure. Either clear the socket timeout on `pause` and re-arm it on `resume`, or scope it to connect plus response head (`upstream.setTimeout(0)` in `'response'`) and rely on downstream `close` for body stalls. The first option is preferred, because it still bounds a stalled loopback body.

**Acceptance proof (tests):**

- **S5-18 extended:** `revokeAll()` during a stream results in the downstream sink seeing `destroy`, and the adapter emits an `error` frame (not `end`).
- **New test, upstream closes mid-body:** a server writes a partial body under a larger `Content-Length`, then its connections are closed. The downstream receives `destroy` / an `error` frame. Through the real relay chain (the S5-20 rig), the browser-side request errors rather than resolving with a short body.
- **New test, pause longer than the timeout:** with a shortened test timeout, a `write()===false` pause that outlasts it does not abort the stream, and `drain` resumes it to a byte-exact finish.
- The existing S1, S3 and S5 suites pass unchanged, and the app-surface SSE cancel tests are unchanged.

**Routing.** **Codex Medium or Sonnet.** It is bounded to `forward()` and the adapter's `cancel`/`destroy`, and needs no Opus re-review. The Opus gate is satisfied once the acceptance tests above are green, and the worker's report must show them.

# 4. Adjudications

## S57.50 implementation choices

| # | Choice | Ruling | Notes |
|---|---|---|---|
| 1 | Hashed remote `previewId` (`remote:` + 16 hex of sha256(stadium previewId)) | **ACCEPT** | It meets the "no Stadium id, no port" projection rule. It is not a secret: the input has low entropy and could in principle be brute-forced to a port. That is acceptable because the phone cannot address ports and no authority depends on the value. Optional: a random per-mint id (O2). |
| 2 | Grant secret generated at ticket entry, not at mint | **ACCEPT** (preferred) | The raw secret exists only in the 303 response, and a grant can be entered once. This is stronger than S57.45 specified. |
| 3 | Stricter upstream request headers (`host`, `accept: */*`, instance header only) | **ACCEPT** | It is strictly narrower than D1. The static server ignores `accept`. |
| 4 | Only upstream 200/400/403/404 pass through; everything else becomes 502 | **ACCEPT** | The static server emits nothing else in normal operation. A 409 or 503 from it also fails the instance echo first. There are no 3xx responses, so no open-redirect path. |
| 5 | A 200 without `Content-Length` is refused | **ACCEPT** | This is required to enforce the 8 MiB cap before the head. StaticPreviewServer always sets it. |
| 6 | `remotePreview` eligibility = origin configured, tunnel connected, session connected, feature advertised | **ACCEPT with a sequencing rule** | It correctly omits static-ness, which the POST decides. It cannot know whether the production relay routes `p-` origins. **Rule: the S3 relay must be deployed before S6 reaches Dad's phone (S8).** Until then a `true` flag would lead to a relay 404 inside the frame. |
| 7 | Host hello always advertises `preview.v1` | **ACCEPT** | The gateway is always present, so the capability is truthful. An old relay ignores unknown hello fields, and the relay's caps gate protects the reverse skew. |

## Explicit POST vs. "no remote auto-start"

**ACCEPT.** `POST /api/games/preview/remote` calls `game.preview.resolve`, which may start the Stadium's StaticPreviewServer and may record the chosen static entrypoint. This is the architected Dad action (S57.45 §B1 step 1), equivalent to Preview Work on the desktop.

It is protected in several ways:
- It is `remote-mutate`, with the action header and Origin checks.
- It is bound to a live device.
- It can only prepare the Game's own root through the Stadium's containment.
- The **content path never starts, restarts or rebinds anything**, and that is the property that matters.

## Unresolved risks listed in S57.50

| Risk | Ruling | Rationale |
|---|---|---|
| Per-device revocation takes effect on the next request, not mid-stream | **ACCEPT** | Each in-flight stream is one asset (≤ 8 MiB) that the device was authorized for when it started. Every subsequent request fails. `revokeAll` (Remote Access off, daemon stop) does abort streams, and does so visibly once MF-1 lands. Per-device mid-stream abort would add a device-to-inflight index for negligible gain. |
| Preview traffic does not slide DeviceRegistry `lastSeenAt` | **ACCEPT** (correct as designed) | The preview credential is not a device credential and must not extend a device's life. Every grant starts with an app-surface POST that authenticates the device, and that POST slides `lastSeenAt`. The 30-day window cannot lapse within the grant's 8 h absolute lifetime except for a device already at its idle boundary, where failing closed is correct. |
| The gateway prefilters the raw percent-encoded pathname; StaticPreviewServer stays authoritative | **ACCEPT** | Both sides decode exactly once with `decodeURIComponent`, normalize `\` to `/`, and reject `.`/`..` segments. A double-encoded `%252e%252e` becomes the literal segment `%2e%2e` on both sides, not a traversal. The adapter's WHATWG parse has already resolved dot segments. `realpath` containment in StaticPreviewServer is the final authority, as architected. |

# 5. Optional hardening (not gating)

- **O1.** Add `Cache-Control: no-store` to the `POST /api/games/preview/remote` JSON, which carries a live ticket. Sideline's `sw.js` caches nothing and the ticket is single-use with a 60 s expiry, so this is defence in depth only. One line in `openRemotePreview`, or a `sendJson` variant.
- **O2.** Replace the hashed `previewId` with a random per-mint id if the phone UI never needs it to be stable across mints.
- **O3 (for S7).** The gateway's denial reason strings (`bad-ticket`, `game-gone`, `bad-path`, `reserved`, `target-error`, `upstream-status`, `upstream-timeout`, `no-length`, `grant-revoked`) differ from the S57.45 §I `DenialCode` vocabulary. S7 owns that reconciliation. Keep the richer set and extend the §I enum; do not collapse it.

Codex or Sonnet can implement any of these without new architecture.
