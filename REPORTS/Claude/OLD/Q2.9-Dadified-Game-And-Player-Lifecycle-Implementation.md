## 3. GAME LIFECYCLE ARCHITECTURE

One pure state model, `src/game-lifecycle.ts`:

```text
known → opening → connected → offline → archived
                       ↑ ↓
                   conflicted
```

`deriveGameState()` resolves in a deliberate precedence order:

| Rank | State | Why it wins where it does |
|---|---|---|
| 1 | `archived` | A finished Game must never reappear just because a window happens to be open |
| 2 | `conflicted` | More than one live session — block exact routing rather than guess a window |
| 3 | `connected` | Exactly one authoritative session |
| 4 | `opening` | Coach issued an open and the deadline has not passed |
| 5 | `offline` | Has connected before, nothing live now |
| 6 | `known` | Registered from the picker, never yet connected |

**The hard rule: `Offline ≠ Archived`.** A closed window or a sleeping Codespace is
Offline — still a live project Coach expects back. Archived is the human saying the
project is finished. The model, the registry, the API and the browser all keep these
separate, and `G2`/`G11`/`G12` prove it.

`Working` was considered and **not** added. Turn state already exists per Player
instance (`turnState`), and a Game-level "Working" would be a second, weaker copy of
truth that could disagree with it. Recorded as a breadcrumb rather than invented.

## 4. ADD GAME IMPLEMENTATION

`POST /api/game/add` — one browser action, whole lifecycle:

```text
browser: + Add Game
  → Control Plane picks a host Stadium (the selected Game's window first)
  → RPC game.pick        → Stadium shows vscode.window.showOpenDialog
                         → resolves Game identity from the chosen folder
  → Control Plane registers the Game (recordKnownGameFromPicker)
  → decideAddGame(state) ─┬─ connected  → select it, no second window
                          ├─ opening    → do nothing, already underway
                          ├─ conflicted → report, never choose a window
                          ├─ unresolved → plain-language refusal
                          └─ open       ↓
  → markOpening + broadcast (browser shows Opening… immediately)
  → RPC game.open        → Stadium opens the window
  → new window activates → StadiumClient connects outbound
  → registry binds the Game, clears Opening
  → SSE  → browser shows Connected, with no refresh
```

`decideAddGame()` is pure, so every branch is provable without a VS Code window
(`G6`–`G9`), and the full HTTP path is proven against a real daemon (`E1`–`E6`).

## 5. WINDOW-OPENING OWNERSHIP

Q2.8G recommended the Control Plane own window opening. Re-evaluated against the code,
that is **half right**, and the split matters:

> **The Control Plane decides. The Stadium executes.**

- The **Control Plane** must decide, because only it knows every live session across
  every window, and therefore whether the Game is already Connected, already Opening, or
  Conflicted. The browser cannot know this, and the requesting window is not necessarily
  the right host.
- The **Stadium** must execute, because opening a window is environment-specific
  mechanics. `vscode.openFolder` uses the human's own VS Code, profile and extensions —
  no `code` CLI, no PATH dependency, no ports, and VS Code natively focuses an
  already-open folder instead of duplicating it.

A daemon-side `spawn('code', …)` was rejected: it would depend on the CLI being on PATH,
would bypass the human's profile, and would be wrong for any future non-desktop Stadium.

## 6. FOLDER PICKER MECHANISM

A browser cannot safely enumerate local paths, and the daemon has no UI. The picker
therefore belongs to the Stadium, and the seam already half-existed in Q2.8:

```text
browser intent  →  Control Plane  →  RPC game.pick  →  VS Code showOpenDialog
                                  ←  { folderPath, game }  ←
```

Only a resolved path and a resolved Game identity travel back — never a directory
listing. The human experiences one coherent Add Game action; the native dialog is simply
where the choosing happens.

If no Stadium is connected at all, Coach says so plainly rather than failing obscurely
(`E11`): *"No Game window is connected yet, so Coach has nowhere to show the repository
picker. Open a Game first."*

## 7. OPENING STATE

`Opening…` is a real state with a deadline, not a spinner.

- Set the instant Coach issues the open, and broadcast immediately, so the human sees
  `Opening…` before the window appears.
- Cleared when the Game's Stadium connects (`recordKnownGame(..., connected: true)`).
- Cleared immediately if the open call fails (`E6`).
- **Expires after 90 s** (`OPENING_TIMEOUT_MS`) and decays to `Offline`
  (`expireStaleOpenings()` runs on every status build), so a window that opened but never
  activated can never leave a Game spinning forever (`G4`).

## 8. ALREADY-OPEN BEHAVIOUR

Three distinct cases, all handled without duplicates:

| Situation | Behaviour | Proof |
|---|---|---|
| Game already **Connected** | Coach selects it and says so. No second window. | `E3`, `G6` |
| Game already **Opening** | Coach reports it is already opening. No second open. | `G7` |
| Folder open in VS Code but Coach not connected | `vscode.openFolder` focuses the existing window rather than duplicating it; the activating extension then connects | product path, human proof |
| Same Game live in **two** windows | `conflicted` — reported, never silently resolved | `E`/`G8`, Q2.8 behaviour retained |

## 9. EXIT / ARCHIVE BEHAVIOUR

Terminology chosen: **Exit Game** in the UI (the human's own word), `archived` in the
model. `Archive` reads like filing; `Exit` reads like finishing, which is the intent.

`POST /api/game/archive`:

```text
removes the Game from the active Sideline
moves selection to a surviving Game
keeps the full Game record (displayName, repoUri, knownRootFsPaths)
NEVER touches the repository — no deletion, no file modification
reversible: POST /api/game/restore, or simply reopening the Game
```

The browser button says *"Exit — removes it from the Sideline, never from disk"*, and
the response says *"Its repository was not changed."* Proven by `E7`, `G11`–`G13`, `UX4`.

## 10. PLAYER LIFECYCLE ARCHITECTURE

```text
Player TYPE       catalog identity          Codex · Claude · AntiGravity · Terminal
Provider ADAPTER  the code behind a type    detect / install / launch / adopt / control / stop
TRANSPORT         how bytes reach the agent app-server stdio · terminal sendText
Player INSTANCE   a live Game-scoped seat   opaque instanceId + seat + ownership + onField
```

Type and instance are never collapsed. `Codex` is a catalog entry;
`Codex · Controlled` seat 1 is an instance with routing coordinates.

Every lifecycle action travels with the selected `gameId` (`E8`), so a Player added to
*Browser Gallery* can never be created, benched, removed or messaged inside *GS3*.

## 11. PLAYER DISCOVERY

New `PlayerDiscoveryService` (`src/player-discovery.ts`), Stadium-scoped, answering the
question the roster cannot:

> **"Who could play here?"** ≠ **"Who IS playing here?"**

Collapsing those two is precisely what let a manually-launched agent be invisible: the
roster only knew about Players Coach created, and nothing ever asked the environment.

- Owned per extension host, because the environment it describes is that host's.
- Imports **no** `vscode` API — probes are injected, so the rules are unit-testable.
- Results carry `stadiumId`. There is deliberately no global `claudeInstalled` boolean:
  a Player on the Windows Stadium says nothing about a Codespace (`P3`).
- Cached per Game in the daemon and published as `status.playerDiscovery`, which is
  `null` when not yet checked — different from an empty catalog, and not collapsed
  into it (`E9`).

**Discovery never fabricates authentication state** (`P1`):

| Observation | State |
|---|---|
| Terminal | `available` |
| probe failed / unknown | `unknown` — never a guess |
| not on PATH | `not-installed` + the adapter's install command |
| installed, no auth probe defined | `ready` |
| installed, probe says not signed in | `authentication-needed` |

The `probeAuth` hook exists and is **intentionally unwired**. Inventing
`claude auth status --json` without verifying it would have fabricated a status. The
consequence is honest and stated: `Authentication Needed` will not appear until a real
probe is added, and a genuine sign-in failure still surfaces through the existing
`needs-sign-in` control outcome at open time.

The UI label chosen is **Check Players** over "Find Players" — the human is verifying a
known roster of supported agents, not searching for unknown ones.

## 12. TERMINAL PLAYER

Terminal is its own Player type and its own transport. It is **not** a costume worn by a
provider (`test: "Terminal is its own Player type, never a costume worn by a provider"`).

```text
+ Add Player → Terminal → Terminal · Ready
```

- Created with `cwd` pinned to the Game root, so a command can never run in another Game.
- Carries `stadiumId`, `gameId`, `playerInstanceId`, `cwd`, ownership, and liveness.
- Minimal control implemented: create, send text, send Enter, know cwd, know alive,
  close-if-owned. No PTY-over-WebSocket, no output streaming.

**Excluded from Play routing.** This was a real defect caught during implementation:
adding `terminal` to the catalog made it a routing candidate, so a Play dispatched to it
would have typed an entire prompt into the human's shell. `getRoutingCapabilities()` now
skips Terminal Players *and* benched Players (`R1`).

**Why it matters:** it is the universal escape hatch. If Coach can open the correct
terminal in the correct Game on the correct Stadium, it can bootstrap almost anything —
which is exactly what the install and authentication helper path uses.

## 13. OWNERSHIP MODEL

Every instance records ownership explicitly at allocation; it is never inferred later.

| Ownership | Meaning | Coach may |
|---|---|---|
| `coach-managed` | Coach created it | dispose it |
| `adopted` | pre-existing, adopted on request | detach; confirm before destroying |
| `external` | observed only | detach only, never destroy |

**Terminal names still grant no authority** (Stage 1.7/1.8). That is why adoption targets
a **shell pid**, and why external agents are matched on executable name or the leading
command-line token — never on a terminal's display name. A shell merely *named* `Claude`
is not Claude (`P6`).

## 14. TAKE OFF FIELD vs REMOVE PLAYER

Three genuinely different actions, never merged:

| Action | Scope | Instance survives? | Process / terminal |
|---|---|---|---|
| **Take Off Field** | execution lifecycle | yes — seat and transport retained, returnable | untouched |
| **Remove Player** | this Game's roster relationship | no | disposed **only if** `coach-managed`; otherwise detach |
| **Close Terminal** | transport only | yes | that terminal only |

`PlayerInstanceRecord.onField` makes benching real: a benched Player keeps its seat, is
not a routing candidate, and returns via Put on Field without becoming a new instance
(`"benching keeps the instance and its seat; only removal retires it"`). The browser
confirms before removing, and the wording differs by ownership — *"Coach will close the
terminal it created"* versus *"Coach will detach and leave your terminal running"*
(`UX3`).

## 15. EXISTING PLAYER DISCOVERY AND ADOPTION

This is the direct repair for the reported AntiGravity failure.

**What used to happen:** AntiGravity running manually → roster blind to it → human closes
it → re-adds through Coach → Coach relaunches it → presents it as `Legacy`.

**What happens now:**

```text
Check Players
  → Coach scans each Game terminal's descendant processes
  → "AntiGravity is already running in \"pwsh\"."
  → [Adopt AntiGravity]
  → roster shows AntiGravity · Adopted, Coach will not close it
```

`P8` reproduces the exact reported shape (a shell → node → `agy.exe` chain) and proves it
is found; `P9` proves Coach never re-offers a shell it already owns.

**The boundary, stated honestly:** adoption is **detection plus an explicit human
action**, not automatic. Coach will not silently seize a process it did not start, and
the spec's instruction was to implement detection and an explicit `Adopt Player` rather
than fake automatic adoption. Adopted instances use the direct-terminal transport, so
they are not controlled-tier — Coach does not overstate its control.

A failed scan reports `externalScanSupported: false` and the browser says so
(`P5`) — absence of evidence is never presented as evidence of absence.

## 16. LEGACY CLEANUP

`Legacy` is an implementation generation. The human now sees capability and state:

```text
Controlled · Terminal · Adopted · External
```

The internal `transport: 'controlled' | 'legacy'` field is **unchanged**, so routing

This does not lie about control tier: an adopted terminal Player is labelled `Adopted`,
not `Controlled`, and only a certified controlled channel is ever labelled `Controlled`.

## 17. CONTROL PLANE vs STADIUM RESPONSIBILITIES

Made explicit so responsibilities cannot drift opportunistically:

| Concern | Owner | Why |
|---|---|---|

| Roster projection | **Control Plane** | Game-scoped, browser-facing |
| Exact routing | **Control Plane** | `stadiumId + gameId + playerInstanceId` |

> **Control Plane coordinates. Stadium executes environment-specific mechanics.**

## 20. KNOWN CONSTRAINTS

### 20.1 Add Game cannot be fully proven inside an Extension Development Host

The product path is `vscode.openFolder`, which opens a window in the human's installed
VS Code. Under an Extension Development Host, Coach is **loaded from
`--extensionDevelopmentPath` and is not installed**, so a window opened that way would
contain no Coach and the Game could never connect.

Handled rather than hidden: `chooseOpenStrategy(extensionMode)` selects
`development-instance` under `ExtensionMode.Development` and launches a separate VS Code
instance using the Q2.8G-proven `--user-data-dir` shape, one profile per Game. This is
**development-only** and clearly quarantined — it is not what a customer runs, and the
product path has no `--extensionDevelopmentPath` and therefore no instance constraint at
all.

The fully authentic product proof needs the packaged extension (`npm run package`, then
install the VSIX). Recommended as the next action (§23).

### 20.2 Authentication state is not yet probed

`probeAuth` exists and is unwired, so `Authentication Needed` will not appear yet.
Deliberate: fabricating a status is worse than not showing one.

### 20.3 Adoption is explicit, not automatic

Coach detects an already-running agent and offers `Adopt`. It will not seize a process it
did not start.

### 20.4 External process scanning is Windows-only

`listWindowsProcesses` uses `Get-CimInstance`. On other platforms
`externalScanSupported` is `false` and the browser says so.

### 20.5 Adopted Players are not controlled-tier

They use the direct-terminal transport and are labelled `Adopted`, never `Controlled`.

### 20.6 The running Stadium is on pre-Q2.9 code

The GS3 Extension Development Host connected during this Play activated before the
recompile, so it is running the older build in memory. It must be restarted to pick up
Q2.9. The daemon was deliberately not restarted.

### 20.7 Small UX debt (Part 20) — fixed

`Copy Report to Clipboard` had no class, so it inherited the primary green/near-black
treatment and looked identical to `Dispatch Play`. It is now `class="secondary"` — light
text on dark, and visually subordinate to Dispatch. One-line change, guarded by `UX5`.

## 23. WAS / IS / WILL BE

**WAS.** Games could be known or manually connected, but Add Game did not complete the
lifecycle: choosing a folder produced a Known Game and stopped, with no window, no
activation and no connection — observed live when the human chose *Gallery Media Suite*
after Q2.8G. Players depended too much on how they were launched: a manually started
AntiGravity was invisible to the roster, so the human had to close it, re-add it through
Coach and put it on the field again purely to make Coach notice it, and it was then
presented as `Legacy`, leaking an implementation generation into product vocabulary.
Terminals existed as plumbing rather than as a Player Coach could offer.

**IS.** One state model governs `known → opening → connected → offline → conflicted →
archived`, with `Offline ≠ Archived` enforced and `Opening` bounded by a 90-second
deadline that decays to Offline. Add Game is one browser action that runs picker →
identity → decision → open → Opening → Connected, with the Control Plane deciding and the
Stadium executing the two VS Code mechanics. Exit Game archives without touching a
repository. Check Players asks the Stadium what could play there, never fabricating an
authentication state, and finds agents already running so they can be adopted rather than
restarted. Terminal is a first-class Player type, Game-scoped by `cwd`, excluded from Play
routing, and is the bootstrap path behind the install and sign-in helper terminals.
Ownership (`coach-managed | adopted | external`) governs what Coach may destroy, terminal
names still grant no authority, and Take Off Field, Remove Player and Close Terminal stay
three different actions. The human sees `Controlled | Terminal | Adopted | External`, and
never the word Legacy. Every mutation converges to the browser over SSE with no refresh.

**WILL BE.** Automated provider installation and authentication once trust and credential
handling are designed; Terminal → controlled Player promotion, keeping the same
`playerInstanceId`; controlled adapters beyond Codex through the existing registry;
graceful provider-specific shutdown; terminal output streaming and an interactive remote
shell; remote Stadium and Codespaces aggregation, which is additive because discovery
already carries `stadiumId` and routing is already three-coordinate; and eventually a
third-party adapter ecosystem. Full deferral rationale is in the breadcrumbs.
