## Controlled Codex regression root cause

**Symptom (live, GameTest).**
- `codex-0a6eab81` was Unavailable / needs-decision with the error `thread not loaded: 01a0971f-8c5e-74e3-ab02-9281630734e9`.
- MANUAL Codex showed *Provider Default · Live discovery unavailable*.

**Root cause.** Two defects stacked:

1. **Changed provider semantics.**
   - `CodexAppServerFactory.restore` called `thread/read` first, as an existence and authority check.
   - In Codex app-server 0.154.0, a fresh process answers `thread/read` with `thread not loaded: <id>` for **every** thread it has not loaded yet: one that exists on disk and one that never existed alike.
   - Restore treated that error as fatal, so a healthy, resumable conversation was reported as broken.
2. **Capability discovery was gated on restore success.**
   - Even with the conversation question open, the same authenticated process could answer `account/read` and `model/list`.
   - Coach never asked, so the Dispatcher lost all model and effort truth.

**Fix (`src/player-control/codex-app-server.ts`, `contract.ts`, `player-roster.ts`).**
- `thread/read` "not loaded" is now *unverified*, not failure. Restore goes on to `thread/resume`, which loads the thread. `validateAuthorityResponse` re-checks thread id, non-ephemerality, Game cwd and authority on the resume result.
- Only a genuine missing signal (`no rollout found for thread id …`) counts as missing. The existing rules are unchanged:
  - history expected → needs-decision ("Can't resume this controlled Player. Its conversation is no longer available.");
  - no history expected → open fresh exactly once.
- Every non-ready restore outcome (needs-decision, writer-busy, api-key, catch-all) now carries `capabilities`. They are captured from the same signed-in process with a 3 s budget.
- `PlayerRoster` records those capabilities, so MANUAL shows real models and efforts even when the conversation needs a decision.
- Writer-busy retry and every authority validation are unchanged.

## thread-not-loaded meaning

Measured against an isolated `CODEX_HOME` with Codex 0.154.0:

| Call in a fresh app-server process | Existing thread | Never-existed thread |
|---|---|---|
| `thread/read` | `thread not loaded: <id>` | `thread not loaded: <id>` |
| `thread/resume` | success (thread loaded, history available) | `no rollout found for thread id <id>` |

**"thread not loaded" means "this process has not loaded that thread yet"**. It is not "missing", "corrupt" or "unauthorized", so it says nothing about existence. `thread/resume` is the authoritative existence check.

## Provider-control architecture

**One contract, independent of transport** (`src/provider-control.ts`):

```
ProviderControlProfile
  promptDelivery, semanticTurns
  model  : { state: available | requires-proof | unavailable | unknown, mechanism, options[], currentLabel?, note? }
  effort : { same shape }
  sessionScopedControl?: { mechanism: 'structured-print', proven, evidence }
```

**One question per exact instance:** `projectInstanceControls(instance, discoveryControls)`.

Source priority:
1. **Exact live Controlled capability.** A Controlled instance with a live snapshot → `controlledControlProfile` (state `available`, semantic, models from `model/list`, efforts as the union of the models' efforts, current label from that instance's active settings).
2. **Provider-specific safe discovery.** Used for a terminal instance whose discovery controls match its `playerType`:
   - Claude: `/model` and `/effort` local commands (Q2.10A).

3. **Unknown.** No controls are attached, and the UI says so. Nothing is invented.

The Control Plane (`daemon.buildStatus`) attaches the projection as `capabilities[].controls`. `buildRouting` and the browser consume that single answer.

**Rules:**
- Never substitute a sibling instance's controls.
- Never let a Player-type default overwrite an exact instance's live truth.

## Claude control findings / proof

**Mechanism audited:** structured print mode with per-invocation flags. Interactive `/model` inside a live session is rejected, because Q2.10A proved it persists to the human's user settings.

**Proof (Claude Code 2.1.270, PowerShell, neutral temp cwd):**

1. `claude -p "Reply OK" --model haiku --effort low --output-format json`
   - Result: session `915db169…`, model `claude-haiku-4-5`.
2. `claude -p --resume 915db169… --model sonnet --input-format stream-json --output-format stream-json --verbose` with the prompt sent as a stream-json user message.
   - The `system/init` event reports model `claude-sonnet-5` with the **same session id**, and the turn completes.
3. `~/.claude/settings.json`: hash identical before and after; `model` still `"opus"`.

**Conclusions:**
- `--model` and `--effort` are **session/invocation-scoped**.
- `--resume` preserves conversation continuity across a model change.
- stream-json gives semantic turn events (init → assistant → result).
- This is sufficient for a **Controlled Claude adapter**.

**Why it is not implemented yet (authority boundary):**
- Print mode cannot answer interactive tool-permission prompts, so a Controlled Claude that edits files needs an explicit `--permission-mode` (`acceptEdits` / `bypassPermissions`) or an allowlist.
- That is the same class of authority as Codex's `approvalPolicy: never` + `danger-full-access`, and it is the human's decision.
- Coach does not pick it silently.

**Implemented now:**
- `claudeControlProfile` carries `sessionScopedControl` (proven, with evidence).
- A **terminal** Claude's controls stay `requires-proof`: Coach never reconfigures a human's interactive session.
- MANUAL shows Claude's real defaults, labelled as Claude's own.

## MANUAL dispatcher architecture

**Target:** the exact `playerInstanceId`, shown by display name ("Claude 2", plus " · Terminal" when not Controlled). A sibling is never substituted.

**Model select** (Controlled, live capability):
- `Auto`: Coach chooses for this Play.
- `Provider Default`: never override.
- Then the real models from `model/list`.

**Reasoning select:**
- `Auto`.
- `Default (<model default>)` / `Provider Default`.
- Then the efforts supported by the chosen model. With model Auto, the list is the union across models.

**Partial override** is allowed: model Auto + effort High, or a chosen model + effort Auto.

**Resolution** happens in the Control Plane (`router.ts` → `resolveCoachAuto`) against that exact instance's live capability:
- `auto` resolves through the provider routing policy for the analysed Play.
- An Auto effort must be supported by the resolved model; otherwise the model's default effort is used.
- `default` passes through unchanged.
- On a Player Coach cannot operate (terminal, or no live capability), Auto resolves to *don't override*. That is truthful: the Player keeps its own settings.

**Terminal Players:** MANUAL shows provider defaults labelled as the provider's own (for example "Claude default · Opus"), and nothing is sent to change them.

## AUTO dispatcher architecture

**Decision pipeline:**
1. Collect on-field candidates. None → "No Player is on field…".
2. Keep only those that **can take Plays** (`ready | busy`). None → "`<names>` can't take Plays right now. Check the Roster for what needs attention."
3. **Choose the provider (WHO).**
   - A single dispatchable Player → selected, whatever its transport ("AUTO chooses WHO; transport decides HOW").
   - Several terminal-only Players → Manual, with a truthful message, until the Analyzer-driven multi-provider choice ships.
4. **Choose the exact instance (WHICH).** Today: the first free controlled instance, deterministic, and it prefers a free sibling over a busy one. WILL BE: context affinity from the Instance Work Ledger.
5. **Choose the model and effort (WHAT, HOW HARD).** The provider policy runs on the Play Analyzer classification, validated against live capability. Without live truth AUTO stops ("Live routing capabilities are unavailable…").
6. **Send / queue / recommend.**
   - Today: stage → human sends.
   - WILL BE: queue for the owner instance, or recommend another instance, when context or collision matters.

**Every decision carries:**
- `rationale { player, instance, model, effort }`;
- a one-line Dadified `summary` (for example "Claude is free and can run this Play now.");
- `transport` and `playLabel`.

## report/context routing architecture

**Report provenance** (additive to the report contract): new reports carry

- Game;
- Play `clientRef`;
- Player type;
- **Player instance id and display name**;
- provider, model, effort;
- timestamp.

The Stadium's report watcher attaches each report to the exact instance in the Ledger. Old reports are not migrated.

**Context routing:**
- A follow-up Play about a report routes by default to the instance that wrote it: "Continue with Claude 2".
- If that instance is busy, AUTO recommends *queue for Claude 2* versus *start on Claude 1 with the report attached*, and explains the trade.
- The report path is passed as context; Coach never pastes whole transcripts.

## queue architecture

- **Owner:** the Control Plane. One queue per exact instance.
- **Item:** the full staged route (instance, model, effort, prompt, playLabel, rationale, `clientRef`).
- **Release:**
  - Controlled: on semantic turn completion.
  - Terminal: on report provenance arrival or a human "Done". Never on timing guesses.
- **Human controls:** view, reorder, cancel, "send now to another instance".
- **Persistence:** in memory first, then an optional per-Game file. A daemon restart shows queued items as *needs confirmation* rather than auto-sending.
- **AUTO:** chooses between queue-for-owner / another free instance / another qualified Player, based on context affinity plus collision assessment, and recommends rather than forcing.

## collision / parallel-work architecture
