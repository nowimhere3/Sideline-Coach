# Canonical Execution Authority

**Decision: the Instance Work Ledger (`src/control-plane/work-ledger.ts`) remains, and is formalised as, the only execution authority.** It is not replaced, and no second state machine is added.

Why:
- It already lives in the single Control Plane process shared by every Stadium and browser.
- It is keyed by Game + exact instance.
- It sees both router delivery verdicts and Stadium turn semantics.
- It persists history and report links, and it already feeds AUTO context affinity and the durable queue.
- Every alternative (Stadium `turnStateByInstance`, the roster snapshot, the browser map) is per-Stadium, lagging, or per-viewer.

**Minimal extensions (additive, optional fields):**

```ts
// LedgerPlay
readonly startedAt: number;              // UNCHANGED meaning: Coach dispatched it (attribution, context affinity rely on this)
readonly executionStartedAt?: number;    // NEW: Control Plane receipt time of the first `started` evidence for this Play
// InstanceLedgerEntry
readonly revision: number;               // NEW: global monotonic counter value at this entry's last mutation
// LedgerRecentPlay
readonly acknowledgedAt?: number;        // NEW: human saw a failure/unknown outcome (See what happened / dismiss)
// LedgerReportLink
readonly acknowledgedAt?: number;        // NEW: human opened this report
// InstanceWorkLedger
readonly epoch: string;                  // NEW: random per Control Plane process; revisions are comparable only within an epoch
```

Rules:
- `executionStartedAt` is set **once**, by the Control Plane's `now()`, on the first `started` for the current Play's `turnRef`. It is never reset by `accepted`, repeated `started`, refresh or reconnect.
  - One clock, the Control Plane host's. The Stadium's `turn.at` is diagnostic.
  - For adapters that emit `accepted` then `started` synchronously, the value equals the accept time; for Codex it is the real `turn/started`.
- After Control Plane replacement, the Stadium re-teaches the active turn (Slice A2). A `busy` capability without a known turn gives `working` with `executionStartedAt` undefined, rendered as Working **without** a clock. It never invents one.
- Terminal outcomes (`completed`, `failed`, `interrupted`, `unknown`) are final for that `clientRef`/`turnRef`: a later `accepted`/`started` carrying the same `turnRef` is ignored. This is already true for `completed`, via `alreadyFinished` in `recordDelivery`; it becomes explicit in `recordTurn`.

# Event / Snapshot / Work Ledger Relationship

| Signal | What it is | May change execution truth? |
|---|---|---|
| Router `status-update` (`sending`, `received`, `failed`, `unknown`) | Delivery verdict (transport) | Yes, via `ledger.recordDelivery`, the existing path |
| Stadium `turn.changed` (`accepted`, `started`, `completed`, `failed`, `interrupted`, `unknown`) | Semantic lifecycle **evidence** from the exact Player | Yes, via `ledger.recordTurn` |
| Stadium `capability.snapshot` `state` (`ready`, `busy`, `unavailable`, `needs-verification`) | **Routing eligibility** evidence | Only for reconciliation: `busy` with no current Play → `working` (no clock); a non-`busy` Controlled Player while `working` with no pending dispatch → `unknown` (never Finished). It can never override a Play that has a terminal event pending on the same ordered socket. |
| Stadium `roster.changed` `instance.turnState` | Stadium-local diagnostic copy | **No.** Never read for presentation. |
| Control state (`active`, `ready`, `lost`, `closed`) | Adapter-internal | Only through the events above |
| `report.changed` / provenance | Returned-work evidence | Links reports to Plays and instances (existing), and completes the loop |
| PlayQueue items | Accepted, not yet delivered | Queue projection (below); not Ledger working |

Capability meanings relative to a Play:
- `ready`: can accept a Play now.
- `busy`: a turn is active or the control is `active`.
- `unavailable` / `needs-verification`: cannot accept Plays.

None of these is itself "Finished". `busy` is not a clock origin.

**Daemon projection:** a new pure module, `src/control-plane/execution-projection.ts`.

```ts
export type ExecutionState =
  | 'idle' | 'starting' | 'working' | 'queued' | 'waiting-capacity'
  | 'needs-you' | 'finished' | 'couldnt-finish' | 'unknown';

export interface ExecutionView {
  instanceId: string;
  state: ExecutionState;
  revision: number;
  playRef?: string;                 // clientRef of the Play this view is about
  summary?: string;                 // promptSummary (already human-safe)
  executionStartedAt?: number;      // present only when state === 'working' and truly known
  finishedAt?: number; durationMs?: number;   // finished / couldnt-finish / unknown
  report?: { path: string; filename?: string; acknowledged: boolean };
  awaitingReport?: boolean;         // finished, no linked report yet, within REPORT_GRACE_MS
  queue?: { count: number; head?: { reasonKind: 'own-current-play' | 'waiting-for-player' | 'unspecified'; waitingOnName?: string } };
  detail?: string;                  // human-safe failure/unknown sentence for "See what happened"
  executionType?: 'reasoning' | 'direct-shell';
}
export function projectExecution(input: {
  entry?: InstanceLedgerEntry; pendingDispatch: boolean; queued: readonly QueuedPlayView[];
  controlState?: string; executionType?: string; now: number;
}): ExecutionView;
```

Derivation precedence, first match wins:
1. `needs-you`: a queue item for this instance is `needs-attention`, **or** a Play is current and the Controlled Player is `needs-sign-in`/`needs-decision`.
2. `working`: Ledger `working` **and** `executionStartedAt` is known (or `busy` re-learned without a start: `working` with no `executionStartedAt`).
3. `starting`: a dispatch is pending (`sending`), or the Ledger is `working` with no `executionStartedAt` yet (accepted, not started).
4. `waiting-capacity`: **reserved; no producer in V0.** Usage Sentinel will produce it later. Never inferred.
5. `queued`: queue items exist and no Play is current.
6. `unknown`: Ledger `unknown` or `disconnected` with an unacknowledged Unknown latest Play.
7. `couldnt-finish`: latest Play `failed`, `interrupted` or `not-sent`, unacknowledged, and no newer Play.
8. `finished`: latest Play `completed` whose linked report is unacknowledged, or which is still `awaitingReport`.
9. `idle`.

When `working`/`starting` and queue items coexist, the state stays working/starting and `queue.count` rides along ("1 more queued").

`status.execution = { gameId, epoch, serverNow, byInstance: Record<instanceId, ExecutionView> }` is computed for **every roster instance** of the selected Game. The existing `capabilities[].work` covers only on-field instances; it stays unchanged for routing compatibility.

**SSE:** after any mutation that changes a view, the daemon broadcasts `event: execution` with `{ gameId, epoch, serverNow, views: ExecutionView[] }`. This is driven from `ledger.onChange` plus queue changes, coalesced per `setImmediate` and computed from the Ledger after the mutation, so it can never be older than the Ledger. The raw `turn` SSE stays for compatibility and diagnostics; the browser stops using it for execution.

# Browser Merge / Refresh Policy

One store:

```js
// key: `${gameId}|${instanceId}`
executionStore = { gameId, epoch, serverOffsetMs, views: Map<instanceId, ExecutionView> }
```

**The one merge rule**, used by both snapshots and events:
1. Ignore anything whose `gameId !== currentGameId`.
2. If `epoch !== store.epoch`: accept **only a full `/api/status` snapshot**, which replaces the store wholesale (Control Plane replaced). Ignore stray events from the old epoch.
3. Otherwise, per instance: apply a view **only if `view.revision > stored.revision`**. For a full snapshot, use `>=`; instances absent from a snapshot are removed.
4. On every status or event, `serverOffsetMs = payload.serverNow - Date.now()`, smoothed by taking the latest.

Consequences:
- A slow `/api/status` that started before an `execution` event cannot regress it (lower revision).
- A stale `started` cannot resurrect Working after `finished` (lower revision).
- Refresh and SSE interleave deterministically, with no timestamp heuristics or duplicate-acceptance special cases.
- `turnStatesByInstance`, the roster `turnState` fallback, and the `duplicateAcceptanceAfterStart` guard are retired for execution.

**Dispatcher state is separate:** a local `dispatchAttempt` (below), never derived from the execution store. A refresh can never end an in-flight submission.

# Reconnect Semantics

- **SSE reconnect** (`hello`): the full `/api/status` snapshot replaces views at `>=` revision. `executionStartedAt` is the original Control Plane timestamp, so elapsed time resumes from it, corrected by `serverOffsetMs`.
- **Page reload:** same as SSE reconnect; the store starts empty.
- **Control Plane replacement** (new epoch): the snapshot replaces everything. Slice A2 makes it truthful:
  - `PlayerRoutingCapability` gains an optional `activeTurn?: { turnRef: string; state: 'accepted' | 'started'; startedAt: number }`, filled by the Stadium from `turnStateByInstance`.
  - `observeRoster` adopts it when the entry is `working` with no `currentPlay`: `currentPlay = { clientRef: turnRef, startedAt, executionStartedAt: startedAt, turnRef }`.
  - This is the only place a Stadium timestamp is accepted, because the Control Plane never saw the start. It is marked `recovered: true` internally.
  - Completion then records history, and report attribution works again.
- **Stadium disconnect:** views become `unknown` ("Can't confirm status"), never `couldnt-finish`.

# Multi-Player Semantics

- The store holds a view for every roster instance. The TEAM header and Player strips render **all** instances in the current Game.
- `selectedPlayerInstanceId` stays a MANUAL-form value only. It must not appear in any execution rendering path, and changing it must not touch the store.
- The Outgoing acknowledgement binds to `dispatchAttempt.playerInstanceId` + `clientRef` from the dispatch reply, never to "first active" or "selected".
- A benched Player with a current Play keeps its strip (the projection covers roster instances, not only capabilities).
- Terminal (`executionType: 'direct-shell'`):
  - with shell integration, the strip shows `▸ Running command` with **no** elapsed timer, and it counts as ACTIVE;
  - an unobserved send shows nothing (Unknown is not claimed as activity);
  - exit maps to `finished` / `couldnt-finish` without "Report ready" copy.

# Frozen Human UX Contract

Adopted **verbatim** from the brief: Parts III and IV. No reopening of placement, auto-scroll, timer location, lifetimes (10 s rich completion, 8 s full acknowledgement), or copy.

# Team Header Architecture

`#rosterSummary` becomes `renderTeamHeader(store, names)`, a pure function of the store:
- `activeCount` = starting + working + queued + waiting-capacity + observed Terminal commands.
- `needsYouCount` = needs-you + couldnt-finish + unknown (all three require a human and none auto-dismiss).
- `reportReadyCount` = finished views with an unacknowledged linked report.

Segments, highest priority first, **at most two**:
- `N NEEDS YOU`
- `N ACTIVE` (plus ` · {Name}` only when exactly one is active and it is the only segment)
- `N REPORT READY`

Quiet = `TEAM`. Connection truths that change a decision stay: `TEAM · Offline`, `TEAM · Synchronizing…`. The old "Players · N On Field" count leaves the header (On Field remains on each card).

**No timer.** The header is updated only on store changes, never by the one-second ticker. Collapse state (`rosterCollapsed`) is never changed by state transitions; only `revealPlayer` may expand it.

# Player-Attached Play Strip Architecture

- `renderPlayStrip(view, name)` returns a strip node, or null for idle.
- It is appended as the **last child of the exact `.player` row** (after actions and queue lines). The existing per-item queue lines with Cancel/Try again stay beneath the strip.
- The existing `appendWorkState` "· Working / · Queued" word is removed. The strip replaces it; On Field stays.
- **One ticker:** a single `setInterval(1000)` updates `textContent` of `[data-elapsed-since]` nodes only, as `formatElapsed(Date.now() + serverOffsetMs - executionStartedAt)`. It never creates, removes or restyles strips, and never touches the header, Outgoing, Incoming or `aria-live` text.
- **Roster re-render survival:** `renderStatus` still rebuilds rows. Before rebuilding it captures:
  - (a) whether focus is inside a row, and the row's `data-instance-id` plus the focused control's `data-focus-key`;
  - (b) `highlightUntilByInstance`.
  
  After rebuilding it re-applies the highlight class and restores focus with `preventScroll: true`. Rows are **never reordered** by state; order stays seat/type order.
- The **old `#activePlayStatus`** and `updateWorkingClock` are removed in Slice D.

**What "one authoritative timer" means technically:**
- exactly **one** start timestamp per Play, `executionStartedAt`, written once by the Control Plane;
- exactly **one** DOM location that shows a ticking value, the strip's `[data-elapsed-since]`;
- exactly **one** interval that formats it.

The browser computes but never owns: no local start, no minimum display time, no timeout.

# Outgoing Handoff Architecture

A local, single-slot `dispatchAttempt`:

```js
{ id, phase: 'submitting' | 'sent' | 'queued' | 'failed', mode: 'auto'|'manual',
  playerInstanceId?, playerName?, clientRef?, failure?: { message, capacityLimited?: boolean },
  fullUntil?: number /* local now + 8000 */ }
```

- **Submitting:** the button label is `Sending Play…` (MANUAL) or `Finding the best Player…` (AUTO), and it is disabled **only while `phase === 'submitting'`**. The prompt stays until confirmed.
- **Reply normalisation** (fixes R3):
  - `status: 'received'` or legacy `outcome: 'accepted' | 'sent-to-terminal'` → `sent`;
  - `status: 'queued'` → `queued`;
  - HTTP error / `status: 'failed'` / `outcome: 'refused'` → `failed`;
  - `status: 'unknown'` / `outcome: 'unknown'` → `sent` with Unknown copy, taken from the store view.
  
  The daemon reply must carry `playerInstanceId` and `playerName` for AUTO **and** MANUAL (Slice A: add them to every `DispatchResult`).
- **Sent / queued:** clear the prompt only if unchanged, and re-enable Dispatch immediately. Render:
  ```text
  ✓ Play sent to {playerName}
  {copy from store view for playerInstanceId where view.playRef === clientRef}
  [ View {playerName} ↑ ]
  ```
  The copy updates **at most once per state change** (starting → working, or → queued / waiting-capacity), and never shows an elapsed value. Until a matching view arrives, show "{Name} is starting your Play."
- **Failed:** `✕ Couldn't send this Play` · `Your Play is still here.` · [Try Again]. Add [Choose Another Player] only when `failure.capacityLimited` (no V0 producer). No scroll. The prompt is preserved.
- **Lifetime:** full while `Date.now() < fullUntil`, then compact `✓ Sent to {Name} · [View]`. The compact line is cleared on the prompt `input` event, on a new dispatch, on View, or on `visibilitychange → hidden`. The store and TEAM are unaffected.
- The Dispatch button **never** shows Received, Working, Completed, Failed, Interrupted or Unknown again. Execution labels belong to strips.

# Completion / Incoming / Report Ready Flow

```text
Stadium turn completed ─► Ledger: recentPlays[0]={outcome:'completed', finishedAt}, currentPlay=∅, revision++
                        ─► execution SSE: state 'finished', awaitingReport (if no linked report)
report.changed (before or after) ─► ledger.recordReports: link by explicit provenance clientRef, else single-active-play
                        ─► revision++ ─► view.report = { path, acknowledged:false }, awaitingReport=false
Browser strip: ✓ Finished · duration · Report ready in Incoming [View Report]   (≤10 s from finishedAt)
            → quiet "On Field · ✓ Report ready"
Human opens the report (View Report button, expanding Preview, or Copy in Incoming for that path)
            → POST /api/work/acknowledge { gameId, reportPath }  → ledger link.acknowledgedAt=now, revision++
            → view → idle (or next state) on every device
New Play for that instance → supersedes (view derives from the new currentPlay)
```

- **Report linking:**
  - The existing `LedgerReportLink.clientRef` matches `recentPlays[0].clientRef` (explicit provenance, Q2.10E-A).
  - A link through `single-active-play` also counts.
  - An unattributed report never shows "Report ready" on a Player.
- **What counts as opening:** only explicit human actions. Auto-selecting `reports[0]` on load does **not** acknowledge.
- **One endpoint:** `POST /api/work/acknowledge { gameId, reportPath? , instanceId?, playRef? }` acknowledges a report link or a failed/unknown Play, Game-scoped. It is persisted by the existing `serialize()`, since `reports` and `recentPlays` are already serialized.
- **No second completion database.**

# Queue / Capacity / Unknown States

- **Queued:** projected from `PlayQueue.forInstance` (Q2.10D).
  - `head.reasonKind = 'own-current-play'` when the target instance has a current Play. Copy: `Waiting for {Name} to finish another Play`, or `…its current Play` when it is the same instance.
  - `'waiting-for-player'` when the queue context names a different owner (`context.ownerInstanceId`).
  - Otherwise `'unspecified'`: `Waiting for an available turn`.
  - A `dispatching` item projects as `starting`. `needs-attention` projects as `needs-you` with [Review] opening the existing queue line (Try again / Cancel).
  - Queued never shows a clock and never counts as working in `workState`.
- **Waiting for capacity:** a reserved state and copy with no producer. The Usage Sentinel will set it later; Scoreboard owns the explanation. It is never inferred from errors in V0.
- **Unknown ("Can't confirm status")** is caused by:
  - the router delivery timeout or a frame send failure;
  - a structured-print process ending without a result;
  - a Controlled Player leaving `ready`/`busy` mid-Play (`observeRoster`);
  - Stadium disconnect;
  - Control Plane replacement without a re-learned turn.
  
  Recovery is new evidence (a linked report makes the view `finished`, with the report and a note "Coach couldn't watch it finish"), a new Play, or human acknowledgement. It is never converted to Couldn't finish.
- **Browser toast change:** Unknown must **not** restore the prompt automatically. That invites duplicate execution. It stays a human choice through [See what happened].

# Risks / Rollback Boundaries

- **Revision/epoch correctness is the linchpin.** Mitigation: every view is computed from the Ledger after mutation; unit tests assert monotonicity; snapshots use `>=` while events use `>`.
- **SSE volume:** coalesce `execution` broadcasts per tick; views are small.
- **Roster DOM rebuild** can drop focus or highlight. Mitigation: explicit capture and restore in C. Keyed DOM diffing is deferred unless tests show churn.
- **Clock skew** is corrected by `serverNow`; network latency error is under 1 s, which is acceptable for a display clock.
- **The router 15 s timeout vs AntiGravity 12 s init** can still yield an honest Unknown followed by Working. The projection handles it truthfully and the prompt is no longer auto-restored. Timeout tuning is out of scope; noted for a later Play.
- **Stale daemon serving the new page:** degrade to no strips (rule above).
- **Rollback:** each slice is one bounded hunk. A/A2 are additive server fields; B–E are `index.html` hunks. Reverting a UI slice restores the prior UI against the additive server without errors.
