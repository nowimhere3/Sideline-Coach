## 1. Verdict

### Q2.10A ARCHITECTURE READY — PROVIDER CONTROL MECHANISM REQUIRES FOLLOW-UP PROOF

The architecture is sound, and most of it is now built and tested:
- the capability layer that separates transport from provider controls;
- stable, cheap discovery of Claude's model and reasoning controls;
- the Play Analyzer foundation;
- truthful AUTO and MANUAL display of Claude's real settings;
- a fresh-scan duplicate guard;
- the Running Players preference.

**Live model and effort switching for a terminal Claude was deliberately not shipped.** The installed Claude binary persists a model chosen inside a running session to the human's **user settings**. The human's `~/.claude/settings.json` already holds `"model": "opus"`. Coach switching models per Play would therefore silently rewrite their default model for every future Claude session. Under this Play's rule *"do not claim success where provider control is brittle or unverified"*, that part stops at architecture, with a concrete proof path (§6).

The reported **duplicate Claude** turned out not to be a detection failure. The "already running" Claude was *this Architect session*, running in the main SidelineCoach window, not in GS3 (§13).

## 3. Claude CLI control-surface audit

The installed CLI (`C:\Users\dmcal\.local\bin\claude.exe`, 2.1.270) was inspected through `--help`, its bundled command registry, and two local command probes.

| Surface | Evidence | Scope |
|---|---|---|
| `--model <alias\|full name>` | `--help`: "Model for the current session … 'fable', 'opus', 'sonnet' or 'claude-fable-5'" | launch-time, session |
| `--effort <low\|medium\|high\|xhigh\|max>` | `--help` | launch-time, session |
| `-n/--name <name>` | `--help`: shown in prompt box and terminal title | launch-time |
| `/model <model>` | registry: `name:"model", argumentHint:"<model>", supportsNonInteractive:true` | **live session**; takes an argument, so no menu is needed |
| `/effort <low\|medium\|high\|xhigh\|max\|auto>` | registry: `name:"effort"`, argument hint built from supported levels plus `auto`; `immediate:true` | **live session** |
| `ANTHROPIC_MODEL`, `CLAUDE_CODE_EFFORT_LEVEL` | present in the binary | process environment |
| `effortLevel`, `model` | settings keys (`model` present in the human's settings) | persisted |

**Discovery probe, run through PowerShell from a neutral folder; LOCAL, no API call, about 1.5 s each:**

```text
claude -p '/model'  → Current model: `Opus 5` (effort: high)
                      Usage: /model <name>. Available: sonnet, opus, haiku, fable, best,
                      sonnet[1m], opus[1m], fable[1m], opusplan, default, or a full model ID.
claude -p '/effort' → Usage: /effort <low|medium|high|xhigh|max|auto>
```

The human-observed menu value *Extra High* is the CLI's `xhigh`. The CLI additionally offers `max`.

**A hazard proven during the audit:** under Git Bash, `/model` was rewritten into `C:/Program Files/Git/model` and reached the model as an ordinary prompt, a small real API spend. Any shell layer that rewrites a leading `/` is unsafe for slash commands. Coach's probe therefore runs through PowerShell.

## 4. Stable vs brittle mechanisms

| Rank | Mechanism | Verdict |
|---|---|---|
| 1 | `--model` / `--effort` launch flags | **Stable and session-scoped.** Changing per Play means a new process, or a print-mode session with `--resume` (§6). |
| 1 | `claude -p '/model'`, `claude -p '/effort'` | **Stable discovery.** Local, cheap, parsed strictly. **Implemented.** |
| 2 | `/model <alias>`, `/effort <level>` typed into a live terminal | **Mechanically stable** (argument forms, no menu), but **unsafe as shipped behaviour**: a model selection can persist to user settings (§5). Unconfirmable from a terminal (Coach cannot read the TUI's reply). **Not shipped.** |
| 3 | Structured terminal interaction | not needed; the argument forms exist |
| 4 | Arrow-key menu navigation ("Down 3 times") | **Rejected.** Brittle across CLI versions and never needed. |

## 5. Why live control is `requires-proof` (the evidence)

The binary contains the model-persistence path:

```text
… if(r!=="userSettings")return!1; let s=fe("userSettings")?.model;
  if(s===void 0||!nh(Tt(s)))return!1 } return Kt("userSettings",{model:e}, …)
```

In plain terms: when user settings already carry a valid model, a model selection is **written back to user settings**. This human's settings carry `"model": "opus"`.

Consequences if Coach typed `/model sonnet` for a medium Play:
- The human's **default for every new Claude session** would silently become Sonnet.
- AUTO would repeatedly overwrite their personal configuration.
- Coach also cannot *confirm* the change landed, because it cannot read the terminal TUI.

Effort has session-only variants in the binary, but its persistence behaviour was not proven either. Both controls are therefore surfaced truthfully and **not operated**.

## 6. New capability-layer architecture

`src/provider-control.ts` is pure and imports no `vscode`.

```text
ProviderControlProfile
  playerType       claude
  promptDelivery   terminal-text | semantic
  semanticTurns    false | true
  model  : ProviderSettingControl
  effort : ProviderSettingControl
  observedAt, source ("claude-cli 2.1.270")

ProviderSettingControl
  state      available | requires-proof | unavailable | unknown
  mechanism  semantic | launch-flag | session-command | none
  options    [{ id: 'opus', label: 'Opus', availability: available|unavailable|requires-credits|unknown }]
  currentLabel   provider-reported DEFAULT (e.g. "Opus 5"), never claimed as live session state
  note           one plain sentence when a control cannot be used yet
```

**The six dimensions are never collapsed.** Player (Claude) ≠ transport (terminal) ≠ provider controls (seen; operation needs proof) ≠ model capability ≠ reasoning capability ≠ routing eligibility (the only Player on field is AUTO's choice, Q2.9C).

**The human UX will not change when transport improves.** A future Controlled Claude flips `model.state` and `effort.state` to `available`, and the same MANUAL *Auto / Opus / Sonnet …* and AUTO *Claude · Opus · High* surfaces light up.

**Proof path to `available`** (recommended next Play):
1. **Controlled Claude adapter.** Print-mode `claude -p --input-format stream-json --output-format stream-json` with per-Play `--model` / `--effort` and `--resume <session-id>`. It is session-scoped by construction, writes no user settings, emits semantic turn events, and needs no keystrokes.
2. **Live `/model` + `/effort`**, only if proven non-persistent in a controlled test, or accepted by the human after a one-time plain disclosure.
3. **Rejected:** snapshotting and restoring `~/.claude/settings.json`. Coach never edits a human's provider configuration.

## 8. Model discovery

- `probeClaudeControls()` runs in the Stadium during **Check Players**, only when Claude is installed.
- It runs through `powershell.exe -NoProfile` so the leading `/` survives, from `os.tmpdir()` so no Game's `.claude` hooks or settings run without that Game's trust decision.
- It has a 20 s timeout and runs the `/model`, `/effort` and `--version` probes in parallel.
- `parseClaudeModelStatus()` is strict. Anything that does not look like the CLI's own answer (for example a model-generated reply) yields `unknown`, never a guessed list.
- Human-facing options: Opus, Sonnet, Haiku, Fable, Provider Default. Long-context `[1m]`, `best` and `opusplan` are kept out of the normal UI.
- **Availability is `unknown` for every model:** the CLI lists aliases, not plan entitlement, so it cannot tell Coach that *Fable requires usage credits*. Coach does not pretend.
- Results ride on `playerDiscovery.catalog[].controls`, so no new endpoint is needed.

## 9. Reasoning discovery

- `parseClaudeEffortLevels()` → `low, medium, high, xhigh, max, auto`, normalised to Low / Medium / High / **Extra High** / Max.
- The provider's own `auto` is excluded from Coach's options: provider "auto" is *not* Coach **Auto** (*Coach chooses*), and the two must never be confused.
- The current effort is read from the `/model` answer (`effort: high` → High).

## 12. Play Analyzer foundation

`src/play-analyzer.ts` is pure, instant and free, with no model call.

```text
analyzePlay(prompt) → { taskType, difficulty: easy|medium|hard, risk: normal|high, size, label }
```

- **taskType** is the existing classifier, **moved here unchanged** (`classifyTask` is re-exported from `routing-policy`, and all prior classification tests stay green).
- **difficulty:** architecture, over 3000 characters, or high-risk and substantive → hard; implementation, high-risk or over 600 characters → medium; otherwise easy.
- **risk:** migration, delete, production, security, credential, auth, permission, data loss, force-push, rewrite history.
- **label:** *Hard architecture Play*, *Medium implementation Play*, *Easy quick Play*, or *Waiting for a Play*.
- `RoutingDecision.playLabel` carries the label, which the browser shows on the staged route.

Richer dimensions (context size, required capabilities, expected duration, resource cost) extend the same object in Q2.10.

## 14. Running-process detection and adoption preference

**Detection:**
- `findExternalCandidates()` (unchanged) finds agents inside this Game's terminals.
- New `findRunningElsewhere()` counts supported agents outside them. It excludes Coach's own extension host, so controlled Codex is never "elsewhere", and counts nested helper processes once.
- Both come from one `scanRunning()`.
- Recruit shows *Also running outside this Game.* on the relevant card.

**Duplicate guard** (Stadium, both provider Add paths, before any launch):

| Fresh scan finds | Result | Browser |
|---|---|---|
| same provider in this Game | `409 running-in-game` + the candidate | card flips to **Running · … [Add to Roster]** |
| same provider elsewhere | `409 running-elsewhere` | Coach dialog *Start another Claude?* → **Start new Claude** resends with `allowDuplicate` |
| nothing, or scan unsupported | proceeds | unknown never blocks |

**Preference** (*Settings → Players & Providers → Running Players*):

| Choice | Behaviour | Ownership |
|---|---|---|
| **Ask me before adding** (default) | offer Add to Roster; guard as above | `adopted` on the human's click |
| **Automatically add to my Roster** | Check Players adopts every in-Game running Player; Add adopts instead of launching | `adopted` (removal never closes the process) |
| **Ignore running Players** | running Players hidden from view (cache keeps the truth); Add never blocks | none |

- Stored in `~/.sideline/preferences.json`, written atomically.
- A malformed file falls back to *Ask me*.
- `GET` / `POST /api/preferences` rejects any unknown value (live-verified: 400).
- Auto-add goes only through the existing `player.adopt` path, so it never launches a process.
- The Roster, Dispatcher and routing all use the one canonical `playerInstanceId` the adoption creates, so no second Claude target is invented.

## 19. Known constraints

- **Live Claude model and effort switching is not operated** (§5). This is the one deliberate stop; proof path in §6.
- **Claude's shown settings are its configured defaults**, read at Check Players. If the human changes the model by hand inside a session, Coach's display can differ until the next check. It is labelled *Claude default* for that reason.
- **Model availability is `unknown`**, because the CLI does not expose plan entitlement (Fable credits).
- **Claude control discovery is Windows-only**, matching the existing Stadium probes. It uses Claude CLI local commands, verified on 2.1.270, and an unrecognised future answer degrades to `unknown`.
- **"Elsewhere" counts any supported agent** outside this Game's terminals, including a Coach Player in another Game window. The confirmation wording stays true in that case too.
- **Mixed runtime until the hosts restart:** the current Stadiums ignore `allowDuplicate` and send no `controls`, so the UI falls back to the Q2.9C wording. It stays compatible, just not yet Q2.10A.

## 20. WAS / IS / WILL BE

### WAS
- Terminal transport was treated as if Coach could not see or control provider settings, so Claude showed *Provider managed* even though its CLI exposes `/model` and reasoning.
- AUTO could choose Claude but said nothing about how it would run.
- MANUAL could not show Claude's settings.
- Recruit showed *Claude · Ready* while a Claude was running in another window, and Add trusted a possibly stale snapshot, so the human saw a duplicate.
- Coach had no human preference for running Players.

### IS
- **Transport and provider-control capability are separate dimensions.**
  - Coach discovers Claude's real model and reasoning controls through stable, local, cheap CLI commands, and shows them truthfully.
  - It does not operate them, because the only live mechanism can rewrite the human's Claude default. That is proven from the binary.
- **The Play Analyzer** labels every Play, and AUTO shows *Hard architecture Play · Claude · Opus 5 · High*, with the settings labelled as Claude's own.
- **Recruit** distinguishes *Running in this Game* (Add to Roster) from *Running outside this Game* (never adopted, but disclosed).
- **Add** re-scans afresh and never silently duplicates.
- **Running Players** (Ask / Automatically add / Ignore) is a saved human choice that adopts through the existing path, keeps ownership `adopted`, and never closes a human process.

### WILL BE
1. A **Controlled Claude adapter** (print-mode stream-json, `--model` / `--effort` / `--resume`) → Claude controls become `available`, MANUAL *Auto / Opus / Sonnet …* and AUTO model/effort selection light up with no UX redesign.
2. **Q2.10 multi-Player routing**:
   - Architect + Workers / Coach decides / Custom Routing Settings;
   - AUTO / CONSERVE / MANUAL;
   - Play Analyzer dimensions;
   - a *Why?* affordance.
3. **Usage Sentinel:** quota, usage windows, reset timers.
4. **Controlled AntiGravity adapter.**
5. **Advanced "+ Add another Claude".**
6. **Mobile Sideline**, then V1 stabilisation.
