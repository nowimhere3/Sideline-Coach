# Executive Result

**Q2.10F.2 Slice D is complete.** After Dispatch, Outgoing tells the human exactly which Player received the Play, offers one intentional `View {Name}` action to reach that exact Player, and then gets out of the way. The transitional `#activePlayStatus` / `renderTransitionalActiveStatus` are removed. TEAM (Slice C) remains the sole live execution surface — Outgoing owns only a short-lived, presentation-only handoff acknowledgement bound to the human's latest `dispatchAttempt`.

- **Outgoing acknowledgement** (`#outgoingAck`, `renderOutgoingAcknowledgement()`): confirmed sent/queued, Unknown, and failed states, each with truthful copy and no elapsed time.
- **8-second full → compact decay** for confirmed handoffs only, via one `setTimeout` per attempt — never the shared strip ticker.
- **`revealPlayer(instanceId)`**: the only V0 code that moves the viewport, and only from an explicit `View` tap — blur, expand TEAM if collapsed, resolve the exact row (graceful message if missing), scroll (motion-aware), highlight (`highlightUntilByInstance`, ~1.5 s, survives rebuilds), then focus the strip or a fallback.
- **Dismissal lifecycle**: material prompt edit, a new dispatch, tapping View, or leaving Outgoing (`visibilitychange` → hidden) all clear the acknowledgement. None of these touch the Work Ledger, the execution store, or TEAM.
- **Dispatch button**: unchanged from Slice B — `Dispatch Play` / `Sending Play…` / `Finding the best Player…` / `Queue for {Name}`. It never shows Working, Finished, Received, Completed or Unknown.

None of the six stop conditions applied. No server code changed. No Slice E behaviour (report acknowledgement, Finished decay, Unknown recovery) was built. No human field proof is claimed; it remains deferred until after E/F.

# Outgoing Acknowledgement

`#outgoingAck` (`role="status" aria-live="polite"`, `hidden` by default) replaces `#activePlayStatus`. `renderOutgoingAcknowledgement()` is the sole writer, driven only by `dispatchAttempt` and, for copy only, the matching canonical view.

| `dispatchAttempt.phase` / `delivery` | Rendered |
|---|---|
| `submitting`, or no attempt, or dismissed | hidden |
| `sent` / `queued`, confirmed (`delivery !== 'unknown'`) | `✓ Play sent to {Name}` · body per Play Matching below · `[ View {Name} ↑ ]` |
| `sent`, `delivery === 'unknown'` | `? Can't confirm {Name} received this Play` · `Check the Game before sending it again.` · `[ View {Name} ↑ ]` |
| `failed` | `✕ Couldn't send this Play` · `Your Play is still here.` · `[ Try Again ]` |

`data-tone` (`sent` / `unknown` / `failed`) drives colour; every state also carries a glyph and words, matching the Slice C accessibility convention (colour never stands alone).

# Exact Target / Play Matching

- The acknowledgement's target is **only** `dispatchAttempt.playerInstanceId` / `playerName` / `clientRef`, from the daemon reply (Slice B's contract) — never the selection, `currentAutoDecision`, TEAM, or roster order.
- `outgoingMatchedView(attempt)` returns the canonical view **only** when `view.playRef === attempt.clientRef`. A stale or newer Play on the same Player is never described (D-2/D-3).
- Body copy:
  - matched view `state === 'working'` → `"{Name} is working on it."`
  - matched view `state === 'queued'`, or `attempt.phase === 'queued'` → `"{Name} has your Play and is waiting to start."`
  - otherwise → `"{Name} is starting your Play."`
- No elapsed value is ever rendered here — confirmed for every state in D-1, D-2/D-3, D-5, D-21/D-22.

# Dispatch Attempt States

Unchanged from Slice B: `submitting` / `sent` / `queued` / `failed`, plus `delivery` and `failure`. Slice D adds exactly one field, reserved by Slice B: `fullUntil?: number`.

- `fullUntil = Date.now() + 8000` is set **only** for a confirmed `sent` (not Unknown) or `queued` reply — Unknown and Failed never decay to a compact/gone form on a timer; they persist until a deliberate dismissal (Part IX below).
- The whole submission path was extracted into one named `submitDispatch()` (previously an inline click-handler closure) so Outgoing's `Try Again` button reuses **exactly** the same code path as Dispatch — same guard (`isSubmitting()`), same `canMutateLiveState()` check, same payload construction from the current prompt/routing state (unchanged since the failure, since failure never mutates them). No new resubmission logic was written.

# Full / Compact Acknowledgement Lifecycle

- **Full → compact**: one `setTimeout(renderOutgoingAcknowledgement, 8000)` (`scheduleOutgoingDecay`) scheduled once per confirmed attempt. It is **not** the shared 1 s ticker — re-verified below. At fire time the function re-derives current state from `dispatchAttempt`/`Date.now()`, so it is naturally correct even if a newer attempt has since replaced the one that scheduled it.
- **Compact form**: one button, `✓ Sent to {Name} · View`, `aria-label="View {Name}"`.
- **Dismissal** (`outgoingDismissed`, cleared only by a new `dispatchAttempt`) is triggered by:
  1. **Material prompt edit** — the existing `promptInput` `input` listener now calls `dismissOutgoingAck()` unconditionally (before its AUTO-only preview logic), for both AUTO and MANUAL. Programmatic prompt clearing (`clearSubmittedPrompt`, direct `.value =` assignment) does not fire `input`, so a confirmed dispatch never self-dismisses its own fresh acknowledgement.
  2. **A new dispatch** — `submitDispatch()` resets `outgoingDismissed = false` and the render-memoization key the instant the new attempt object is created, replacing the previous acknowledgement immediately, before the request is even awaited.
  3. **Tapping View** — `goView()` calls `dismissOutgoingAck()` before `revealPlayer(...)`, in both full and compact form.
  4. **Leaving Outgoing** — a `document.addEventListener('visibilitychange', …)` listener calls `dismissOutgoingAck()` when `document.visibilityState === 'hidden'`. This single-page layout has no other navigation concept (see Compatibility Notes), so `visibilitychange` is the literal signal named in the frozen architecture doc's Outgoing Handoff Architecture section.
- None of the four dismissal paths write to `executionStore`, `dispatchAttempt` beyond the flag, or the Work Ledger.

# View Player Navigation

`revealPlayer(instanceId)`, the only V0 code allowed to move the viewport, in the required order:

1. `document.activeElement?.blur?.()`.
2. `if (rosterCollapsed) setRosterCollapsed(false)`.
3. `rosterRows.get(instanceId)` — if missing, `showToast('That Player has left the Team.', true)` and stop (no exception, no DOM touched).
4. `row.scrollIntoView({ block: 'center', behavior: reducedMotion ? 'auto' : 'smooth' })`.
5. `highlightUntilByInstance.set(instanceId, Date.now() + 1500)`, add `player-reveal`, and a matching `setTimeout` clears both the map entry and the class unless a later `View` re-armed it first.
6. `focusElement(record.strip || findByFocusKey(record.row, 'name') || record.row)`, using the existing `{ preventScroll: true }` — no second scroll.
7. No sort, no reorder — the row is focused/highlighted exactly where it already sits.

`makePlayerText` now stamps the Player-name element with `data-focus-key="name"` and `tabindex="-1"`, giving View a real, accessible fallback target when no strip is rendered (idle) — D-16b.

# Compatibility Notes

- **Button behaviour is unchanged from Slice B**: `Dispatch Play` / `Sending Play…` / `Finding the best Player…` / `Queue for {Name}`. Slice D added no new button label.
- **Outgoing wording change**: nothing before Slice C ever showed "is starting your Play." / "is working on it." / "has your Play and is waiting to start." below Dispatch — Slice B's transitional line only ever said `◉ Working · {elapsed}` for a Working attempt and nothing otherwise. Slice D's copy is richer and present for every confirmed/queued/unknown/failed outcome, not only Working.
- **No new server contract.** `dispatchAttempt.fullUntil` is a purely local, additive field (as Slice B's report already reserved it); no daemon reply field was added or required.
- **"Leaving Outgoing"**: this build is a single scrolling page with one workflow area — there is no tab/route/history concept of "Outgoing" distinct from "the rest of the page" (Settings is the only other view, reached via `#settingsView`, and does not itself dismiss the acknowledgement since it doesn't hide the document). `visibilitychange` (browser tab hidden/backgrounded) is therefore the only meaningful, already-existing signal for "the human is no longer looking at this," and it is what the frozen architecture doc names explicitly. Opening Settings does not clear the acknowledgement; this is a deliberate, conservative choice rather than inventing a second navigation system, and is called out as a limitation below.

# Remaining Limitations

- **Opening Settings does not dismiss the acknowledgement.** Only `visibilitychange` does. If this is judged wrong once a human uses it, it's a one-line addition (`closeSettings`/`openSettings` could also call `dismissOutgoingAck()`), deliberately left out to avoid inventing scope beyond what the architecture doc named.
- **Unknown never decays or disappears on its own** — by design (truthfulness over tidiness), but it does mean a human who dispatches, gets Unknown, and simply keeps looking at the same Game without editing/redispatching/viewing/leaving will see it indefinitely. Slice E's deliberate Unknown recovery is the intended eventual resolution.
- **No 8 s decay for Failed** — it persists until dismissed the same way Unknown does. This matches the brief (no decay time was specified for Failed) but is worth flagging as a deliberate asymmetry with the confirmed-sent case.
- **`Try Again` resubmits with whatever is currently staged** (prompt text, AUTO/MANUAL mode, selected Player, model/effort) at the moment it's clicked, not a frozen snapshot of what failed. Since nothing mutates those between a failure and the click (the prompt is explicitly preserved, and Slice B/C's dispatch flow doesn't touch routing state on failure), this is equivalent to "try the same thing again" in every tested scenario, but it is technically live-state resubmission rather than exact-replay.

# WAS / IS / WILL BE

## WAS

Outgoing showed a transitional `◉ Working · {elapsed}` pill below Dispatch, bound to the last attempt's exact Player, but only for the Working state — every other outcome (sent-but-not-yet-working, queued, failed, Unknown) showed nothing there at all. There was no View action; a human who wanted to see a Player's card had to scroll and find it themselves. `#activePlayStatus` and the Player strip could show overlapping "Working" information at once.

## IS

Outgoing has one truthful, short-lived acknowledgement bound to the human's latest dispatch attempt, covering every outcome (confirmed sent, queued, Unknown, failed) with human copy and no elapsed time, decaying to a compact pill after 8 seconds for confirmed handoffs, and clearing on material edit, a new dispatch, an explicit View, or leaving the tab. `View {Name}` is the one intentional, accessible, motion-aware way to reach the exact Player, and it is the only code in V0 allowed to move the viewport. TEAM (Slice C) is now unambiguously the sole live execution surface; the old duplicate is gone.

## WILL BE

- **Slice E:** Finished's 10 s rich decay and quiet `On Field · ✓ Report ready` form, View Report, `POST /api/work/acknowledge` wiring, and deliberate Unknown-attempt recovery (never automatic).
- **Slice F:** end-to-end hardening, the lifecycle fixture promoted to asserted e2e tests, and the first human field proof of the completed loop.
