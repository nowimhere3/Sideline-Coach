## 1. EXECUTIVE SUMMARY

Report 1.8 removed raw shell plumbing from the customer-facing Player card, but the deeper defect survived: a Controlled Player whose conversation could not be restored still showed **🟢 On Field · Controlled** with an error note underneath — a green card claiming a broken Player. `onField` (the roster's field/bench truth) and `controlState` (the controlled binding's health) were tracked independently and never reconciled.

This change makes `restoreControlled()` in `src/player-roster.ts` the single seam that reconciles them:

1. Restore the same conversation (unchanged behavior on success).
2. If restore fails, attempt **one bounded self-healing recovery**: open a brand-new controlled conversation for the same roster instance, silently, before telling the human anything.
3. If recovery succeeds, the Player stays On Field / Controlled with no error text; a one-time "Started a fresh conversation." note and the original diagnostic are preserved internally only.
4. If recovery also fails, the Player is benched (`onField = false`) — reversible, still on the roster, with a clean "Needs attention: …" message and no plumbing. The existing "Put on Field" action now doubles as "Try Again" for a benched controlled Player (relabeled in the UI) and re-runs the same bounded restore → recovery sequence. Remove Player is untouched — still the only way to actually retire the instance.

`On Field` now means "Coach can dispatch to this Player" — not merely "a previous restore attempt didn't fail."

---

## 2. ROOT CAUSE

`PlayerRoster.restoreControlled()` (`src/player-roster.ts`) previously did, on any non-`ready` restore outcome:

```ts
binding.state = outcome.kind;
binding.stateMessage = outcome.message;
binding.presentation.unavailable(binding.stateMessage);
```

It never touched `this.book.setOnField(...)`. `onField` is the field the roster UI (`src/public/index.html`) uses for the 🟢/🟡 indicator and "On Field"/"On Bench" text, completely independent of `controlState`/`stateMessage`, which only ever appeared as an additional note on the card. A failed restore therefore always presented as **green + broken**, and there was no recovery path at all short of the human removing and re-adding the Player.

Separately, `codex-app-server.ts`'s `resolveLaunch()` invokes `Get-Command codex` / `Get-Command node` through PowerShell to locate the CLI; any failure there (PATH not yet refreshed in this Extension Host, install in progress, etc.) throws before any provider process even starts, which is exactly the field-observed plumbing seam. Report 1.8 already sanitizes that message for the customer and preserves it as `outcome.diagnostic`. This change does not touch that adapter-level sanitization — it fixes what the roster *does* with a restore failure once it has one, regardless of which adapter or failure mode produced it.

## 3. IMPLEMENTATION

### 3.1 `src/player-control/host.ts` — bounded fresh-open recovery
Added `PlayerControlHost.reopenFresh(request)`:
- Removes the existing binding record for the instance (if any) and detaches any live control, then calls the existing `open()` for a brand-new conversation.
- **Non-destructive on failure**: if `open()` does not return `ready`, the original binding record is pushed back unchanged. A failed recovery attempt never discards the old (unresumable) conversation's binding — a later restore attempt still has the same information it had before.
- On success, `open()`'s own persistence replaces the binding with the new session, exactly as any other fresh controlled-Player open.

### 3.2 `src/player-roster.ts` — `restoreControlled()` reconciles state with truth
- Success path (`outcome.kind === 'ready'`) is unchanged.
- On any restore failure: capability truth is recorded first (unchanged), then `this.controlHost.reopenFresh(request)` is attempted once.
  - Recovery `ready` → `binding.state = 'ready'`, `stateMessage = 'Ready'`, Player stays On Field/Controlled. A `'Started a fresh conversation.'` notice plus the preserved restore diagnostic go to `binding.presentation.notice(...)` (internal/Dev Mode only, never the card state).
  - Recovery failure → `binding.state` becomes the more specific of the two failure kinds (`needs-sign-in` / `needs-verification` / `needs-decision`), `stateMessage` is `"Needs attention: " + <sanitized recovery message, falling back to the sanitized restore message, falling back to a generic sentence>`, both diagnostics go to `presentation.notice(...)`, and **`this.book.setOnField(instanceId, false)`** — this is the one new line that actually fixes the defect.
- The pre-existing "no authority for this permission setting" early-return branch was also missing this bench call; it now benches too, for the same architectural reason (a Player Coach cannot dispatch to is not On Field, regardless of why).

### 3.3 `src/player-roster.ts` — `putInstanceOnField()` doubles as "Try Again"
For an instance whose controlled binding exists and is not `ready`/`restoring`, "Put on Field" now re-enters `restoreControlled()` (bounded restore → recovery, same as above) instead of blindly flipping `onField` with no real reconnection. A plain (non-controlled, or already-healthy) Player keeps the original immediate behavior.

### 3.4 `src/public/index.html` — honest button label
The roster card's field/bench button is labeled **"Try Again"** instead of "Put on Field" specifically when the instance is benched *and* has a controlled binding in a non-ready, non-restoring state (i.e., benched by failed self-healing, not by a manual bench). Same click handler, same endpoint — only the label changed, so it says what it will actually do.

### 3.5 Breadcrumb
Added inline at `PlayerRoster.restoreControlled()` (no standalone document):
```
WAS: Restore failure was surfaced directly on an otherwise green On Field Player card.
IS:  Coach attempts bounded self-healing. On Field means dispatchable. Failed recovery
     moves the Player to a reversible non-dispatchable state.
WHY: Conversation continuity failure is not the same as Player unavailability, and
     customer-facing state must reflect actionable truth rather than internal restore
     plumbing.
```

## 4. STATE DISTINCTIONS PRESERVED

- **Roster membership** (`PlayerInstanceBook`) — untouched by this change; a benched Player is never retired.
- **On Field / Bench presentation** (`record.onField`) — now driven by dispatchability, reconciled in the one seam above.
- **Controlled binding health** (`ControlledPresentation.state` / `stateMessage`) — still the detailed truth (`ready` / `needs-sign-in` / `needs-verification` / `needs-decision`), now consistent with `onField` instead of contradicting it.
- **Conversation continuity** — may be lost silently on a successful recovery (new `sessionRef`, old one discarded by `open()`'s persistence) or preserved for a later retry when recovery itself fails (old binding record is restored by `reopenFresh`).
- **Removal** — `removePlayer()` is untouched; it remains the only explicit-human path that actually ends the roster relationship. Verified via `Q2.11-3` (bench → `removePlayer` still succeeds) and the existing `Q2.9A-11` / `Q2.9C-11` ownership/no-retire-in-bench tests, which still pass unmodified.

## 6. BOUNDARIES RESPECTED

- No change to any adapter's restore/open contract semantics (`codex-app-server.ts`, `structured-print.ts` untouched) — their existing internal "open fresh once when nothing was expected" fallback is unchanged; this fix operates one layer up, at the roster's reconciliation of restore outcome with field state.
- No retry storms: exactly one bounded recovery attempt per failed restore (`reopenFresh`), and "Try Again" is human-initiated, never automatic polling.
- No git state changes: no commits, pushes, stashes, or resets.
- No standalone breadcrumb document created; breadcrumb lives inline at the seam it documents.
