## 7. EXACT ROOT CAUSE

### Break 1 — the reported regression (status field rename)

`src/public/index.html` reads the roster as `status.players`:

```js
const instances = (status.players || []).flatMap((player) => player.instances || []);
const onFieldCount = (status.players || []).reduce(
  (count, player) => count + (player.fieldState === 'on-field' ? player.instances.length : 0), 0);
$('rosterSummary').textContent = `Players · ${onFieldCount} On Field`;
```

`ControlPlaneDaemon.buildStatus()` published the same data as **`roster`**. `status.players`
was `undefined` → `|| []` → `0 On Field`, empty roster list, and an empty Target Player
dropdown reading `No Player on field`.

### Break 2 — routing projection dropped (same rename class)

The browser reads a nested `routing` object:

```js
routingCapabilities  = status.routing?.capabilities  || [];
currentAutoDecision  = status.routing?.activeDecision || null;
currentAutoError     = status.routing?.autoError     || null;
currentRoutingMode   = status.routing.mode;
```

The daemon published flat `capabilities` plus `routingMode: 'auto'` (hard-coded) and **never
computed an AUTO decision at all**. So even with Break 1 fixed, Target Player would have
stayed empty of routing candidates and the AUTO panel would have been permanently dead.

### Break 3 — router misread its own roster shape

`ControlPlaneRouter.dispatch()` derived AUTO candidates by treating `session.roster` as a
flat `{ instanceId, transport, state, provider }[]`. It is not: `roster.snapshot` carries
`PlayerRoster.status()`'s **grouped** `{ id, name, fieldState, instances[] }[]`. The filter
`roster.filter((p) => p.transport === 'controlled')` therefore matched nothing, always.

The same code then read `session.capabilities` as `ProviderCapabilitySnapshot[]` and indexed
it by `cap.provider`. It is actually `PlayerRoutingCapability[]`, where the provider lives at
`capability.provider`. Both misreads pointed the same way: **AUTO dispatch could never find a
candidate and would always fail with "No controlled Player on field."**

### Break 4 — endpoints and SSE event dropped

Browser calls with no daemon handler: `POST /api/route`, `POST /api/route/preview`,
`POST /api/game/add`. The daemon also never emitted `event: hello`, which drives the
browser's `synchronizeAfterHello()` reconnect-convergence path.

### The single sentence

> Q2.8 relocated status assembly from the extension host to the detached daemon and
> reauthored the payload from the registry's internal vocabulary instead of the browser's
> field-proven consumer contract. Every break above is one instance of that one mistake.

## 9. WHY THE CODEX TERMINAL STAYED ALIVE WHILE COACH SHOWED 0 PLAYERS

The two surfaces are fed by entirely different paths that only converge at the broken
boundary.

The `Codex · Controlled` terminal is a `vscode.Pseudoterminal`
(`ControlledPlayerPresentation`) created **synchronously** inside the `PlayerRoster`
constructor by `adoptControlledRestores()`, then driven directly by provider events from
`PlayerControlHost`. It is a local, in-process mirror. It never consults the Control Plane,
so it printed `READY · same conversation` the moment `thread/resume` returned — truthfully.

The browser roster travels the full chain and is re-serialized twice. It was correct at
every hop and then mapped onto a key the reader never looks up.

Because the terminal is `isTransient: true`, it cannot be a leftover from a previous window —
its presence is itself proof that the persisted binding was adopted and resumed **in the
current Extension Development Host**. The human's contradictory evidence was the strongest
signal in the investigation, and it was pointing at the right thing all along.

## 10. WHY 172/172 TESTS MISSED IT

Two blind spots that exactly compose:

**(a) `PlayerRoster` was untestable, so every test invented its own roster shape.**
`src/player-roster.ts` requires the `vscode` module, so no Node test imported it — confirmed:
zero occurrences of `out/player-roster.js` across the entire pre-repair suite. The canonical
roster authority had **no automated consumer**.

**(b) The two sides of the contract were mocked independently, each self-consistently.**

- The browser-simulation tests (`multi-game-foundation`, `routing-intelligence`,
  `game-foundation`, `dispatcher-reliability-ux`) run the *real* `index.html` script against
  a *hand-written* `/api/status` body — and those fixtures use `players` and `routing`. They
  fed the browser the old, correct shape, so the browser always worked.
- The `stadium-bridge` tests exercise the *real* daemon but **never fetch `/api/status`**.
  They assert registry internals directly.

Nothing ever joined the real daemon's output to the real browser's parser. The contract
between them was the one thing untested.

**(c) The fixtures encoded the bug's false assumption.** `stadium-bridge` seeds sessions with
`roster: [{ instanceId: 'player_1', transport: 'controlled', state: 'ready' }]` — the flat
shape Break 3 wrongly assumes, never the grouped shape `PlayerRoster.status()` actually
emits. The test data was written to match the buggy reader, so the reader looked correct.

**(d) Every dispatch test passes `routingMode: 'manual'`.** Not one exercises the AUTO
candidate derivation, so Break 3 was invisible.

This coverage gap is treated as part of the bug, and is closed in §13.

## 12. THE REPAIR

The smallest architectural repair that restores the invariant: **the Control Plane publishes
the contract the browser consumes**, and the daemon owns the AUTO-routing projection that
used to live in `CoachServer`.

`buildStatus()` now carries a load-bearing comment naming the reason:

```ts
/**
 * The field names here are load-bearing: `players` and `routing` are the
 * field-proven Q2.6 contract that src/public/index.html parses. Renaming them
 * silently blanks the roster and the Target Player list even while the
 * upstream Stadium roster is perfectly healthy, so they must not drift.
 */
```

`roster` and `capabilities` are retained alongside `players` and `routing` so nothing built
against the Q2.8 field names breaks.

### Eventual-consistency invariant

"Not initialized yet" is now modelled explicitly rather than collapsed into an authoritative
empty roster. `rosterSynchronized` is `false` from session registration until the first
`roster.snapshot` arrives. While false:

- `/api/status` reports `rosterSynchronized: false` and `routing.autoError: "Roster is still synchronizing with the Stadium…"`
- the browser renders `Players · Synchronizing…` and `Synchronizing roster…`, never `0 On Field`
- AUTO dispatch returns `409` rather than a misleading "no Player on field"

### Reconnect invariant

`StadiumClient.announceGameAndState()` builds its snapshot by calling
`playerRoster.status()` at announce time, so every reconnect republishes **current** canonical
truth, never an activation-time copy. Proven by scenario Q2.8F-6.

## 19. WAS / IS / WILL BE

### WAS
Q2.6 assembled `/api/status` inside each Extension Host (`CoachServer.buildStatus()`) and
published `players` + `routing`. The browser parsed those keys. Roster and routing were
field-proven.

### IS
Q2.8's detached Control Plane owns status assembly. Q2.8 published the same truth under
different keys (`roster`, flat `capabilities`, hard-coded `routingMode`) and dropped
`/api/route`, `/api/route/preview`, `/api/game/add`, and `event: hello`. The browser, reading
the unchanged Q2.6 contract, rendered a healthy Player as zero. Q2.8F restores the contract
in the daemon, fixes the router's roster-shape misread, models "synchronizing" as distinct
from "empty", and adds an end-to-end regression harness that joins the real roster authority
to the real browser parser — plus a self-deriving contract guard that fails automatically on
any future status-field drift.

### WILL BE
The status contract is now covered by a test derived from the page itself, so this class of
failure cannot recur silently. Remaining open items, untouched here: packaging strategy
(`.vscodeignore` vs `files`), `coach.port` cleanup now that Stadiums bind no ports, and
Legacy Player semantics — explicitly future OT work.
