## 6. ROOT CAUSE

### 6.1 Primary — VS Code cannot run two Extension Development Hosts for one extension source in one instance

From this machine's own VS Code 1.137.0 bundle
(`…/Microsoft VS Code/645f29cc31/resources/app/out/main.js`, minified, reformatted here):

```js
// findWindowOnExtensionDevelopmentPath
function HT(windows, paths) {
  const matches = p => paths.some(q => Je.isEqual(C.file(q), C.file(p)));
  for (const w of windows)
    if (w.config?.extensionDevelopmentPath?.some(matches)) return w;
}

async openExtensionDevelopmentHostWindow(paths, options) {
  const existing = HT(this.getWindows(), paths);
  if (existing) {
    this.lifecycleMainService.reload(existing, options.cli);   // ← RELOAD, not open
    existing.focus();
    return [existing];                                          // ← returns the OLD window
  }
  … // only now does it create a new window
}
```

Every request for an Extension Development Host — CLI, debug adapter, or compound — funnels
through `openExtensionDevelopmentHostWindow`. If **any** existing window in the instance
already has that `extensionDevelopmentPath`, VS Code reloads it and returns it.

`reload()` reloads the window on **its existing workspace**. That is why the reloaded host came
back as GS3 rather than switching to GameTest, and why the human saw a *restart* rather than a
second window.

`getWindows()` is scoped to one VS Code instance, and an instance is keyed by `--user-data-dir`.
That is the seam the repair uses.

### 6.2 Secondary — `launch.json` was saved wrapped in markdown code fences

The working-tree file literally began `` ```json `` and ended `` ``` ``:

```text
0000000   `   `   `   j   s   o   n  \n   {  \n           "   v   e   r  …
```

VS Code's JSONC parser is error-tolerant, recovered the root object, and ran the configurations
anyway — so this corruption produced **no visible error** and masked itself. Anything using
strict `JSON.parse` did fail, silently (§9).

This defect alone would not have caused the reported symptom. It mattered because it made the
harness untrustworthy while the real constraint was being hunted elsewhere.

## 8. WHY OUR REPEATED `launch.json` EXPERIMENTS FAILED

They could not have succeeded. Every variant tried was a rearrangement of the same
impossible topology:

| Variant tried | Why it still failed |
|---|---|
| Compound of two `extensionHost` configs | Both resolve to the same `--extensionDevelopmentPath` → second reloads the first |
| `stopAll: false` | Governs stopping, not window creation — irrelevant to `openExtensionDevelopmentHostWindow` |
| Second config pointing at `${workspaceFolder}` | Different *workspace*, identical *extensionDevelopmentPath* — reuse is keyed on the latter |
| Second config pointing at the fossil `sideline-coach` folder | Same |
| Second config pointing at the fresh `SidelineCoach-GameTest` clone | Same |

The reuse key is the **extension source path**, never the Game workspace path. Changing the
workspace argument — which is what every experiment varied — cannot affect the outcome. Adding
a second `extensionDevelopmentPath` entry does not help either: `HT()` matches if *any* path in
the new request matches *any* path on an existing window.

The one thing never varied was `--user-data-dir`, and that is the only variable that mattered.

## 9. THE DIAGNOSTIC THAT WAS ALREADY TELLING US

`Diagnostics/local/CURRENT.md` had been reporting, unresolved:

```text
ERROR A4 — launch host folder target is absent or unknown
WARN  A3 — preLaunchTask unknown has no explicit tasks.json definition
```

Cause: `tools/diagnostics/collect-preflight.mjs` read launch.json with

```js

```

Strict `JSON.parse` choked on the markdown fences, the `catch` swallowed it, and
`parseLaunch` degraded every field to `'unknown'`. The tool was correctly reporting that it
could not read launch.json; the message just said *absent or unknown* rather than
*unparseable*, so it read as noise.

**Repaired:** `readJson` is now JSONC-aware (`stripJsonComments`, string-safe, comment-stripping
is a no-op on strict JSON). A3 and A4 now pass, leaving only the two known pre-existing findings
(`A6` legacy `coach.port` 49152, `A5` three Sideline Coach copies) — neither related to Q2.8G.

## 10. DEVELOPMENT HARNESS REPAIR

**One VS Code instance per Game, one extension source, one Control Plane.**

`tools/dev/dev-games.json` (development-only config; `workspace` is resolved relative to the
repo root so sibling checkouts stay portable):

```json
{ "hosts": [
  { "name": "gs3",      "label": "GS3",                    "workspace": "../GS3",                     "inspectExtensionsPort": 9229 },
  { "name": "gametest", "label": "SidelineCoach-GameTest", "workspace": "../SidelineCoach-GameTest",  "inspectExtensionsPort": 9230 }
]}
```

Each host is spawned as:

```text
Code.exe
  --user-data-dir=~/.sideline/dev-hosts/<name>/user-data     ← makes it a separate INSTANCE
  --extensions-dir=~/.sideline/dev-hosts/<name>/extensions
  --disable-workspace-trust                                  ← fresh profile still activates
  --extensionDevelopmentPath=<SidelineCoach repo root>       ← SAME source for every host
  --inspect-extensions=<port>                                ← optional debugger attach
  <Game workspace path>                                      ← positional, last
```

`--user-data-dir` is the load-bearing argument. It is what makes `getWindows()` return an empty
set in the new instance, which is what stops the reload path in §6.1 from firing.

Profiles live under `~/.sideline/dev-hosts/`, beside the existing Control Plane state and
outside the repository, so window layout persists between runs without polluting the tree.

**Preflight guards** (fail before spawning, so the human never has to work out which of two
windows silently failed to appear): missing Game checkout, missing `out/extension.js`,
duplicate host name, duplicate debug port, unsafe host name, unknown `--only` target.

**Debugger access is preserved.** `Dev: Attach to GS3 Host` (:9229) and
`Dev: Attach to GameTest Host` (:9230) attach to either harness-launched host.

**`.vscode/launch.json`** is de-fenced, the impossible compound is deleted, and a JSONC comment
at the top of the file explains exactly why no compound may be re-added.

## 14. TEST COVERAGE GAP

**The gap, stated precisely:** Q2.8's automated matrix drives `StadiumClient` and
`ControlPlaneDaemon` **as Node objects inside one test process**. It proved the *registry and
protocol* can hold two Stadium sessions and two Games. It could not — and structurally cannot —
prove that **VS Code will create two Extension Development Host windows**, because no VS Code
main process is involved in a Node test at all.

So the Q2.8 claims were true and the human experience was also true. They were claims about
different layers:

```text
Node integration proof        │  synthetic StadiumClients  ✅ passed
                              │
      ← THE GAP →             │  VS Code window orchestration  ❌ never exercised
                              │
Real Extension Host proof     │  two live EDH windows      ❌ impossible as configured
```

**Guards added — deliberately the smallest that meaningfully reduce the gap:**

1. `.vscode/launch.json is machine-parseable` — fails on markdown fences or non-`{` start.
   Would have caught defect 2 the moment it was saved.
2. `.vscode/launch.json declares no compound that starts two extensionHosts` — fails on the
   impossible topology and explains why in the assertion message. Would have caught defect 1.
3. 16 further tests over launch-plan construction (distinct user-data-dirs, shared extension
   source, workspace last, distinct debug ports, trust disabled), config validation, executable
   discovery, and verifier reporting including the conflicted case.
4. `tools/dev/verify-multi-game.mjs` — a **live runtime** check against the real Control Plane.

**This does not replace human proof, and must not be read as doing so.** Guards 1–3 are static;
guard 4 only reports what the daemon already believes. Nothing here observes a VS Code window.
The human step in §16 remains the only proof that two Extension Development Hosts exist.

## 17. Q2.9 — DADIFIED ADD GAME ARCHITECTURE RECOMMENDATION

North star: **the human chooses WHAT Game; Coach chooses HOW to connect it.**

```text
+ Add Game  →  native folder picker  →  Opening…  →  Connected ✅
```

Coach performs, with no human infrastructure knowledge:

```text
resolve Game identity from the chosen folder
  → is this Game already Connected?            → select it, done
  → is a VS Code window already open on it?    → focus it, wait for activation
  → otherwise open a new VS Code window on it
  → extension activates → StadiumClient connects outbound
  → Control Plane registers the session and binds the Game
  → Known → Opening → Connected
```

**Seams that already exist:**

- `resolveGameContextSync()` already resolves identity from an arbitrary `WorkspaceFolderLike`,
  which `coach.addGame` already exploits with a synthetic folder object.
- `StadiumRegistry.knownGames` already holds Games with no live session, and `getGames()` already
  emits `connected | offline | conflicted`.
- `KnownGameRecord.knownRootFsPaths` already records where a Game has been seen — the input to
  "already open?" detection.

**What is missing, and where it belongs:**

1. **Window opening must be a Control Plane capability, not a browser or extension one.** The
   browser has no Stadium; the extension window that receives the request is not necessarily the
   one that should host the new Game. The daemon already runs detached with process-spawn rights
   and already knows every live session — it is the only correct owner. Add `game/open`.
2. **An `Opening` state between Known and Connected**, with a timeout and a plain-English failure
   ("VS Code opened but Sideline Coach did not activate — is the extension installed?") plus
   Retry. Today `coach.addGame` registers a Game and leaves it `offline`, which is honest but
   dead-ends the human.
3. **Product Add Game must not reuse the dev harness.** The harness deliberately isolates
   `--user-data-dir` to force separate instances. The product wants the opposite: the human's
   real VS Code, real profile, real extensions — one instance, many windows, which VS Code
   supports natively for ordinary folders. `--extensionDevelopmentPath` is what makes multiple
   instances necessary, and the product has no `--extensionDevelopmentPath`.

That last point is the single most important product consequence of this Play: **the constraint
found in §6.1 is a development-time constraint only.** With Coach installed as a normal
extension, `code <folder>` opens as many windows as wanted in one instance, each activating Coach,
each connecting outbound. Nothing in Q2.8G's root cause blocks the Q2.9 product experience.

### Exit Game breadcrumb (Q2.9, do not implement now)

```text
Known → Opening → Connected → Working → Offline → Archived
```

`Offline ≠ Finished`. A stopped Codespace or a closed window is **Offline**. A completed project
is **Archived**. Archive removes a Game from the active Sideline and never touches the repository —
no file deletion, no repo modification, ever. `KnownGameRecord.isArchived` already exists and
`getGames()` already filters on it; what is missing is the Control Plane surface and the browser
action.

## 18. AMENDMENT — GAME + PLAYER LIFECYCLE ARCHITECTURE (PART Q ANSWERS)

**Q1 — Distinction between Player type, instance, terminal, transport, adapter.**

```text
Player type       catalog identity            "Codex", "Claude", "Terminal"
Provider adapter  the code implementing a type  detect/install/auth/launch/control/stop
Transport         how bytes reach the agent    app-server stdio · PTY · terminal sendText
Terminal          one concrete transport, and separately a presentation surface
Player instance   a live seat in one Game      opaque instanceId + seat + fieldState + ownership
```

The load-bearing rule is already established in Stage 1.16 and must not be relaxed:
**control is not presentation.** A visible terminal is authoritative for input only when Coach
owns the process or PTY behind it.

**Q2 — Should Terminal be a Player type, a transport, or both?** **Both, via composition.**
Terminal is a genuine transport that other adapters may use, *and* a first-class Player type
whose adapter happens to be a thin wrapper over that transport. Do **not** build a Terminal that
pretends to be Codex. A Terminal Player is a Terminal Player.

**Q3 — What owns Player discovery?** A new **`PlayerDiscoveryService`, per Stadium session,
extension-side**, feeding results to the Control Plane like the roster does. Not `StadiumClient`
(a transport), not `PlayerRoster` (owns *live instances*, a different lifecycle). Discovery asks
"what could play here?"; the roster answers "who is playing here?" Discovery delegates to each
adapter's `detect()`, so a new provider ships detection with itself.

**Q4 — What owns terminal creation and destruction?** A **`TerminalOwnershipRegistry`** in the
extension host, because only the extension host has `vscode.window.terminals`. It records, per
terminal, the `(stadiumId, gameId, playerInstanceId, cwd, ownership)` tuple. The Control Plane
*requests*; the extension host *owns*.

**Q5 — How does Coach know it may close a terminal/process?** Explicit recorded ownership, never
inference:

```text
coach-managed  Coach created it        → may dispose per policy, no prompt
adopted        pre-existing, adopted   → confirm with the human, or merely detach
external       observed only           → never destroy; detach only
```

Coach must never infer permission from a terminal's name. Stage 1.7/1.8 already proved names
carry no authority.

**Q6 — Take Off Field vs Remove Player vs Close Terminal.**

| Action | Scope | Instance survives? | Process/terminal |
|---|---|---|---|
| Take Off Field | execution lifecycle | yes, benched, returnable | untouched |
| Remove Player | this Game's roster relationship | no | disposed **only if** `coach-managed`; confirm if `adopted`; detach if `external` |
| Close Terminal | transport only | yes, may go Unavailable | that terminal only |

Collapsing Remove into Take Off Field would destroy the roster's ability to represent a benched
Player — do not.

**Q7 — Add Player by provider state.**

```text
installed + authenticated    → create instance → Ready → offer Put On Field
installed + unauthenticated  → Authentication Needed → [Open Authentication Terminal] → [Check Again]
not installed                → Not Installed → show adapter's install command → [Open Install Terminal] → [Check Again]
unknown                      → say Unknown and offer [Check Again]; never guess Ready
```

The install/auth terminal is a real Game-scoped Terminal Player, not a special case. That is the
whole point of Part D.

**Q8 — Promoting a Terminal Player into a controlled provider Player.** Keep the same
`playerInstanceId` and swap the adapter behind it. Player instance IDs deliberately carry no Game,
Stadium, machine, or executable-path identity, so identity survives the swap; bindings are already
`gameId`-scoped. **Minting a new instanceId on promotion would break every exact routing coordinate
and every persisted binding** — this is the specific mistake to avoid.

**Q9 — Smallest architecture supporting Detect → Install → Authenticate → Launch → Adopt →
Control → Stop.** Extend the existing `PlayerControlHost.register(type, factory)` registry — it is
already an adapter registry keyed by Player type — with an optional lifecycle interface:

```ts
interface PlayerAdapter {
  readonly id: string;                    // 'codex' | 'claude' | 'terminal'
  readonly displayName: string;
  detect(stadium): Promise<DetectionResult>;      // Not Installed | Installed | Auth Needed | Ready
  installGuidance?(): InstallGuidance;            // command text + docs URL; Coach never runs it silently
  createInstance(ctx): Promise<PlayerInstance>;   // existing factory path
  adopt?(existing): Promise<PlayerInstance>;      // Terminal → controlled promotion
  shutdown?(instance, reason): Promise<void>;     // graceful stop, ownership-gated
  readonly ownership: 'coach-managed' | 'adopted' | 'external';
}
```

Everything beyond `id`, `displayName`, `detect`, and `createInstance` is optional, so Q2.9 can ship
Terminal + Codex without stubbing fields it has not earned. The promise this preserves — *any
compatible CLI coding agent becomes a Player by adding an adapter, without redesigning Coach* —
is a real promise, but not a universal one: GUI-only agents, proprietary protocols, unsupported
platforms, and licensing or authentication constraints remain genuine limits.

**Q10 — Q2.9 versus later OT.**

| Q2.9 | Later OT |
|---|---|
| Add Game (picker → open → Opening → Connected) | Automated provider install |
| Game Exit / Archive | OAuth brokers, credential vaults |
| Check Players (per-Stadium discovery) | Player marketplace |
| Add Player: Terminal + Codex | Terminal output streaming / interactive remote shell |
| Install/Auth terminal + Check Again | Usage billing, licensing |
| Ownership model + Remove Player | Codespace / remote Stadium aggregation |
| Minimal terminal control (create, send, alive, cwd, close-if-owned) | Full PTY-over-WebSocket |

**Player discovery must be Stadium-scoped** (Part M). Never a global `claudeInstalled: boolean` —
a Player installed on the Windows Stadium says nothing about a Codespace. `StadiumSession` already
holds per-session capabilities, so this is additive.

All deferred capabilities are recorded in `Docs ANCHOR/ARCHITECTURE-BREADCRUMBS.md` under
**WILL BE → Q2.8G Deferred Capabilities**, each with *why deferred*, *enabling seam*, *bucket*, and
*the architectural mistake that would make it harder later*.

## 19. WAS / IS / WILL BE

**WAS.** The two-Game bridge appeared broken for several sessions while the Q2.8 Control Plane was
correct throughout. `.vscode/launch.json` was saved wrapped in markdown fences and, more decisively,
declared a compound of two `extensionHost` configurations — a topology VS Code structurally cannot
execute. Diagnostics had been reporting the corruption as `ERROR A4` / `WARN A3` the whole time, but
strict `JSON.parse` in the collector degraded the message to *absent or unknown*, so it read as noise.
Diagnosis was delayed by treating the absent second Game as an application-layer bug rather than a
harness-layer impossibility.

**IS.** VS Code reuses and reloads an existing Extension Development Host window whenever a new one
is requested for an `--extensionDevelopmentPath` already open in that instance, and instances are
keyed by `--user-data-dir`. The development harness therefore launches one VS Code instance per Game
under `~/.sideline/dev-hosts/<name>/`, all sharing one extension source and one detached Control
Plane, with optional debugger attach on :9229/:9230. Two Stadium sessions bound to two distinct
Games against one daemon and one browser port have been observed live, as has window-closure
survival. The Q2.8 product architecture is unchanged: detached daemon, one browser port, zero
extension listener ports, outbound StadiumClient, exact `stadiumId + gameId + playerInstanceId`
routing.

**WILL BE.** Q2.9 delivers two Dadified lifecycles sharing one principle — *the human chooses intent,
Coach performs mechanics*. Game lifecycle: Add Game (picker → open window → Opening → Connected),
Reconnect, Offline, Exit/Archive, with window-opening owned by the Control Plane. Player lifecycle:
Check Players (Stadium-scoped discovery), Add Player, Terminal as a first-class Player type, the
install/authenticate terminal path, explicit ownership, Put On Field / Take Off Field / Remove Player.
Deferred to later OT: automated install and authentication, credential vaults and OAuth brokers,
Terminal→provider promotion at scale, terminal output streaming and interactive remote shell,
Codespace and remote Stadium aggregation. Full deferral rationale is in the breadcrumbs.
