# WHAT WAS

Before S9.0, `src/control-plane/router.ts` built exactly one machine-authored
footer for a Controlled, non-direct-shell Play: the `sideline-provenance`
marker (WHO wrote it — Game, clientRef, instance, provider, model, effort,
timestamp). Nothing told the Player WHERE to write its report. S6 durably
decided the canonical Reports root and provider lanes; S7 projected that
decision to the Stadium for watch/scan scope; S8.0 created the root and lanes
on disk. None of the three touched dispatch. A Player receiving a Play had no
machine-authored destination coordinate at all — it could write anywhere its
own habits or the human Play text implied, with no guarantee that location
was the one Incoming actually watches.

# WHAT CHANGED

- `src/report-provenance.ts` — new `buildReportDestinationInstruction(destination)`,
  a small, separate human-readable text block. It is never folded into the
  `sideline-provenance` JSON marker, which stays about WHO, not WHERE.
- `src/control-plane/router.ts` — a new injectable seam,
  `setReportDestinationResolver((gameId, playerType, sessionFeatures) => string | undefined)`.
  For a Controlled, non-direct-shell Play only, the router calls it with the
  exact dispatched `gameId`, the exact `routed.playerType`, and the exact
  dispatching session's own `features` array; when it returns a string, that
  string — untouched, unjoined, unmodified — is appended as the destination
  clause after the provenance marker.
- `src/control-plane/daemon.ts` — the one concrete resolver,
  `resolveCanonicalReportDestination(gameId, playerType, sessionFeatures)`,
  wired via `router.setReportDestinationResolver(...)` beside the router's
  other existing `set*` wiring (`setPlayQueue`, `setRouteContextProvider`).
  It reads `this.gameFilesystem.get(gameId)` — the same, sole,
  already-existing `GameFilesystemCoordinator` S6/S7/S8.0 use — and nothing
  else.

No other file was touched by this Play. Pre-existing uncommitted work from
other in-flight Plays (`src/game-files.ts`, `src/stadium-client.ts`,
`src/server.ts`, `src/control-plane/protocol.ts`,

# NOT-READY BEHAVIOR

`resolveCanonicalReportDestination` returns `undefined` — never a guessed or
partially-built path — for every one of:

- `contract` absent entirely (Game never reconciled);
- `contract.reports.state` is `unknown`, `not-set`, `needs-choice`, or
  `needs-attention` (tests S9-16…19, parameterized over all four);
- the dispatched provider's lane key does not exist in `contract.reports.lanes`
  at all (test S9-20);
- the lane exists but its own `state` is `needs-attention` rather than
  `ready` (test S9-21).

In every one of these cases the Play still dispatches normally, with
provenance only — S9.0 never blocks, delays, or degrades dispatch itself; it
only ever adds or omits one optional clause. No new dispatch-blocking policy
was invented, per the Play's STOP CONDITIONS — none of the STOP conditions
were triggered.

**Diagnostic seam (Part G).** No new logging was added. The dominant
diagnostic case — a Stadium that cannot consume the canonical contract at
all — already has its own truthful log line in the existing S7 code
(`applyGameFilesystemContract`: `"Stadium for <gameId> does not support
game.filesystem.apply; legacy report discovery remains active."`), which
fires on every `game-connected`/reinspect attempt for that Game regardless of
S9.0. The remaining not-ready states are normal, expected, and often
transient (a Game before its first reconcile, or between an empty roster and
its first recruit) — logging every Controlled dispatch during that window
would be diagnostic noise disproportionate to a one-clause omission, and the
existing Dev-Mode `diagnostics(gameId)` projection (S6) already exposes
`reports.state`, `reports.lanes`, and `pendingReportsAction` for anyone who
needs to see why. Adding a second logging path here would itself have been
the "large new UX" the Play said not to build.

# MIXED-VERSION BEHAVIOR

The exact dispatching session's own `features` array — the same array S7's
`applyGameFilesystemContract` and S8.0's `runFilesystemEnsure` already gate
on — is checked for `'game.filesystem.apply.v1'` before any contract lookup
even happens. A Stadium lacking that feature never receives a destination
clause, **even when the durable contract itself already says `ready`**
(test S9-26: contract seeded ready, session registered with only
`['game.files.v1']`) — because a Stadium that cannot apply the canonical
contract is, by S7's own truth, still running legacy-glob-only report
discovery, and telling its Player to write into the canonical root would be
a false claim of alignment. No second compatibility architecture was built;
the literal feature string and its meaning are reused verbatim from S7.

# EXACT GAME ISOLATION

No new isolation mechanism. `resolveCanonicalReportDestination` takes
`gameId` as an explicit parameter (never `this.registry.getSelectedGameId()`)
and reads `this.gameFilesystem.get(gameId)` — the same Game-keyed durable
store S6 already isolates by construction (proven in S6's own test suite;
re-exercised here through the dispatch path). Proven directly:

- **S9-23** — two Games, two different canonical roots (`Reports` vs
  `REPORTS`), dispatched with `Promise.all` (genuinely interleaved, not
  sequential) — each frame carries only its own Game's destination.
- **S9-24** — Game A dispatched with an explicit `gameId`, then the
  registry's `selectedGameId` is changed to Game B, then Game A is dispatched
  again — its destination is unchanged. Destination follows the dispatched
  Game, never the Control-Plane-selected one; `globalState`/browser selection
  was never consulted in the first place (the resolver has no access to
  either).

# USER-PROMPT SPOOF RESISTANCE

The destination clause is generated exclusively from trusted dispatch

Control Plane; human Play text is never parsed for it. Test S9-5 dispatches

the real, machine-resolved coordinate. There is no code path anywhere in
`dispatch()` that reads `humanPrompt`/`contextPrompt` before computing
`destination`.
