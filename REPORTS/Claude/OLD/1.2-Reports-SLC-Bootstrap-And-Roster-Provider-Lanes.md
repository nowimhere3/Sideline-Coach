# REPORT ROOT ENSURE BEHAVIOR

`ensureGameDirectory(rootFsPath, relPath)`:
1. Validates the relative path (`validateRelativeGamePath` /
   `isBlockedRelativePath`, reused from `game-files.ts`) and containment
   (`isPathInsideRoot`) — traversal/absolute paths are rejected before any
   `fs` call.
2. If something already exists at the target: a real directory (or a
   symlink/junction that resolves to a real directory *inside* the Game
   root) is idempotent success; a symlink/junction that escapes is
   `needs-attention` (`escapes-game`); a file or anything else is
   `needs-attention` (`name-collision`) — never overwritten, deleted, or
   renamed.
3. If nothing exists: checks every ancestor for a symlink escape
   (`checkAncestorSymlinkEscape`, reused), then `fs.mkdir` with
   `recursive: false` (never silently creates missing parents), then
   verifies with a fresh `stat` that the result really is a directory before
   reporting `ready`.
4. Any unexpected `mkdir`/`stat` failure becomes `needs-attention`
   (`create-failed`) — an unlucky permission or I/O error can never leave the
   contract silently retrying forever (see IDEMPOTENCY).

`Reports-SLC` is created via `ensureGameFilesystemStructure` with
`root: { name: 'Reports-SLC' }`; on success the Control Plane records
provenance `created` — not `adopted` — through `recordReportsRootCreated`,
which also clears `pendingReportsAction`. On failure/collision,
`recordReportsRootAttention` records the truthful attention code without
ever claiming success, and also clears `pendingReportsAction` (so a genuine
collision or I/O failure stops the retry loop rather than re-attempting
`mkdir` on every future reconnect/roster change).

# ROSTER PROVIDER LANE BEHAVIOR

The current roster is read from the same snapshot the browser already
displays (`PlayerRoster.status(gameId)` via `StadiumRegistry.getRosterForGame`),
filtered to entries with at least one live instance and with `id !== 'terminal'`
(Terminal is a first-class Player type but authors no reports — Part C's own
examples exclude it). The stable key used for the lane is the catalog's
`name` field (`Codex` / `Claude` / `AntiGravity`) — never a model, effort,
Player instance ID, terminal ID, or arbitrary human label. Two instances of
the same type collapse to one roster key before any RPC is sent, so "2 Codex
Players" only ever produces `<ReportsRoot>/Codex/`.

Lanes are ensured only for keys **missing entirely** from
`contract.reports.lanes` — a key already present, in either `ready` or
`needs-attention` state, is never re-requested. `recordLaneEnsured` enforces
this again at the durable-write layer (`if (current.reports.lanes?.[laneKey])
return current;`), so even a caller bug that asked twice could not overwrite
history. This is also how Part D (never delete historical lanes) and Part E
(lanes always land inside whichever root is authoritative — the freshly
created `Reports-SLC`, or an already-adopted `Reports` / `REPORTS` /
`Docs REPORT` / human-selected root) are both satisfied by construction: the
lane request always carries `lanesRoot` set to the contract's own current
root, and lanes are never requested at all unless a root is either just
created or already `ready`.

The Control Plane remains the sole durable filesystem-contract owner

picks up the new canonical root and lanes with no second watcher-ownership

# IDEMPOTENCY

Two independent layers make repeated ensure passes a true no-op:
1. **Orchestration:** `runFilesystemEnsure` only sends the RPC at all when
   `pendingReportsAction === 'create-reports-slc'` or at least one roster key
   is missing from `contract.reports.lanes`. Once the root is `created` and
   every current roster lane exists, a repeated pass sends nothing.
2. **Durable recording:** `recordReportsRootCreated` / `recordReportsRootAttention`
   compare against the current contract and skip the revision bump (and the
   `onChange` broadcast) when nothing actually changed; `recordLaneEnsured`
   refuses to touch an already-present lane key at all.

Test S8-24 proves both: after the root and both lanes exist, a second
`runFilesystemEnsure` call touches no additional file, sends no additional
RPC, and leaves `revision` unchanged.

# SAFETY / COLLISION HANDLING

- File where a folder is expected (`Reports-SLC` or a lane): `needs-attention`
  / `name-collision`, file bytes untouched (S8-3, S8-9, S8-23).
- Escaping symlink/junction: `needs-attention` / `escapes-game`, nothing
  written outside the Game root (S8-5; skips gracefully on environments that
  disallow creating junctions).
- Traversal / absolute paths: rejected before any `fs` call (S8-4).
- Ambiguous root (`needs-choice`) or any other `needs-attention` state:
  `runFilesystemEnsure` never even calls the RPC — it only acts when the
  contract is exactly `create-reports-slc` or exactly `ready` (S8-22, S8-23).
- Concurrent-creator race (`EEXIST` on `mkdir`): treated as a benign race,
  falls through to the same post-creation `stat` verification as any other
  path.
