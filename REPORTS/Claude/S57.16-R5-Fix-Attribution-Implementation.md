# Contracts

## Link (§8.2)

First proven wins:

1. `scout-continuation`: the post-Scout continuation's Formation Play.
2. `named-report` / `incoming-report` / `latest-play`: `detectFollowUp` + `resolveContextOwner` named an owner. A report reference proves its author only through the report's own provenance `clientRef` or the Ledger's report link. `latest-play` uses the owner's newest Ledger Play. Wording-only `latest-report` is not proof and does not link (S57.1 lists three evidence kinds).
3. `touch-overlap`: same Game, a Play finished within 72 h before the follow-up, overlapping touches (newest wins, deterministic tie-break).

The parent must be a same-Game Play Film witnessed. No link means no event and nothing is attributed.

## Attribution (§8.3)

Ordered, first match wins; rule ids `R5-1`..`R5-7`. The default is `unattributed`.

| # | Cause | Confidence |
|---|---|---|
| 1 | parent `failureClass` provider/auth/quota/harness/interrupted, or outcome `interrupted`/`not-sent` → `environment-drift` | high |
| 2 | another instance completed a Play overlapping the parent's touches between parent finish and follow-up → `upstream-change` | medium |
| 3 | parent was post-Scout + follow-up names the Scout report + correction wording → `bad-scout-evidence` | medium |
| 4 | change wording, no defect wording → `prompt-change` | medium |
| 5 | names a stage/step → `planned-continuation` | high |
| 6 | parent context `unknown` or handoff + follow-up supplies a report/file it lacked → `missing-context` | low |
| 7 | defect wording + same touches → `player-defect` | low |
| — | nothing matched → `unattributed` | low |

Written once, at the follow-up's real dispatch, as a Film `attribution` event.

## Authority

- Envelope `FIX CAUSE:` → `source: 'envelope'`, high, written at dispatch instead of a rule event.
- Coach: `coachAttributionEvent(...)` builds a `source: 'coach'` high event. R5 owns the data seam only; R7 will add the chips.
- `effectiveAttributions` picks one winner per linked follow-up. Coach/envelope outrank any rule even when the rule event is later. Among authoritative events the last valid one wins. Invalid causes and events for a pair Film never linked are void.

## Resolution (§5.1)

`projectFirstPassResolutions(events, now)` is a pure projection with an injected clock. **Window:** 72 h from the Play's finish, or the dispatch of the 3rd later same-Game Play touching the same files, whichever is first. Only follow-ups dispatched inside the window count. Until it closes the Play is `pending` and gives R3 nothing.

| Settled state | When |
|---|---|
| `clean` | completed, window closed, **no linked follow-up** |
| `repaired` | completed, a follow-up attributed `player-defect` |
| `failed` | failed/partial/blocked with a `player-defect` repair, or `failureClass: 'player'` |
| `excluded` | interrupted/unknown/not-sent, environment failure class, or any linked follow-up that is not `player-defect` (credit is withheld, blame is not assigned) |

`resolution` events are an audit journal, written only when a Play's settled state changes. Belief never reads them; it re-derives from facts, so replay stays exact and there is no second authority.

# Interpretations For Coach

1. **`planned-continuation` withholds credit.** S57.1 §5.1 lists it (with prompt-change, upstream-change, environment-drift, unattributed) as *excluded*, and §8.1 calls it "not a fix at all". I followed §5.1 literally: any linked follow-up that is not `player-defect` makes the parent `excluded` rather than `clean`. Effect: heavily-continued Plays, including every Scout Formation that gets its one continuation, accrue little clean evidence. This is safe (never over-credits) but conservative. If Coach wants planned continuations not to taint `clean`, it is a one-line change in `projectFirstPassResolutions`.
2. **Failed/partial/blocked is a Player failure only when proven.** R2 records no failure class and never fabricated one, so without `failureClass: 'player'` or a `player-defect` repair, such an outcome is `excluded`, not a failure. Nothing writes `failureClass` yet.
3. **Rule 5 cannot verify the plan.** §8.3 says the stage is one "in the parent's report". Report bodies are not stored, so the rule matches stage wording in the follow-up on a proven link. Confidence stays high per spec.
4. **Rule 2 overlaps against the parent's touches**, and "another instance" means a different instance than the parent's.
5. **Envelope with no link:** a `FIX CAUSE:` value on a Play with no proven parent writes nothing, because there is no pair to attribute. An unrecognizable value is ignored and the rules run.
6. **Attribution is computed at dispatch.** If a parent has not finished by then, rules 1 and 2 cannot fire. In practice parents are finished, because a busy owner queues.
7. **Historical R2 Film has no profile.** The gap is closed for new Plays only; no back-fill from ledger labels was attempted (bounded ledger, no touches).
8. **Follow-on for R6:** `priors.json` packaging is still open (S57.13).
