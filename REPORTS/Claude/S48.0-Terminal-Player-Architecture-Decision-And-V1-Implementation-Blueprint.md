## RESULT

**Terminal Player V1 keeps the native VS Code Terminal as its substrate, stays on the direct-shell transport, and becomes observable by consuming `TerminalShellExecution.read()` and publishing line-assembled, sanitized output into the existing `PlayerActivityNotice` rail.** No PTY, no `node-pty`, no `PlayerControl` adapter, no xterm.js, no new browser surface. The decisive finding is that **AntiGravity S47 was right and Scout A was wrong**: `TerminalShellExecution.read(): AsyncIterable<string>` is a *stable, non-proposed* API present in the exact `@types/vscode` this repo compiles against, and the repo's `engines.vscode: ^1.95.0` floor sits safely above the 1.93 finalization. The second decisive finding is that **the browser is already ready**: `isTerminalEligible` in `src/public/index.html:2763` contains **no transport check** — Scout A's claim that it requires `transport === 'Controlled'` is false. A `direct-shell` Player that reaches `working`/`starting`/`finished` is already terminal-eligible today and already renders an Expand button; the only thing it lacks is lines to show. The result is that V1 is a genuinely small slice — one new activity category, one output tap, one stale placeholder string — while the expensive options (PTY ownership, contract unification, TTY emulation) are all *deferred without being foreclosed*.

## ARCHITECTURE DECISION

### 1. Substrate — **A. Native VS Code Terminal** (PTY deferred)

Terminal Player remains `vscode.window.createTerminal` at the Game root. Observability comes from `terminal.shellIntegration.executeCommand(cmd)` → `execution.read()`.

Verified API semantics (from the typings this repo compiles against):

- `read(): AsyncIterable<string>` — **stable**, not proposed.
- Yields **raw terminal data including escape sequences** — one merged stream. **stdout and stderr are not distinguishable.** This is accepted, not worked around: a human watching a terminal sees one merged stream too.
- *"you must call `read` immediately after the command is executed … to not miss any data."* The call must be **synchronous** with `executeCommand()`, in the same tick. This is an implementation invariant, not a preference.
- Requires shell integration to be active. Without it there is no `shellIntegration` object at all, so no `executeCommand` and no `read`.
- `exitCode` may be `undefined` for several enumerated reasons (sub-shell, Ctrl-C, misbehaving integration). `describeTerminalExit` already maps that to `unknown` honestly.

### 2. Player contract — **A. Remain direct-shell, bridge into the activity rail**

Terminal Player does **not** implement `PlayerControl`. It keeps `transport: 'legacy'`, and gains a bridge into the same sanitization choke point.

The rails converge at `player-activity.ts`, not at `PlayerControl`. `projectControlEvent` gets a sibling, `projectTerminalOutput`, and both produce the identical `PlayerActivityNotice`. That is the right convergence point because it is where the *security boundary* lives — which is what actually needs to be shared. Sharing the *process abstraction* would be aesthetic unification, and would be wrong (see *Why This Path*).

### 3. Process ownership — unchanged, and deliberately so

`coach-managed` for `addTerminalPlayer()`, `adopted` for `adoptTerminal()`. VS Code owns the shell process; Coach holds a reference. The existing invariant holds without new code: Coach-created → Coach may `dispose()`; adopted → detach only, never dispose.

### 4. Activity transport — existing rail, unchanged below the extension host

`PlayerRoster.activityChanged.fire()` → `extension.ts:265` → `stadiumClient.sendPlayerActivity` → WS `player.activity` → daemon re-sanitize + bounded store → SSE + HTTP backfill → browser. **Zero changes to `stadium-client.ts`, `daemon.ts`, or the SSE/backfill contract.**

### 5. Session model — a shell session is *not* a provider session, and gets its own ref

```
terminalSessionRef = `${shellPid}:${shellStartedAt}`
sessionKey         = sessionKeyFor(terminalSessionRef)   // existing SHA-256[:8], unchanged
```

`recordProvenance` (`player-roster.ts:1339-1347`) **already computes and persists both components**. No new probing, no new persistence, no schema change. A restarted shell yields a new `sessionKey`, and the daemon store's existing session-rotation rule (`player-activity.ts:180-184`) clears the old transcript automatically. The Play's constraint — *"do not simply pretend a terminal is an AI provider conversation"* — is honoured: the ref is shaped like a process, and only the opaque digest travels.

### 6. Work Ledger semantics — **no schema change; shell lifetime is simply never modelled as a Play**

| Shell condition | Ledger | Mechanism |
|---|---|---|
| alive + idle | `idle`, no `currentPlay` | absence of dispatch |
| command starting | `working` | `emitTurn('accepted'/'started')` already fires |
| command running | `working` | unchanged |
| command completed / failed | `completed` / `idle` | `finishTerminalCommand` → `describeTerminalExit` |
| command outcome unreported | `unknown` | `exitCode === undefined` |
| shell disconnected / exited | `disconnected` | `onDidCloseTerminal` → emit `turn: unknown` for any in-flight command |
| shell restored / re-adopted | `idle`, same `instanceId`, **new `sessionKey`** | provenance match on `shellPid` + `shellStartedAt` |

The shell's lifetime shows up as *Player presence*; only a dispatched command is ever a Play. That is the whole separation, and it costs nothing because the ledger already keyed off dispatch rather than process.

### 7. UI — **reuse Live Player Terminal V0.3 as-is.** No TTY emulation.

The goal is "see his guts", not "run vim from a phone". Two small edits only:

- `index.html:2211` — register `output: 'OUTPUT'` in `CONSOLE_LABELS`, or entries are silently dropped at line 2239.
- `index.html:2281` — retire `'Terminal Player output is not captured yet.'`; a direct-shell Player with no lines yet should say it is waiting, like any other Player.

`isTerminalEligible` needs **no change**.

### 8. Security boundary — four layers, one of them new and structural

| Layer | Where | What it does |
|---|---|---|
| **0 — Scope (new)** | `runTerminalCommand` | **Only Coach-dispatched Plays are read.** `execution.read()` is attached solely to executions Coach itself started. The human's own typing in that terminal is never captured. |
| 1 — Projection | extension host, `projectTerminalOutput` | line assembly → ANSI/control strip → `redactSecrets` → length cap |
| 2 — Re-sanitization | daemon, `PlayerActivityStore.record` | re-applies the identical boundary; never trusts the sender |
| 3 — Gates | daemon, `livePlayerTerminalEnabled()` | Dev Mode **and** View Player Terminal, both on |

Layer 0 is the important new one, and it is a *structural* control rather than a pattern-matching one. It is what makes raw shell streaming acceptable at all: Coach only ever observes a command a human explicitly approved and dispatched.

## WHY THIS PATH

### Rejected: PTY / `node-pty` ownership (Scout A's recommendation)

Rejected on a false premise plus four real costs.

The premise — "no API can read shell output" — is disproved at `index.d.ts:8001`. Beyond that:

1. **Native dependency in a shipped `.vsix`.** `node-pty` is a native module with an Electron ABI binding. It would have to be rebuilt per VS Code Electron version and shipped per platform/arch. That is a permanent release-engineering tax on a product whose whole thesis is that the machine carries the complexity.
2. **It destroys the best property Terminal Player already has.** A native VS Code terminal **survives `Developer: Reload Window`**, and `recordProvenance` re-adopts it by `shellPid` + `shellStartedAt`. A Coach-owned PTY in the extension host dies with the extension host. We would be trading away real reload survival for stream separation.
3. **It breaks the human out of their own terminal.** Today Dad can type in that terminal. A PTY behind a `Pseudoterminal` means Coach owns stdin, and the "adopt an existing shell" path becomes incoherent — you cannot adopt a process you did not spawn into a PTY you own.
4. **It inverts the ownership invariant.** Coach-owned PTY makes every Terminal Player coach-managed by construction, quietly erasing the `adopted` case the product deliberately protects.

What PTY buys — separate stderr, reliable exit codes, operation without shell integration, resize, raw stdin — is precisely the *future control* set. It stays available: a PTY-backed adapter can be added later **behind the same `PlayerActivityNotice` contract**, and nothing in V1 would have to be rewritten. That is the optionality this decision is protecting.

### Rejected: `TerminalControl` implementing `PlayerControl` (S47 Path A)

Superficially attractive — the shapes line up (`state: ready|active|lost|closed`, `deliver`, `interrupt?`, `close`). Rejected because the *semantics* underneath do not:

- `PlayerControlFactory.open()` is a promise that **Coach spawns and owns a process**. VS Code owns this one. `close()` would then be obligated to kill a process Coach may not own.
- `restore(request, binding)` means *resume a provider conversation from a `sessionRef`*. A shell has no resume. We would be implementing a method whose contract we cannot honour, and the honest implementation of it is "reopen fresh" — which is a lie dressed as a restore.
- `ControlledBindingRecord` rejects it structurally: `INSTANCE_PATTERN = /^(claude|codex|antigravity)-[0-9a-f]{8}$/` plus an exact key-count check (`keys.length !== 7 && keys.length !== 8`). Widening a *persisted, validated* schema to admit a record shape that means something different is a migration risk taken for tidiness.
- The persistence it would give us is **worse than what exists**. Provenance (`shellPid` + `shellStartedAt` in `workspaceState`) already survives window reload and re-adopts the live shell. `BindingStore` restore would not.

The Play warned: *do not choose unification merely for aesthetic consistency.* This is that case. The genuine shared concern is the **security boundary**, and V1 shares it exactly.

### Rejected: xterm.js / full TTY emulation

Deferred, not refused. It buys correct rendering for curses apps, `\r` progress bars and colour. It costs a bundled emulator, a raw-byte path that bypasses `sanitizeActivityText` (because ANSI is the payload), and a second retention model — while the proven mobile-fullscreen, Copy All / Copy New surface would have to be rebuilt against it. Copy behaviour in particular gets materially worse: a `<pre>` log copies cleanly; a terminal buffer does not.

The smallest honest handling of `\r` is a projection rule (keep the final segment of a carriage-return-overwritten line), not an emulator.

### Chosen: shell-integration tap (S47 Path B, sharpened)

It is the only option where the substrate, the ownership model, the persistence model, the dispatch path, the daemon and the browser are **all already correct**, and the missing piece is a stream we are currently receiving and throwing away at `player-roster.ts:709`.

## ACTIVITY CONTRACT

### New category

```ts
// src/player-activity.ts
export type ActivityCategory =
  'working' | 'message' | 'command' | 'tool' | 'declined' | 'result' | 'channel' | 'output';
```

A distinct category is required, not cosmetic. Three source facts force it:

1. `PlayerActivityStore.record` (`player-activity.ts:190`) **suppresses consecutive identical `command`/`tool` lines**. Terminal output legitimately repeats — reusing `command` would silently swallow real lines.
2. `sanitizeActivityText`'s non-`message` branch collapses all whitespace (`:99`). That destroys the column alignment of `git status`, `ls -la`, test output — i.e. most of what makes terminal output readable.
3. Reusing `message` would label every shell line `MESSAGE` on Dad's surface. *A human should be able to understand the product without understanding the plumbing underneath it* — and labelling it `STDOUT` would be the opposite error (`containsTechnicalPlumbing` in `contract.ts` already treats the word "stdout" as plumbing). `OUTPUT` is the human word.

### Events emitted per dispatched command

| Event | Category | Text |
|---|---|---|
| command accepted | `working` | `Running: <first line, ≤120 chars>` (exists) |
| each assembled output line | **`output`** | one sanitized line |
| volume ceiling hit | `channel` | `Output trimmed — N lines not shown` |
| completion | `result` | `Completed · exit code 0` / `Failed · exit code N` / `Finished — exit code not reported` (exists) |
| shell lost while running | `channel` | `Terminal closed while the command was running` |

**stderr is not a separate event.** `read()` yields one merged stream; claiming separation would be a lie the API cannot support.

### Projection rules for `output` (all in the extension host)

1. **Line assembly** — buffer chunks, split on `\n`, hold the trailing partial until the next chunk or stream end. Chunk boundaries from `read()` do not align to lines; publishing raw chunks would garble every line.
2. **Carriage return** — for a line containing `\r`, keep only the final segment. That is what the terminal would have shown, and it collapses progress bars to their last state instead of flooding.
3. **ANSI / control strip** — existing `ANSI` and `CONTROL` regexes (`player-activity.ts:80-81`), unchanged.
4. **Redaction** — existing `redactSecrets`, unchanged.
5. **Whitespace** — `output` preserves leading and internal whitespace (trailing trimmed). Explicitly unlike the other non-`message` categories.
6. **Length** — `ACTIVITY_LINE_MAX` (240), with the existing `…` ellipsis.
7. **Throttle** — cap lines per second per instance; coalesce the excess into one `channel` notice rather than dropping silently.
8. **Volume ceiling** — cap total `output` lines per command (the daemon keeps 300 per Player regardless). State the trim; never pretend the output was complete.
9. **Backpressure** — the pump is `for await`, so it applies natural backpressure; the throttle and ceiling bound what reaches the wire.
10. **Never disturb a Play** — the pump is wrapped like `publishActivity` already is (`player-roster.ts:1132`): observability failures are swallowed.

## SECURITY MODEL

| Concern | Handling |
|---|---|
| **Scope** | Only Coach-dispatched Plays are observed. The human's own typing in that terminal is never read. This is the primary control and it is structural. |
| **Secrets in output** | `redactSecrets` twice (host + daemon). Best-effort, and honestly so. |
| **Environment dumps** (`env`, `Get-ChildItem env:`) | Named values are redacted; **unconventionally-named ones are not**. Mitigated by scope: the human chose to dispatch `env` as a Play. Not claimed as solved. |
| **File dumps** (`cat .env`) | Same honest bound. `DB_HOST=prod.internal` matches no credential pattern and will appear. |
| **ANSI / control injection** | Stripped at host and re-stripped at daemon. The browser renders into `textContent`, never `innerHTML`. |
| **Large output** | Per-second throttle + per-command ceiling + 300-line daemon bound + 240-char line cap. Trims are announced. |
| **Copy behaviour** | Copy All / Copy New return the **sanitized retained** lines — never raw bytes. Unchanged. |
| **Storage** | Memory-only, bounded, per `gameId|instanceId`. No durable transcript in V1. |
| **Game / instance isolation** | Store keyed `gameId|instanceId`; terminal `cwd` pinned to Game root at creation. Unchanged. |
| **Gates** | Dev Mode **and** View Player Terminal. Off by default; costs and exposes nothing when off. |

**Stated plainly:** raw shell output is a genuinely larger exposure surface than structured provider events, and regex redaction is not a proof. V1's real protection is that Coach only watches commands a human deliberately dispatched, behind two gates that are off by default.

## LIVE PLAYER TERMINAL RETENTION BREADCRUMB

**WAS** — The Live Player Terminal could vanish as soon as execution completed. For a developer, that terminal is evidence, and it disappeared on the machine's schedule rather than the human's.

**IS** — S46.0 established a baseline retention lifecycle: manual Collapse, post-completion Copy release, and next-Play continuity. `isTerminalEligible` admits `finished`, and `consolePinnedByInstance` pins a deliberately-expanded terminal after completion (`index.html:2776`). Retention is already a *named*, testable behaviour rather than an incidental timer.

**WHY** — *Terminal disappearance should follow a clearly defined user action or explicit retention policy, not an incidental UI timeout.* Once the human deliberately opened that view, destroying it is Coach overriding human choice.

**WILL BE** — Retention becomes explicit product policy, selectable among: keep until manual Collapse; keep until successful Copy; keep until next Play; keep until the resulting report is discovered; keep full history while View Player Terminal is on.

**Architectural guarantee this decision provides.** Retention is decided entirely in the browser, from `(sessionKey, epoch, playRef, pin-set)`. No execution plumbing, no daemon contract and no notice shape encodes a retention rule. Adding the `output` category changes *what is retained*, never *how long*. **A future retention policy is a browser-side change and nothing else.** Nothing in V1 is to be implemented against this breadcrumb.

---

## V1 SCOPE

V1 **will**:

1. Add the `output` activity category through the existing sanitization choke point.
2. Consume `execution.read()` for Coach-dispatched terminal commands, assemble lines, and publish them.
3. Give Terminal Player a real `sessionKey` from `shellPid:shellStartedAt`, so a restarted shell starts a clean transcript.
4. Render terminal output in the existing Live Player Terminal — desktop, mobile fullscreen, Copy All / Copy New, post-play retention, all unchanged.
5. Report completion and failure honestly, including `unknown` when the shell reports no exit code.
6. Degrade honestly and visibly when shell integration is unavailable or the command is multi-line: say the command is running unobserved, rather than showing an empty terminal.
7. Throttle, cap and announce trimming.
8. Preserve every existing invariant: exact-instance routing, `checkTerminalCommand`, ownership, Scout exclusion, both gates.

## NOT V1

- PTY / `node-pty` / ConPTY ownership.
- `PlayerControl` / `TerminalControl` adapter; changes to `INSTANCE_PATTERN` or `ControlledBindingRecord`.
- xterm.js or any ANSI/TUI emulation.
- Arbitrary stdin, interactive REPL steering, Ctrl-C / interrupt.
- Separate stderr (the API cannot supply it).
- Observing the human's own typing in the terminal.
- Durable / on-disk transcripts.
- Terminal Player in AUTO routing. **Terminal stays MANUAL.**
- Configurable retention policy (breadcrumb only).
- Any change to `daemon.ts`, `stadium-client.ts`, `work-ledger.ts`, `execution-projection.ts`, `host.ts`, `bindings.ts`, `contract.ts`.

### Play T2 — Terminal output tap and terminal session key

**Objective.** In `runTerminalCommand`, attach `execution.read()` synchronously, assemble lines, publish `output` notices with a terminal `sessionKey`; handle completion, throttling, trim announcement and honest degradation.

**Files.** `src/player-roster.ts` (primary), `src/terminal-player.ts` (line-projection helper, kept `vscode`-free and testable).

**Invariants.**
- `read()` is called **in the same tick** as `executeCommand()`. The typings require it; a deferred call loses data.
- Availability is feature-detected (`typeof execution.read === 'function'`), matching the existing defensive shape at `player-roster.ts:226`.
- **Only executions in `runningCommands` are read.** Human-typed commands are never captured.
- Output pump failures never affect the Play — same `try`/swallow discipline as `publishActivity`.
- `sessionKey` derives from provenance already captured by `recordProvenance`; no new process probing.
- `checkTerminalCommand`, exact-instance refusals, bench/closed/busy refusals: all unchanged.
- No multi-line command silently claims observation (`observed: false` path preserved).
- No change to dispatch routing, daemon, ledger, or projection.

**Verification.**
- Unit: line assembly across chunk boundaries that split mid-line; `\r` progress-bar collapse; throttle emits one trim notice; stream end flushes the trailing partial line.
- Unit: `sessionKey` changes when `shellStartedAt` changes; stays stable across commands in one shell.
- Integration: a fake `execution` yielding scripted chunks produces the expected ordered notices.
- Existing `test/p0-1-terminal-player.test.mjs` must still pass unchanged.

**Player.** Claude Sonnet at high effort, or AntiGravity A-Team. **Difficulty: medium-high.** The architecture is settled and the seam is one function — but the same-tick `read()` invariant and the line-assembly edge cases are easy to get subtly wrong, so this one wants a careful implementer and real tests. Not an Opus task.

## RISKS

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| R1 | **Shell integration absent** → no output at all | **Material** | Detect and say so. The failure must be legible, never a blank terminal. Windows/pwsh is auto-injected by default, so this is an edge case, not the common path. |
| R2 | **`read()` attached a tick late loses the start of output** | **Material** | Same-tick invariant is stated in the typings and is a named Play invariant with a test. |
| R3 | **Secrets in output that match no pattern** (`cat .env` with plain names) | **Material, accepted** | Bounded by scope (dispatched Plays only) and two default-off gates. Documented as a known limit, not claimed solved. |
| R4 | **High-volume output floods the rail** | Moderate | Per-second throttle + per-command ceiling + 300-line daemon bound; trims announced. |
| R5 | **Multi-line commands stay unobserved** | Moderate | Pre-existing (`player-roster.ts:715`). V1 makes the degradation visible instead of silent. |
| R6 | **`exitCode === undefined`** on sub-shells or Ctrl-C | Low | `describeTerminalExit` already reports `unknown` honestly. |
| R7 | **`@types/vscode` installed at 1.137 while engine floor is 1.95** | Low | `read()` finalized in 1.93, below the floor. Feature-detect anyway, matching the existing listener guard. |
| R8 | **Merged stdout/stderr misread as separation** | Low | Never claim separation anywhere in UI, events, or docs. |

## BREADCRUMBS

Three durable breadcrumbs should exist after implementation.

**1. `src/player-activity.ts` header — update the existing `WILL BE`.**
Its current text already predicts this work (*"Terminal Player stdout/stderr … can feed this same `PlayerActivityNotice` without changing the browser contract"*). On landing, that prediction moves into `IS`, and the new `WILL BE` names durable history and richer Codex activity.

**2. `src/player-roster.ts`, at `runTerminalCommand` — the substrate decision.**
> **WAS:** Terminal Player sent an exact command and watched only for its exit code; the output belonged to VS Code alone.
> **IS:** The same command's output is read through `TerminalShellExecution.read()`, assembled into lines, sanitized in the host, re-sanitized in the daemon, and shown in the Live Player Terminal. Only commands Coach was asked to run are ever read — the human's own typing in that terminal is not.
> **WHY:** The human wanted to see the living Player's guts without Coach seizing ownership of their shell. The native terminal survives a window reload and stays theirs to type in; a Coach-owned PTY would have taken both.
> **WILL BE:** Interrupt, and — if a real need appears — a PTY-backed adapter behind this same `PlayerActivityNotice` contract. stdout and stderr stay merged because this API yields one stream.

**3. `src/terminal-player.ts` — session identity.**
> A terminal session is not a provider conversation. Its ref is `shellPid:shellStartedAt`; only the opaque digest leaves the host. A new shell is a new transcript.

The Live Player Terminal retention breadcrumb is **preserved unimplemented**, as recorded above.

## SCOUT ECONOMICS — TRUTHFUL ASSESSMENT

Product evidence for the "3 cheap Scouts + 1 A-Team Scout → Opus decision" experiment. Verdict: **the formation worked, and it was worth it — with one real cost and two real failures.**

### What the Scouts bought

**Substantial, and mostly in the form of a map rather than answers.** The single highest-value artifact was the *seam list*: S47 §13 and Scout A's "Architect-Review Seams" table told me which four or five functions in a ~67-file `src/` tree the decision actually turned on. Without it I would have had to read the entire Controlled rail — `structured-print.ts`, `codex-app-server.ts`, `host.ts`, `controlled-player-presentation.ts`, `player-instances.ts` — to learn what "Controlled" means before I could decide whether Terminal should join it. **I opened none of those five files.** That is the saving, and it is real.

Scout A's substrate comparison table (existing vs. needed, per capability) and its ownership table were directly reusable as decision inputs. S47's survival matrix framed the reload question correctly and led me straight to the finding that killed the PTY option. Scout B resolved where to look for persistence, and honestly flagged its own open UNKNOWN about `BindingStore` — which I then closed in one grep. Scout C contributed least that was load-bearing; its security content largely restated S43.

### Where the Scouts were wrong

Two contradicted findings, both in Scout A, both material:

1. **Scout A R2 / S1: "VS Code shell integration is read-only… no API to read stdout/stderr," therefore a PTY is required.** Disproved at `node_modules/@types/vscode/index.d.ts:8001`. Had this gone unchallenged, it would have pushed V1 toward `node-pty` — a native dependency, a per-Electron-version build tax, and the loss of window-reload survival. **This single error, uncaught, would have been the most expensive mistake available in this Play.** The Play's instruction not to accept either Scout blindly is what caught it.
2. **Scout A S9: `isTerminalEligible` requires `transport === 'Controlled'`.** False; the real gate at `index.html:2763` has no transport term. Believing it would have added a phantom browser work item and, worse, invited a redesign of a surface that was already correct.

Both failures share a shape: **Scout A reported plausible-sounding API and code details with the same confidence as the things it actually read.** Its file-and-line citations for code it had genuinely opened were accurate throughout. Its claims about *absent* capability — what the API does not offer — were not verified and were wrong. That is a usable rule: a Scout can be trusted on "here is what exists"; a Scout's "this is impossible" must always be re-verified by the Architect.

Notably, the A-Team (AntiGravity) Scout got both of these right where the cheap Scout got them wrong, and flagged `execution.read()` specifically as unconsumed. **The A-Team pass earned its cost.** A formation of cheap Scouts alone would have handed me a confidently wrong substrate recommendation.

### The cost nobody planned for

The three cheap Scout reports were written as **UTF-16LE raw terminal captures with embedded ANSI escape sequences, a PowerShell `NativeCommandError` banner at the head, and the Scout's own tool-call log interleaved with its prose.** They were not readable as Markdown. Decoding and stripping them consumed premium effort before a single finding could be read, and a naive first pass silently corrupted the text.

This is a **Scout delivery defect, not a reconnaissance defect** — the content underneath was largely sound. But it is a direct tax on the economics being measured, and it is fixable at the Scout-harness level: Scout reports should be written as UTF-8 Markdown files by the Scout, not captured from its terminal. Recommend this be fixed before the next formation.

### Net verdict

**Favourable, and repeat the pattern — with the A-Team pass kept in it.** The Scouts converted an open-ended archaeology problem into a targeted verification problem, which is exactly the intended trade. Premium effort went where it should have: resolving two contradictions, pricing three rejected alternatives, and deciding. Two refinements for next time:

1. **Fix Scout report encoding** — plain UTF-8 Markdown, no terminal capture.
2. **Require Scouts to mark capability-absence claims as unverified** unless they cite the type definition or source that proves the absence. Both of Scout A's errors were absence claims.

## FINAL RECOMMENDATION

**1. Is Terminal Player architecture ready to implement?**
**Yes.** Both contradictions are resolved against source, not opinion: `TerminalShellExecution.read()` is stable in the targeted API, and the browser's eligibility gate has no transport restriction. The substrate, contract, session model, ledger semantics, UI and security boundary are all decided, and the decision requires **no change** to the daemon, the dispatch path, the work ledger, the execution projection, the control host or the binding store.

**2. What is the very next Play?**
**Play T1 — Terminal output activity category.** Add `output` to `ActivityCategory` / `ACTIVITY_CATEGORIES` with whitespace-preserving sanitization and no duplicate suppression; register `output: 'OUTPUT'` in `CONSOLE_LABELS`; retire the stale `'Terminal Player output is not captured yet.'` placeholder. Small, well-fenced, unit-testable, and it makes T2 a pure wiring job.

**3. Who should run it?**
**T1:** a Worker or Sonnet at medium effort — fully specified, two files, existing test file to extend. **T2:** Sonnet at high effort or AntiGravity A-Team, medium-high difficulty. **No further Opus time is needed on Terminal Player.** The architecture was the expensive part, and it is done.

**4. What should Dad expect to see when it works?**
He adds Terminal to his Team, types `git status`, and sends it. The Terminal strip lights up. He taps Expand — on his desk or fullscreen on his phone — and the real branch, the real modified files, the real untracked list scroll past as they happen. When it ends he sees `Completed · exit code 0`. He hits Copy All and pastes it wherever he wants. The terminal stays until he collapses it. He never hears the words PTY, shell integration, stdout or transport.

He can see the guts of his Terminal Player.
