## EXACT DIRECTIVE GRAMMAR

Recognition is `recognizeScoutDirective(prompt)` in `src/control-plane/route-constraints.ts`. Deterministic, no NLP, no fuzzy spelling.

**Region:** the **first non-blank line only**. A first line that is a code fence or a `>` quote is never a directive. A directive on line 2+ (after a title, after prose, inside a fence or quote) is content.

**Presentation ignored:** heading (`# `), list (`- `, `* `, `1. `) markers, and bold/italic/backtick emphasis wrapping the phrase (`**…**`, `__…__`, `*…*`, `_…_`, `` `…` ``), plus case.

**Grammar:**

```
HEAD      = scout | scout this | scout this play | scout needed        (case-insensitive)
BEFORE    = "before <clause>" up to . ! ? : ; or end of line           (only after "this" / "this play")
SEPARATOR = end of line
          | ":"  ","  ";"                                              (any HEAD, including bare "Scout")
          | "."  "!"                                                   (not after bare "Scout")
          | " - "  " – "  " — "
DIRECTIVE = HEAD [BEFORE] SEPARATOR
```

The token after `scout` must not continue a word, so `Scouts`, `Scout's` and `Scoutt` are out. **A separator is required**: `Scout found this yesterday`, `Scout this play support was added`, `Scout the parser for bugs` all stay ordinary prose.

### Positive examples (all route to Scout)

`Scout` · `Scout this` · `Scout this play` · `Scout needed` · `SCOUT NEEDED:` · `SCOUT THIS PLAY` · `**Scout this play**` · `**Scout this play:** investigate it.` · `**Scout needed**: …` · `* Scout this play` · `- Scout this play` · `# Scout this play` · `` `Scout this play` `` · `_Scout needed_` · `Scout needed: investigate the routing parser.` · `Scout, investigate the routing parser.` · `Scout this play, investigate the routing parser.` · `Scout this play` + newline + `Investigate the routing parser.` · `Scout this before Claude implements it.` · `scout this play - investigate it.` · `Scout this play.` · leading blank lines/indent.

## ROUTING PRECEDENCE (as built)

1. **Explicit routing control**
   - Structured envelope (`AGENT:` / `PLAYER:` …), resolved or unresolved. It outranks the directive; an unresolved structured Player still stops visibly (S56.0).
   - A natural "Use X …" imperative already recognized in the header also outranks it.
   - The **Scout opening directive** (new). It carries no model/effort, so a `MODEL:`/`REASONING:` header alongside it behaves exactly like `AGENT: Scout` (Scout has no model catalog → visible "Unrecognized model" stop).
2. Exact special routing (Terminal) — only reached when there are no constraints, so a directive is never mistaken for a shell command.
3. Existing AUTO Scout recommendation (`analyzeScoutNeed`) — untouched; a directive is not an AUTO recommendation and carries no `scoutNeed`/continuation.
4. Ordinary task classification / provider routing — never reached by a recognized directive.

**No substitution.** The directive rides the existing explicit-Player path, so an unavailable / busy / not-on-field / stale-capability Scout returns `Scout is currently unavailable. Coach did not choose another Player because you asked for Scout.` Nothing is dispatched to Claude/Codex. MANUAL routing is unchanged: the human already chose the Player, and the opening words stay Play text.

## CONTROL / PLAY SEPARATION (executionPrompt)

`RouteConstraints.directive?: { kind: 'scout'; matched; executionPrompt? }` (in `capability-types.ts`) is the seam: original prompt (what the human typed) / route directive (`matched`) / execution prompt.

| Human input | Scout receives |
|---|---|
| `Scout this play, investigate whether X is safe.` | `Investigate whether X is safe.` |
| `Scout this play` ⏎ `Investigate the routing parser.` | `Investigate the routing parser.` |
| `Scout needed: investigate the routing parser.` | `Investigate the routing parser.` |
| `SCOUT NEEDED:` ⏎ ⏎ `Line one.` ⏎ `Line two.` | `Line one.` ⏎ `Line two.` (later lines verbatim, incl. code and lists) |
| `Scout this play` / `Scout needed` / bare `Scout` | the **original Play unchanged** (nothing fabricated) |
| `Scout this before Claude implements it.` | the original Play unchanged (the "before …" clause is timing control, not an objective) |

The router (`src/control-plane/router.ts`) delivers `executionPrompt` only when an AUTO decision actually landed on Scout and a directive with an objective exists. The queue and delivery paths use it; report-request detection still reads the original text so a "report" wording is never lost. Only the first letter of the objective is capitalized; nothing else is rewritten.

## COMPATIBILITY / AMBIGUITY RISKS

- **Bare `Scout` (or `Scout: …` / `Scout, …`) as a Play's first line is a directive.** That is what the brief asks for, but a pasted document whose title line is exactly `Scout` or `Scout: <something>` would be routed to Scout. Titles with any other words (`Scout Player architecture notes`) do not.
- **A separator is mandatory.** `Scout this play investigate the parser` (no comma/colon/dash/period) is **not** recognized, because `Scout this play support was added` must stay prose and there is no safe way to tell them apart without NLP. Users get the ordinary route in that case. If field use shows this is common, the next step is a small allow-list of known verbs after `this play`, not open-ended parsing.
- **Only line 1.** `Title line` ⏎ `Scout this play` is not recognized. The structured `AGENT: Scout` header remains the path for headers.
- **"Scout this before Claude implements it" delivers the whole original Play** because the "before …" clause is not an objective. Scout gets the same words the human typed, including that clause.
- **Structured or "Use X" routing beats the directive.** `Scout this play` ⏎ `AGENT: Codex` routes to Codex; the directive words are then ordinary Play text.
- **Legacy local-server AUTO path** (`src/server.ts` `computeAutoRoute` callers) now routes a directive to Scout (or stops truthfully) but does not strip the directive, so Scout receives the original prompt there. Production dispatch goes through the control-plane router, which does.
- A Scout directive coexisting with `MODEL:` / `REASONING:` headers stops with the existing "Unrecognized model … requested for Scout" message (same as `AGENT: Scout` today).
- No behavior change for Plays that do not start with a Scout directive; verified by the existing 117 routing/Scout tests plus S5.

## WAS / IS / WILL BE

- **WAS:** Scout could be recommended by AUTO intelligence or chosen by a structured field, but a natural opening command such as "Scout this play" was ordinary prose and could be staged as Claude · Opus · High.
- **IS:** Unmistakable opening Scout directives are control-plane commands, intercepted before task classification and routed explicitly to Scout with the objective separated from the command. Descriptive references stay Play content. An unavailable Scout is a truthful stop.
- **WILL BE:** The same control/play separation generalizes into a canonical ingestion layer (originalPrompt / routeDirective / executionPrompt) so natural coaching language such as "Use Claude Sonnet 5 Medium to implement this" normalizes into routing control plus clean execution content. Intelligent AUTO, AI Health, Player Scorecards, CONSERVE, task-fit routing and scheduling stay separate policy layers.
