## 1. Executive Verdict

**ARCHITECTURE READY.** Intelligent Routing can be built on the existing chain without a second routing brain, a second telemetry store, or changes to Stage 2A.

Sixteen decisions shape everything else:

1. **One brain, one object.** A pure `recommendRoute()` function produces a `RoutingRecommendation`. In V1 it goes to the Coach. Later it goes to a Policy Gate. The only code that turns advice into an executable route is one adapter, `optionToDecision()`. Today's `PROVIDER_PREFERENCE` table stops being a rule and becomes an input to the cold-start prior.
2. **What gets scored.** Evidence is recorded at the finest level (`playerType · modelId · effort`). Belief is estimated up a hierarchy (`playerType → lineage → modelId → effort`) with partial pooling. A Player *instance* (`claude-1` vs `claude-2`) is never a statistical unit. Instances carry availability and field possession, not skill.
3. **Priors plus local evidence.** Beta-Binomial shrinkage. A researched prior is a small number of pseudo-reps (n₀ ≤ 6). Local evidence is weighted by comparability, recency and attribution confidence. It overtakes the prior after a handful of comparable reps and can never create certainty it has not earned.
4. **Stored evidence.** A single append-only **Routing Film** journal (`~/.sideline/routing-film.jsonl`) holds decision and outcome events keyed by `clientRef`. It is not a telemetry store. Resource numbers inside it are frozen **receipts** and are never read back as current resource truth. Scorecards are *derived views* of the Film, not a second source of truth.
5. **Fix attribution.** A follow-up is `unattributed` by default. It never counts against the previous Player until an evidence rule or a one-tap Coach correction says `player-defect`. An unattributed repair simply withholds first-pass credit.
6. **Field possession.** Reuse `resolveContextOwner`. Convert its output into a *possession value* using an evidence tier, a time-decay factor and a session-continuity factor. That value becomes a *context reacquisition cost* charged to non-owner candidates. V1 adds no new context receipts.
7. **Resources: capacity × time.** Each window (5H, Weekly) gets a **pace pressure** π = (time left in window ÷ window length) ÷ (capacity left). A Play's resource cost is Σ price(π) × expected burn. Capacity that will reset before it can be used is priced near zero. Dad's LOW/CRITICAL thresholds set a price floor, but only on capacity that will still be scarce while the Play runs.
8. **Resource view.** Option **B**: a read-only `RoutingEconomicsSnapshot`, composed by a pure function from the *same* `normalizeAlarmFacts` normalizer that AlarmEngine uses, plus `ProviderResourcePolicy` verbatim. `ProviderResourcePolicy` is left unchanged. (Verified: persisted `AlarmStateSnapshot` holds no `remainingPercent`, so extending the policy would give it a second upstream.)
9. **Play cost.** Estimated from before/after receipts, each with an isolation-confidence grade. Always presented as a range with low/medium/high confidence. Never presented as exact causality.
10. **Scout economics.** Scout ROI = premium burn saved × pressure price − Scout cost − delay − expected harm from bad intelligence. Field possession or fresh Scout intelligence already held lowers the savings term toward zero, which produces "No Scout — field already possessed."
11. **Three kinds of confidence.** *Recommendation Strength* (margin versus uncertainty), *Evidence Strength* (how much local film exists) and, only after graduation, *Calibrated Confidence* (P(first-pass acceptance)). **No percentage is shown to Dad until a task class graduates.**
12. **Three independent dimensions.** *Authority* (AUTO / MANUAL: who chooses), *Posture* (FAST / BALANCED / SURE / CONSERVE: what "best" means) and *Scarcity* (ResourcePolicy `none/low/critical`: a fact about the world). The posture called CONSERVE is not the same thing as `isConserveActive`.
13. **Schedule-after-reset.** A separate durable `DeferredPlay` store plus a thin scheduler. When a deferred Play fires, it goes back through the normal router (and so through PlayQueue). PlayQueue is not extended; its semantics stay "run when this instance frees up."
14. **Shadow mode first.** Every dispatched Play logs the recommendation, what the Coach actually chose, and the eventual outcome. Unchosen alternatives stay `unobserved`.
15. **Staging.** Nine bounded Worker Plays plus one research Play (§20). None of them changes what AUTO dispatches until a separate cutover Play, run after shadow evidence exists.
16. **Automation later.** Future automatic dispatch attaches at exactly three seams: `PolicyGate`, `optionToDecision` and the `DeferredPlay` trigger. None of them forks the recommendation algorithm (§22).

```

[1] AUTHORITY GATE ───── fully explicit route (MANUAL or envelope locks every dimension)?
   │                         └─ compute recommendation anyway (shadow), authority='coach', never shown in Dad Mode
   ▼

   ▼
[3] CANDIDATE SEATS ──── reuse routing-policy eligibility (operable, autoEligible, roster, constraints, Terminal/Scout
   │                     separation). Expand each seat over catalog models × supportedEfforts that constraints allow;
   │                     prune to ≤ 12 targets (drop dominated efforts, keep one per lineage per effort band)
   ▼
[4] BELIEF ──────────── CapabilityBelief(target, profile) from PriorPack + Film  (§5, §6)
[5] POSSESSION ──────── resolveContextOwner → PossessionValue per seat (§9)
[6] ECONOMICS ───────── RoutingEconomicsSnapshot → price per provider window; cost & interrupt risk per option (§11)
[7] OPTIONS ─────────── for each target: send | queue (owner busy) | handoff (existing semantics)
   │                     + scout-first variants (§10) + wait-for-reset variants (§15)
   ▼
[8] UTILITY ─────────── posture-weighted U(option) (§5.4) → rank
[9] SELECTION ───────── primary · nextBest (different playerType or lineage) · waitOption · scoutOption
[10] STRENGTH & TEXT ── recommendationStrength · evidenceStrength · (calibrated if graduated) · reason codes → Dad/Dev text
   ▼
RoutingRecommendation (pure, deterministic for the same inputs and clock)
   │
   ├─ V1:     → Coach (preview chip)                 → Coach's choice → existing router → dispatch
   └─ Future: → PolicyGate → optionToDecision → existing router → dispatch
```

Rules:

- Steps [2]–[10] are **pure**. The clock and every input are injected.
- The one side effect is the Film append, and it happens **at dispatch**, keyed by `clientRef`. `/api/route/preview` recomputes on every keystroke and never writes to the Film.
- Step [3] must call the *existing* eligibility helpers. If they are not exported cleanly today, the Worker extracts them without changing behavior (see Stage R4, §20). There is exactly one definition of "who can take this Play."
- The existing `RoutingDecision` that AUTO produces is carried into the recommendation as `baseline`. Shadow mode measures agreement against it.

## 5. V1 Statistical Recommendation Model

### 5.1 Outcome variable

The primary learning signal is **first-pass acceptance**:

```
firstPass(play) =
  1   if outcome ∈ {completed} AND resolution = clean   (no player-defect repair linked within the window)
  0   if outcome ∈ {failed, partial, blocked} for player reasons, OR a repair is attributed player-defect
  —   (excluded) if the failure cause is provider/auth/quota/harness/interrupted/not-sent,
      or the repair is unattributed / environment-drift / prompt-change / upstream-change / planned-continuation
```

This follows the existing doctrine in `routing-policy.ts`: *"provider/auth/quota/harness failure is not Player skill evidence."* `interrupted` and `unknown` ledger outcomes are excluded, not counted as failures.

**Resolution window:** closes after 72 hours, or after 3 later Plays in the same Game that touch the same files, whichever comes first. The Play is `pending` until then. Pending Plays contribute nothing.

### 5.2 Comparable-Play weighting

Each Film observation *i* is weighted for the Play being scored:

```
w_i = sim(class_i, class) · sim(diff_i, diff) · decay(age_i) · attrib_i · gameBonus_i

sim(class)  : same 1.0 · architecture↔implementation 0.25 · quick↔any 0.1 · default↔any 0.3
sim(diff)   : same 1.0 · adjacent 0.6 · easy↔hard 0.25
decay(age)  : 0.5 ^ (age / 90 days)                  // silent server-side model changes
attrib_i    : 1.0 clean / Coach-confirmed player-defect · 0.6 rule-inferred high · 0.3 rule-inferred low
gameBonus_i : 1.15 if same gameId, else 1.0           // small; capability is league-wide
```

Scout-role observations never mix with Player-role observations.

### 5.3 Posterior (Beta-Binomial with hierarchical partial pooling)

For a target node *k* (for example `codex/codex-frontier/<modelId>/high`) and profile *p*:

```
prior(k,p) = Beta(α₀, β₀),  α₀ = m₀·n₀,  β₀ = (1−m₀)·n₀            // §6

S_k = Σ w_i·y_i          over observations exactly at node k
F_k = Σ w_i·(1−y_i)
S_anc, F_anc = same sums over each ancestor's OTHER descendants (siblings, cousins)

posterior(k,p) = Beta( α₀ + S_k + Σ_level λ_level·S_anc(level),
                       β₀ + F_k + Σ_level λ_level·F_anc(level) )

λ: effort-siblings (same modelId) 0.35 · modelId-siblings (same lineage) 0.15 · lineage-siblings (same playerType) 0.05
Pooled pseudo-reps from ancestors are capped at 6 in total, so a busy sibling can never drown a node's own film.

firstPass.mean = α/(α+β);  lo/hi = Beta 20th/80th percentiles (closed-form approximation or a small lookup)
nLocalEff      = S_k + F_k   (own node only; pooled reps are reported separately in Dev)
```

This is the whole statistical engine. There are no bandits, no reinforcement learning and no trained model. Every number is a readable sum.

### 5.4 Utility and ranking

```
C_play   = Σ_windows price_w · burn_w(p50)  + reacquisition(seat)             // §9, §11
C_eff    = C_play · (1 + (1 − q) · ρ_repair)          ρ_repair = 0.6          // a cheap miss costs a repair
q        = firstPass.mean   (SURE posture uses firstPass.lo)
D_hours  = scout delay + queue estimate + wait-to-reset
Risk     = interruptRisk (§11) + 0.1·[any resource evidence UNKNOWN]

U = q − λ_c·C_eff − λ_d·urgencyMult·D_hours − λ_r·Risk
```

| Posture | λ_c | λ_d (per hour) | λ_r | q uses | Weekly-reset waits allowed |
|---|---|---|---|---|---|
| FAST | 0.5 | 0.30 | 0.5 | mean | no |
| BALANCED | 1.0 | 0.05 | 0.5 | mean | no |
| SURE | 0.8 | 0.05 | 1.0 | lo (20th pct) | no |
| CONSERVE | 2.5 | 0.01 | 0.5 | mean | yes (≤ 36 h, urgency ≠ now) |

`urgencyMult`: whenever 0.3 · normal 1 · now 5.

These constants are V1 defaults. They live in one frozen `ROUTING_WEIGHTS` object with a version string that is stamped on every recommendation, so Film analysis always knows which weights produced which advice.

**Selection stability.** When the top two options fall inside a *toss-up* margin (§12), the primary is whichever option matches today's `baseline` AUTO decision. This stops recommendations from flickering between previews.

### 5.5 Drift

For each node with ≥ 5 recent comparable outcomes: if the mean of the last 5 falls outside the posterior's 5th–95th percentile band, mark `drift: 'suspected'`. That halves the decay half-life for the node until the next 5 outcomes land inside the band. The flag appears in Dev Mode. Drift never silently resets evidence.

## 6. Researched Prior + Local Evidence Model

`RESEARCHED PRIOR + LOCAL FIELD EVIDENCE = CURRENT CAPABILITY BELIEF` is implemented literally as §5.3.

### 6.1 CapabilityPriorPack (repo-shipped, versioned)

```jsonc
{
  "schemaVersion": 1,
  "packVersion": "2026.09-r1",
  "lineages": [                                   // modelId → lineage mapping, pattern-based
    { "playerType": "claude", "lineage": "claude-opus",   "match": "^(claude-)?opus" },
    { "playerType": "claude", "lineage": "claude-sonnet", "match": "^(claude-)?sonnet" }
  ],
  "priors": [
    {
      "node": "claude/claude-opus/*/high",          // any level; '*' = inherit across that level
      "taskClass": "architecture", "difficulty": "hard",
      "firstPass": 0.80, "strength": 5,             // m₀, n₀  (n₀ ≤ 6, hard cap)
      "burn": { "fiveHour": [0.08, 0.15, 0.25], "weekly": [0.01, 0.02, 0.04] },
      "durationMin": [10, 20, 40],
      "researchedAt": "2026-09-26",
      "sources": ["<citation>", "..."],
      "researchQuality": "cross-checked" | "single-source" | "extrapolated"
    }
  ]
}
```

### 6.2 Prior strength rules (so priors can never fake certainty)

- `strength` cap by quality: cross-checked 6 · single-source 4 · extrapolated 2.
- **Age decay of the prior:** `n₀_eff = n₀ · 0.5^(age/180 days)`. Research goes stale. Its mean stays, its weight fades.
- **Inheritance for unseen versions:** a new `modelId` with no prior inherits its lineage node's prior mean with `n₀ × 0.5` and `source: 'inherited'`. An unknown lineage falls back to the `playerType` node. With no node at all, the fallback is the **baseline-preference prior**, derived from today's `PROVIDER_PREFERENCE`: rank 1 → m₀ 0.70, rank 2 → 0.62, rank 3 → 0.55, strength 2. The existing depth chart becomes the weakest possible prior instead of a rule.
- **Local takeover:** with n₀ = 5, local evidence carries half the weight after about 5 comparable reps and about 80% after about 20. That is useful at zero reps and honest at five.

### 6.3 Reconciling with the depth-chart principle

The `routing-policy.ts` doctrine forbids *"a fantasy ranking from model names"* and *"artificial benchmarks."* Priors are the preseason scouting report, not the depth chart. They are capped, they decay with age, they are labeled *prior* everywhere in Dev Mode, and real film overtakes them quickly. That is consistent with the doc comment's own WILL-BE: *"keep general priors separate from local real-game film."*

### 6.4 Producing the pack

A dedicated **research Play** (R0, §20) fills the pack from public evidence. That means provider release notes and published evaluations, mapped onto Sideline's task classes. The cited sources and the mapping rationale go in `sources` and in a companion report. An A-Team review Play checks it before it merges.

## 7. Player Scorecard Schema (Routing Film)

A Scorecard is a **view**, not a file:

```
Scorecard(node, taskClass) = fold(Film events)  →  { firstPass posterior, n, outcomes by cause,
                                                     retries, substitutions, duration p50, burn p50, unattributedRate }
```

The only durable store is the append-only Film. Each line is one event:

```ts
type RoutingFilmEvent =
 | { v: 1; kind: 'decision'; at: number; clientRef: string; gameId: string;
     profile: Pick<PlayProfile,'taskClass'|'difficulty'|'role'|'urgency'|'promptFingerprint'> & { touchesCount: number; followUp: 'new-work'|'continuation' };
     recommendation: RecommendationDigest;          // primary/nextBest/wait/scout targets + U + strengths + weightsVersion + engineVersion
     baseline?: TargetDigest;                        // what static AUTO would have sent
     chosen: TargetDigest & { action: 'send'|'queue'|'handoff'|'scout-first'|'wait' };
     decidedBy: 'coach-manual' | 'coach-envelope' | 'coach-accepted-primary' | 'coach-accepted-next-best'
              | 'coach-accepted-wait' | 'coach-accepted-scout' | 'auto-baseline' /* future: 'policy-gate' */;
     possession: { tier: PossessionTier; value: number };
     receiptBefore: ResourceReceipt[] }             // chosen provider's windows only
 | { v: 1; kind: 'outcome'; at: number; clientRef: string;
     ledgerOutcome: LedgerOutcome; failureClass?: 'player'|'provider'|'auth'|'quota'|'harness'|'interrupted';
     durationMs?: number; executionStartedAt?: number; retries: number;
     substitutedTo?: TargetDigest; reportProduced: boolean;
     receiptAfter: ResourceReceipt[]; burn?: BurnObservation }
 | { v: 1; kind: 'link'; at: number; clientRef: string; parentClientRef: string;
     linkEvidence: 'named-report'|'incoming-report'|'latest-play'|'touch-overlap'|'scout-continuation' }
 | { v: 1; kind: 'attribution'; at: number; clientRef: string /*the follow-up*/; parentClientRef: string;
     cause: FixCause; source: 'rule' | 'coach' | 'envelope'; confidence: Conf; ruleId?: string }
 | { v: 1; kind: 'resolution'; at: number; clientRef: string; state: 'clean'|'repaired'|'failed'|'excluded' }

interface ResourceReceipt { provider: 'claude'|'codex'; window: 'five_hour'|'weekly';
  remainingPercent?: number; resetsAt?: number; observedAt?: string; stale: boolean }   // copy of NormalizedAlarmFact
```

**Intentionally not stored:** prompt text (only the fingerprint, matching the ledger's "never the prompt itself"), report bodies, token counts, per-tool telemetry, provider responses.

**Why this is not "another telemetry store":** it records *routing decisions and their outcomes*, which nothing owns today. The resource numbers it holds are point-in-time receipts, like a box score noting the score at a substitution. `RoutingEconomicsSnapshot` never reads them.

**Size and hygiene:** rotate at 5 MB into `routing-film.<n>.jsonl` and keep the latest 3. Beliefs fold only the last 365 days anyway (decay already makes older film negligible). Keep a `schemaVersion` on every line and use tolerant readers.

**Retries and substitutions:** `retries` counts re-sends of the same `clientRef` (existing retry path). `substitutedTo` records the Coach re-routing the same intent to another target after a failure. A substitution makes the original an observation, and that observation is only a failure if its cause is `player`.

## 8. Fix Attribution Model

### 8.1 Causes

```ts
type FixCause =
  | 'player-defect'          // the previous Player's work was wrong/incomplete against a stable ask
  | 'prompt-change'          // Coach changed/added requirements
  | 'planned-continuation'   // next stage of an agreed plan (not a fix at all)
  | 'environment-drift'      // tool/dependency/runtime/provider failure
  | 'bad-scout-evidence'     // premium Player acted on wrong Scout intelligence
  | 'missing-context'        // Player lacked context Sideline/Coach should have supplied
  | 'upstream-change'        // another Play changed the ground under it
  | 'unattributed';          // default
```

`planned-continuation` is an addition to the Play's list. Staged plans (like §20 of this report) generate many follow-ups that are not repairs.

### 8.2 Linking (reuse, don't rebuild)

A Play gets a `link` event to a parent when an existing signal fires:

- `detectFollowUp` says `continuation` and `resolveContextOwner` names a report or Play (evidence `named-report`, `incoming-report` or `latest-play`); or
- touch overlap with a Play completed in the same Game within 72 h; or
- the Play is a `scoutContinuation` (parent = the Formation).

A Play with no link has nothing to attribute.

### 8.3 Rule-based inference (pure, ordered, first match wins)

| # | Rule | Cause | Confidence |
|---|---|---|---|
| 1 | Parent `failureClass` ∈ provider/auth/quota/harness/interrupted | environment-drift | high |
| 2 | Between parent and follow-up, another instance completed a Play touching an overlapping path | upstream-change | medium |
| 3 | Parent was a post-Scout continuation, and follow-up names the Scout report with correction language (`wrong`, `stale`, `incorrect`, `doesn't exist`) | bad-scout-evidence | medium |
| 4 | Follow-up carries change language (`instead`, `actually`, `change of plan`, `also add`, `new requirement`, `scope`) and no defect language | prompt-change | medium |
| 5 | Follow-up names a stage/step of a plan in the parent's report (`Stage 2`, `next Play`, `R3`) | planned-continuation | high |
| 6 | Parent `context.state` was `unknown` or `handoff`, and follow-up supplies a report/file the parent did not have | missing-context | low |
| 7 | Defect language (`fix`, `bug`, `broken`, `regression`, `doesn't compile`, `tests fail`, `you missed`) + same touches + no rule above matched | player-defect | low |
| — | nothing matched | unattributed | — |

Rule 7 is deliberately **low** confidence, so its failure weight is 0.3 (§5.2). One vaguely worded repair costs a Player roughly a third of a failure, not a whole one.

### 8.4 Human burden

- **Dad Mode:** Dad is never asked. Zero added clicks.
- **Dev Mode:** a follow-up card shows `Cause: player-defect (rule 7, low)` with a one-tap chip row to correct it. A correction writes an `attribution` event with `source: 'coach'` and confidence high. The last event for a pair wins.
- **Envelope (optional, zero UI):** a `FIX CAUSE:` structured header field, parsed by the existing S56 envelope machinery as one more recognized dimension. `source: 'envelope'`, confidence high.

### 8.5 Bias safeguard

Unattributed repairs *withhold credit* instead of assigning blame, so a Player whose defects are phrased vaguely learns more slowly but is never framed. Dev Mode shows each node's `unattributedRate`. A high rate is a signal to improve rules or confirm causes, not a penalty.

## 9. Field Possession / Context Value Model

### 9.1 Tiers (derived from existing evidence only)

| Tier | Existing evidence | Base value |
|---|---|---|
| `active` | seat is currently working this Play's continuation (ledger `currentPlay`) | 1.00 (drives queue vs handoff, as today) |
| `owner-strong` | `resolveContextOwner` → owner, confidence strong (latest-play / explicit provenance) | 0.85 |
| `owner-medium` | owner, confidence medium (single-active-play attribution, wording follow-up) | 0.55 |
| `game-recent` | seat completed any Play in this Game with overlapping touches | 0.30 |
| `game-only` | seat worked this Game, no overlap | 0.10 |
| `none` | — | 0 |

### 9.2 Decay

```
possession(seat) = base(tier) · 0.5^(ageMin / halfLife) · continuity

halfLife   : 240 min (the owner is likely still holding a warm session)
continuity : 1.0 if the seat's controlled session is known to persist across Plays
             0.4 if the session is known to have restarted (the owner then holds only what the report says,
                 and a handoff preamble gives any sibling the same thing)
             0.7 UNKNOWN  (today's state: see the open fact in §18.3)
```

**Key insight:** after a session restart, the owner's advantage shrinks to what the report already carries, and the existing `buildHandoffPreamble` gives that to *anyone*. Decay is therefore mainly about **session continuity**, with clock time as a stand-in until continuity is observable.

### 9.3 Turning possession into economics

```
reacquisition(seat) = (maxPossession − possession(seat)) · reacq(taskClass) · burn_p50(target)

reacq prior: architecture 0.35 · implementation 0.25 · default 0.20 · quick 0.05
reacq is then learned from Film: median burn of `handoff`/non-owner Plays ÷ owner Plays among
comparable continuations (needs ≥ 8 per side; otherwise the prior is used).
```

Possession never *forces* a route. It shows up as a lower cost for owners, which Dev Mode itemizes.

### 9.4 Context receipts: not needed in V1

`resolveContextOwner` plus the ledger already provide tier and age. The one fact they lack is **session continuity**. If the open-fact check in §18.3 shows it is observable (for example a stable thread or session id on controlled transport), a later micro-Play adds a single field, `sessionEpoch`, to `LedgerPlay`. No separate receipt store is needed. Possession after a Control Plane restart falls back to the Film's most recent `decision` per seat and Game, with `continuity` = UNKNOWN.

### 9.5 Scout intelligence as shared possession

A Scout report delivered for this Game and topic is possession that **every** seat can use through the handoff preamble. It lowers `reacq` for all candidates by up to 50%, and it lowers the value of buying another Scout (§10).

## 10. Scout ROI Model

### 10.1 Scout tiers

| Tier | What | Cost basis | Reliability input |
|---|---|---|---|
| `existing-intel` | Fresh, uncontradicted Scout report already in this Game | 0 | report freshness (below) |
| `cheap-formation` | Free/cheap Scout Formation (current Scout lanes) | declared cost class (usually free) + delay | Combine runtime readiness × intel-quality prior 0.50 |
| `strong-scout` | Single stronger model Scout | its provider window price × burn | prior 0.65 |
| `a-team-reconciled` | Formation + A-Team reconciliation (the S57.0 pattern) | Formation + A-Team burn | prior 0.80 |

Combine Scorecards answer **"will this receiver run and follow the contract?"** (P_runs). Correctness of the intelligence (P_right) is a separate belief, learned only from `bad-scout-evidence` attributions and clean downstream premium Plays:

```
P_useful(tier) = P_runs(Combine) · P_right(tier)     // P_right: Beta(prior m, n₀=4) + Film
```

### 10.2 Net value

```
reconFraction = reconPrior(taskClass, difficulty)                    // hard architecture 0.30 · impl 0.20 · quick 0.05
              · (scoutNeed.materialEvidenceGap ? 1.3 : 1)
              · (1 − maxPossession)                                  // field already possessed → ~0
              · (existing-intel fresh ? 0.3 : 1)

savedBurn     = P_useful · reconFraction · burn_p50(primaryTarget)
gain          = λ_c · price(primary provider) · savedBurn
              + qualityLift                                          // +0.02·P_useful for hard/architecture, else 0
cost          = λ_c · scoutPriceCost + λ_d · urgencyMult · delayHours(tier) + harm
harm          = (1 − P_right) · 0.5 · reconFraction · C_play          // wrong intel wastes premium work

netValue = gain − cost
```

### 10.3 Decision rule

- **SCOUT FIRST** when `netValue > 0.02` (a stability margin) **and** urgency ≠ `now` **and** `maxPossession < 0.55`. The Scout option becomes `primary` only if its combined U (Scout then premium) beats direct `send`. Otherwise it appears as `scoutOption`.
- **NO SCOUT — FIELD ALREADY POSSESSED** is a reason code, emitted when `maxPossession ≥ 0.55` or a fresh `existing-intel` covers the topic.
- `scoutNeed.reconnaissancePrimary` (the Play *is* reconnaissance) keeps today's Scout routing path. ROI only governs *Scout-before-premium*.

### 10.4 Freshness and contradiction of Scout intelligence

- **Stale:** a file the Scout report cites (or any path in the Play's touches) changed since the report's `at` (git log on those paths). Also stale after 72 h regardless.
- **Contradicted:** any `bad-scout-evidence` attribution against it, or a later A-Team reconciliation marks its claims as rejected.
- Stale or contradicted intel is never `existing-intel`. It is shown in Dev Mode as "Scout packet on file — stale" and does not reduce `reacq`.

### 10.5 Worked example

Hard architecture Play, Opus, 5H burn p50 20%, price 1.0, BALANCED, no possession, cheap Formation (P_runs 0.9, P_right 0.5, delay 10 min):

savedBurn = 0.45 · 0.30 · 0.20 = 0.027 → gain ≈ 0.027 + 0.009 = 0.036
cost = 0 + 0.05 · 0.17 h ≈ 0.008 + harm 0.5 · 0.5 · 0.3 · 0.21 ≈ 0.016 → 0.024
net ≈ +0.012 → **no Scout** (below the 0.02 margin)

Now make Opus 5H scarce (price 3.0): gain ≈ 3·0.027 + 0.009 = 0.090. Harm scales with the pricier C_play (about 0.63), so harm ≈ 0.047 and cost ≈ 0.056. Net ≈ +0.034 → **SCOUT FIRST · saves scarce Claude 5H**. This is exactly the Play's thesis: *a cheap 10-minute Scout that protects a scarce premium window beats speed.*

## 11. Resource Economics Model

### 11.1 Pace pressure (capacity × time)

For provider *p* and window *w* with remaining fraction R, time to reset T and window length L (5H = 300 min, Weekly = 10 080 min):

```
π_w = (T / L) / max(R, 0.01)        // time left as a share of the window ÷ capacity left
      π < 1 → capacity outpaces time (spend; it may expire)
      π ≈ 1 → on pace
      π > 1 → scarce relative to time left
price_w = clamp(π_w, 0.05, 10)
```

**Dad's thresholds as a floor.** If ResourcePolicy says LOW/CRITICAL for window *w* **and** that scarcity persists through the Play (T_w > expected duration p50):
`price_w = max(price_w, 1.5 (LOW) | 4.0 (CRITICAL))`.
If the window resets during the Play, the floor does not apply to the pre-reset portion: Dad's threshold describes a window that is about to end.

**Split at reset.** For expected duration d and burn b:

```
pre  = b · min(1, T/d)          charged at price_w
post = b − pre                  charged at fresh-window price 1.0
```

### 11.2 Cost and interrupt risk

```
C_play(p)   = Σ_w [price_w·pre_w + 1.0·post_w]  +  reacquisition        // §9
interrupt_p = P(burn_5h,pre > R_5h) from the BurnEstimate range (p75 > R → 0.5, p50 > R → 0.9)
```

`interrupt` feeds *Risk*, and when high it proposes the wait option.

### 11.3 The Play's example, worked

- **A** (Codex): 5H R 0.95, T 240 min → π 0.84. Weekly R 0.15, T 4 d → π = (0.571/0.15) = 3.8 (Weekly LOW → floor 1.5, stays 3.8).
- **B** (Claude): 5H R 0.25, T 10 min → π 0.13. Weekly R 0.60, T 2 d → π 0.48.

A Play expected to burn 12% 5H and 3% Weekly over 30 min:

- **A:** 0.84·0.12 + 3.8·0.03 = 0.101 + 0.114 = **0.215**
- **B:** pre = 0.12·(10/30) = 0.04 < R 0.25 (no interrupt) → 0.13·0.04 + 1.0·0.08 + 0.48·0.03 = 0.005 + 0.080 + 0.014 = **0.099**

**B is less than half the economic cost** despite its 25% gauge. "Highest percentage wins" would have picked A.

### 11.4 Cross-provider comparability (a stated assumption)

Each provider's windows are priced in *pressure-weighted fractions of its own budget*. Comparing Claude against Codex this way assumes Dad values "a scarce slice of either subscription" about equally. The assumption is surfaced in Dev Mode and can later be tuned per provider (`providerValueWeight`, default 1.0) if Dad disagrees.

### 11.5 Providers without resource truth

`AlarmProvider` is `'claude' | 'codex'` only (verified), so AntiGravity, OpenRouter Scouts and others have **no canonical resource facts**. Their price is `UNKNOWN`, handled by §18. A Coach-declared `costClass` (`free`, `metered`, `subscription-unknown`) may say *what kind* of cost exists. It is a declared fact, never a percentage.

### 11.6 Urgency and waiting

Covered by λ_d (§5.4) and the wait option (§15). Weekly-reset waits are considered only under CONSERVE and never for `now`.

### 11.7 Play-level cost estimation (approximation, never causality)

**Observation.** At dispatch and at completion, the Film stores receipts for the chosen provider's windows. The observed burn is `Δ_w = R_before − R_after`, graded for **isolation**:

| Grade | Conditions |
|---|---|
| `high` | same reset cycle (`resetsAt` unchanged) · before-receipt observed ≤ 15 min before dispatch · after-receipt observed after completion and ≤ 15 min later · no other same-provider seat working during the Play (ledger) |
| `medium` | as high, but the receipt brackets are loose (≤ 45 min) |
| `low` | concurrent same-provider work overlapped; Δ split pro rata by overlapping duration, flagged |
| `none` | reset crossed · either receipt stale/missing · Δ < 0 · Δ above 3× the comparable p75 (possible external/out-of-band usage) |

`none` observations are kept for audit and never used for estimation. Δ = 0 at provider percent resolution is recorded as censored `≤ 1%` (§18.3).

**Estimation for a new Play:**

```
comparable set = Film observations with isolation ∈ {high, medium}, same target node or pooled per §5.3, weighted per §5.2
log-burn mean  μ = (n₀·log(prior p50) + Σ w_i·log Δ_i) / (n₀ + Σ w_i)       // shrinkage on the log scale
range          = p25/p75 from weighted empirical quantiles when Σw ≥ 5, else the prior range widened by 1.5×
confidence     = high (Σw ≥ 15 and ≥ 50% high-isolation) · medium (Σw ≥ 5) · low (otherwise) · unknown (no prior either)
```

**Presentation.** Always a range with a confidence word (`~8–15% of Claude 5H · medium`). Never "this Play cost 11%." Attribution is associative: *"Plays like this have typically used …"*.

**Later (not V1):** a daily non-negative least-squares fit of window Δ against the Play mix could de-confound concurrent work. It stays out of V1 because it is harder to explain than it is worth at low volume.

## 12. Recommendation / Confidence Semantics

### 12.1 Three quantities, never blended

| Quantity | Meaning | Values | When shown |
|---|---|---|---|
| **Recommendation Strength** | How clearly the primary beats the next best, given uncertainty | `clear` (Δ > 2σ_Δ) · `lean` (Δ > 0.5σ_Δ) · `toss-up` | always (Dad sees a word) |
| **Evidence Strength** | How much *local* film supports the belief | `prior-only` (nLocalEff = 0) · `thin` (< 5) · `building` (5–20) · `established` (≥ 20) | Dad sees it only when `prior-only`/`thin`; Dev always |
| **Calibrated Confidence** | P(first-pass acceptance) for this target on Plays like this | a percentage | **only after graduation** for that task class |

`Δ = U₁ − U₂`. `σ_Δ` is combined from the Beta variances of q₁, q₂ and the burn ranges (a first-order propagation; no simulation).

### 12.2 What "Codex · 91%" will mean

After graduation, and only then: **"Sideline estimates a 91% chance Codex finishes this kind of Play with no Player-caused repair."** It is a statement about Codex on this Play, not about "fit" and not a ranking score. Until graduation, Dad sees **words** (`Codex · Strong pick`). A percent is never shown before calibration earns it.

### 12.3 Graduation gate (per task class, computed from shadow film)

- ≥ 30 resolved (non-pending, non-excluded) outcomes in the class across all targets
- 3-bin reliability check: each bin's observed rate within ±10 pp of mean predicted
- Brier score beats the base-rate predictor (the class's pooled first-pass rate)
- recomputed weekly; a class that fails later *un-graduates* back to words

Graduation is reported in Dev Mode. Dad sees the percent appear with no ceremony.

## 14. AUTO / MANUAL / CONSERVE Relationship

These are **three different dimensions**. Only one of them is a Coach "mode."

| Dimension | Question | Values | Owner | Changes |
|---|---|---|---|---|
| **Authority** | *Who chooses the route?* | MANUAL (Coach picks exact) · AUTO (Sideline picks unconstrained dimensions) · per-Play envelope locks individual dimensions | Coach (`routingMode`, envelope) | Candidate set and whether advice can act |
| **Posture** | *What does "best" mean?* | FAST · BALANCED · SURE · CONSERVE | Coach preference (default BALANCED); optional per-Play `POSTURE:` envelope field | Utility weights (§5.4) |
| **Scarcity** | *How scarce is capacity right now?* | none · low · critical (+UNKNOWN) | ResourcePolicy (Dad's thresholds) | Prices (§11), never weights |

Consequences:

- **CONSERVE posture ≠ scarcity.** Posture CONSERVE means "I'd rather wait or use cheaper Players even when nothing is scarce." Scarcity LOW means "Dad's threshold for this window has been crossed." Under BALANCED, scarcity already raises prices through the floor, so BALANCED *automatically behaves thriftier* when resources are scarce without switching posture. Posture is never auto-switched.
- **Naming:** keep Stage 2A's `isConserveActive`/`conserveLevel` untouched (it is a stable contract). In routing vocabulary and UI, the fact is called **Scarcity**. **CONSERVE** is reserved for the posture. Dev Mode shows `Posture: BALANCED · Scarcity: Claude Weekly LOW`.
- **SURE** replaces "SAFE", so it doesn't collide with safety/sandbox language. It means "maximize the lower bound."
- **MANUAL + recommendation:** computed in shadow, logged, invisible in Dad Mode. **Dad's explicit routing always wins.** Dev Mode may show "Sideline would have picked …" as information only.

## 15. Schedule-After-Reset Architecture

### 15.1 Decision: separate `DeferredPlay` store plus a thin scheduler that feeds the normal router

Why not extend PlayQueue:

1. PlayQueue items are **locked to an instance** and drain on **instance completion**. Deferred intent is keyed to a **provider window condition**, and its target seat may not exist after the reset.
2. PlayQueue's restart semantics (`dispatching → needs-attention`) are tuned for concurrency. Deferred intent needs "condition passed while down → re-validate" semantics.
3. Keeping them separate means each queue answers exactly one question.

### 15.2 Types

```ts
interface DeferredPlay {                      // durable: ~/.sideline/deferred-plays.json (atomic write)
  id: string; gameId: string; createdAt: number;
  prompt: string;                             // must be held to run later (same as QueuedPlay)
  target: RouteTarget; seat?: string;
  constraints?: RouteConstraints;
  condition: { kind: 'reset'; provider: 'claude'|'codex'; window: 'five_hour'|'weekly';
               cycleResetsAt: number;          // the horizon this intent waits for
               notBefore?: number };
  armedBy: 'coach';                           // V1: only a Coach click arms one
  recommendationId: string;
  state: 'waiting' | 'firing' | 'handed-off' | 'needs-attention' | 'cancelled';
  attention?: string;
}
```

### 15.3 Firing

- **Primary trigger:** AlarmEngine `alarm:reset_boundary_reached` (or `alarm:recovered`) for `(provider, window)` with a new horizon > `cycleResetsAt`.
- **Fallback:** a timer at `cycleResetsAt + 2 min` (events can be missed), plus a check on startup.

On trigger, **re-validate before acting**:

1. Fresh `RoutingEconomicsSnapshot` shows the window's `remainingPercent` recovered and not stale.
2. The target seat (or an equivalent seat of the same target) is operable.
3. The Coach hasn't cancelled.

- If all three pass: hand the Play to `router.routePlay` with the stored target as an explicit constraint and `whenBusy: 'queue'`. It is now ordinary routed work (PlayQueue included).
- If any check fails: `needs-attention` with one Dadified sentence (`"Claude's 5H reset couldn't be confirmed — still waiting for your call."`). **Never substitute a different Player.**

### 15.4 V1 authority

Firing a deferred Play is **executing the Coach's armed intent**, not acting on a recommendation, so it respects invariant 9. Only a Coach click (`SCHEDULE`) creates one.

### 15.5 When the wait option is generated

- 5H: the primary's provider has T_5h ≤ 90 min, and either interrupt risk ≥ 0.5 or waiting improves U by ≥ 0.02.
- Weekly: only under CONSERVE, urgency ≠ now, T_wk ≤ 36 h.

## 18. Unknown / Stale Evidence Behavior

### 18.1 The rule

UNKNOWN is a first-class value that travels all the way to the output. It is never coerced to 0, 100%, "cheap" or "expensive."

| Situation | Treatment in scoring | Shown |
|---|---|---|
| Resource fact stale/missing (`stale: true` or `evidenceState: 'unknown'`) | price = `'unknown'`. U uses neutral price 1.0 **plus** `Risk += 0.1`. CONSERVE ranks it after known-cheap options but does not exclude it | Dev: `price unknown (stale 42 min)`. Dad: `RESOURCE_UNKNOWN` subline only if it's the headline |
| Provider with no resource truth (AntiGravity, Scouts) | same as above; `costClass` may annotate | Dev only |
| Fact and policy disagree (fact below threshold, policy still NORMAL between evaluations) | **policy verdict wins** for floors; `policyLag: true` noted. No second threshold evaluation | Dev |
| No prior and no local film | baseline-preference prior (§6.2), evidence `prior-only` | Dad: `Early pick · still learning` |
| Burn estimate lacks isolated comparables | prior range, confidence `low` | Dev |
| Possession continuity unknown | continuity 0.7, labeled | Dev |
| Scout intel freshness unknown (no cited paths) | treated as stale after 24 h | Dev |
| Attribution pending | contributes nothing | Dev |

### 18.2 Never

- display a percentage for UNKNOWN
- recommend `wait-for-reset` against an UNKNOWN horizon
- let a stale receipt from the Film stand in for current state

### 18.3 Open facts (bounded; none block the architecture)

1. **Session continuity on controlled transport:** does a controlled Claude/Codex seat keep the same provider session or thread across Plays? This decides whether `sessionEpoch` is observable (§9.4). Smallest seam: the controlled-player session/turn start path under `src/player-control/`. Until it's checked, continuity is UNKNOWN (0.7).
2. **Quantization of provider usage percent:** if providers report integer percents, a small Play shows Δ = 0. Handled generically: Δ = 0 is recorded as `≤ 1%` (censored) and excluded from medians but counted in "small Play" frequency.
3. **Play completion hook location:** the Worker in R2 locates the exact ledger completion call site for the Film `outcome` event. This is an implementation detail, not an architecture question.

## 19. Shadow Mode

### 19.1 What runs

From stage R6, `recommendRoute()` runs on every **dispatched** Play: AUTO, MANUAL, envelope-locked and Scout. It runs after the existing router has produced its decision. It changes nothing. It appends one `decision` event.

### 19.2 What's logged

`recommendation` (digest), `baseline` (static AUTO), `chosen`, `decidedBy`, strengths, possession, `receiptBefore`. Later events: `outcome`, `link`, `attribution`, `resolution`.

### 19.3 What's measured (Dev shadow report)

| Metric | Definition | Honest caveat |
|---|---|---|
| Agreement | share of Plays where primary target = chosen target | — |
| Disagreement outcome | first-pass rate of chosen routes when rec ≠ chosen vs = chosen | selection-biased; shown with n |
| Calibration | reliability bins of `firstPass.mean` vs resolved outcome **for chosen routes only** | only chosen routes have outcomes |
| Burn prediction error | predicted p50 vs observed Δ on `high`/`medium` isolation Plays | isolation-limited |
| Scout ROI check | premium burn on Scouted vs non-Scouted comparable Plays | observational, confounded; labeled so |

**Counterfactual honesty:** unchosen alternatives are recorded as `unobserved`. The report never states "Codex would have succeeded." V1 attempts no off-policy estimation (there are no randomized propensities, and there should be none; Dad's Plays are not experiments).

### 19.4 Exit criteria for leaving shadow (advisory chip, R8)

≥ 50 dispatched Plays logged, burn-error median within ±50% on isolated Plays, and no invariant-test regressions. A calibrated **percent** has its own gate (§12.3).

## 21. Test Strategy

All engine code is pure with an injected clock, so almost everything is a table test.

- **Golden examples:** §11.3 (A vs B → B cheaper), §10.5 (scout flips from no to yes as price rises), §6.2 takeover curve (n = 0, 5, 20).
- **Property and monotonicity tests:**
  - more remaining R → price never increases
  - later reset T → price never decreases
  - adding a clean success never lowers `firstPass.mean`
  - adding an `unattributed` repair changes nothing
  - raising possession never raises reacquisition
  - the CONSERVE posture never ranks a strictly more expensive, equal-q option higher
- **Invariant tests (must-never):**
  - explicit/MANUAL route → recommendation `advisoryOnly`, decision byte-identical to pre-engine
  - UNKNOWN resource → no percent anywhere in the Dad view
  - preview calls → zero Film writes
  - Film write failure → dispatch still succeeds
  - the recommendation never mutates the `RoutingDecision`
  - a Film receipt is never an economics input
- **Replay tests:** a fixture Film (hand-built, about 40 events) → exact belief snapshot. Changing `weightsVersion` must change the stamped version.
- **Refactor guard (R4):** the existing routing suite plus a golden corpus of about 50 recorded prompts and candidate sets → identical decisions.
- **Attribution rules:** a positive and a near-miss negative per rule; ordering test (rule 1 beats rule 7).
- **Scheduler (R9):** fake timers and fake alarm events — fire-on-event, fire-on-fallback, restart with condition already passed, stale evidence → needs-attention, target missing → needs-attention (no substitution).
- **Dad copy snapshots:** every `ReasonCode` template stays within its length limit.

## 22. Future Automation Breadcrumbs

The same `RoutingRecommendation` feeds every future consumer. There are exactly **three attachment seams**:

1. **`PolicyGate.evaluate(rec, policy, now) → { verdict: 'act' | 'ask-coach' | 'hold'; reason }`**
   Policy is Dad-configured (for example "act automatically when strength = clear, task class graduated, calibrated ≥ 85%, posture ≠ SURE, no UNKNOWN in the primary's windows"). V1 has no gate: every path is `ask-coach`.
2. **`optionToDecision(rec, option, ctx)`**
   The single bridge from advice to an executable `RoutingDecision` or `DeferredPlayIntent`. Coach clicks use it in V1, and the gate uses it later. There is no other conversion path.
3. **`DeferredPlay` trigger**
   Its fire step already re-validates. Future autonomy routes the fire through `PolicyGate` instead of `armedBy: 'coach'`.

**AUTO cutover (a separate Play after shadow):** `computeContextAwareRoute` takes its ranking from `rec.primary` instead of `PROVIDER_PREFERENCE`. Choosing AUTO mode *is* Dad's policy opt-in. At that point the static table survives only as the baseline prior (§6.2), and there is **one brain**. The Film's `decidedBy` gains `'policy-gate'`/`'auto-engine'`, so shadow analysis continues unbroken across the cutover.

What must stay true for this to work:

- `recommendRoute` stays pure and never checks "am I in V1 or autonomous mode." Mode lives only in the gate.
- Consumers never re-rank. If a consumer needs a different answer, it changes the posture or constraints and calls `recommendRoute` again.
- Every automated action writes the same `decision` event a Coach click would. Game film does not care who pressed SEND.
