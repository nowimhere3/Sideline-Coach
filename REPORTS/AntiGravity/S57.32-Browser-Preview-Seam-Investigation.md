## 1. EXECUTIVE VERDICT

### Scout Claim Adjudication: **OVERSTATED / PARTIALLY CONFIRMED WITH CORRECTIONS**

The Scout Formation summarized the feasibility of browser preview as **"SUPPORTED WITH SMALL SEAM"**. Against current repository truth, that conclusion is **overstated** because the Scouts suffered from a fundamental category error: **they investigated framing Sideline Coach's own web UI (`src/public/index.html`) rather than discovering and previewing the *Game web application* (the user's project running on Vite, Next.js, Create React App, etc.)**.

When re-evaluated against the true product goal—*Dad clicks "Preview in Browser" to see the web application being developed in that Game workspace*—the architectural seams divide sharply into two distinct phases:

1. **Local Preview (Desktop, Tablet, Phone):** **CONFIRMED WITH SMALL SEAM.**  
   Local preview requires **no daemon HTTP proxy**, **no relay traversal**, and **no complex HTML rewriting**. Because Dad and the running Game dev server reside on the same local environment, the local browser (or a lightweight Sideline multi-viewport shell) can reach the dev server directly. VS Code already provides the exact native API (`vscode.env.asExternalUri`) needed to bridge local, WSL, SSH, and GitHub Codespaces port mapping cleanly.
2. **Remote / Phone Preview (Send to Phone via Relay):** **OVERSTATED / MATERIAL ARCHITECTURAL RISK.**  
   Proxying arbitrary local dev servers through the Sideline Control Plane daemon and across the remote relay (`h-<hostId>.<relayDomain>`) introduces substantial security hazards (SSRF, arbitrary localhost exposure) and severe runtime breakage (dev-server `Host` header rejections, root-relative `/` asset 404s, WebSocket/HMR disconnects, and CSP/CORS blocks). Remote preview cannot be treated as a trivial proxy seam.

> [!IMPORTANT]
> **COACH REVIEW REQUIRED:**  
> The core architectural boundary decision is whether **V1 should strictly deliver Local Preview** (Desktop/Tablet/Phone views rendered locally or in system browser via `asExternalUri`), while **deferring Remote Relay Proxying to V2** where a dedicated, encrypted per-port tunnel architecture can be formally specified.

## 4. WHAT THE SCOUTS GOT WRONG / OVERSTATED

1. **The Core Target Confusion (The Grand Category Error):**  
   The Scouts repeatedly discussed serving and framing `src/public/index.html`. They conflated *viewing the Sideline Coach control plane dashboard* with *viewing the running web project that the user is building*. Dad does not need a "preview" of Sideline Coach; Dad needs to see the React/Vite/Next app running in the Game workspace.
2. **"Small Seam" HTTP Reverse Proxy Fallacy:**  
   The Scouts proposed that the daemon could trivially expose a Game preview by mounting an HTTP proxy at `/preview/:gameId/`. This completely ignores fundamental web application constraints:
   - **Modern Dev Server Host Checks:** Vite, Webpack Dev Server, and Next.js explicitly block requests whose `Host` header does not match `localhost` (DNS rebinding protection). Passing remote relay hosts causes immediate `403 Invalid Host header`.
   - **Root-Relative Asset Resolution:** Web bundlers emit absolute root paths (e.g., `<script src="/src/main.tsx">`, `href="/assets/style.css"`). Under a subpath proxy (`/preview/123/`), all asset requests hit `/src/main.tsx` on the daemon, resulting in instant 404 failure unless complex, fragile HTML/JS rewriting is introduced.
   - **Hot Module Replacement (HMR) WebSockets:** Vite and Next.js rely on dedicated WebSocket channels for live reload (`ws://localhost:5173/`). A naive HTTP proxy does not tunnel or rewrite HMR sockets.
3. **Unnecessary Daemon Proxy for Local Preview:**  
   The Scouts assumed all preview traffic must flow through the Control Plane daemon. For local desktop development, this is completely unnecessary. The user's browser is on the same machine as the dev server; connecting directly to `http://localhost:<port>` is faster, safer, and preserves all dev-server semantics without proxy overhead.

## 5. CANONICAL PREVIEW ENDPOINT MODEL

The canonical preview representation must bind directly to the existing `GameStadiumBinding`. Because a Game might be opened across different Stadiums, or run different dev servers over time, the identity belongs to the **Game in an active Stadium session**.

```typescript
export type PreviewProtocol = 'http' | 'https';
export type PreviewSource = 'declared' | 'detected-port' | 'package-script' | 'manual';
export type PreviewStatus = 'active' | 'stale' | 'offline';

export interface PreviewEndpoint {
  readonly previewId: string;
  readonly gameId: string;
  readonly stadiumId: string;
  
  /** The direct local loopback address (e.g., "http://127.0.0.1:5173"). */
  readonly localUrl: string;
  
  /** 
   * External resolved URI via vscode.env.asExternalUri.
   * On Codespaces or Remote SSH, this is the public forwarded HTTPS URL.
   */
  readonly externalUrl?: string;
  
  readonly port: number;
  readonly protocol: PreviewProtocol;
  readonly source: PreviewSource;
  readonly label?: string;              // e.g., "Vite Dev Server", "Next.js"
  readonly observedAt: number;
  readonly status: PreviewStatus;
}
```

### Discovery Hierarchy (Deterministic Truth Over Heuristics)
To discover this endpoint without burdening Dad with technical trivia:

1. **Level 1 — Native VS Code Port Forwarding (Most Deterministic):**  
   VS Code tracks active listening ports from integrated terminals. The Stadium extension can inspect forwarded ports or listen to `vscode.workspace.onDidChangePortAttributes`.
2. **Level 2 — Package Manifest Inspection (`package.json`):**  
   Read `package.json` in `rootFsPath`. Common scripts (`vite` -> default 5173, `next dev` -> default 3000, `react-scripts start` -> default 3000) establish high-confidence candidate ports.
3. **Level 3 — Explicit Configuration Fallback:**  
   Allow an optional property in Game settings or `.sideline/game.json` (e.g. `"previewPort": 5173` or `"previewUrl": "http://localhost:5173"`).
4. **Level 4 — Stadium Health Probe:**  
   Before announcing an endpoint as `active`, the Stadium issues a lightweight HTTP `HEAD` or `GET` request to `http://127.0.0.1:<port>`. If refused, the endpoint is marked `offline`.

## 7. REMOTE / PHONE PREVIEW ARCHITECTURE

### The Threat of "Send to Phone" via Remote Relay
The Scouts envisioned using the existing Sideline remote relay (`h-<hostId>.<relayDomain>`) to proxy Game traffic directly to a mobile device.

While attractive, this creates significant technical blockers:
1. **SSRF & Host Security:** A daemon that accepts incoming HTTP paths and forwards them to `127.0.0.1:<targetPort>` creates a potent Server-Side Request Forgery vulnerability. If an unconstrained port parameter is accepted, any paired phone (or stolen token) could probe sensitive host services:
   - Control Plane internal daemon (port 3100)
   - PostgreSQL / MySQL (5432 / 3306)
   - Redis / Docker / cloud metadata (6379 / 2375 / 169.254.169.254)
2. **Dev Server Host Header Rejection:** Modern dev servers reject requests where `Host` is not `localhost` or `127.0.0.1`.
3. **Subpath Asset Collisions:** Serving a Game preview under `https://h-xyz.relay.domain/preview/game-123/` breaks all scripts requesting `/assets/...`.

### The Safe Remote Architectures
If remote phone preview is desired, it must follow one of two safe paths:
- **Path 1 — Direct Tailscale / Cloudflare Tunnel (Recommended for Dad):**  
  If Dad uses `coach.publicUrl` (Tailscale Funnel or Cloudflare Tunnel), the Game dev server itself is bound to the local network or assigned its own tunnel port/subdomain.
- **Path 2 — Isolated Stadium Proxy with Strict Allowlisting:**  
  The Control Plane proxies traffic **only** for registered `PreviewEndpoint` ports whose status is actively confirmed by the Stadium, strictly rewrites the `Host` header to `127.0.0.1:<port>`, and terminates requests outside the active allowlist with `403 Forbidden`.

> [!WARNING]
> Due to the complexity of root-relative asset rewriting and HMR WebSockets over relays, **Remote Relay Preview should be excluded from V1**.

## 9. SECURITY BOUNDARY & THREAT MODEL

```mermaid
flowchart TD
    subgraph Untrusted / Remote
        Phone[Phone Browser]
        Attacker[Compromised Device / Token]
    end

    subgraph Sideline Trust Boundary
        Daemon[Control Plane Daemon]
        AuthGuard[Auth Guard & Token Check]
        Allowlist[Strict Port Allowlist]
    end

    subgraph Host Localhost Services
        GameServer["Target Game Server (e.g. Vite 5173)"]
        PrivateDaemon["Sideline Daemon Internal (3100)"]
        InternalDB["Local Databases / Redis (5432, 6379)"]
    end

    Phone --> AuthGuard
    Attacker --> AuthGuard
    AuthGuard --> Allowlist
    Allowlist -->|Port == 5173 (Registered)| GameServer
    Allowlist -.->|BLOCKED: Port 3100| PrivateDaemon
    Allowlist -.->|BLOCKED: Port 5432| InternalDB
```

### Essential Security Invariants
1. **Strict Port Allowlist:**  
   The daemon must NEVER accept arbitrary ports in preview URLs. Only ports actively registered in an active `PreviewEndpoint` from a connected Stadium are reachable.
2. **Private Port Denylist:**  
   Hardcoded block on ports `3100` (Control Plane), `49152+` (dynamic test ports), and known database ports (`5432`, `3306`, `27017`, `6379`).
3. **Iframe Sandboxing:**  
   If the preview is embedded inside a Sideline web view, the iframe must include:
   ```html
   <iframe sandbox="allow-scripts allow-forms allow-same-origin allow-popups" ... />
   ```
   Crucially, the iframe must run under a separate origin or loopback port to prevent Game scripts from accessing Sideline Coach cookies, localStorage, or SSE tokens.
4. **Stale Port Purging:**  
   When a Stadium disconnects or a Game changes, all registered `PreviewEndpoint` records for that Stadium are immediately revoked.

## 10. SMALLEST MISSING SEAM

The smallest safe implementation consists of 4 focused steps:

```text
[Stadium: extension.ts]
   │  1. Detect dev port / script
   │  2. Resolve via vscode.env.asExternalUri
   ▼
[stadium.hello / game.preview.changed]
   │  3. Propagate stadiumType & PreviewEndpoint
   ▼
[Control Plane / UI]
   │  4. Render [ Preview in Browser ] button & Viewport Shell
```

1. **Protocol Propagation (`stadiumType`):**  
   Add `stadiumType: StadiumType` to `StadiumHelloParams` in `src/control-plane/protocol.ts` and pass `ctx.stadium.stadiumType` in `src/stadium-client.ts` (`sendHello`).
2. **Stadium Endpoint Discovery:**  
   In `src/extension.ts`, inspect active terminal commands / `package.json` dev scripts, resolve the port via `vscode.env.asExternalUri`, and send a `game.preview.snapshot` notification to the Control Plane.
3. **Control Plane Registry Storage:**  
   Store `previewEndpoint?: PreviewEndpoint` on `StadiumSession` in `src/control-plane/stadium-registry.ts`.
4. **Preview Actuator & Shell:**  
   Expose `[ Preview in Browser ]` in the Coach web UI / status bar. Clicking opens the responsive viewport shell or fires `openExternal`.

## 12. WHAT SHOULD WAIT FOR V2

- **Send Preview to Phone via Remote Relay:** Proxying through the relay requires dedicated subdomain isolation or tunnel multiplexing to avoid root-relative path breaking and SSRF.
- **Autonomous Dev Server Lifecycle:** Coach automatically starting `npm run dev` if no server is running. (In V1, Dad or an AI Player starts the dev server in the terminal).
- **Simultaneous Multi-Device Mirroring:** Synchronizing clicks and scroll events across Desktop, Tablet, and Phone simultaneously (e.g. BrowserSync style).
- **Subpath HTTP Reverse Proxy in Daemon:** Unnecessary for local preview and dangerous without extensive URL rewriting.
