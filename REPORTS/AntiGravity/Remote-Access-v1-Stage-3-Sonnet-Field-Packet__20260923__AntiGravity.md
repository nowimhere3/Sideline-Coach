### 1. WIRE FRAME OWNERSHIP & CANONICAL SCHEMA

* **Decision:** Create ONE canonical contract file: `src/control-plane/relay-frames.ts`.
* **Rationale:** Avoids wire schema drift between `RelayClient` and the reference relay (`relay/reference-relay.ts`). Re-exports or aligns existing `FrameReq` and `FrameRes` in `src/control-plane/remote-dispatch.ts` so Stage 2 callers and tests remain 100% backward compatible without duplicating interfaces.
* **Exact Wire Definitions:**
  ```ts
  // --- Relay → Host Frames ---
  export interface RelayChallengeFrame {
    t: 'challenge';
    nonce: string; // 32-byte base64url random nonce
  }

  export interface RelayReqFrame {
    t: 'req';
    id: string; // crypto.randomUUID() generated by relay
    method: string; // GET, POST, etc.
    path: string; // Path and query string (e.g. /api/status?v=1)
    headers: Record<string, string>; // Strict 7-header allowlist only
    body?: string; // UTF-8 payload (<= 1 MiB)
    bodyB64?: string; // Optional binary payload representation
  }

  export interface RelayCancelFrame {
    t: 'cancel';
    id: string; // Request ID to abort
  }

  export interface RelayPingFrame {
    t: 'ping';
    ts: number; // Relay epoch ms timestamp
  }

  export interface RelayGoAwayFrame {
    t: 'goaway';
    reason: string; // e.g. 'superseded' | 'shutdown' | 'protocol_error'
  }

  export type RelayToHostFrame =
    | RelayChallengeFrame
    | RelayReqFrame
    | RelayCancelFrame
    | RelayPingFrame
    | RelayGoAwayFrame;

  // --- Host → Relay Frames ---
  export interface HostHelloFrame {
    t: 'hello';
    v: 1;
    hostPublicId: string; // 20-char lowercase base32
    publicKey: string; // 64-char lowercase hex (raw 32-byte Ed25519 public key)
    sig: string; // base64url Ed25519 signature over raw binary nonce
    client: string; // 'sideline/1.0'
  }

  export interface HostHeadFrame {
    t: 'head';
    id: string;
    status: number;
    headers: Record<string, string>;
  }

  export interface HostDataFrame {
    t: 'data';
    id: string;
    chunk?: string;
    chunkB64?: string;
  }

  export interface HostEndFrame {
    t: 'end';
    id: string;
  }

  export interface HostErrorFrame {
    t: 'error';
    id: string;
    code: string;
  }

  export interface HostPongFrame {
    t: 'pong';
    ts: number; // Echoes the ping timestamp
  }

  export type HostToRelayFrame =
    | HostHelloFrame
    | HostHeadFrame
    | HostDataFrame
    | HostEndFrame
    | HostErrorFrame
    | HostPongFrame;

  export type TunnelFrame = RelayToHostFrame | HostToRelayFrame;
  ```
* **Adapter Integration:** In `src/control-plane/remote-dispatch.ts`, type `FrameReq` as `RelayReqFrame` (or alias with identical shape) and `FrameRes` as `HostHeadFrame | HostDataFrame | HostEndFrame | HostErrorFrame`.

### 2. HEADER ALLOWLIST

* **Decision:** Replace the denylist in `src/control-plane/remote-dispatch.ts` with the strict 7-header ALLOWLIST mandated by ADR D3:
  1. `accept`
  2. `content-type`
  3. `cookie`
  4. `origin`
  5. `x-sideline-action`
  6. `last-event-id`
  7. `user-agent`
* **Defense in Depth & Authority:**
  * **Relay Layer:** When receiving browser requests, the relay filters incoming headers against this exact 7-header allowlist before serializing into the `RelayReqFrame`.
  * **Host Layer (Authoritative):** The host's `InProcessRemoteAdapter` re-enforces the exact same 7-header allowlist, lowercases all header names, and discards all others. The host **never** trusts the relay to have sanitized headers.
  * **Credentials Dropped:** `authorization`, `proxy-authorization`, and any header not on the allowlist are stripped at the relay AND rejected by the adapter. In addition, `daemon.ts` ignores `?token=` and `Authorization` for any `remote-device` principal.

### 3. COOKIE FLOW

* **Decision:** `cookie` is permitted through the allowlist strictly to transport `sl_dev`.
* **Exact Pipeline:**
  1. The browser sends `Cookie: sl_dev=<raw-device-token>`.
  2. Relay includes `cookie` in `RelayReqFrame.headers`. Relay **never** parses, validates, modifies, or stores `sl_dev`. To the relay, it is an opaque string.
  3. `InProcessRemoteAdapter` parses `sl_dev` from `frame.headers.cookie` via `parseCookies()`.
  4. Adapter calls `this.options.deviceRegistry.authenticate(rawToken)`.
  5. If valid, adapter mints `Principal { kind: 'remote-device', deviceId, authenticatedBy: 'in-process', expectedOrigin }`.
  6. **Crucial Isolation:** The adapter strips `cookie` before handing `req` to `daemon.dispatchRemoteRequest()`. The internal daemon route handlers never see `sl_dev`.
  7. When response headers are formatted, the adapter attaches `Set-Cookie: sl_dev=<raw-device-token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000` to slide the 30-day session window.

### 6. ED25519 CHALLENGE / HELLO SPECIFICATION

* **Nonce:**
  * Length: Exactly 32 bytes (256 bits) from `crypto.randomBytes(32)`.
  * Encoding: `base64url` string.
  * Lifetime: 30 seconds. Relay stores active nonces in a `Map<WebSocket, { nonce: string; expiresAt: number }>`.
  * Single-Use: Nonce is immediately deleted from the map upon receipt of a `hello` frame (whether valid or invalid). Replay is physically impossible.
* **Signing Contract:**
  * The host signs the **raw 32 bytes** decoded from the base64url nonce:
    `const rawNonce = Buffer.from(frame.nonce, 'base64url');`
    `const sig = crypto.sign(null, rawNonce, hostIdentity.privateKey).toString('base64url');`
* **Public Key Encoding:**
  * 64-character lowercase hex string (`publicKeyHex`), exactly matching `StoredHostKey.publicKeyHex`.
* **Signature Encoding:**
  * `base64url` string of the 64-byte Ed25519 signature.
* **Verification Procedure (Relay):**
  1. Retrieve and delete pending challenge for this socket. If absent or `Date.now() > expiresAt`, terminate with `goaway` / close code `4401`.
  2. Verify `publicKey` matches `/^[0-9a-f]{64}$/`.
  3. Verify `deriveHostPublicId(Buffer.from(publicKey, 'hex')) === hostPublicId`. If mismatch, terminate with close code `4403`.
  4. Import public key via JWK:
     ```ts
     const pubKey = crypto.createPublicKey({
       key: { kty: 'OKP', crv: 'Ed25519', x: Buffer.from(publicKey, 'hex').toString('base64url') },
       format: 'jwk'
     });
     ```
  5. Verify signature:
     ```ts
     const valid = crypto.verify(null, Buffer.from(nonce, 'base64url'), pubKey, Buffer.from(sig, 'base64url'));
     if (!valid) { ws.close(4403, 'Invalid signature'); return; }
     ```
  6. Register verified `hostPublicId → ws`.

### 7. DUPLICATE HOST CONNECTION POLICY

* **Decision:** **NEW CONNECTION SUPERSEDES OLD (Replace Policy)**.
* **Rationale:** Critical for daemon restart and crash-recovery reliability. If a daemon crashes or reloads, the old TCP connection may linger in half-open state. Rejecting the new connection would leave the desktop stranded and inaccessible.
* **Teardown Semantics:**
  1. If a newly authenticated `hello` presents a `hostPublicId` that already has an active socket:
  2. Relay sends `{ t: 'goaway', reason: 'superseded' }` to the OLD socket.
  3. Relay terminates old socket with close code `1000` (Normal Closure) or `4000` (Superseded).
  4. Relay cancels all active in-flight browser requests associated with the old socket (browser receives 503 `host_offline`).
  5. Relay binds the NEW socket to `hostPublicId`.

### 8. HEARTBEAT DIRECTION & TIMING

* **Decision:**
  * **Direction:** **RELAY SENDS `ping`**, **HOST REPLIES `pong`**.
  * Relay sends `{ t: 'ping', ts: Date.now() }` every 20 seconds.
  * Host immediately responds with `{ t: 'pong', ts: frame.ts }` echoing the timestamp.
* **Missed Heartbeat Threshold:**
  * Relay tracks `lastPongReceivedAt`. If 40 seconds (2 intervals) elapse without a valid pong, relay closes socket with code `4008` (Policy Violation / Timeout).
  * Host Watchdog: If host receives no frame (or ping) from relay for 60 seconds (3 missed intervals), host closes socket and triggers reconnect backoff.
* **SSE Interaction:** SSE `: hb` comment every 15s (`daemon.ts:3318`) is an independent application-level keepalive for the phone browser. WSS ping/pong is the transport-level keepalive between daemon and relay. They operate independently.

---

### 9. RECONNECT & BACKOFF SCHEDULE

* **Schedule:** Base delays: `1, 2, 5, 10, 30` seconds (capped at 30s).
* **Jitter:** `±20%` uniform random jitter: `actualDelay = baseDelay * (0.8 + 0.4 * Math.random())`.
* **Counter Reset:** Attempt counter resets to 0 upon successful completion of the `hello` handshake.
* **Intentional Shutdown:** Calling `RelayClient.stop()` cancels backoff timers, closes WSS with code `1000`, and will NOT reconnect.
* **`goaway` Handling:**
  * If `reason === 'superseded'`: Do NOT reconnect (another daemon instance is authoritative).
  * If `reason === 'shutdown'` or server restart: Reconnect following backoff schedule.
* **In-Flight Disconnect Semantics:**
  * On WSS disconnect, every in-flight request on the host is cancelled via `adapter.cancel(id)`.
  * Relay aborts pending browser requests with HTTP 503.
  * Transport **never** automatically retries HTTP mutations. Application/browser handles re-requests.

### 10. BACKPRESSURE & FLOW CONTROL (CORRECTED FROM SCOUT CLAIMS)

* **Refutation of Scout Claim:** Node.js `ws.WebSocket` **DOES NOT emit a `'drain'` event**. Scout 1's proposed `ws.on('drain')` would never fire, causing permanent write stalls.
* **Host Backpressure Implementation:**
  * Host checks `ws.bufferedAmount`.
  * If `ws.bufferedAmount > 4 * 1024 * 1024` (4 MiB): Host pauses writing chunks to WSS and queues them in a local bounded queue.
  * **Resume Mechanism:**
    1. In the completion callback of `ws.send(chunk, (err) => { ... })`, inspect `ws.bufferedAmount`. If `ws.bufferedAmount <= 2 * 1024 * 1024` (low watermark), resume writes and flush the queue.
    2. Additionally, hook the underlying TCP socket drain: `(ws as any)._socket?.once('drain', () => checkAndFlush())`.
  * **Bounded Safety Cap:** If host local queue exceeds 8 MiB while paused, drop the connection or abort the largest in-flight stream to prevent out-of-memory crashes.
* **Relay Per-Response Queue Cap:**
  * Relay buffers up to 1 MiB (`1,048,576` bytes) per active response.
  * If a slow browser does not consume and relay queue exceeds 1 MiB: Relay closes that browser response, sends `{ t: 'cancel', id }` to host, and frees the queue. Other requests and the host connection are unharmed.

### 11. REQUEST BODY & RESPONSE LIMITS

* **Request Body Max:** 1 MiB (`1,048,576` bytes).
* **Oversized Request:** Relay returns HTTP 413 `Payload Too Large` immediately to the browser without forwarding across WSS.
* **Binary Framing (`bodyB64` / `chunkB64`):** Included in `relay-frames.ts` schema for completeness, but Stage 3 payloads are UTF-8 JSON / text.
* **Malformed Frame Handling:** If unparseable JSON or missing mandatory fields (`t`, `id`), close socket with code `1002` (Protocol Error).

### 12. REQUEST IDS

* **Generation:** Generated exclusively by the RELAY upon receiving a browser HTTP request.
* **Format:** `crypto.randomUUID()` (standard RFC 4122 v4 UUID).
* **Collision Policy:** If host receives an `id` that already exists in `inflight`, host returns `{ t: 'error', id, code: 'duplicate_id' }`.
* **Lifecycle:** Cleaned from active maps upon `end`, `error`, `cancel`, or socket close.

---

### 13. CANCELLATION SEMANTICS

* **Pipeline:**
  Browser disconnects (EventSource close / client abort)
  → Relay detects client close
  → Relay sends `{ t: 'cancel', id }` to host
  → RelayClient calls `adapter.cancel(id)`
  → Adapter emits `'close'` on pseudo-`Readable`
  → Daemon SSE cleanup runs (`removeSseClient`)
  → Inflight map cleans up.
* **Idempotency:** Calling `cancel(id)` on unknown or already-finished ID is a safe no-op.
* **Host Disconnect:** Relay terminates all pending browser responses. Host cancels all inflight requests. Zero memory leaks.

### 14. CROSS-HOST ISOLATION

* **Invariant:** Browser traffic intended for Host A can NEVER reach Host B.
* **Relay Enforcement:**
  1. Relay extracts `hostPublicId` from subdomain: `h-<hostPublicId>.<relayDomain>`.
  2. Relay looks up `verifiedSockets.get(hostPublicId)`.
  3. If missing → 503 `host_offline`.
  4. If found → frame sent strictly to that socket.
* **Verification:** Acceptance test with two distinct hosts connected simultaneously verifies 100% strict isolation.
