This Play is strictly **documentation, reconnaissance, and breadcrumb capture**. No runtime source code has been modified in Q2.5.

### Core Architectural Findings

1. **The Invariant Holds: Game ≠ Stadium:**
   - A **Game** is the durable logical software project / codebase being coached (the *WHAT*).
   - A **Stadium** is the execution environment, OS platform, and host process where a Game runs (the *WHERE*).
   - Sideline Coach must sit *above* and *around* the Game concept, allowing multiple Games to be registered, remembered, selected, and monitored without collapsing Game identity into VS Code window handles, terminal names, or local folder paths.

2. **The Localhost / Single Extension Host Reality:**
   - In VS Code, a single Extension Host process runs within the context of **one** VS Code window.
   - For a standard single-folder workspace (`GS3`), the extension host has native execution authority (terminals, debugging, child processes with window PTYs) strictly for that **one** open folder.
   - **Crucial Reconnaissance Distinction:** In the current single-window host, Coach can **know** arbitrarily many Games (via persistent registry in `globalState`), can **read** their report files from disk, but can only **execute** Plays in the currently **Connected** workspace.
   - If a known Game is not open in the current VS Code window, it is truthfully marked **Offline** (or *Not Connected*). Coach does NOT fake multi-Game execution, fabricate terminals, or silently execute across folders without a connected Stadium.
   - (In VS Code multi-root workspaces (`.code-workspace`), multiple workspace folders ARE simultaneously connected in the same extension host, allowing concurrent execution across those folders).

3. **Human North Star UX:**
   - The top header provides an intuitive Game switcher:
     ```text
     Game: GS3 ▾
     ┌──────────────────────┐
     │ GS3        Connected │
     │ Browser Gallery  Off │
     │ FloppyDisk       Off │
     │ Sideline Coach   Off │
     ├──────────────────────┤
     │ + Add Game           │
     └──────────────────────┘
     ```
   - Selecting another Game feels as natural as a coach turning their clipboard to another game on the schedule.
   - Switching Game immediately projects that Game's Roster, Incoming Reports, Staged Route, and Dispatcher state, with zero cross-Game leakage.
   - If an Offline Game is selected, the UI displays clear, honest status: `Browser Gallery · Offline` with guidance to open it in VS Code or connect its Stadium.

4. **Zero Cross-Game Leakage & Exact Target Safety:**
   - All dispatches strictly enforce:
     ```text
     gameId + playerInstanceId
     ```
   - If a Play targeted for Game A arrives while Game B is selected or connected, the server immediately rejects the dispatch with `409 Conflict`.
   - Staged routes for Game A are automatically invalidated upon switching to Game B.
   - Stored controlled Player bindings for Game A are quarantined if attempted in Game B (`cross-game-quarantine`).

## 3. CANONICAL GAME REGISTRY

The Game Registry is the authoritative inventory of all Games known to this Coach installation.

### Data Shape

```typescript
export interface GameRecord {
  readonly gameId: string;              // Canonical immutable identity (e.g. 'game_git_3b9a712f')
  readonly displayName: string;         // Human-facing display name (e.g. 'GS3', 'Browser Gallery')
  readonly fingerprintSource: GameFingerprintSource; // 'marker' | 'git-remote' | 'git-root' | 'registry'
  readonly repoUri?: string;            // Normalized Git remote origin URL, if git-backed
  readonly knownRootFsPaths: string[];  // Known local filesystem mount paths on this Stadium
  readonly addedAt: number;             // Timestamp when first added to registry
  lastSeenAt: number;                   // Timestamp when last observed active/connected
  isArchived?: boolean;                 // Soft deletion / hidden flag
}

export interface GameRegistryState {
  readonly version: 1;
  readonly games: Record<string, GameRecord>; // Keyed by gameId
  selectedGameId?: string;                    // Currently selected Game ID
}
```

### Key Principles of GameRecord
1. `gameId` is immutable and primary. It is never rewritten when folders move or are renamed.
2. `displayName` is presentation-only. It defaults to the workspace folder name or marker name, but is editable without altering `gameId`.
3. `knownRootFsPaths` is an array because a Game (e.g. a Git repo) might be checked out at different paths or cloned on different drives.
4. `repoUri` enables recognizing the same Game across different mounts or Stadiums.

## 4. GAME IDENTITY & RESOLUTION

Game identity follows the established Q2.2 4-tier resolution ladder:

```text
┌──────────────────────────────────────────────────────────────┐
│                  4-TIER GAME RESOLUTION LADDER               │
├──────────────────────────────────────────────────────────────┤
│ Tier 1: .sideline/game.json marker (gameId + displayName)    │
│ Tier 2: Normalized Git remote origin SHA-256 fingerprint    │
│ Tier 2 Fallback: Git root commit SHA-256 fingerprint         │
│ Tier 3: Stadium Local Registry in globalState (non-git repo) │
│ Tier 4: Unknown (explicit fallback)                          │
└──────────────────────────────────────────────────────────────┘
```

### Identity Rules
1. **Never use display name as authority:** Two games can both be called `FloppyDisk` (e.g. a fork and an original), but their `gameId`s will differ.
2. **Never use local filesystem path as identity:** Moving `C:\Projects\GS3` to `D:\Code\GS3` must produce the identical `gameId`.
3. **Move / Rename Behavior:**
   - If a Git repo is renamed or moved on disk, `readGitRemoteOriginFromConfig()` produces the identical normalized Git URL and identical `gameId`.
   - The Game Registry recognizes the existing `gameId`, appends the new path to `knownRootFsPaths`, updates `lastSeenAt`, and seamlessly reconnects.
4. **Duplicate Detection:**
   - When a user adds a folder, Coach computes its canonical `gameId`.
   - If `gameId` already exists in `GameRegistryState.games`: Coach recognizes it as an existing Game, updates its root path if changed, and selects it. No duplicate entry is created.

## 5. PERSISTENCE OWNER

### Where Does Game Registry Belong?

| Storage Candidate | Pros | Cons | Decision |
| :--- | :--- | :--- | :--- |
| **`workspaceState`** | Scoped per workspace | **Fatal:** Stored only for the currently open folder. Other folders / windows cannot see known games. | **REJECTED** |
| **Project Repo Files (`.sideline/`)** | Portable across clones | **Fatal:** Commits machine-specific local paths, registry state, or user preferences into public Git repos. | **REJECTED** |
| **`globalState` (VS Code Profile)** | Persistent across all windows, folders, and restarts on this Stadium. Machine-local. | Limited to this VS Code profile/machine until future cloud Stadium sync. | **ACCEPTED (Primary)** |
| **External JSON / DB** | Independent of VS Code | Premature complexity for Q2.x proving environment. | **FUTURE (Stadium Bridge)** |

### Persistent Keys
- `sidelineCoach.gameRegistry.v1`: Stores `GameRegistryState` in `context.globalState`.
- `sidelineCoach.selectedGameId`: Stores last selected `gameId` in `context.globalState`.

## 6. KNOWN / SELECTED / RUNNING / CONNECTED GAME SEMANTICS

To prevent false claims of authority, Sideline Coach explicitly defines four lifecycle tiers for Games:

```text
┌─────────────────────────────────────────────────────────────┐
│                         KNOWN GAME                          │
│ Exists in Game Registry (globalState).                      │
│ Coach remembers project, reports, and history.              │
└──────────────────────────────┬──────────────────────────────┘
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
┌──────────────────────────────┐    ┌──────────────────────────────┐
│        CONNECTED GAME        │    │         OFFLINE GAME         │
│ Has an active Stadium        │    │ Has no active Stadium        │
│ connection. Filesystem mount │    │ connection. Cannot execute   │
│ is live; reports can scan;   │    │ Plays or launch Players.     │
│ Players can be spawned.      │    │ Reports are cached/read-only.│
└──────────────┬───────────────┘    └──────────────────────────────┘
               │
               ▼
┌──────────────────────────────┐
│         RUNNING GAME         │
│ Connected Game with one or   │
│ more active Players on field │
│ or active Plays in flight.   │
└──────────────────────────────┘

* SELECTED GAME: The Game currently chosen by the human in the UI.
  Can be Connected, Running, or Offline.
```

### Definitions & UI Representation

| State | Definition | UI Selector Presentation | Main Panel Status |
| :--- | :--- | :--- | :--- |
| **Known** | Recorded in `globalState` registry | Visible in `Game: GS3 ▾` dropdown | N/A |
| **Connected** | Open in current VS Code workspace | `GS3 · Connected` (green pip) | Normal live coaching cockpit |
| **Running** | Connected + Players on field / Play in flight | `GS3 · 2 Players On Field` (blue pip) | Live roster, active status runner |
| **Offline** | Registered, but not in active workspace | `Browser Gallery · Offline` (gray pip) | Read-only mode; dispatch disabled; clear guidance |
| **Selected** | Currently focused in browser UI | Checkmark / active item in dropdown | The active view |

## 9. INCOMING / REPORT SCOPING ARCHITECTURE

### The Problem
Currently, `scanReports()` searches `coach.reportGlobs` across `vscode.workspace.findFiles()`. If multiple workspace folders are open, reports are scanned from all folders. In `describeReport(uri)`, each report is tagged with its `gameId` via `resolveGameContextSync`.

### Multi-Game Architecture for Reports
1. **Filtering by Selected Game:**
   - When the client requests reports (`GET /api/reports?gameId=...`) or receives SSE report events, the server filters reports strictly by `report.gameId === selectedGameId`.
   - Reports for Game A never appear in Game B's Incoming tab.
2. **Agnostic Folder Layout Seam:**
   - Default glob remains `**/Docs REPORT/**/*.{md,txt}`.
   - Future Playbook/SOP seam: `GameRecord` optionally allows custom `reportGlobs?: string[]` per Game. If specified, Coach searches that Game's specific report paths.
3. **Offline / External Game Reports:**
   - If a Game is registered and exists on local disk (`knownRootFsPaths[0]`), but is not open as the active VS Code workspace:
   - Coach can scan that local path directly using Node.js `fs.readdir` or fast glob, indexing reports for that Game.
   - The reports render with badge: `[ Local Filesystem · Offline Game ]`.

## 10. PLAYER & ROUTING STATE ISOLATION

### Strict Isolation Rules
1. **Roster Projection Filtering:**
   - `PlayerRoster.status()` and `getRoutingCapabilities(activeGameId)` already filter instances and capabilities by `gameId`.
   - In Q2.6, `PlayerRoster` will strictly project only Players whose binding matches the selected `gameId`.
2. **Dispatch Safety Gate (C1 / Q2.2 Enforcement):**
   - The `/api/dispatch` endpoint enforces:
     ```typescript
     if (clientGameId && clientGameId !== activeConnectedGameId) {
       this.json(res, 409, {
         success: false,
         message: `Play targeted Game '${clientGameId}', but active Game is '${activeConnectedGameId}'.`
       });
       return;
     }
     ```
   - If the selected Game is **Offline**, `/api/dispatch` immediately rejects:
     ```typescript
     this.json(res, 400, {
       success: false,
       message: `Game '${selectedGame.displayName}' is offline. Connect its Stadium or open in VS Code to dispatch Plays.`
     });
     ```
3. **Staged Route Invalidation on Switch:**
   - When the human switches Game:
     - `selectedPlayerInstanceId` is set to `''`.
     - `manualSelectedModel` and `manualSelectedEffort` are cleared.
     - `currentAutoDecision` is recomputed against the newly selected Game's Players.
     - The staged route chip immediately updates to the new Game or displays `No Players on Field`.

## 11. GAME SWITCHING LIFECYCLE & RACE-SAFETY

### Exact Switching Sequence

```text
Human selects 'Browser Gallery' from Game dropdown
                     │
                     ▼
1. Browser: optimistic UI update:
   - Switches header to 'Game: Browser Gallery'
   - Sets Game status chip to 'Switching…'
   - Disables Dispatch button during switch
                     │
                     ▼
2. Client sends HTTP: POST /api/game/select { gameId: 'game_git_browser_gallery' }
                     │
                     ▼
3. Server validates & updates:
   - Verifies gameId exists in Game Registry (globalState)
   - Updates selectedGameId = gameId
   - Persists selectedGameId to globalState
   - Re-evaluates Game connection state (connected vs offline)
   - Scopes Roster, Reports, and Auto-Route to new gameId
   - Returns 200 OK with full updated Status
                     │
                     ▼
4. Server broadcasts SSE 'status' event to all connected clients
                     │
                     ▼
5. Browser renderStatus(newStatus):
   - Roster updates to Browser Gallery players
   - Incoming updates to Browser Gallery reports
   - Route chip updates to Browser Gallery staged route
   - If Offline: Dispatcher disabled with clear guidance
   - If Connected: Dispatcher idle and ready
```

### Race-Safety Guarantees
- **In-flight Dispatch Guard:** If a dispatch is currently in-flight (`Sending…` or `Working…`), Game switching is blocked or warns the human, preventing orphan responses.
- **Atomic State Swap:** The server returns the entire canonical state in the `POST /api/game/select` response, ensuring the client transitions atomically without mismatched interim states.
- **No Residual Target:** The client zero-initializes target player IDs before rendering the new status, preventing any keystroke or click from targeting the prior Game's Player.

## 15. SINGLE EXTENSION HOST REALITY: WHAT IS POSSIBLE TODAY

Reconnaissance Question 10 explicitly asks:
*Can the current extension host truly execute multiple Games, or only know about them?*

### Authoritative Technical Truth

1. **In a Single-Folder Workspace (Today's Standard):**
   - The extension host runs inside **one** VS Code window.
   - It can **KNOW** about any number of registered Games (via `globalState`).
   - It can **READ** reports and files from any local path.
   - It can **ONLY SAFELY EXECUTE** in the folder open in that window.
   - Why? Because:
     - VS Code terminals (`vscode.window.createTerminal`) are anchored to the open window;
     - VS Code task and build commands run in the open workspace;
     - Controlled Codex adapters validate `thread.cwd === gameRoot`. If Coach spawned a Codex instance for a different folder, its Pseudoterminal would intrusively clutter the active window, and its session bindings would pollute the wrong `workspaceState`.
   - **Verdict:** Today's single-window host can **Know Many, Execute One**. Non-active games are truthfully marked **Offline**.

2. **In a Multi-Root Workspace (`.code-workspace`):**
   - A single VS Code window opens multiple folders simultaneously (e.g. `GS3` + `SidelineCoach`).
   - In this mode, the extension host has native VS Code authority over **all** included folders!
   - Terminals can be created in any folder; `findFiles` searches all folders.
   - **Verdict:** In multi-root workspaces, Coach can **Know Many, Execute Multiple** concurrently!

3. **In Multi-Window Setups (Future Stadium Bridge):**
   - User opens Window 1 (`GS3`) and Window 2 (`Browser Gallery`).
   - Each window runs an Extension Host.
   - Future Stadium Bridge will allow Window 1 to act as Hub or coordinate via local IPC, enabling cross-window coaching without port collisions.

## 16. SECURITY & SAFETY INVARIANTS

1. **No Accidental Play Cross-Fire:**
   A Play written for Game A must structurally never be sent to a Player executing in Game B. Enforced by:
   - Server-side active `gameId` verification on every dispatch;
   - Client-side staged route invalidation on Game switch;
   - Isolated player instance IDs tied to explicit `gameId` in `PlayerRoster`.
2. **Provider Cwd Invariant Preserved:**
   `validateStoredThread` checking `thread.cwd === gameRoot` remains inviolate. Changing the selected Game never forces or fakes cwd for an existing provider thread.
3. **No Credential / Token Cross-Contamination:**
   Game registration stores only filesystem paths and Git URLs. No provider tokens or user secrets are ever written to Game records.
4. **Machine-Local State Remains Machine-Local:**
   Game Registry is stored in `globalState`. It is never written into the user's Git repositories.

## 20. WAS / IS / WILL BE

- Sideline Coach assumed exactly one Game existed, tied to the active VS Code window's primary folder.
- `resolveGameContextSync` inspected only `workspaceFolders?.[0]`.

- Cross-Game switching required opening a separate VS Code window or reloading another folder.

- 4-tier resolution ladder produces canonical `gameId` independent of folder renames.
- Controlled Player bindings and restore plans are scoped by `gameId`.

- Routing intelligence (`AUTO` / `MANUAL`) operates within the single active Game.

### WILL BE (Q2.6 & Quarter 3 Future)
- Multi-Game Foundation active: Coach maintains a durable **Game Registry** in `globalState`.
- Human seamlessly switches between known Games via header dropdown: `Game: GS3 ▾`.
- Known vs Connected vs Running vs Offline state is explicitly and truthfully presented.

## 21. APPROVED FUTURE PRODUCT BREADCRUMBS RECORDED

The following eight newly approved product concepts are durably recorded in product breadcrumbs:

### 1. Front-Door Routing Model: AUTO / CONSERVE / CUSTOMIZE
- **AUTO:** Coach chooses the best fit model and effort based on prompt complexity and live capabilities.
- **CONSERVE:** Coach protects scarce premium reasoning quota (e.g. Claude Opus, OpenAI Ultra) while still meeting Play requirements. Explicitly prompts user:
  ```text
  Architecture Play detected · Premium reasoning recommended.
  Conserve route: Codex Terra · High
  Best route: Claude Opus · XHigh
  [ Stay Conservative ] [ Use Best ]
  ```
- **CUSTOMIZE:** Opens the deep routing cockpit (Player → Model → Effort → Rationale → Usage). The current Q2.4 MANUAL system naturally moves behind Customize.

### 2. Usage & Budget Board Telemetry
- Inspects truthful provider usage telemetry (e.g. `/status` in Codex, `/usage` in Claude Code).
- Never fabricates percentages or makes unmetered guesses.
- Tracks provenance tiers: `LIVE STRUCTURED`, `LOCAL PARSED`, `USER PROVIDED`, `UNKNOWN`.

### 3. Player Strengths & Capability Roles
- Routing reasons about functional capability roles rather than rigid provider stereotypes:
  - `Architect`
  - `Implementation Worker`
  - `Forensics / Diagnostic Investigator`
  - `Documentation / Release-State Worker`
  - `Quick Bounded Worker`
  - `High-Risk Reviewer`
- A Player/model can fulfill multiple roles based on capacity and prompt type.

### 4. Player Recruitment & Extensible Roster (`RECRUIT PLAYER`)
- Standardized extensible Player adapter interface:
  ```text
  Detect → Install if needed → Authenticate → Discover capabilities → Certify transport → Add to Roster → Put on Field
  ```
- Allows adding new agents (e.g. Hermes, OpenCode) without rewriting Coach core.

### 5. Game Playbook & SOP Contract
- Durable repository operational knowledge:
  - North Star & Architecture Breadcrumbs
  - Operating SOPs
  - Report Contract & Filing Cabinet rules
  - Debugging & Verification policies
- If existing docs exist, Coach maps to them without reorganizing the user's repository.

### 6. Play Envelope
- Coach automatically wraps user prompt payloads with mechanical Game context:
  - Target role & constraints
  - Report destination path & filename format
  - Verification & testing policies
- The human focuses on the task; Coach handles repetitive framing.

### 7. Standard Report Contract
- Reports describe **Next Play Requirements** rather than commanding routing decisions:
  ```text
  NEXT PLAY: Implement cache invalidation
  TASK CLASS: implementation
  RISK: low
  MINIMUM CAPABILITY: standard coding
  RECOMMENDED ROLE: Implementation Worker
  ```
- Coach matches requirements with available roster, quota, and human priorities.

### 8. Coach Brief
- Compact canonical brief exposed for external strategy/conversational AIs (mobile, tablet, voice):
  - Current Game, latest Play, latest result, latest report, next-Play requirements, available roster, budget status, suggested route.
- Avoids dumping the entire codebase context into conversational models.

### Core Future Separation Principle
> **Reports describe requirements.**  
> **Coach knows resources.**  
> **Human supplies priorities.**  
> **Routing policy chooses the route.**  
> **Players receive only the context required for their Play.**
