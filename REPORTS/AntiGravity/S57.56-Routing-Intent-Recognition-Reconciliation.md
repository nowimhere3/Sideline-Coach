# EXECUTIVE FINDING

The two field-proven mismatches (`CODEX 5.6 sol Medium` → `Codex 1 · GPT-6.1-Sol · Ultra` and `Sonnet Medium` → `Claude · Opus · High`) did **NOT** occur because AUTO deliberately overrode explicit constraints.

They occurred because **the recognition pipeline dropped explicit intent before `RouteConstraints` could be created**, causing the engine to fall back to task-complexity classification:

1. **In Field Failure A (`CODEX 5.6 sol Medium`):**  
   When structured fields (e.g. `AGENT: Codex`, `ROLE: Architect`, or Markdown headers) are present anywhere in the prompt, [`resolveSmartRouteConstraints`](file:///C:/Users/dmcal/Documents/GitHub/SidelineCoach/src/control-plane/smart-route-resolver.ts#L501-L504) bypasses natural parsing and routes exclusively to [`recognizeRouteConstraints`](file:///C:/Users/dmcal/Documents/GitHub/SidelineCoach/src/control-plane/route-constraints.ts#L586). There, a structured `AGENT: Codex` field matches the Player, but line 643 (`if (!player && ... intercept = opening)`) **silently drops the opening line's parsed model (`5.6 sol`) and effort (`medium`)** because `player` was already resolved. Alternatively, if formatted as a title (`CODEX 5.6 sol Medium - Architecture`), the title is rejected because it is not ALL CAPS. In either case, model and effort became `undefined`. The task classifier saw high-complexity architecture content and chose Codex's strongest model with `ultra` effort: `Codex 1 · GPT-6.1-Sol · Ultra`.
2. **In Field Failure B (`Sonnet Medium`):**  
   The natural shorthand parser in [`route-constraints.ts:403`](file:///C:/Users/dmcal/Documents/GitHub/SidelineCoach/src/control-plane/route-constraints.ts#L403) (`parseRouteCall`) strictly demands the grammar `PLAYER [MODEL] [EFFORT]`. Because `Sonnet` is a model family and not a Player name, `parseRouteCall` rejected the line entirely. If structured fields were present (e.g. `AGENT: Claude`), `player` was set to Claude but `model` and `effort` were omitted. If prose followed on line 1, [`trySmartNaturalRoute`](file:///C:/Users/dmcal/Documents/GitHub/SidelineCoach/src/control-plane/smart-route-resolver.ts#L355) rejected the line due to unconsumed tokens (`unconsumed.length > 0`). With model and effort dropped, AUTO classified the prompt as `architecture` and routed to Claude's deepest model with `high` effort: `Claude · Opus · High`.

**The Core Law Violated:**  
Explicit human routing intent was silently dropped and replaced by task-complexity inference.

# CURRENT RECOGNITION GAPS

1. **First-Line Limitation:**  
   Both natural parsers evaluate only the first non-blank line. Lines 2–10 are invisible to natural language recognition.
2. **Full-Sentence / Conversational Filler Rejection:**  
   Any unconsumed token (e.g., `Please`, `send`, `this`, `to`, `using`) triggers `unconsumed.length > 0` in `smart-route-resolver.ts` or fails token-length/grammar checks in `parseRouteCall`.
3. **Speech-to-Text / Spoken Numbers:**  
   Spoken numbers (`six point one`, `five dot six`, `six one`, `three point eight`) are not normalized to digits (`6.1`, `5.6`, `3.8`), resulting in unconsumed tokens that abort recognition.
4. **Model-First Shorthand Without Player:**  
   Phrases like `Sonnet Medium` or `5.6 Sol Low` fail in `parseRouteCall` because no Player alias leads the line.
5. **Sub-Family Ambiguity Silent Picks:**  
   In `trySmartNaturalRoute:418-443`, a broad family token like `Gemini` silently picks a default model (e.g. Flash) instead of stopping or offering a choice between Pro and Flash.
6. **Effort Normalization Gaps:**  
   `med` is handled via a special case in `smart-route-resolver.ts:243`, but is missing from canonical [`normalizeEffortValue`](file:///C:/Users/dmcal/Documents/GitHub/SidelineCoach/src/control-plane/route-normalization.ts#L236) in `route-normalization.ts`.

# PARTIAL-CONSTRAINT CONTRACT

When a human supplies partial routing information, resolved dimensions become **immutable anchors**:

1. **Model + Effort Explicit (Player Implied):**  
   - Example: `Sonnet Medium`  
   - Result: `player = claude` (uniquely implied), `model = sonnet`, `effort = medium`.  
   - Invariant: AUTO may NOT change `sonnet` to `opus` or `medium` to `high`.

   - Example: `Codex Medium`

   - Invariant: AUTO may pick any model in Codex that supports `medium` (e.g. `gpt-5.6-sol`), but MUST preserve `effort = medium`.

   - Example: `High` on opening line  
   - Result: `effort = high`.

When explicit routing instructions conflict within the prompt:

# FIRST-10-LINES OPTIONS FOR OPUS

Head Coach requirement:
> Explicit routing intent may appear anywhere within approximately the first ten meaningful lines.

Opus must choose between the following deterministic architectures:

### Option A: Zone-Priority Extraction (Recommended)
- **Mechanism:**
  1. Inspect the first 10 unfenced, non-blockquote lines.
  2. Parse structured fields (`AGENT:`, `MODEL:`, `EFFORT:`) anywhere in lines 1–10.
  3. Scan lines 1–10 sequentially for an unmistakable natural route call or imperative sentence (`Send to...`, `Use...`).
  4. Merge resolved dimensions: Structured fields win on dimension collision; otherwise dimensions accumulate (e.g. shorthand provides model/effort, structured provides instance).
- **Pros:** Completely eliminates the dropped-intercept bug; naturally tolerates headers, preamble, or greeting on line 1.
- **Cons:** Requires clear precedence rules when multiple lines mention different entities.

### Option B: Bounded Imperative Intent Window
- **Mechanism:**  
  Only scan line 1 for shorthand. If line 1 is non-routing prose or heading, scan lines 2–10 ONLY for strict imperative carrier phrases (`Send this to [X]`, `Route to [X]`, `Use [X]`).
- **Pros:** Very low false-positive risk.
- **Cons:** Fails if the user simply types `Sonnet Medium` on line 2 after a markdown title.

### Option C: Token-Density Pre-Filter with Closed Vocabulary
- **Mechanism:**  
  Evaluate each of the first 10 lines against a strict scoring threshold: count tokens belonging to the closed catalogue (Player + Model + Effort) divided by total tokens in the line. If ratio ≥ 0.6 or matches strict grammar, treat as route instruction.
- **Pros:** Flexible against slight conversational variations.
- **Cons:** Risk of false positives on prose lines that happen to mention models.

# FALSE-POSITIVE RISKS

The engine must not hijack ordinary explanatory text. Examples of non-routing prose and required behavior:

| Candidate Text | Intended Interpretation | Why It Must NOT Route |
|---|---|---|
| `"This architecture supports Claude and Codex."` | Informational prose | `isChoiceOrNegation` flags `and`; connective veto applies. |
| `"We should compare Sonnet with Opus."` | Comparison | `with` is not a routing verb; two models mentioned without assignment. |
| `"Avoid using GPT-6 Astra for simple tasks."` | Guidance / Policy | Leading negation `Avoid using` maps to model exclusion or prose. |
| `"Refer to the Codex 5.6 documentation below."` | Reference | Non-routing verb `Refer to`; trailing nouns (`documentation below`). |

**Deterministic Anti-Hijacking Rules:**
1. A line is a route call **only if** all non-connector words belong to the catalogue (Player, Model, Effort, Version, Instance).
2. Carrier sentences must start with an approved imperative verb list (`send`, `route`, `run`, `use`, `dispatch`, `target`).
3. Connective words (`and`, `or`, `vs`) immediately invalidate positive routing.
