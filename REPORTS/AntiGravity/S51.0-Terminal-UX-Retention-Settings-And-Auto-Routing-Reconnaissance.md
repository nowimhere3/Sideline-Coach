## LIVE TERMINAL RETENTION LIFECYCLE

### Step-by-Step Lifecycle Trace:

1. **Play Dispatched:**
   - Stadium Client routes dispatch to `playerRoster.runTerminalCommand(instanceId, command)`.
   - Execution begins; turn events `accepted` and `started` fire.
   - Work Ledger transitions `entry.workState = 'working'`.
   - Execution Projection projects `ExecutionView.state = 'working'`.
2. **Live Terminal Eligibility (`src/public/index.html:2763-2766`):**
   - `isTerminalEligible` evaluates:
     `liveConsoleEnabled() && view.executionType !== 'scout-formation' && record.typeName !== 'Scout' && (view.state === 'working' || view.state === 'starting' || view.state === 'finished')`.
   - Returns `true` while `'working'`.
3. **Expansion (`consoleExpandedByInstance`):**
   - Dispatched plays start **collapsed** by default.
   - User must manually click `[Expand]`.
   - Clicking `[Expand]` adds `instanceId` to `consoleExpandedByInstance`.
4. **Execution Completes:**
   - Shell command finishes. VS Code fires `onDidEndTerminalShellExecution`.
   - `finishTerminalCommand` calls `describeTerminalExit(exitCode)`.
   - If `exitCode === 0`: `outcome.state = 'completed'`, summary `'Completed · exit code 0'`.
   - If `exitCode !== 0`: `outcome.state = 'failed'`, summary `'Failed · exit code N'`.
   - If `exitCode === undefined`: `outcome.state = 'unknown'`.
5. **State Transition in Ledger & Projection:**
   - Turn event fires with outcome state.
   - `work-ledger.ts:287`:
     - If `'completed'`: `workState = 'completed'`, `recentPlays[0].outcome = 'completed'`.
     - If `'failed'`: `workState = 'idle'`, `recentPlays[0].outcome = 'failed'`.
     - If `'unknown'`: `workState = 'unknown'`, `recentPlays[0].outcome = 'unknown'`.
   - `execution-projection.ts:121-133`:
     - If `latest.outcome === 'failed'`: returns `state: 'couldnt-finish'`.
     - If `latest.outcome === 'completed'`: returns `state: 'finished'`.
6. **Browser Rendering & Pinning (`src/public/index.html`):**
   - `renderPlayerStrips()` runs:
     - Line 2884: If `view.state === 'finished'` AND `consoleExpandedByInstance.has(instanceId)` is true, line 2885 sets `consolePinnedByInstance.add(instanceId)`.
     - If `view.state === 'couldnt-finish'` or `'unknown'`, **nothing pins**.
7. **Decay / Release:**
   - For `view.state === 'finished'`:
     - `isRichFinished(view)` is true for 30 seconds (`RICH_FINISHED_MS = 30_000`).
     - After 30 seconds, `scheduleFinishedDecay` calls `renderPlayerStrips()`.
     - If `consolePinnedByInstance.has(instanceId)` is true, line 2653 rescues the strip copy and keeps it visible!
     - If the user clicks `Collapse`, line 2805 deletes `consolePinnedByInstance` and line 2804 deletes `consoleExpandedByInstance`. The strip immediately unmounts.
     - If the user clicks `Copy All` or `Copy New`, line 2438 deletes `consolePinnedByInstance` and line 2439 deletes `consoleExpandedByInstance`. The strip immediately unmounts.

## FAST-COMMAND BLIP ROOT CAUSE

### Why a Long-Running Command (~30s) Remains Inspectable:
- While running, `view.state` remains `'working'` for 30 seconds.
- The human has ample time to notice the active strip, click `[Expand]`, and watch output.
- When execution completes, `consoleExpandedByInstance.has(instanceId)` is already `true`.
- Therefore, line 2885 automatically adds `consolePinnedByInstance.add(instanceId)`.
- When `RICH_FINISHED_MS` (30s) decays, line 2653 rescues the strip copy because it is in `consolePinnedByInstance`. It remains pinned and inspectable indefinitely until explicit collapse or copy.

### Why a Fast Command (<1s) or Fast Failure Visibly Blips and Disappears:
There are two distinct root causes:

#### Cause 1: Fast Failure (`outcome: 'failed'`)
1. Terminal command fails (e.g. exit code 1, invalid flag, missing file).
2. `describeTerminalExit` emits turn `failed`.
3. `execution-projection.ts:122` projects `view.state = 'couldnt-finish'`.
4. In `src/public/index.html:2604-2617` (`stripCopy`):
   ```javascript
   case 'couldnt-finish':
   case 'unknown':
     if (scout && isReportReady(view)) return { ... };
     return null;
   ```
   `stripCopy` returns `null` for non-Scout Players!
5. `renderPlayStrip` returns `null`.
6. Furthermore, `isTerminalEligible` (line 2766) requires `view.state === 'working' || view.state === 'starting' || view.state === 'finished'`. It rejects `'couldnt-finish'`.
7. **Result:** A fast failure displays for the brief fraction of a second that it was in `'working'`, and as soon as the failure event arrives, the entire card is stripped from the DOM. The human sees a momentary flash ("blip") and the terminal is gone.

#### Cause 2: Fast Success (<1s) Without Prior Expansion
1. Command succeeds in 50ms (e.g. `git status`).
2. `view.state` transitions from `'working'` to `'finished'` in 50ms.
3. Because it finished so fast, the human did not click `[Expand]` while it was running. `consoleExpandedByInstance` is empty.
4. When `renderPlayerStrips` runs, line 2884 (`if view.state === 'finished' && consoleExpandedByInstance.has(instanceId)`) is **false**. Therefore, `consolePinnedByInstance` is **not** set!
5. The card remains visible in collapsed form only during the 30-second `RICH_FINISHED_MS` window.
6. Once 30 seconds pass without expansion, or if another play runs, the card decays to `null`.
7. If the human does expand it during those 30 seconds and then clicks `Copy All`, line 2438 immediately deletes pinning and closes it.

## RETENTION POLICY OWNERSHIP SEAM

### 1. Separation of Concerns
- **Execution Truth (Daemon & Work Ledger):**
  Must remain factual. When a process exits, the turn is ended and the Player is idle/ready. Falsifying `view.state === 'working'` to keep a terminal visible would corrupt ledger turn history, break session accounting, and block future dispatches.
- **Presentation Intent (Browser Client):**
  Owns retention. S48.0 established that retention is decided entirely in the browser from `(sessionKey, epoch, playRef, pin-set)`. The browser controls whether an idle/completed card is rendered in the UI.

### 2. Candidate Policies & Mechanisms

| Policy | Trigger to Dismiss / Collapse | Browser Mechanism |
|---|---|---|
| **Manual Collapse** (Recommended Default) | Human clicks `[Collapse]` | Only `consoleExpandedByInstance.delete()` releases. Strip and terminal stay until operator dismisses. |
| **Next Play** | Next Play starts on this Player | Line 2887 already deletes pinning on `starting`/`working`. Keep terminal open until new play begins. |
| **Duration Timer** | User-selected time (e.g. 5m, 15m, 1h) | Replaces fixed `RICH_FINISHED_MS` (30s) with user-configured duration preference. |
| **Successful Copy** | Human clicks `Copy All` | Current S46 behavior. Should only be active if explicitly configured as policy. |
| **Full History** | Never auto-dismiss while View Player Terminal is on | Preserves all finished terminal strips in a history section. |

### 3. Architecture Boundary
Retention policy belongs in `CoachPreferences.terminalRetentionPolicy` and is evaluated in `src/public/index.html` within `stripCopy` (lines 2618–2646) and `renderPlayStrip` (line 2653). No changes to `daemon.ts` or `work-ledger.ts` are needed.

## REPORT VISIBILITY RELATIONSHIP

### Lifecycle Comparison

| Dimension | Markdown Report Lifecycle | Terminal Evidence Lifecycle |
|---|---|---|
| **Substrate** | Markdown files written to disk (`.md`) | Ephemeral in-memory terminal stdout/stderr lines |
| **Discovery** | Filesystem watcher in daemon (`work-ledger.ts`) | Extension host output pump (`TerminalShellExecution.read()`) |
| **Transport** | File read via HTTP GET `/api/reports/content` | WS `player.activity` → daemon store → SSE / backfill |

| **Viewer** | Incoming Reader modal (`openReportViewer`) | Inline card terminal viewer (`.play-console`) |
| **Durability** | Persistent on disk across restarts | Transient, memory-only (max 300 lines) |

### Architecture Verdict:
**Do NOT unify these systems.**
- Markdown reports are durable work deliverables produced by AI reasoning agents.
- Terminal evidence is streaming execution telemetry produced by local shell commands.
- Forcing Terminal output into the report acknowledgement system would require fabricating synthetic report files or mock ledger links.
- They must remain separate lifecycle systems.

## AUTO TERMINAL ROUTING SEAM

### 1. The Current Reality
In `src/routing-policy.ts:330-338`, `candidate.playerType !== 'terminal'` and `candidate.executionType !== 'direct-shell'` are hard-coded exclusions. If AUTO is run with only Terminal on field, Sideline returns:
`"Terminal runs exact commands, so AUTO does not send it Plays. Choose Terminal in Manual, or put a reasoning Player on field."`

### 2. Product Requirement
AUTO may route **unambiguously terminal-only intent** directly to an eligible Terminal Player (e.g. `git status`, `npm install`, `ls`, `cargo build`).
Prompts requiring diagnosis, explanation, or reasoning (e.g. `"figure out why npm install is failing"`) must continue routing to AI reasoning agents.

### 3. Classification Seam: Why `checkTerminalCommand` is Insufficient
`src/terminal-player.ts:39-57` (`checkTerminalCommand`):
- Acts as a **rejection guard**, not an intent classifier.
- Checks if text starts with `REQUEST_OPENERS` (`please`, `can`, `why`, `how`, etc.) or ends with `?` without shell syntax.
- If prompt is `"check git status"`, `checkTerminalCommand` returns `{ ok: true }` because `"check"` is not in `REQUEST_OPENERS`! But `"check git status"` is an English instruction, not an executable command.
- Conversely, `"why does this command fail: git status"` contains shell syntax (`:`), which might slip past basic guards.

### 4. Smallest Future Routing Seam
1. **Command Intent Classifier (`src/terminal-player.ts`):**
   Add `isUnambiguousShellCommand(prompt: string): boolean`:
   - Validates that the first token is a known command/executable (`git`, `npm`, `pnpm`, `yarn`, `cargo`, `docker`, `python`, `node`, `ls`, `dir`, `cat`, etc.) or exact executable path.
   - Validates that tokens follow shell argument syntax (flags `--flag`, `-f`, paths).
   - Rejects natural language sentences even if they lack request openers.
2. **Routing Policy Seam (`src/routing-policy.ts`):**
   Inside `computeAutoRoute`:
   ```typescript
   const isTerminalIntent = isUnambiguousShellCommand(prompt);
   const terminalCandidate = everyCandidate.find(c => (c.playerType === 'terminal' || c.executionType === 'direct-shell') && c.state === 'ready');
   
   if (isTerminalIntent && terminalCandidate) {
     return {
       decision: {
         mode: 'auto',
         gameId: activeGameId,
         playerInstanceId: terminalCandidate.instanceId,
         playerLabel: playerName(terminalCandidate),
         provider: 'none',
         model: undefined,
         modelDisplayName: 'Provider managed',
         effort: undefined,
         reason: 'AUTO detected unambiguous terminal command.',
         ...
       }
     };
   }
   ```
3. **Precedence Invariants:**
   - **Explicit Human Selection Wins:** Manual mode always bypasses AUTO classification.
   - **Reasoning Over Terminal:** If intent is ambiguous or natural language, Terminal is excluded and reasoning players take priority.
   - **Terminal Command Safety Guard:** `checkTerminalCommand` in `player-roster.ts:720` remains authoritative as the final defense before execution.

## RISKS

1. **Auto-Routing Command Injection / Destruction Risk:**
   If AUTO routes natural language prompts to a shell, destructive accidental executions could occur. The intent classifier must be conservative: any prompt that does not strictly match trusted shell syntax must fall back to reasoning models.
2. **Execution State Falsification Risk:**
   Retaining terminal evidence must not keep `view.state` in `'working'`. The Player must be reported as completed/idle so ledger truth and subsequent dispatches are not blocked.
3. **Memory Leaks in Browser:**
   If retention is set to "until manual collapse" and many commands are run, stale terminal bodies could accumulate if not properly bounded or cleaned up on game switch.

## ARCHITECT HANDOFF

### What is Already Decided:
- Substrate remains native VS Code terminal via direct-shell transport (`legacy`).
- Output uses `TerminalShellExecution.read()` and publishes through `PlayerActivityNotice` (`output` category).
- Terminal evidence retention belongs strictly in the client/browser presentation layer; daemon and ledger semantics must remain unchanged.
- Report lifecycle and Terminal evidence lifecycle must remain separate.
- Copy is not inherently dismissal.

### What Source Evidence Establishes:
- Terminal is currently hard-excluded from AUTO.
- Fast failures disappear because `stripCopy` returns `null` for `couldnt-finish`.
- Fast successes disappear if unexpanded because `consolePinnedByInstance` only attaches to already-expanded terminals.

- Default retention duration / policy (Manual Collapse vs configured timer).
- Exact whitelist / syntax rules for `isUnambiguousShellCommand` in AUTO routing.
