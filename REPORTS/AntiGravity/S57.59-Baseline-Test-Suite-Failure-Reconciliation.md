# FULL-SUITE NON-TERMINATION

### The Hang Mechanism
**FACT:**
- In `src/player-control/codex-app-server.ts`, `runBounded()` spawns `child` via Node's `child_process.spawn()`.
- **`child.unref()` is never called.**
- In Node.js, an active `ChildProcess` handle maintains an active reference on the libuv event loop.
- When `killProcessTree()` is called, if the child process survives or is in a zombie state, or if the process handle isn't closed, the event loop cannot exit.
- When `node --test` runs files with `--test-isolation=process`, each test file runs in a dedicated Node child process.
- The worker running `test/codex-adaptive-compatibility.test.mjs` (PID 39220) completed all 24 tests, completed its `after()` hook, but **could not exit** because the libuv event loop was held open by the active handle to probe PID 49872.
- The parent test runner (PID 18380) buffers/waits for child test runners to exit and send their final TAP/spec streams. Because PID 39220 never exited, PID 18380 waited forever.
- Line 402 of `npm-after.log` was the last output received. No summary line was ever produced.
- After 120 seconds, the parent test command timed out.

**INFERENCE:**
- In `runBounded()`, calling `child.unref()` once the timeout fires (or when spawned with `detached: true` / unref upon abort) guarantees that even if a child process experiences termination latency on Windows, it cannot hold the parent process or test worker event loop open.
- In `test/codex-adaptive-compatibility.test.mjs`, CC-8's directory cleanup check should allow sufficient wait time for Windows process CWD handle release (matching the `waitFor` pattern already used for PID termination).
