## 1. EXECUTIVE SUMMARY

The objective of **Q2.2** is to design the architectural foundation for **Game identity** within Sideline Coach.

In Quarter 1 (historical Stage 1), Sideline Coach proved terminal control, controlled player persistence/resume (P1–P28), and dispatcher reliability UX (Q2.1). However, the codebase currently conflates the **Game** (the software project being coached) with the **Stadium** (the local execution host, VS Code window, or filesystem path). This conflation produces fragile path dependencies, breaks if folders are moved or opened in remote environments, creates ambiguity in multi-root workspaces, and prevents clean mobile dogfooding across devices.

This report establishes the fundamental domain invariant:

$$\mathbf{Game} \neq \mathbf{Stadium}$$

A **Game** is the logical software system / codebase being coached.  
A **Stadium** is the physical execution environment where that Game is currently mounted, edited, or coached.

### Key Architectural Recommendations:
1. **Tiered Hybrid Game Identity:** Game identity is derived through a deterministic 4-tier resolution ladder:
   - **Tier 1 (Explicit Project Marker):** Optional repo-local `.sideline/game.json` file.
   - **Tier 2 (Git Canonical Fingerprint):** Normalized git remote origin URL hash or root commit SHA (survives clones, machines, and directory moves).
   - **Tier 3 (Coach Registry Fallback):** Generated stable ID stored in Coach storage for non-git scratch projects.
   - **Tier 4 (Explicit Unknown):** When no workspace is open or unidentifiable, explicitly report `Game = Unknown` (never fake an identity).
2. **Formal Data Models:** Introduction of explicit TypeScript abstractions: `GameIdentity`, `StadiumIdentity`, and `GameStadiumBinding`.
3. **Option A Browser UX for Q2.2:** The mobile/web client presents the **single current canonical Game** prominently in the skybox header, supplemented by a secondary Stadium context chip (`Stadium: Windows · <path>`). Multi-Game switching UI is explicitly deferred to later quarters to maintain bounded focus.
4. **Preserved Persistence Invariants:** Controlled Player persistence (P1–P28) and shell provenance are augmented with `gameId` scoping to guarantee that conversations and turns are never resumed across different Games.
5. **Bounded 4-Phase Implementation:** A structured plan designed for a subsequent bounded worker with zero architectural drift.

## 2. CORE INVARIANT: GAME ≠ STADIUM

The foundational domain model of Sideline Coach separates the logical system from its physical hosting environment:

```
+-------------------------------------------------------------------------+
|                                  GAME                                   |
|  - Logical software project / codebase / repository                     |
|  - Architecture documentation & decisions (Docs ANCHOR/)                 |
|  - Incoming reports from AI agents (Docs REPORT/)                       |
|  - Play history, strategies, and session intentions                     |
|  - Durable identity across machines, clones, containers, and time      |
+-------------------------------------------------------------------------+
                                    |
                            Bound via Binding
                                    |
                                    v
+-------------------------------------------------------------------------+
|                                STADIUM                                  |
|  - Physical host execution environment                                  |
|  - OS platform (Windows, macOS, Linux, Dev Container, Codespaces)       |
|  - Filesystem mount path (e.g. C:\Users\... or /workspaces/...)         |
|  - Host process, terminal sessions, PTYs, shell PIDs                    |
|  - Network port, localhost daemon, auth access token                    |
|  - VS Code window / workspace session                                   |
+-------------------------------------------------------------------------+
```

### The Invariant in Practice:
- **One Game, Multiple Stadiums:** A developer may coach `SidelineCoach` on a Windows desktop at home (`Stadium A`), push changes, open the same repo in GitHub Codespaces on an iPad (`Stadium B`), or have a teammate open it on macOS (`Stadium C`). All three execution environments host the **exact same Game**.
- **One Stadium, Multiple Games:** A single workstation or VS Code instance may host a multi-root workspace (e.g. `frontend/` and `backend/`), or switch between distinct client projects throughout the day.
- **Anti-Patterns Rejected by this Invariant:**
  - *Anti-Pattern 1 (Path Identity):* Identifying a Game solely by `workspaceFolders[0].uri.fsPath`. (Breaks on folder rename, container mount, or cross-machine access).
  - *Anti-Pattern 2 (Window Identity):* Identifying a Game by the VS Code window instance or workspace ID. (Breaks on window reload, split windows, or headless runners).
  - *Anti-Pattern 3 (Process / Port Identity):* Identifying a Game by the running node HTTP port (49152) or PID. (Port 49152 is a Stadium socket, not a project).

## 4. ANALYSIS OF GAME IDENTITY OPTIONS (COMPARISON MATRIX)

To determine how a Game should be uniquely and durably identified, we evaluate five potential strategies against core design criteria:

| Criterion | Option 1: Git Origin / Root Commit | Option 2: Project Marker (`.sideline/game.json`) | Option 3: Absolute Filesystem Path | Option 4: Coach-Owned Global Registry | Option 5: Hybrid Tiered Model (Recommended) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Durability across Clones/Machines** | **High** (Identical git origin or root commit across all clones) | **High** (If committed to repo) | **Zero** (Fails immediately across machines or containers) | **Low** (Machine-local registry cannot be shared without cloud) | **High** (Inherits Tier 1 & 2 durability) |
| **Zero-Config / Frictionless** | **High** (Automatic for any git repository) | **Low** (Requires generating or committing a file) | **High** (Uses existing folder path) | **High** (Automatic on Coach start) | **High** (Automatic via git or registry fallback) |
| **Robustness to Path Rename/Move** | **High** (Git SHA and remote URL are path-agnostic) | **High** (Moves with the folder) | **Zero** (Breaks immediately upon rename or move) | **Medium** (Registry needs heuristic to detect renames) | **High** (Path-independent) |
| **Non-Git / Scratch Directory Support** | **Zero** (Fails if directory is not a git repo) | **High** (Works anywhere) | **High** (Works on any path) | **High** (Assigns synthetic UUID) | **High** (Falls back to Coach registry UUID) |
| **Multi-Root / Monorepo Support** | **Medium** (Sub-projects share root commit unless submodules) | **High** (Each sub-project can have its own marker) | **Low** (Path collisions possible) | **Medium** (Requires root-relative scoping) | **High** (Marker overrides git root when present) |
| **Repo Cleanliness / No Pollution** | **High** (Writes zero files to user repo) | **Medium** (Creates `.sideline/` directory) | **High** (Zero files written) | **High** (Stored in VS Code AppData) | **High** (Zero files required; marker is optional) |
| **Deterministic Fallback to Unknown** | **High** | **High** | **Low** (Always produces a string, even if invalid) | **Low** (Tends to invent synthetic IDs) | **High** (Explicit `Unknown` when untracked & unidentifiable) |

## 5. RECOMMENDED GAME IDENTITY MODEL

We recommend **Option 5: Tiered Hybrid Game Identity**.

This model provides zero-configuration onboarding for standard git repositories, allows deliberate overrides for complex monorepos or enterprise projects via an optional marker file, supports non-git scratch environments gracefully, and strictly falls back to `Unknown` when identity cannot be proven.

### The 4-Tier Resolution Ladder:

```
[Target Workspace Folder]
          |
          v
+------------------------------------+
| Tier 1: Explicit Project Marker    | ---> Found? ---> Use canonical marker gameId & displayName
| (.sideline/game.json)              |
+------------------------------------+
          | Not found
          v
+------------------------------------+
| Tier 2: Git Canonical Fingerprint  |
| - Remote Origin URL hash, OR       | ---> Valid Git Repo? ---> Derive stable gameId: "game_git_<hash>"
| - Root Commit Tree SHA hash        |
+------------------------------------+
          | Not a git repo
          v
+------------------------------------+
| Tier 3: Coach Registry Fallback    |
| (Stored in Coach global/workspace) | ---> Known Local Project? ---> Use persisted local "game_reg_<hash>"
+------------------------------------+
          | Empty / unidentifiable
          v
+------------------------------------+
| Tier 4: Explicit Unknown           |
| (gameId: "unknown", state: unknown)| ---> Never invent false identity; human must open valid workspace
+------------------------------------+
```

### Stable `gameId` Generation Specification:
- **Format:** `game_<source>_<hash8>`
  - `game_marker_<id>` (e.g. `game_marker_sideline_coach` from `.sideline/game.json`)
  - `game_git_<hash8>` (e.g. `game_git_9f82a1c4` derived from `sha256(canonicalGitRemoteUrl)` or `sha256(initialCommitSha)`)
  - `game_reg_<hash8>` (e.g. `game_reg_7b31d04e` for non-git scratch workspaces)
  - `unknown` (reserved literal for unresolvable states)
- **Canonical Git Remote Normalization:**
  Before hashing, git remotes are normalized:
  1. Strip trailing `.git`
  2. Strip protocol prefixes (`https://`, `http://`, `ssh://`, `git@`)
  3. Convert hostname delimiters (e.g. `github.com:owner/repo` -> `github.com/owner/repo`)
  4. Lowercase all characters.  
  *Example:* `git@github.com:nowimhere3/Sideline-Coach.git` and `https://github.com/nowimhere3/Sideline-Coach` both normalize to `github.com/nowimhere3/sideline-coach`, producing the identical hash `e14e0b8a`.

## 7. GAME DISCOVERY & RESOLUTION ALGORITHM

When Coach activates or when workspace folders change (`onDidChangeWorkspaceFolders`), Coach executes the deterministic Game Resolution Algorithm:

```
Algorithm: ResolveActiveGame(workspaceFolders, config)
Input: vscode.WorkspaceFolder[], WorkspaceConfiguration
Output: ResolvedGameContext

1. IF workspaceFolders is empty or undefined:
     RETURN {
       game: { gameId: 'unknown', displayName: 'No Game Open', fingerprintSource: 'unknown' },
       stadium: GetCurrentStadiumIdentity(),
       binding: { gameId: 'unknown', stadiumId: currentStadiumId, rootFsPath: '', isPrimary: false, status: 'unbound' }
     }

2. Let primaryFolder = DeterminePrimaryFolder(workspaceFolders):
     - In single-root: workspaceFolders[0]
     - In multi-root: Check for workspace file setting `coach.primaryFolder` or root containing `.sideline/game.json`, else default to workspaceFolders[0].

3. Check for Tier 1 Marker:
     Let markerPath = path.join(primaryFolder.uri.fsPath, '.sideline', 'game.json')
     IF FileExists(markerPath):
       Let markerData = SafeReadJson(markerPath)
       IF markerData.gameId is valid string:
         RETURN ConstructContext(
           gameId = "game_marker_" + markerData.gameId,
           displayName = markerData.displayName || primaryFolder.name,
           source = 'marker',
           root = primaryFolder.uri.fsPath
         )

4. Check for Tier 2 Git Fingerprint:
     Let gitDir = FindGitDir(primaryFolder.uri.fsPath)
     IF gitDir exists:
       Let remoteUrl = ExecGit(primaryFolder, 'config --get remote.origin.url')
       IF remoteUrl is non-empty:
         Let normalized = NormalizeGitUrl(remoteUrl)
         Let hash = Sha256(normalized).slice(0, 8)
         RETURN ConstructContext(
           gameId = "game_git_" + hash,
           displayName = ExtractRepoName(normalized) || primaryFolder.name,
           source = 'git-remote',
           repoUri = normalized,
           root = primaryFolder.uri.fsPath
         )
       ELSE:
         Let rootCommit = ExecGit(primaryFolder, 'rev-list --max-parents=0 HEAD')
         IF rootCommit is non-empty:
           Let hash = Sha256(rootCommit.trim()).slice(0, 8)
           RETURN ConstructContext(
             gameId = "game_git_" + hash,
             displayName = primaryFolder.name,
             source = 'git-root',
             root = primaryFolder.uri.fsPath
           )

5. Check for Tier 3 Coach Local Registry:
     Let registryKey = "sidelineCoach.projectRegistry.v1"
     Let storedRegistry = coachGlobalState.get(registryKey) || {}
     Let existingId = storedRegistry[primaryFolder.uri.fsPath]
     IF existingId:
       RETURN ConstructContext(gameId = existingId, displayName = primaryFolder.name, source = 'registry', root = primaryFolder.uri.fsPath)
     ELSE:
       Let generatedId = "game_reg_" + RandomHex(8)
       storedRegistry[primaryFolder.uri.fsPath] = generatedId
       coachGlobalState.update(registryKey, storedRegistry)
       RETURN ConstructContext(gameId = generatedId, displayName = primaryFolder.name, source = 'registry', root = primaryFolder.uri.fsPath)

6. Fallback to Tier 4:
     RETURN Explicit Unknown Context.
```

### Multi-Root Workspace Handling:
In multi-root workspaces:
- The server identifies the primary Game via `coach.primaryFolder` or auto-detection.
- Secondary roots are recorded in the `GameStadiumBinding` table as auxiliary mounts.
- If secondary roots belong to completely different git repositories, Coach warns in status that a multi-Game workspace is detected and scopes dispatcher actions to the designated primary Game.

## 8. STORAGE & CANONICAL OWNERSHIP STRATEGY

To maintain clarity and prevent data corruption, Coach must enforce a strict separation of storage tiers:

| Storage Tier | Scope | Location | Ownership | Examples |
| :--- | :--- | :--- | :--- | :--- |
| **Durable Game Identity** | Project-wide (Shared across clones and developers) | Inside the repo or git history | Owned by the Game repository | `.sideline/game.json`, git commit tree, git remote origin |
| **Local Stadium Bindings** | Machine-wide / User-specific | VS Code `globalState` or `~/.sideline/stadium.json` | Owned by the Coach host environment | `stadiumId`, path mappings, machine hardware alias, token secrets |
| **Workspace State** | Window / Folder specific | VS Code `workspaceState` | Owned by the specific VS Code session | Shell PIDs, local window terminal bindings, UI collapse state |
| **Ephemeral Runtime** | In-Memory (Process lifetime) | Node.js process memory (`CoachServer`) | Destroyed on reload / restart | Active SSE connections, uncommitted play buffers, HTTP listener |

## 9. PLAYER ROSTER & CONTROL BINDING

### Are Players Game-Scoped or Stadium-Scoped?
A Player possesses a dual nature:
1. **Logical Assignment is Game-Scoped:** An agent instance (e.g. `Codex 1`) is participating in a specific project's strategy, executing plays against that repository's codebase, and generating reports for that Game.
2. **Physical Execution is Stadium-Scoped:** The OS terminal, PTY process, memory space, child process PID, and IPC socket exist physically on that specific Stadium.

### Integration with Controlled Player Persistence (P1–P28):
In Stage 1.19 / Stage 1.21, Coach established rigorous persistence contracts (P1–P28) using `WorkspaceStateBindingStore`.  
In Q2.2, `ControlledBindingRecord` is extended to include `gameId`:

```typescript
export interface ControlledBindingRecord {
  instanceId: string;
  playerType: string;
  seat: number;
  adapter: string;
  sessionRef: string;
  historyExpected: boolean;
  pendingPlay: PendingPlayBinding | null;
  gameId?: string; // Optional during migration, mandatory once resolved
}
```

### Safety Rule on Restore:
When `PlayerRoster` executes `adoptControlledRestores()`:
1. If `record.gameId` is defined and does **not** match the currently resolved `activeGame.gameId`:
   - Coach places the Player into state `needs-decision`.
   - Error message: `"Player conversation belongs to Game '${record.gameId}', but active Game is '${activeGame.gameId}'. Automatic restore quarantined."`
   - Zero plays are dispatched.
2. If `record.gameId` matches:
   - Normal restore proceeds according to P4–P7.
3. If the user renames or moves the folder:
   - Because `gameId` is derived from git/marker and remains identical, the restore succeeds seamlessly even though `gameRoot` path shifted! (The new `gameRoot` is provided to `ControlOpenRequest`).

## 10. PLAYS & INCOMING REPORTS SCOPING

### Incoming Reports Scoping:
Today, `scanReports()` scans all files matching `coach.reportGlobs`.
Under Game Foundation:
- Each discovered report file's URI is checked against `vscode.workspace.getWorkspaceFolder(uri)`.
- The folder is mapped to its resolved `GameIdentity`.
- The `CoachReport` object is tagged with `gameId: resolvedGame.gameId`.
- The mobile UI displays reports belonging to the current canonical Game. Reports originating outside the current Game's workspace boundaries are marked as `external` or quarantined.

### Play Dispatch Scoping:
When a Play is submitted via `POST /api/dispatch`:
- The request payload is validated against the active Game context.
- If the browser client submits a play with a mismatched `gameId` (e.g. browser was open to an old project before a workspace switch), the server rejects the dispatch with `409 Conflict`: `"Play targeted Game '${body.gameId}', but active Game is '${activeGame.gameId}'."`
- The turn record and dispatch audit log store the canonical `gameId`.

## 11. BROWSER / MOBILE UX ARCHITECTURE

### Evaluation of UX Options:

#### Option A: Single Current Canonical Game (Recommended for Q2.2)
- **Concept:** The mobile interface focuses 100% on the single active Game running on the host Coach instance.
- **Header Layout:**
  ```
  +-------------------------------------------------------------+
  | 🏈 Sideline Coach              [Dot: Live] Connected        |
  | GAME: Sideline Coach                                        |
  | Stadium: Windows (CALGARY-PC) · /SidelineCoach              |
  ```

- **Advantages:**
  - Extremely bounded implementation (minimal HTML/CSS touch).
  - Eliminates cognitive overload for the human on mobile.
  - Leaves zero room for dispatcher routing mistakes.
  - Reuses all existing Q2.1 dispatcher reliability UX components unchanged.

#### Option B: Multi-Game Selector / Switcher (Deferred to Later Quarters)
- **Concept:** A dropdown or drawer allowing the user to view and switch between multiple open workspaces or remote daemons from a single phone screen.
- **Why it is Rejected for Q2.2:**
  - Requires multiplexed SSE streams, cross-window messaging, and complex state synchronization across separate VS Code processes.
  - Massively widens the scope beyond foundational identity into multi-session routing.
  - Unnecessary for the primary workflow where a developer works in one primary workspace at a time.

### Recommendation:
Implement **Option A** in Q2.2. Lay the complete data model foundation so that Option B can be added in Quarter 3 or 4 without breaking schema changes.

## 12. SECURITY & BOUNDARIES

1. **Repo Boundary Validation:**
   - Coach must verify that any resolved `gameRoot` is a canonical absolute path without unresolvable symlinks that escape the repository root.
   - All report scanning must stay within configured workspace roots (`exclude: **/{.git,node_modules}/**`).
2. **Path Traversal Guards:**
   - When serving reports or accepting file paths via API, paths containing `..` or leading to parent directories outside the Game root are strictly rejected with `403 Forbidden`.
3. **Token Auth Integrity:**
   - Coach's timing-safe access token authentication (`crypto.timingSafeEqual`) continues to protect all endpoints. Access is bound to the Stadium daemon.

## 13. EDGE CASES & FAILURE MODES

| Edge Case | Detection | Coach Behavior & UI Presentation | Safety Guarantee |
| :--- | :--- | :--- | :--- |
| **No Workspace Open** | `workspaceFolders` is undefined or empty | `game.gameId = 'unknown'`. UI displays `Game: Unknown (Open a workspace in VS Code)`. Dispatcher disabled. | Controlled players refuse to launch (`400 Bad Request`). No plays dispatched. |
| **Detached HEAD / No Git** | Folder exists, but `.git` directory absent and no marker | Falls back to Tier 3 Coach Local Registry. Assigns stable `game_reg_<hash8>`. UI displays folder name. | Project retains stable identity across reloads on this machine. |
| **Renamed / Moved Folder** | User moves folder on disk; git remote/history preserved | Tier 2 Git Fingerprint matches existing `gameId`. Restores succeed with new path. | Conversations resume cleanly despite filesystem move. |
| **Two Windows Open to Same Repo** | Two VS Code instances open to identical git repo | Both resolve identical `gameId`, but distinct `stadiumId` (or window session IDs). Port conflict handled by Coach port finder. | P10 duplicate instance quarantine prevents colliding provider sessions. |
| **Offline Operation** | No internet connection to query remote git server | Git remote URL is read from local `.git/config` file (requires zero network calls). | Fully functional offline. |
| **Monorepo with Multiple Sub-Projects** | Single git repo contains multiple independent services | Optional `.sideline/game.json` in sub-folder establishes distinct `gameId`. If absent, shares monorepo root `gameId`. | Flexible, opt-in granular identity. |

## 16. ARCHITECTURAL RISKS & MITIGATIONS

1. **Risk: Git CLI Performance Latency:**
   - *Concern:* Spawning `git config` or `git rev-list` on every `/api/status` poll could cause CPU spikes or UI lag.
   - *Mitigation:* Resolve `GameIdentity` **once** at startup and cache the result. Invalidate the cache only when VS Code fires `onDidChangeWorkspaceFolders` or file watcher detects `.git/config` / `.sideline/game.json` changes. Status polls return cached in-memory identity (0ms latency).
2. **Risk: Backward Compatibility with Existing Persistent Records:**
   - *Concern:* Existing `ControlledBindingRecord` items in `workspaceState` do not have `gameId` populated.
   - *Mitigation:* Treat missing `gameId` as legacy-compatible during migration; adopt them and backfill the current `gameId` upon next save.
3. **Risk: Windows vs POSIX Path Discrepancies:**
   - *Concern:* Git remotes or paths formatted with backslashes on Windows could hash differently from POSIX.
   - *Mitigation:* Normalize all paths and URLs with forward slashes, strip case where appropriate, and lowercase URLs prior to hashing.
