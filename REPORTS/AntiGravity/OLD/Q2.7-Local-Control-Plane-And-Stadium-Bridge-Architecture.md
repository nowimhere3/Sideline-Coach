## 1. VERDICT & EXECUTIVE SUMMARY

### VERDICT: GO WITH CONSTRAINTS — LOCAL CONTROL PLANE / STADIUM BRIDGE ARCHITECTURE READY

Quarter 2 Play Q2.7 (**LOCAL CONTROL PLANE AND STADIUM BRIDGE ARCHITECTURE**) is complete.

This architectural reconnaissance defines the bridge mechanism allowing Sideline Coach to support multiple simultaneous active VS Code windows (and future Codespaces/remote environments) without port collisions, listener conflicts, or cross-Game state leakage.

### Core Architectural Conclusions

1. **Stadium Extensions Connect Outbound:**
   - Stadium extensions make authenticated, persistent **OUTBOUND** connections to the Control Plane.
   - Individual VS Code windows **never listen on TCP ports**. This completely eliminates `EADDRINUSE` port collisions when multiple windows are open on the same machine.
   - This exact same outbound topology directly translates to the future cloud Control Plane without refactoring.

2. **Single Canonical Browser Endpoint:**
   - The Control Plane alone owns the single browser-facing HTTP/WebSocket port (default: `127.0.0.1:3100` or configured `coach.port`).
   - The human on desktop or mobile always connects to one single stable URL.

3. **Durable Stadium Identity vs Session Instance Identity:**
   - **Durable `stadiumId`:** Stable machine fingerprint surviving window restarts and system reboots (e.g. `stadium_win32_<machineHash>`).
   - **Session `instanceId`:** Transient activation identifier unique to each VS Code window / extension host process (e.g. `inst_<stadiumId>_<pid>_<timestamp>`).
   - Multiple open VS Code windows are correctly identified as concurrent sessions belonging to the same host Stadium.

4. **Preserved Certified Invariants Across the Bridge:**
   - **Exact Target:** Dispatches route by explicit coordinates: `(stadiumId, gameId, playerInstanceId)`. No display name guessing.
   - **Acknowledgement Boundaries:** Control Plane marks `Received` **only** when the local Stadium Player adapter confirms write-ahead logging and provider ingress. Connection drops prior to ingress resolution strictly yield `Unknown`.
   - **Zero Automatic Resends:** In accordance with C8/C9/P20/P21 invariants, an `Unknown` outcome is never automatically resent by the bridge.

5. **Q2.6 Field Proof Formally Recorded:**
   - Human field testing in `[Extension Development Host] GS3` verified Q2.6 Multi-Game Foundation end-to-end: `+ Add Game` works, non-connected games are truthfully `Offline`, switching to GS3 restores Roster, Incoming, and routing immediately without manual browser refresh.
   - **Q2.6 is formally recorded as FIELD-PROVEN.**

### Candidate Evaluation Verdict: OPTION D (Auto-Spawned Detached Daemon)

- **Zero Human Friction:** The user simply installs the Sideline Coach extension and presses `F5` (or opens VS Code). No manual terminal commands or separate background services required.

## 4. STADIUM IDENTITY & SESSION MODEL

### Durable Identity vs Session Identity

A Stadium is **NOT** a Game, **NOT** a window title, **NOT** a port, and **NOT** a terminal.

```typescript
export interface StadiumIdentity {
  readonly stadiumId: string;       // Durable machine/environment fingerprint (e.g. 'stadium_win32_8f2b1c')
  readonly displayName: string;     // Human-friendly label (e.g. 'Windows Desktop', 'MacBook Pro', 'Codespace')
  readonly platform: 'win32' | 'darwin' | 'linux';
  readonly stadiumType: 'vscode-desktop' | 'vscode-web' | 'codespace' | 'standalone';
}

export interface StadiumSessionRecord {
  readonly instanceId: string;      // Unique per window/extension-host activation (e.g. 'inst_win32_pid1204_ts1710')
  readonly stadiumId: string;       // Foreign key to StadiumIdentity
  readonly pid: number;             // Extension host PID
  readonly startedAt: number;
  lastSeenAt: number;
  connectionState: 'connected' | 'reconnecting' | 'offline';
  games: StadiumGameBinding[];      // Games currently open in this window
}

export interface StadiumGameBinding {
  readonly gameId: string;
  readonly displayName: string;
  readonly rootFsPath: string;
  readonly isPrimary: boolean;
}
```

### Deterministic Resolution Rules
1. **Durable `stadiumId`:**
   - On desktop: Derived from stable machine fingerprint (`crypto.createHash('sha256').update(os.hostname() + os.userInfo().username).digest('hex').slice(0, 8)`), cached in `~/.sideline/stadium-id`.
   - On GitHub Codespaces: Reads `$CODESPACE_NAME` (e.g. `stadium_codespace_octocat-repo-1234`).
   - In Docker/Containers: Reads container machine-id or environment variable `SIDELINE_STADIUM_ID`.
2. **Window Session `instanceId`:**
   - Minted fresh on each `activate()` call: `inst_${stadiumId}_p${process.pid}_${Date.now()}_${crypto.randomBytes(4).toString('hex')}`.
   - Distinguishes Window 1 from Window 2 on the same physical desktop.
3. **Cloned Environment Protection:**
   - If an entire VM or disk image is cloned, the first activation detects a mismatch between cached machine credentials and OS environment, generating a fresh durable `stadiumId`.

### Cardinality Rules
1. **One Game → One Live Stadium (Today's Standard):**
   - Project `GS3` is open in Window 1 (Stadium 1).
   - Project `SidelineCoach` is open in Window 2 (Stadium 2).

   - Project `Browser Gallery` is in the Game Registry, but neither Window 1 nor Window 2 has it open.
   - Appears as **Offline** with dispatch safely disabled (`400 Bad Request`).
3. **One Game → Multiple Live Stadiums (Duplicate Binding):**
   - User has `GS3` open on both Windows Desktop and a remote Codespace.
   - **Fail-Safe Policy for Q2.8 First Slice:**
     - The first slice requires **one authoritative connected Stadium per Game**.
     - If Stadium 2 connects claiming a `gameId` already actively bound by Stadium 1, the Control Plane **refuses to guess**.
     - The Game status becomes `Ambiguous / Conflicted`.
     - Automated dispatch is blocked until the human selects which Stadium to target via an explicit disambiguation chip (`[ Use Windows ]` or `[ Use Codespace ]`).

### Critical Acknowledgement Boundaries (Answers to Questions 11 & 12)
- **When does Control Plane say `Sending…`?** Immediately when HTTP/WS request is validated and forwarded to the target Stadium.
- **When does Control Plane say `Received`?** **ONLY** when the target Stadium returns `dispatch.accepted` (indicating provider ingress confirmed and write-ahead logged).
- **What happens if connection drops between Control Plane and Stadium?**
  - If the socket drops *before* `dispatch.accepted` is received, the Control Plane marks the dispatch outcome as **`Unknown`**.
  - The browser restores the prompt draft.
  - **Zero automatic resends are allowed.** Re-sending blindly could duplicate provider turns or billing.

## 10. TRANSPORT & PORT OWNERSHIP

### Transport Decision: WebSocket over Localhost (`ws://127.0.0.1:3100/stadium`)
- **Browser Compatibility:** Native `WebSocket` API supported in all browsers.
- **Node.js Compatibility:** Built into Node.js runtime and standard lightweight libraries (`ws`).
- **Cross-Platform:** Identical behavior on Windows, macOS, and Linux (unlike named pipes or domain sockets which have platform-specific permission and path semantics).
- **Cloud Migration Path:** 100% cloud-ready. Switching from local to cloud is a simple change from `ws://127.0.0.1:3100` to `wss://relay.sidelinecoach.com`.

### Port Ownership Rules
1. **Single Local Port:** The Control Plane daemon alone binds `127.0.0.1:3100` (or `coach.port`).
2. **Zero Extension Ports:** Extension hosts bind **zero** listener ports. They are purely outbound WebSocket clients.
3. **Occupied Port Handling:**
   - If port 3100 is occupied by a non-Sideline process, the daemon increments to 3101, 3102, etc.
   - The daemon writes its active port, PID, and local token to `~/.sideline/control-plane.json`.
   - Activating extensions read `~/.sideline/control-plane.json` to discover the live port.

## 11. LOCAL AUTHENTICATION FIRST

- **Security Principle:** Even on localhost, IPC must not be trustless.
- **Local Pairing Secret:**
  - Upon startup, the Control Plane generates a 32-byte cryptographic token (`sideline_sec_<randomHex>`).
  - Stored at `~/.sideline/token` with strict OS permissions (`0600` on Unix; Windows DACL restricted to current user SID).
  - Also stored in VS Code `context.secrets` for seamless extension access.
- **Handshake Verification:**
  - Every Stadium connecting over `ws://` must pass `token` in the `stadium.hello` handshake frame.
  - Every HTTP/SSE browser client must pass `token` via `Authorization: Bearer <token>` or `?token=<token>` query param.

## 12. FAILURE & RECONNECT CONVERGENCE

| Failure Scenario | Local Behavior | Browser Dashboard Impact | Reconnect Resolution |
|---|---|---|---|
| **VS Code Window Closes** | Control Plane detects socket close; marks Stadium session `offline` | Games open in that window turn `Offline`; dispatch disabled | If reopened, extension reconnects; Games become `Connected` without browser refresh |
| **Extension Host Crashes** | Heartbeat timeout fires after 15s; Stadium session purged | Roster shows `No Stadium Connected`; warning chip rendered | VS Code restarts extension host; fresh `instanceId` re-registers |
| **Control Plane Restarts** | Extensions detect disconnect; enter exponential backoff retry (1s, 2s, 5s) | Dashboard shows `Reconnecting…` dot; input disabled | Daemon comes up; extensions reconnect, push snapshots, dashboard turns green |
| **Temporary Network Drop** | Socket drops; pending in-flight dispatch without ingress becomes `Unknown` | In-flight status becomes `Unknown`; prompt draft preserved | Reconnect synchronizes state; no duplicate send |
| **Game Moves to Other Window** | Window 1 closes game; Window 2 opens game | Seamless: Game stays `Connected`; active Stadium shifts | Control Plane updates binding; dashboard remains steady |

## 14. QUESTIONS THE REPORT MUST ANSWER (1–18)

1. **What should the local Control Plane process actually be?**
   A lightweight, zero-dependency Node.js background process auto-spawned detached by the first activating extension host (or run in-process by the primary host in the first slice).
2. **Should it live inside one VS Code extension host or outside VS Code?**
   Outside individual extension hosts as a detached daemon process, ensuring it survives individual window closures and eliminating port contention.
3. **How do multiple extension hosts discover it?**
   Via a canonical user-local JSON file: `~/.sideline/control-plane.json` (containing `{ port, pid, token, startedAt }`).
4. **How does each Stadium authenticate/register?**
   Over an outbound WebSocket connection sending `stadium.hello` with the local pairing token read from `~/.sideline/token`.
5. **What is stable Stadium identity vs session identity?**
   Stable `stadiumId` represents the host machine/environment (durable fingerprint); `instanceId` represents the specific running VS Code window process (session lifetime).
6. **What data stays Stadium-local?**
   Provider API credentials, OAuth tokens, active terminal PTYs, child processes, local file descriptors, and exact OS paths.
7. **What data moves into Control Plane ownership?**
   Game Registry, Stadium Registry, global routing decisions, aggregated Incoming report summaries, active dispatch lifecycle states, and browser SSE distribution.
8. **What exact transport should Q2 use locally?**
   WebSocket over localhost (`ws://127.0.0.1:3100/stadium`) for Stadiums, combined with HTTP/SSE for browser dashboards.
9. **How do we avoid port collisions?**
   Stadium extensions connect strictly outbound; they never open TCP listener ports. Only the Control Plane binds port 3100.
10. **How does the browser connect to one canonical UI endpoint?**
    The browser always connects to `http://127.0.0.1:3100/?token=<token>`. All open windows and games are visible in that single interface.
11. **How are dispatch acknowledgements preserved safely across the bridge?**
    Via strict two-phase ingress confirmation: Control Plane marks `Received` only after Stadium logs write-ahead and receives provider `turn/start` acceptance. Premature drops become `Unknown`.
12. **How does reconnect/reconciliation work?**
    On reconnect, Stadium sends `roster.snapshot` and `capability.snapshot`. The Control Plane reconciles active `turnRef`s without altering surviving provider threads.
13. **How are reports/events aggregated without cross-Game leakage?**
    Every report event carries explicit `gameId`. The Control Plane tags and indexes reports by `gameId`; browsers query and filter strictly by `selectedGameId`.
14. **How does this evolve into cloud-hosted Control Plane later?**
    The extension's `StadiumClient` code is 100% outbound WebSocket. Pointing the extension to a cloud relay requires only changing the URL and authentication bearer token.
15. **How does this interact with VSIX installation/distribution?**
    Zero friction. The VSIX packages both the extension client and daemon script. It installs normally via VS Code's extension manager.
16. **What is the smallest Q2.8 implementation slice?**
    Implement `StadiumClient` (outbound WebSocket) in the extension, with CoachServer embedding the WebSocket Hub on port 3100. When Window 2 opens, it connects as a client to Window 1's server.
17. **What automated tests are mandatory?**
    A 20-scenario suite verifying multi-stadium registration, heartbeat liveness, multi-window game isolation, cross-stadium routing, and acknowledgement preservation.
18. **Does implementation require a premium Opus architecture review?**
    **NOT REQUIRED for local Q2.8 implementation.** (Detailed rationale below).

## 15. PREMIUM OPUS ARCHITECTURE REVIEW RECOMMENDATION

### RECOMMENDATION: NOT REQUIRED (for Q2.8 Local Slice)

**Technical Reasoning:**
1. **Concrete, Bounded Primitives:** The local Stadium Bridge requires no complex distributed consensus (Paxos/Raft), multi-region syncing, or cloud billing infrastructure. It is a straightforward local WebSocket hub-and-spoke pattern between Node processes on `localhost`.
