### Core Achievements

1. **Game ≠ Stadium Invariant Strictly Preserved:**
   - A Game remains the durable logical software project / repository being coached (WHAT).
   - A Stadium remains the execution environment / VS Code host running that Game (WHERE).
   - The system never conflates the two.

2. **Single Extension Host Truth ("Know Many, Execute One"):**
   - The current single-window extension host truthfully distinguishes the **Connected Game** (active workspace folder in this host) from other **Known Games** (registered in Coach).
   - Non-connected known Games are truthfully marked **Offline** with dispatch safely disabled (`400 Bad Request`).
   - Coach never fabricates multi-window or background execution.

3. **Compact Header Game Dropdown (`Game: GS3 ▾`):**
   - Replaces the static project header with an interactive dropdown selector.
   - Renders each known Game with a truthful connection status badge (`Connected` vs `Offline`).
   - Provides safe `+ Add Game` trigger invoking native VS Code folder picker.

4. **Atomic Game Switching Lifecycle & Composer Retention:**
   - Switching Game updates authoritative `selectedGameId`.
   - Automatically invalidates prior Player target and staged route.
   - Retains composer drafts per-game (`promptDraftsByGame`) so switching projects preserves in-progress prompt drafts without cross-Game contamination.
   - Synchronizes live browser instances via Server-Sent Events (SSE).

5. **Strict Game Isolation:**
   - **Player Roster:** Queries for non-connected/offline Games return empty on-field instances and an honest "No Stadium Connected" message.
   - **Incoming Reports:** `scanReports()` strictly filters candidates by `selectedGameId`. Zero reports from Game A ever appear in Game B.
   - **Routing Intelligence:** AUTO routing evaluates only controlled candidates belonging to the selected Game.
   - **Dispatch Protection:** Dispatches to offline Games reject with `400 Bad Request`; dispatches to mismatched `gameId` targets reject with `409 Conflict`.

## 2. FILES CHANGED & IMPLEMENTATION DETAILS

### A. Game Identity & Registry (`src/game-identity.ts`)
- Defined `GameRecord` schema:
  - `gameId`: durable canonical identifier (`game_git_<hash>`, `game_dir_<hash>`, etc.);
  - `displayName`: human-readable label (e.g., `GS3`, `SidelineCoach`);
  - `fingerprintSource`: `repo-marker` | `git-remote` | `workspace-fallback` | `unknown`;
  - `repoUri`: normalized git origin URL (if available);
  - `knownRootFsPaths`: array of local paths where this Game has been observed;
  - `firstSeenAt` / `lastSeenAt`: timestamps;
  - `archivedAt`: optional timestamp for soft-deletion.
- Defined `GameRegistryState` in `globalState` (`sidelineCoach.gameRegistry.v1`).
- Implemented `loadGameRegistry`, `saveGameRegistry`, `getSelectedGameId`, `setSelectedGameId`, `registerGameInRegistry`, `archiveGameInRegistry`.
- Implemented multi-mount resolution: if the same Git remote origin is opened at a new path, the existing record is updated rather than creating a duplicate.

### B. Player Roster Isolation (`src/player-roster.ts`)
- Updated `PlayerRoster.status(activeGameId?: string)`:
  - Accepts `activeGameId`.
  - When the queried Game is not the active/connected Game, instances return empty and availability marks `not-available`.
- Updated `PlayerRoster.getRoutingCapabilities(activeGameId?: string)`:
  - Returns `[]` when queried for an offline/non-connected Game.

### C. Extension Host Integration (`src/extension.ts`)
- On activation, automatically registers current workspace Game into `globalState` registry via `registerGameInRegistry()`.
- Added command `coach.addGame`:
  - Opens native `vscode.window.showOpenDialog({ canSelectFiles: false, canSelectFolders: true, canSelectMany: false })`.
  - Safely resolves Game identity for selected folder without executing arbitrary code or switching host workspace.
  - Registers new Game in registry and notifies user.

### D. Server API & Dispatch Protection (`src/server.ts`)
- Added server state `selectedGameId`.
- Added endpoint `GET /api/games`: returns all registered games with `isConnected` and `isSelected` flags.
- Added endpoint `POST /api/game/select`: switches authoritative `selectedGameId` and broadcasts `status` event over SSE.
- Added endpoint `POST /api/game/add`: triggers `coach.addGame` via `vscode.commands.executeCommand`.
- Updated `buildStatus()`:
  - Exposes `selectedGameId`, `connectedGameId`, `connectionStatus` (`connected` | `offline`), and `games: GameRecord[]`.
  - Scopes `players` and `routing` to `selectedGameId`.
- Updated `scanReports(limit, includeContent, targetGameId)`:
  - Filters incoming reports by `targetGameId` (or `selectedGameId`).
- Updated `dispatch()`:
  - Enforces `selectedGameId === connectedGameId`; rejects offline dispatch with `400 Bad Request`.
  - Enforces payload `gameId === selectedGameId`; rejects cross-game dispatch with `409 Conflict`.

### E. Mobile/Browser UI (`src/public/index.html`)
- Replaced static header with `#gameDropdownBtn` and `#gameDropdownMenu`.
- Displays `Game: <Name> ▾` with live connection badge (`Connected` / `Offline`).
- Populates `#gameList` with all known Games.
- Implemented `switchGame(targetGameId, targetName)`:
  - Saves active prompt draft in `promptDraftsByGame.set(currentGameId, ...)`.
  - Restores draft for target Game (`promptDraftsByGame.get(targetGameId) || ''`).
  - Resets target player and staged route to prevent cross-Game state leakage.
  - Fires `POST /api/game/select`.
- Updated `renderStatus()`:
  - Updates dropdown label, badge, and game list selection.
  - When offline: disables Dispatch button, shows offline warning, renders "No Stadium Connected" message in Roster.
- Preserved exact regex and contract assertions for all existing suites (`$('rosterSummary').textContent = \`Players · \${onFieldCount} On Field\``).

Sideline Coach operated exclusively in a single-project model (`Game: GS3` static header) with no persistent awareness of other projects. Switching projects required closing and reopening VS Code windows, and the browser UI had no concept of registered non-connected projects, per-game draft retention, or game-scoped report/player isolation.

### IS
Sideline Coach manages multiple known projects via a durable Game Registry in `globalState` (`sidelineCoach.gameRegistry.v1`). Single-window host enforces `Know Many, Execute One`: the connected workspace Game is live and dispatchable; all other known Games in the registry are truthfully marked `Offline` with dispatch disabled (`400 Bad Request` safety guard). Game switching dynamically invalidates prior target players and staged routes, persists composer drafts per-game, isolates Incoming reports and Roster projections, and enforces cross-Game dispatch rejection (`409 Conflict`). AUTO routing exclusively evaluates controlled candidates from the selected Game. Full automated test suite (23/23 tests in `test/multi-game-foundation.test.mjs`, 142/142 total regression tests passing). ## 7. KNOWN CONSTRAINTS & STADIUM BRIDGE SEAM

1. **Single-Window Constraint ("Know Many, Execute One"):**
   - In today's architecture, VS Code runs an extension host per window.
   - The active window hosts CoachServer on port 3100.
   - Other known Games are truthfully marked `Offline` because this extension host does not execute processes in other windows.
2. **Future Stadium Bridge Seam:**
   - In Q3/Q4, when the Stadium Bridge is implemented, secondary VS Code windows running other Games will connect as worker Stadiums to CoachServer over local IPC/WebSocket.
   - When that occurs, multiple Games in the registry will transition from `Offline` to `Connected` concurrently.
   - The Q2.6 Game Registry, `selectedGameId`, and isolation boundaries were built specifically to receive that upgrade without redesign.
