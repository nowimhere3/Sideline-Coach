### Architectural Governance & Constraints

- **Rule: OBSERVATION ≠ POLICY:** Provider discovery code is strictly decoupled from routing decisions. Discovery observes *what is available*; routing policy determines *what Coach chooses*.
- **Constraint 1 (No Fabricated Capacity Routing):** Because Claude does not programmatically expose remaining quota, Q2.3 AUTO routing **must not** base routing decisions on provider capacity or fabricate remaining percentages. Capacity telemetry is captured as an observation capability for future work.
- **Constraint 2 (Exact Target Guarantee):** Routing resolves to an exact `playerInstanceId` scoped to the canonical `gameId`. Dispatch preserves exact instance targeting and strictly vetoes cross-Game dispatch or silent sibling substitution.
- **Constraint 3 (Certified Control Precedence):** AUTO routes exclusively to certified controlled Players (`Codex · Controlled`). Uncertified legacy terminals (`Terminal.sendText`) are excluded from AUTO by default and surfaced in MANUAL with explicit uncertified badging.
- **Constraint 4 (Strict MANUAL Hierarchy):** In MANUAL mode, `Player → Model → Effort` forms a strict dependency chain: selecting a Player populates only valid models for that provider; selecting a Model populates only valid reasoning efforts for that model.

## 7. PROVIDER-NEUTRAL CAPABILITY SCHEMA

The capability architecture defines three minimal provider-neutral contracts in `src/capability/`:

```typescript
export type CapabilityFreshness = 'live' | 'cached' | 'stale' | 'unavailable';

export interface ModelDescriptor {
  readonly id: string;
  readonly displayName: string;
  readonly description?: string;
  readonly isDefault: boolean;
  readonly supportedEfforts: string[];
  readonly defaultEffort?: string;
}

export interface ProviderCapabilitySnapshot {
  readonly provider: string;            // 'codex' | 'claude' | 'agy'
  readonly authenticated: boolean;
  readonly accountEmail?: string;
  readonly planType?: string;
  readonly models: readonly ModelDescriptor[];
  readonly defaultModelId?: string;
  readonly observedAt: number;
  readonly freshness: CapabilityFreshness;
}

export interface PlayerRoutingCapability {
  readonly instanceId: string;
  readonly playerType: string;
  readonly transport: 'controlled' | 'legacy';
  readonly fieldLabel: string;
  readonly state: 'ready' | 'busy' | 'unavailable' | 'needs-verification';
  readonly capability: ProviderCapabilitySnapshot;
  readonly activeModel?: string;
  readonly activeEffort?: string;
}
```

## 8. CAPABILITY FRESHNESS & CACHE RULES

1. **Cache TTL:**
   - **`live`:** Observed within the last 60 seconds.
   - **`cached`:** Between 60 seconds and 10 minutes.
   - **`stale`:** Older than 10 minutes (triggers asynchronous background re-discovery).
   - **`unavailable`:** Discovery failed or provider child unreachable.
2. **Invalidation Seams:**
   - Player instance put on field or resumed.
   - Player Control Host emits `{ kind: 'settings' }`.
   - Explicit human "Refresh Roster" action.
3. **Safety Rule:**
   - AUTO never executes routing on `unavailable` capability snapshots.
   - If discovery is `unavailable`, AUTO requests human manual routing or halts safely.

## 9. MANUAL DEPENDENCY ARCHITECTURE

MANUAL routing enforces a strict, cascade-filtered UI dependency:

```text
[ Select Player ]  (Codex 2 · Controlled)
        ↓  (loads Codex capability snapshot)
[ Select Model ]   (GPT-6-Astra | GPT-5.6-Sol [Default] | GPT-5.6-Terra | GPT-5.6-Luna | GPT-5.5 | Provider Default)
        ↓  (loads selected model's supportedReasoningEfforts)
[ Select Effort ]  (Low | Medium | High [Default] | Extra High | Max | Ultra)
```

### Hierarchy Rules
1. Selecting a new Player automatically populates the Model selector with that Player's valid models and selects its active/default model.
2. Selecting a Model automatically populates the Effort selector with only the effort levels supported by that model.
3. If a model does not support reasoning effort, the Effort selector is disabled and displays `Not Supported`.
4. Invalid combinations (e.g. `GPT-5.5` with `Ultra`) are impossible to select in the DOM.

## 14. EXACT-TARGET & GAME-SCOPING PRESERVATION

- **Target Safety:**
  - Routing resolves to an exact immutable `playerInstanceId` (e.g. `codex-inst-84f9`), never a terminal name or generic type.

## 17. PRE-SEND ROUTE REVALIDATION

When the human clicks `Dispatch Play`:
1. **Target Liveness Check:** Ensure `playerInstanceId` is still `live` and `ready`.
2. **Game Invariance Check:** Verify `gameId === activeGameId`.
3. **Collision / Busy Guard:** If the selected player became `busy` while the user was typing:

   - In `AUTO`: re-stage to another available controlled player if one exists, or notify the human.
