## 2. EMPIRICAL RUNTIME PROBE & FEASIBILITY ANALYSIS

### Question 1 & 2: Detached Process Feasibility & Parent Window Closure on Windows

We performed an empirical runtime probe on Windows 11 under the actual workspace environment:

1. **The VS Code Executable as Node Runtime:**
   - Inside the VS Code Extension Host, `process.execPath` points to `Code.exe` (e.g. `C:\Users\dmcal\AppData\Local\Programs\Microsoft VS Code\Code.exe`).
   - We verified empirically that running `Code.exe` with environment variable `ELECTRON_RUN_AS_NODE: '1'` executes pure Node.js v24.18.1 with full standard library support:
     ```text
     $env:ELECTRON_RUN_AS_NODE=1; & 'C:\...\Code.exe' -e "console.log('ELECTRON NODE OK', process.version)"
     Output: ELECTRON NODE OK v24.18.1
     ```
   - In standard Node environments (CLI, test suites), `process.execPath` is `node.exe`, which ignores `ELECTRON_RUN_AS_NODE` and executes Node directly.
   - **Conclusion:** `process.execPath` with `ELECTRON_RUN_AS_NODE: '1'` is completely universal across both Extension Development Host and production VS Code. The user does not even need Node.js installed on their machine.

2. **Detached Process Survival on Windows:**
   - We tested spawning a detached child script using `child_process.spawn`:
     ```typescript
     const out = fs.openSync(logFile, 'a');
     const child = child_process.spawn(process.execPath, [daemonScript], {
       detached: true,
       stdio: ['ignore', out, out],
       windowsHide: true,
       env: { ...process.env, ELECTRON_RUN_AS_NODE: '1' }
     });
     fs.closeSync(out);
     child.unref();
     ```
   - When the parent process immediately exited (`process.exit(0)`), the child process **continued executing independently on Windows**, writing heartbeats to disk without being killed by the parent's exit.
   - **Conclusion:** On Windows, a detached unreferenced child process safely survives the termination or closure of its parent VS Code window.

## 3. SPAWN, DISCOVERY & RECOVERY MECHANICS

### Questions 3 & 4: Daemon Script Location in Dev Mode vs Installed VSIX Mode
- Both modes use the standard VS Code API: `context.asAbsolutePath('out/control-plane/daemon.js')`.
- **In Development Mode (`F5`):** Resolves to `C:\Users\dmcal\Documents\GitHub\SidelineCoach\out\control-plane\daemon.js`.
- **In Installed VSIX Mode:** Resolves to `~/.vscode/extensions/local.sideline-coach-0.1.0/out/control-plane/daemon.js`.
- Zero environment-specific hacks required.

### Question 5: Spawn Race Protection (Simultaneous Window Startup)
When two VS Code windows activate simultaneously:
1. **Lockfile Mutex (`~/.sideline/control-plane.lock`):**
   - The activating extension attempts to acquire a lockfile via `fs.openSync(lockPath, 'wx')` (`O_CREAT | O_EXCL`).
   - At the OS filesystem level, `O_EXCL` is strictly atomic: exactly one extension host succeeds.
   - The winner acquires the lock and spawns the daemon.
   - The loser yields, waits up to 2000ms (polling every 100ms), and checks for the appearance of `control-plane.json` and a healthy response on `/api/health`.
2. **Port Binding as Ultimate Safety Rail:**
   - The daemon itself binds TCP port `127.0.0.1:3100`. Only one process can bind the port.
   - If an edge-case duplicate was spawned, the second daemon encounters `EADDRINUSE` on startup and immediately exits cleanly with zero side-effects.

### Questions 6 & 7: Discovery Record (`~/.sideline/control-plane.json`) & Dead PID Recovery
- **File Path:** `~/.sideline/control-plane.json` (user-local directory).
- **Contents:**
  ```json
  {
    "protocolVersion": 1,
    "port": 3100,
    "pid": 31180,
    "startedAt": 1710182400000,
    "controlPlaneUrl": "http://127.0.0.1:3100"
  }
  ```
- **Security Invariant:** No pairing secrets or sensitive tokens are stored in `control-plane.json`. Tokens are stored in a separate restricted file (`~/.sideline/token`, permissions `0600`).
- **Dead PID Recovery:**
  Before spawning, an extension reads `control-plane.json` and tests health:
  1. Checks if PID is alive via `process.kill(record.pid, 0)`.
  2. Pings `GET http://127.0.0.1:port/api/health` with a 250ms timeout.
  3. If health check succeeds: Connects immediately as Stadium client.
  4. If PID is dead (`ESRCH`) or health check fails: The record is recognized as stale (leftover from an OS crash or reboot). The extension removes the stale lockfile and JSON record, then safely spawns a fresh daemon.

## 4. PORT OWNERSHIP & LOCAL AUTHENTICATION

### Question 8: Port Ownership & Occupied Ports
- **The Invariant:** ONLY the detached Control Plane binds a listener port. Stadium extensions bind **ZERO** listener ports.
- **Occupied Port Handling:**
  - If default port 3100 is occupied by an unrelated non-Sideline process, the Control Plane increments to 3101, 3102, etc.
  - The Control Plane writes the bound port to `control-plane.json`.
  - Stadium clients and the `Coach: Copy Mobile URL` command read `control-plane.json` to get the authoritative URL.
  - The developer always opens a single dashboard URL.

### Question 9: Local Authentication
- **Pairing Secret:**
  - Control Plane generates a 32-byte cryptographic token (`sideline_sec_<hex>`) on initial setup.
  - Stored at `~/.sideline/token` with strict OS permissions (`0600`).
  - Read by Stadium extensions and passed in the `stadium.hello` handshake frame.
  - Read by browser dashboards via URL query param (`?token=<token>`) or `Authorization: Bearer` header.
  - Provider credentials (API keys, ChatGPT tokens, OAuth refresh tokens) remain 100% Stadium-local; they are NEVER transmitted to the Control Plane.

## 5. DAEMON LIFECYCLE & WEBSOCKET DEPENDENCY

### Question 10: Daemon Lifecycle Policy
- **Policy: Connected-Refcount with Idle Timeout.**
  1. The Control Plane daemon remains running as long as at least **one** Stadium client is connected OR an active Play is executing.
  2. When all Stadium clients disconnect (e.g. all VS Code windows are closed) AND no web browser is active:
     - An idle timer starts (default: **30 minutes**).
     - If a new VS Code window opens before the timer expires, the timer cancels and the daemon remains alive.
     - If the timer expires with 0 connected Stadiums and 0 active browsers: the daemon terminates cleanly.
  3. **Benefits:**
     - Closing Window 1 does not kill the server while Window 2 remains open.
     - Quick window reloads/restarts do not incur cold-start latency.
     - The PC does not accumulate orphaned background processes after work concludes.

### Question 11: WebSocket Dependency & Packaging
- **Dependency:** Add `ws` (and `@types/ws`) to `package.json` dependencies.
- **Why `ws`:** It is the universal, zero-native-compilation, lightweight Node.js standard (~50KB pure JS).
- **Packaging:** Bundles cleanly into `out/` during compilation.
- **Protocol Types:** Shared pure TypeScript contracts in `src/control-plane/protocol.ts` are imported by both `StadiumClient` and `ControlPlaneServer`.

## 6. STADIUM IDENTITY & GAME BINDINGS

### Durable Stadium ID vs Session Instance ID
- **Durable `stadiumId`:**
  - Generated once on initial activation as a UUID (`crypto.randomUUID()`) and persisted in `~/.sideline/stadium-id`.
  - Survives VS Code restarts, reboots, and window closures.
  - Avoids hardware fingerprint fragility or privacy concerns.
  - In Codespaces, reads `$CODESPACE_NAME`.
- **Session `instanceId`:**
  - Minted fresh on each `activate()`: `inst_${stadiumId}_p${process.pid}_${Date.now()}`.
  - Uniquely identifies Window 1 vs Window 2 on the same machine.

### Game ↔ Stadium Cardinality for Q2.8
- **Rule:** Exactly **one authoritative connected Stadium per Game**.
- **Duplicate Binding Fail-Safe:** If Window 2 connects claiming a `gameId` already actively bound by Window 1:
  - The Control Plane flags the binding as `Ambiguous / Conflicted`.
  - Automated dispatch is disabled for that Game until the human explicitly selects which window to route to.
  - Zero cross-stadium guessing.
