### 3. Relay Path vs Dedicated Subdomain
- **CLAIM:** Scout C proposed choosing between a subpath under the existing remote host (e.g. `remote.mysidelinecoach.com/preview/v1/<hostPublicId>/...`) and a dedicated preview subdomain (e.g. `p-<hostPublicId>.<relayDomain>`).
- **EVIDENCE:**
  - **Origin Isolation & Cookie Security:** On `remote.mysidelinecoach.com`, the `sl_dev` cookie is scoped to `Path=/`. If static preview HTML runs under the same origin, any script within the Game HTML can issue ambient, authenticated `fetch()` calls to `/api/*` endpoints. A distinct origin/subdomain prevents ambient API access and shields the parent session storage.
  - **Path Resolution for Subresources:** Static web applications frequently use root-relative paths (e.g. `<script src="/app.js">`, `<img src="/images/logo.png">`). Under a subpath (`/preview/v1/game/index.html`), the browser resolves root-relative paths to `remote.mysidelinecoach.com/app.js` (404/corruption), completely breaking the preview. Under a dedicated origin or subdomain, `/` maps directly to the Game root.
  - **Infrastructure Burden:** A dedicated subdomain requires wildcard DNS and wildcard TLS certificates on the public relay (`*.remote.mysidelinecoach.com`).
- **RECONCILED STATUS:** **INFERENCE / Architectural Tradeoff (Architect Decision Required).**
- **WHY:** Both approaches have concrete engineering tradeoffs that require Opus's architectural judgment.

## 7. Security Invariants (Locked)

The Architect must preserve these non-negotiable security boundaries:

1. **No Arbitrary Localhost:** Remote preview must NEVER accept arbitrary ports or localhost targets from the client. The target port is retrieved solely from the authoritative Stadium session for the currently active Game.
2. **Single Approved Capability:** Exactly ONE static PreviewEndpoint owned by the currently active Game in the connected Stadium is authorized.
3. **Authenticated Viewer Only:** Remote access requires a valid `sl_dev` cookie verified by `DeviceRegistry`. Unpaired or unauthorized requests must receive 401.
4. **Strict Containment Remains Authoritative:** The existing `StaticPreviewServer` filesystem protections (`path.resolve`, `realpath`, dotfile/secret blocking, GET/HEAD only) must remain the ultimate file access arbiter.
5. **No Credential / Cookie Leakage:** The phone must not be able to leverage preview content execution to exfiltrate host credentials, daemon tokens, or `sl_dev` cookies.
6. **Default-Deny Gating:** Non-static previews (e.g. Vite, Next.js, dev servers requiring arbitrary ports/WebSockets) must CONTINUE to return `reason: 'remote-viewer'` in R13.

## 8. Architect Decisions Required

The Scout output is compressed to the following core architectural decisions for Claude Opus:

### Decision 1: Preview Addressing Structure (Origin Isolation vs DNS Complexity)
- **Why it matters:** Determines whether Game HTML scripts execute within the Sideline web app origin or in a sandbox/separate origin, and whether root-relative URLs (`/style.css`) function correctly.
- **Supported Options:**
  - *Option A (Dedicated Subdomain / Origin):* Route preview requests through a dedicated preview subdomain (e.g., `p-<hostPublicId>.<relayDomain>`).
  - *Option B (Path-Scoped with Sandbox):* Route preview requests under the existing host (e.g., `https://remote.mysidelinecoach.com/preview/v1/<gameId>/...`), embedded in an `<iframe sandbox="allow-scripts">` without `allow-same-origin`.
- **Known Tradeoffs:**
  - Option A provides perfect origin isolation and root-relative path resolution (`/` is the game root), but requires wildcard DNS and TLS certificates on the relay.
  - Option B works with existing DNS/TLS, but root-relative paths in static games will fail without URL rewriting or a `<base>` tag injection, and ambient cookie sharing requires strict iframe sandboxing.
- **Evidence That Could Eliminate an Option:** If the production relay cannot easily provision on-demand wildcard TLS certificates for subdomains, Option A is eliminated for R13.

---

### Decision 2: Content Forwarding Transport (Daemon HTTP Reverse Proxy vs Stadium-Relay Tunnel)
- **Why it matters:** Defines how HTTP bytes flow from the host Control Plane to the `StaticPreviewServer`.
- **Supported Options:**
  - *Option A (Daemon-Level Loopback HTTP Proxy):* The daemon knows the ephemeral port of the active Stadium's `StaticPreviewServer` and uses Node's `http.request()` to forward requests to `127.0.0.1:<port>`, streaming responses back through `InProcessRemoteAdapter`.
  - *Option B (Stadium WebSocket Protocol Extension):* The daemon forwards raw HTTP requests to the Stadium over the existing Stadium-to-Daemon WebSocket, and the Stadium responds with streamed data frames.
- **Known Tradeoffs:**
  - Option A is vastly simpler: both Daemon and Stadium run on the same physical machine; loopback HTTP is already bound and listening.
  - Option B adds complex framing and buffering over an existing WebSocket that was designed for JSON RPC.
- **Evidence That Could Eliminate an Option:** The fact that `StaticPreviewServer` is already listening on `127.0.0.1` makes Option B unnecessary architectural overhead for static files.

---

### Decision 3: Binary Response Framing in `InProcessRemoteAdapter`
- **Why it matters:** Static games (like GS3) contain images (PNG, JPEG, SVG) and potentially audio/fonts.
- **Supported Options:**
  - *Option A (Enable `chunkB64` for Buffers):* Update `InProcessRemoteAdapter.write/end` to emit `chunkB64` (base64) when chunks are binary Buffers, which `reference-relay.ts` already knows how to decode.
  - *Option B (Text Only in R13):* Restrict static preview strictly to HTML/CSS/JS, rejecting or corrupting binary assets.
- **Known Tradeoffs:** Option B would break games with images. Option A requires a 3-line change in `remote-dispatch.ts`.

---

### Decision 4: Remote Viewer URL Representation
- **Why it matters:** How the phone client discovers the URL to render.
- **Supported Options:**
  - *Option A (Viewer-Aware Projection):* When `/api/games/preview` is requested by `principal.kind === 'remote-device'`, the daemon replaces `clientUrl` in the returned JSON with the remote-accessible preview URL.
  - *Option B (Explicit `remoteUrl` Field):* Extend the wire projection to include `remoteUrl?: string` alongside `clientUrl`.
- **Known Tradeoffs:**
  - Option A allows `index.html`'s existing `renderPreviewEndpoint` to work with minimal changes.
  - Option B keeps desktop and remote URLs distinct in the payload.
