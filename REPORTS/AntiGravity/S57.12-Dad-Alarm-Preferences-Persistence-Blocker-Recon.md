## 2. EXACT SOURCE OF `Choose a preference to update.`

The exact user-visible message originates from a single backend validation guard in the Control Plane daemon:

- **File:** [`src/control-plane/daemon.ts`](file:///C:/Users/dmcal/Documents/GitHub/SidelineCoach/src/control-plane/daemon.ts#L2999-L3002) (line 3000 in current working tree; line 2548 in git commit baseline `HEAD`).
- **Exact Code:**
  ```typescript
  if (!hasRunningPlayers && !hasDevMode && !hasLiveConsole && !hasAdvancedDiscovery && !hasRemoteSensitiveTerminalOutput && !hasRemoteAccess && !hasTerminalRetention && !hasTimeFormat && !hasAnyAiScoreboardField && !hasAlarms && !hasProductTelemetry) {
    this.sendJson(res, 400, { success: false, message: 'Choose a preference to update.' });
    return;
  }
  ```
- **Context:**
  When `/api/preferences` receives a `POST` request, it checks whether the body contains at least one recognized preference property. In the baseline implementation (and in any running daemon process started before the fix was compiled), `hasAlarms` was completely absent from the whitelist check. Because the client sent only `{ alarms: next }`, every one of the checked preference flags evaluated to `false`, causing the guard to execute and emit HTTP 400 with `message: 'Choose a preference to update.'`.

## 7. VERIFIED ROOT CAUSE

The failure has two verified, compounding causes:

### Cause A: Source Contract Omission in Stage 1B
When Codex implemented Stage 1B (documented in `REPORTS/Codex/S56.3-AI-Usage-Alarms-Stage-1B-Routing-And-Alarms-Settings.md`), it created the UI controls in `index.html` and wired them to post `{ alarms: next }` to `/api/preferences`. However, Codex explicitly stated in report line 51:
> *"The daemon preference endpoint ... required no Stage 1B production changes."*

This statement was factually wrong. Because `daemon.ts` uses an explicit property whitelist rather than open object merging, any property not explicitly listed in the validation guard trips `if (!hasRunningPlayers && ...)` and returns `400 "Choose a preference to update."`.

### Cause B: Detached Daemon Runtime Decoupling
The Sideline Coach Control Plane daemon runs as an out-of-process detached background Node process (PID 76328 recorded in `~/.sideline/control-plane.json`). `src/public/index.html` is served dynamically from disk on each HTTP request, so Dad immediately received the new Settings UI. However, the background daemon process serving port 3100 had been started prior to the `daemon.ts` patch and remained running with build `cp-b4fb1589c5f023fbed935490` (which lacks `hasAlarms`). As a result, the backend rejected incoming `{ alarms: ... }` payloads as unknown preference requests.
