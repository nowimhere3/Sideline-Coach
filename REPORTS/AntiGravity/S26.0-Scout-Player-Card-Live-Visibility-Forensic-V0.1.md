### 8. Recruit / Bench / Remove semantics

**Location of Authorities:**
- **Roster Membership Authority:** `PlayerRoster` (`src/player-roster.ts`), holding `PlayerInstanceBook` (`src/player-instances.ts`).
- **Persisted Team State:** `context.workspaceState` via `PlayerRoster.persistProvenance()` and `WorkspaceStateBindingStore`.
- **On Field / Bench:** `PlayerInstanceRecord.onField: boolean`, toggled via `PlayerRoster.takeOffField()` and `PlayerRoster.returnToField()`.
- **Remove Player:** `PlayerRoster.removePlayer()`, which kills the process/terminal, clears bindings, retires the instance from `PlayerInstanceBook`, and cleans `workspaceState`.
- **Recruit Players Source:** `PlayerDiscoveryService.discover()` (`src/player-discovery.ts`), which enumerates `PLAYER_ADAPTERS` (`src/player-adapters.ts`), probing whether binaries (`codex`, `claude`, `agy`) are installed and searching OS process tables.

**Analysis — Can Scout cleanly plug into this machinery today?**
**NO.** Current roster code deeply assumes:
1. Every Player belongs to `PLAYER_ADAPTERS` (`src/player-adapters.ts`).
2. Every Player instance in `PlayerInstanceBook` has an `instanceId` conforming to `/^(claude|codex|antigravity|terminal)-[0-9a-f]{8}$/`.
3. Every Player instance is backed by an OS process: either a `vscode.Terminal` (direct terminal transport) or a `PlayerControlHost` process with a pseudo-terminal.
4. "Adding" a Player executes a command or spawns a background CLI process.
5. "Removing" a Player disposes an OS terminal or kills a process.
6. "Discovery" probes whether an executable command exists in `PATH` or in active OS process lists.

Scout violates all six assumptions:
- Scout is an orchestrator/dispatcher of subordinate ephemeral runs, not an OS process.
- Scout has no long-running daemon or terminal to launch or kill.
- Scout's availability is not an executable in PATH, but evidence on disk (scorecards, Combine tryouts, OpenRouter credential).
- Trying to force Scout into `PlayerRoster` without an architectural seam would break terminal lifecycle management, process discovery, and seat allocation.

### A. Current Architecture
Today, Scout exists as:
- An isolated execution adapter (`ScoutPlayerAdapter` in `src/scout-player.ts`) that wraps `runScoutFormation`.
- An optional capability injected into `StadiumClient.sendCapabilitySnapshot()`.
- A dedicated AUTO routing rule in `src/routing-policy.ts` (`computeScoutAutoRoute`) that bypasses standard candidate filtering.
- A cosmetic DOM element synthesized directly in `src/public/index.html` (lines 3379-3401) from `status.routing.capabilities`, existing outside `status.players`.

### B. Exact Break
Two distinct breaks explain the field truth:
1. **The Scoping Break (Total Invisibility):** `extension.ts` passes the active Game's root to `ScoutPlayerAdapter.capability(gameRoot)`. The adapter looks for scorecards and verification files in `<gameRoot>/REPORTS/Scout Only/`. External Games do not contain this folder, so `capability()` returns `undefined`. Scout is never emitted in `capability.snapshot`, so neither the synthetic card nor the Manual dropdown nor AUTO ever sees Scout.
2. **The Test Illusion:** `test/q2-14-scout-player-card.test.mjs` injected fake in-memory candidates directly into `runScoutFormation`, and `test/q2-10f-2-...` injected `withScoutCapability(daemonStatus())` directly into the webview test fixture. Neither test exercised the live Stadium extension host resolving capability across real Game directories.

### C. Missing Seam
What Claude and Codex possess that Scout lacks:
- **Roster Native Representation:** Claude and Codex are defined in `PLAYER_ADAPTERS`, tracked in `PlayerInstanceBook`, projected into `status.players`, and participate in `workspaceState` persistence.
- **Roster Lifecycle Controls:** Claude and Codex have first-class `onField` booleans that drive "Put on Bench" and "Put on Field", and removal handlers that cleanly detach them.
- **Recruit Participation:** Claude and Codex are part of the `playerDiscovery.catalog`, allowing them to appear in the "Recruit Players" card.

### D. Existing Work Worth Preserving
The following previous work is sound and should NOT be rewritten:
- `src/scout-formation.ts`: The Formation dispatch engine, `onSelected` callback, candidate registry, and synthesis logic.
- `src/scout-combine-formation-bridge.ts`: Ingestion of Combine scorecards into dynamic Formation candidates.
- `src/scout-openrouter-credential.ts`: Secure SecretStorage credential handoff for OpenRouter.
- `src/control-plane/work-ledger.ts`: Turn recording and `promptSummary` capture for "N Scouts running".
- `src/stadium-client.ts` `deliverScout()`: Execution of Formations and translation into `started`, `accepted`, and terminal turn events.
- `src/public/index.html` `stripCopy()`: Durable Report Ready handoff ("Report ready ✓ / View Report") and aggregate timer logic.

### E. Smallest Repair (Conceptual — Reconnaissance Only)
To make Scout visible in live Games immediately:
1. Configure `ScoutPlayerAdapter` in `src/extension.ts` with a `durableReportRoot` resolver that points to canonical Sideline Coach reports / global storage (e.g. `path.join(context.extensionPath, 'REPORTS', 'Scout Only')` or `context.globalStorageUri`), rather than per-game relative paths.
2. Allow `inspectScoutFormationAvailability` to evaluate canonical scorecards regardless of which Game is active.

To make Scout truly roster-native (Product Invariant):
1. Introduce a virtual / adapter-backed Player concept in `PlayerRoster` that does not require a `vscode.Terminal` or shell PID.
2. Allow Scout to allocate a virtual seat in `PlayerInstanceBook` (Seat 1).
3. Connect Scout's `onField` state to `PlayerRoutingCapability.autoEligible` and Manual selection.
4. Expose Scout in `playerDiscovery.catalog` when enabled, with "Add to Roster" putting Scout on the Team, and "Remove Player" retiring the virtual instance.

### F. Risk / Architectural Question
**Architectural Review Required:**
Making Scout roster-native is **NOT a simple one-line adapter job**.
`PlayerRoster`, `PlayerInstanceBook`, `PlayerDiscoveryService`, `PlayerControlHost`, and terminal recovery assume that a Player is an OS process with a shell PID.
Bridging an orchestrator Player (which commands 1..N ephemeral subordinate runners per Play) into a roster architecture built for persistent interactive shells is a core architectural seam. An Architect must review and define the contract for "Virtual / Orchestrated Players" on the Sideline Team before implementation begins.
