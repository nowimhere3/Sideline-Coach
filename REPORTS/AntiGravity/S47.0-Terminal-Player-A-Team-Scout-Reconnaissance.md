## 3. EXECUTIVE SUMMARY

The product mission of **Terminal Player** is:
> *"See the living Player's guts."*

A Terminal Player is **not** merely another visual skin or report viewer. It represents a real execution substrate—a terminal, shell, or process session—modeled as an on-field Player.

### Key Architectural Discoveries:
1. **The Architecture Split**:
   - Controlled AI Players (`claude`, `codex`, `antigravity`) use `PlayerControl` and `PlayerControlHost`. They emit structured `ControlEvent`s, which feed `PlayerActivityNotice` and stream cleanly into the Live Player Terminal.
   - The existing Terminal Player (`src/terminal-player.ts`) was implemented under `playerType: 'terminal'` with `transport: 'legacy'`. It operates directly inside `PlayerRoster` via VS Code's `window.createTerminal` and `shellIntegration.executeCommand`. It does **not** implement `PlayerControl`, emits **zero** `ControlEvent`s, and therefore produces **no activity stream**.
2. **Process Ownership Today**:
   - No central daemon or background PTY owns general shell processes.
   - For Controlled Claude/AntiGravity (`StructuredPrintControl`), a Node child process is spawned **ephemerally per turn** and exits at the end of the turn.
   - For Controlled Codex (`CodexAppServerControl`), a persistent child process runs `codex app-server` via JSON-RPC stdio.
   - For the existing Terminal Player, **VS Code owns the terminal process** in its UI terminal server. Sideline Coach only holds a reference to `vscode.Terminal`.
3. **Observability & Stdout Capture**:
   - In the existing Terminal Player, when a command runs via VS Code shell integration, output is drawn by VS Code into its terminal buffer. Sideline Coach **never reads or captures stdout or stderr**.
   - Raw stdout is not retained anywhere in Sideline Coach. The only retained text in the Control Plane is `PlayerActivityStore` (bounded to 300 redacted, ANSI-stripped, single-line summaries).
4. **Live Player Terminal Reuse**:
   - The existing Live Player Terminal V0.3 UI **can be 100% reused**. It already keys by exact `instanceId` and already considers `executionType: 'direct-shell'` eligible.
   - If stdout/stderr lines are converted into `PlayerActivityNotice` (e.g. `category: 'command'`, `category: 'tool'`, or `category: 'result'`), the browser terminal UI will render them immediately without any front-end redesign.

## 8. PROCESS OWNERSHIP

**[FACT]** Today, Sideline Coach has three distinct process ownership patterns:
1. **VS Code Window-Owned**:
   - `vscode.window.createTerminal()` delegates process ownership to VS Code's internal terminal service.
   - Sideline Coach does not control the process lifecycle, stdin pipe, or output stream directly.
2. **Extension Host Child Process**:
   - `child_process.spawn()` in `StructuredPrintControl` and `CodexAppServerControl`.
   - The extension host owns `stdin`, `stdout`, `stderr`, and process termination via `killTree()`.
   - If the extension host reloads, all child processes are terminated or orphaned.
3. **Daemon Child Process**:
   - The daemon process itself is spawned detached by `src/control-plane/launcher.ts`.
   - The daemon does not currently spawn or own Player execution processes.

## 9. STDIN / STDOUT / STDERR

### STDIN
- **[FACT]** There is currently **no interactive stdin stream** in Sideline Coach.
- `StructuredPrintControl`: `child.stdin.end(prompt)` sends prompt once on spawn.
- `CodexAppServerControl`: Stdio JSON-RPC client sends newline-delimited JSON requests.
- `PlayerRoster.runTerminalCommand`: `terminal.sendText(command, true)` simulates keystrokes into the VS Code terminal window.
- `ControlledPlayerPresentation`: `handleInput()` displays `"Send Plays through Sideline Coach."` and ignores user input.

### STDOUT & STDERR
- **[FACT]** In `PlayerRoster.runTerminalCommand`:
  - When `shellIntegration` is present, `shell.executeCommand(command)` returns a `vscode.TerminalShellExecution`.
  - In recent VS Code APIs (1.93+), `execution.read()` exists as an async iterable stream of command output. **Sideline Coach does not call `execution.read()` today.**
  - When `shellIntegration` is absent, output goes directly to the terminal UI; extension host has zero access.
- **[FACT]** In `StructuredPrintControl`:
  - `child.stdout` is parsed as JSON lines. Raw text is buffered locally up to 1 MB during the turn, then discarded.
- **[FACT]** In `PlayerActivityStore`:
  - The Control Plane only stores sanitized `{ seq, at, category, text }` lines. It does not store raw stdout streams.

## 10. LIVE PLAYER TERMINAL REUSE

**[INFERENCE]** Live Player Terminal V0.3 is ideally positioned to be the primary viewing surface for Terminal Player.

### Why It Fits:
1. **Keyed by exact `instanceId`**: The entire UI (`consoleActivity.get(instanceId)`) is keyed by instance ID.
2. **Already terminal-eligible**: `src/public/index.html` already includes:
   ```javascript
   const isTerminalEligible = liveConsoleEnabled()
     && view.executionType !== 'scout-formation'
     && record.typeName !== 'Scout'
     && (view.state === 'working' || view.state === 'starting' || view.state === 'finished');
   ```
   A Terminal Player with `executionType: 'direct-shell'` passes this check.
3. **Built-in ergonomics**: Half-screen desktop (`50vh`), fullscreen mobile, copy controls (`Copy All`, `Copy New`), auto-follow with scroll pause, and post-play retention.

### Why It Might Strain:
1. **No ANSI / Terminal Emulation**:
   - The viewer renders plain text with monospace font inside a pre-wrapped div.
   - `sanitizeActivityText` strips all ANSI escapes.
   - Interactive TUI programs (e.g. `htop`, `vim`, curses spinners, progress bars that overwrite lines using `\r`) will look degraded or garbled if emitted as raw stream fragments.
2. **Rate Limits**:
   - High-throughput terminal output (e.g. `cat 10MB.log`) would flood WebSocket, daemon memory (300 line cap), and DOM. Line truncation (`ACTIVITY_LINE_MAX = 240`) and batching/throttling would be mandatory.

## 11. SECURITY BOUNDARY

**[FACT]** Current security in `src/player-activity.ts` is structural + regex:
1. **Allow-list**: Only approved categories (`working`, `message`, `command`, `tool`, `declined`, `result`, `channel`).
2. **Secret Redaction**: 15 specific regex patterns for Bearer tokens, private keys, API keys, basic auth, AWS, GitHub, etc.
3. **Size Boundaries**:
   - Maximum regex input cap: 8,000 characters.
   - Maximum line length: 240 characters.
   - Maximum message length: 1,200 characters.
   - Maximum retained lines in daemon: 300 per Player.
4. **Gates**: Dev Mode AND View Player Terminal must both be enabled.

### Hazards for Raw Terminal Streaming:
- **Environment Dumps**: `env`, `export`, `set`, or `Get-ChildItem env:` output can expose sensitive environment variables whose names or values do not match standard credential formats.
- **File Dumps**: Running `cat .env` or inspecting configuration files containing database credentials.
- **Terminal Injection**: ANSI escape bombs or terminal control sequences that manipulate terminal state. (Currently mitigated by regex ANSI stripping).
- **Process Flooding**: A command producing millions of lines per second could exhaust daemon memory or freeze the browser rendering thread.

## 12. CONTRADICTIONS & HAZARDS

1. **Contradiction: Existing `terminal` player is excluded from `PlayerControl`**
   - Controlled players use `PlayerControl` -> `publishActivity` -> Live Player Terminal.
   - The existing `terminal` player lives in `PlayerRoster` as `transport: 'legacy'`. It has no `PlayerControl` object, so it cannot participate in `publishActivity` without custom one-off wiring or a new `TerminalControl` adapter.
2. **Contradiction: `ControlledBindingRecord` schema rejects `terminal`**
   - In `src/player-control/bindings.ts`, `INSTANCE_PATTERN` is `/^(claude|codex|antigravity)-[0-9a-f]{8}$/`.
   - If someone tries to register `terminal` as a controlled binding without changing this schema, validation fails and drops it.
3. **Contradiction: Controlled players are ephemeral per-turn; Terminal Player is long-lived**
   - Claude and AntiGravity spawn a process on demand per turn and kill it on completion.
   - A shell terminal process remains alive between commands. `WorkLedger` expects a discrete turn lifecycle (`accepted` -> `started` -> `completed`).
4. **Hazard: VS Code Shell Integration availability**
   - In VS Code, shell integration depends on user shell configuration (`bash`, `zsh`, `pwsh`).
   - If shell integration is inactive, VS Code provides **zero** output capture and **zero** exit code reporting (`observed: false`).
5. **Hazard: Terminal vs. Log Viewer mismatch**
   - The Live Player Terminal UI is designed as a sanitized log stream, not an xterm.js terminal emulator. Interactive console programs will not behave like a real TTY.

## 14. GENUINE UNKNOWNS

The following questions cannot be determined from source code alone and represent genuine product/architecture decisions for Opus:

1. **Substrate: VS Code Terminal vs. Headless Node Process**:
   - *Option A*: Run inside a VS Code terminal window (`vscode.window.createTerminal`). Advantage: User can see and interact with the terminal in VS Code; native shell integration. Disadvantage: Output reading is limited by VS Code's extension API (`execution.read()`).
   - *Option B*: Run headless via Node `child_process` (or `node-pty`). Advantage: Full programmatic control over stdin, stdout, and stderr streams; identical behavior across all environments. Disadvantage: Not visible in VS Code's native terminal panel unless mirrored via pseudoterminal.
2. **One-Shot Command vs. Long-Lived Interactive REPL**:
   - Does "Terminal Player" mean running one command at a time (like `npm test` or `git status` with a start/finish turn), or does it mean an active shell session where environment variables, directory changes, and background jobs persist across turns?
3. **Observability Ceiling: Log View vs. Full TTY Emulation**:
   - Is text line streaming (via `PlayerActivityNotice`) sufficient for V1, or does the user expect interactive curses/ANSI terminal emulation?

## 15. DEFERRED PRODUCT BREADCRUMB

### Live Player Terminal Retention Policy

> **FIELD OBSERVATION**:
> The Live Player Terminal can currently disappear sooner than the operator wants.
> For developers, that terminal is valuable evidence.
> Once the human has deliberately opened the terminal, Sideline should not casually destroy that view merely because execution completed or a presentation timer expired.
> We want terminal retention to become an explicit product policy.
>
> **Potential future modes may include**:
> 1. Keep terminal/history until explicit human Collapse or successful Copy action.
> 2. Keep terminal until the next Play is dispatched to that exact Player.
> 3. Keep terminal until the resulting report is produced/discovered.
> 4. Keep full terminal history while View Player Terminal is enabled.
>
> **Durable Principle**:
> *Terminal disappearance should follow a clearly defined user action or explicit retention policy, not an incidental UI timeout.*
>
> *(Note: S46.0 implemented the initial baseline for Post-Play Retention with manual Collapse, post-completion Copy release, and next-play continuity. Formalizing user-configurable retention policies remains a deferred product breadcrumb).*
