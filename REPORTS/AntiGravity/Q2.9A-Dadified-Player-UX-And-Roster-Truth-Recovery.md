## First broken state/projection boundary

The first broken boundary was between **Player type availability** and **Player instance membership**.

`Codex Ready` is discovery truth. It does not establish an instance ID, seat, ownership, transport binding, or roster membership. The old projection converted adapter availability into `ready-on-bench` and rendered the Player type as if it were a Player instance. That was the first semantic corruption; duplicates and stale actions followed from it.

The repaired boundary is:

```text
Discovery catalog / external candidate
        ↓ explicit Add or Add to Roster
Player instance with instanceId + ownership + onField
        ↓ canonical Stadium roster snapshot
Roster card
```

The browser does not mint or retain a competing Player state.

## Recruit vs Roster truth model

```text
Recruit Players  = Who COULD join this Game?
Roster           = Who HAS joined this Game?
Field state      = Who is ACTIVE right now?
```

Recruit renders catalog entries and unclaimed running-process candidates. Roster flattens only canonical `status.players[].instances`. Field state is the instance's canonical `onField` value, reinforced by text and color.

## Root causes repaired

### Phantom Player root cause

Adapter availability and roster field state were coupled. Empty instance lists could still become `ready-on-bench`, and the browser rendered type rows. The adapter projection now reports `not-on-roster`, while the Roster renderer creates cards only inside `for (const instance of instances)`.

### Duplicate Player root cause

The old browser mixed one Player-type row with separately rendered instance rows and exposed `Add another`. A human saw two representations of one concept. The duplicate renderer was deleted. One canonical instance now creates one roster card containing identity, field state, ownership/capability, field action, and removal.

### Stale adoption root cause

Discovery was a cached snapshot. Adding a running process to the roster did not originally remove that exact candidate from the snapshot, so the detached adoption CTA survived. The runtime now filters by shell pid, returns the reconciled discovery with the lifecycle result, updates the per-Game Control Plane cache, and broadcasts status. The Recruit renderer additionally suppresses actions for rostered Player types. A later Check Players excludes claimed shell pids, so it cannot recreate the stale CTA.

## Final card hierarchy

```text
[green marker]  Claude
                On Field · Adopted
                [Put on Bench] [Remove Player]

[yellow marker] Terminal
                On Bench · Terminal
                [Put on Field] [Remove Player]
```

- Line 1 is always Player identity.
- Line 2 is textual field state plus human capability/ownership.
- Green means On Field.
- Yellow means On Bench.
- Color is never the only state signal.
- `Put Controlled on Field`, `Take Off Field`, and customer-facing `Legacy` are absent from normal UX.

## Custom modal and ownership preservation

Coach-managed Terminal copy:

```text
Remove Terminal?
Coach created this terminal. Removing this Player will also close it.
```

Adopted Player copy:

```text
Remove Claude?
Claude will leave your roster. Coach did not start it, so your existing terminal will stay open.
```

The modal is a Sideline Coach `alertdialog`, not `window.confirm()`. Destruction remains gated by runtime ownership:

- `coach-managed` → detach and dispose Coach-owned transport/terminal.
- `adopted` / `external` → detach only; leave the human process and terminal running.

The already field-proven Coach-managed Terminal close path was not changed.
