## 2. Adjudication of Scout Contradictions & Ambiguities

The three Scout reports (`SCOUT-r10-film-calibration-data`, `SCOUT-r10-math-graduation`, `SCOUT-r10-gating-ui-lifecycle`) identified several critical architectural questions and apparent contradictions. Here is the authoritative resolution:

### Contradiction 1: 30 Resolved Outcomes vs. 50 Dispatched Plays
- **Scout Conflict:** Confusion over whether §12.3's requirement of "$\ge 30$ resolved outcomes per task class" conflicts with or replaces §19.4's "$\ge 50$ dispatched Plays logged".
- **Authoritative Resolution:** **They are completely independent gates governing different subsystems.**
  1. **§19.4 (R8 Advisory Chip Shadow Exit):** Requires $\ge 50$ *dispatched* shadow Plays logged across the entire system, median absolute relative burn error $\le 50\%$ on qualifying isolated Plays, and green invariant tests. This governs global exit from pure shadow mode to allow the Dad advisory chip to render when AUTO disagrees with the recommendation.
  2. **§12.3 (R10 Task-Class Calibration Graduation):** Requires $\ge 30$ *resolved* (non-pending, non-excluded) first-pass outcomes *within a specific task class* across all targets, a 3-bin reliability check ($\le \pm 10$ pp error), and a Brier score strictly beating the class base-rate predictor.
- **Opus Instruction:** R10 **must not** weaken, alter, or satisfy R8's 50-play exit gate. `R8_ADVISORY_STAGE_GATE` remains closed. R10 operates strictly on task-class statistical graduation.

### Contradiction 2: Three-Bin Reliability Check & Sparse/Empty Bin Treatment
- **Scout Conflict:** How are the 3 reliability bins partitioned, how are boundary values handled, and what happens if one or more bins contain zero or few samples?
- **Authoritative Resolution:**
  - **Bin Definitions:** The unit probability interval $[0, 1]$ is split into 3 equal-width intervals:
    - Bin 0: $[0.0, 0.3333)$ (Low confidence)
    - Bin 1: $[0.3333, 0.6667)$ (Medium confidence)
    - Bin 2: $[0.6667, 1.0]$ (High confidence)
  - **Boundary Calculation:** To prevent off-by-one errors when $p = 1.0$:
    $$\text{binIndex} = \min(2, \lfloor p \times 3 \rfloor)$$
  - **Sparse & Empty Bin Policy:** In practice, recommendations often cluster in the high-probability bin ($p > 0.67$), leaving the low bin ($p < 0.33$) sparsely populated or empty.
    - Let $n_b$ be the number of resolved outcomes in bin $b$.
    - A bin is considered **evaluable** if $n_b \ge \text{SHADOW\_MIN\_N.calibrationBin}$ ($5$ samples).
    - **Graduation Requirement:**
      1. Every *evaluable* bin ($n_b \ge 5$) must satisfy $|\text{observedRate}_b - \text{meanPredicted}_b| \le 0.10$.
      2. If a bin is non-empty but sparse ($1 \le n_b < 5$), it is reported in Dev Mode with its $n$ and labelled insufficient, but does not unilaterally block graduation unless its raw deviation exceeds $0.25$ (gross miscalibration guard).
      3. **Minimum Support Invariant:** At least **2 bins must be evaluable** ($n_b \ge 5$) to graduate. If all 30+ outcomes fall exclusively into a single bin (e.g. all in Bin 2), the system has not demonstrated calibration across varying confidence levels and remains in `'evaluating'` / `'shadow'`.

### Contradiction 3: Attribution Weights vs. Binary Outcomes in Calibration Math
- **Scout Conflict:** In `film-index.ts`, `FilmObservation.firstPass` is `{ y: 0 | 1, attribution: number }`. Should Brier score and reliability diagrams use weighted outcomes ($w_i \cdot y_i$) or raw binary outcomes ($y_i \in \{0, 1\}$)?
- **Authoritative Resolution:**
  - **Calibration uses raw binary outcomes $y_i \in \{0, 1\}$ for skill-eligible, resolved Plays.**
  - **Attribution Weight Rationale:** Attribution weights ($1.0$ for clean, $1.0$ for Coach-confirmed defect, $0.6$ for rule-inferred high, $0.3$ for rule-inferred low) belong to the **Bayesian posterior belief engine** (§5.2, §5.3) to control the speed of belief updating under uncertain follow-up attribution.
  - In contrast, calibration graduation (§12.3) evaluates the empirical validity of predicted probabilities: *Did the event occur or not?*
  - An outcome resolved as `clean` is $y = 1$. An outcome resolved as `repaired` or `failed` due to `player-defect` is $y = 0$.
  - All outcomes resolved as `excluded` (provider/harness/auth failures, non-player defects) or `pending` (within the 72h / 3-touch window) are **strictly excluded from calibration** ($N$ does not count them).

### Contradiction 4: Base-Rate Predictor Formulation
- **Scout Conflict:** Is the base-rate predictor compared against pooled per-target, or pooled across the entire task class?
- **Authoritative Resolution:**
  - Per S57.1 §12.3: *"Brier score beats the base-rate predictor (the class's pooled first-pass rate)"*.
  - This is unambiguous: **Pooled across all targets within the task class.**
  - The pooled base rate $\bar{y}_{\text{class}}$ is the simple mean outcome across all eligible resolved Plays in that class:
    $$\bar{y}_{\text{class}} = \frac{1}{N_{\text{class}}} \sum_{i=1}^{N_{\text{class}}} y_i$$
  - The base-rate Brier score is:
    $$BS_{\text{base}} = \frac{1}{N_{\text{class}}} \sum_{i=1}^{N_{\text{class}}} (\bar{y}_{\text{class}} - y_i)^2 = \bar{y}_{\text{class}} (1 - \bar{y}_{\text{class}})$$
  - The model Brier score is:
    $$BS_{\text{model}} = \frac{1}{N_{\text{class}}} \sum_{i=1}^{N_{\text{class}}} (p_i - y_i)^2$$
    where $p_i$ is the predicted first-pass probability frozen in the recommendation digest for the chosen route.
  - Model must satisfy:
    $$BS_{\text{model}} < BS_{\text{base}}$$
  - If the model cannot outperform a naive constant predictor assigning the class average to every Play, it is uncalibrated and cannot graduate.

### Contradiction 5: Graduation State Architecture — Derived vs. Persisted
- **Scout Conflict:** Should graduation be purely derived from Film on every call, or durably stored in a database/JSON file?
- **Authoritative Resolution:**
  - Sideline Coach principles dictate: **Routing Film is the single durable source of truth.** Scorecards and reports are *derived views*.
  - Recomputing full calibration over historical Film on every UI keystroke is unnecessary overhead.
  - **The Reconciled Seam:**
    1. A pure function `evaluateTaskClassGraduation(events, pack, now, taskClass)` computes graduation deterministically from Film.
    2. An in-memory cache / daemon store holds the latest evaluation snapshot (`CalibrationGraduationStore` or cached record in daemon state).
    3. Recomputation occurs:
       - On daemon startup.
       - Periodically on a weekly timer / background cadence (or lazily at dispatch if `now - lastEvaluatedAt > 7 * 24 * 3600 * 1000`).
       - On explicit Dev Mode refresh / Dev API call.
    4. Optional persistence: If desired for fast daemon cold starts, a small cache file at `~/.sideline/calibration-graduation.json` may store the last evaluated state, but this file is strictly a cache and can be safely deleted or re-derived from the Film at any time.

## 3. Mathematical & Algorithmic Specification

### 3.1 Dataset Construction per Task Class
For a given task class $C \in \{\text{'architecture'}, \text{'implementation'}, \text{'quick'}, \text{'default'}\}$:
1. Index all Film events chronologically via `indexFilmPlays(events)`.
2. Compute resolved first-pass states via `projectFirstPassResolutions(events, now)` and join with `buildAttributedFilmIndex`.
3. Filter to plays satisfying **all** of the following:
   - `play.decision.recommendation` is present and contains frozen predictions.
   - `play.decision.chosen` is present.
   - `play.decision.profile?.taskClass === C`.
   - `firstPass` observation is resolved: `state !== 'pending'` and `state !== 'excluded'`.
   - Frozen predicted probability $p_i = \text{predictedFirstPass}(\text{decision}, \text{chosenKey})$ is defined ($0.0 \le p_i \le 1.0$).
   - Resolved binary outcome $y_i \in \{0, 1\}$ is defined.
4. Total resolved count:
   $$N_C = \sum_{i \in \text{eligible}_C} 1$$

### 3.2 Graduation Criteria Evaluation
A task class $C$ transitions from `'shadow'` (or `'evaluating'`) to `'graduated'` if and only if **all four conditions hold simultaneously**:

1. **Sample Size Gate:**
   $$N_C \ge 30$$
2. **Model Performance Gate (Brier Skill Score):**
   $$BS_{\text{model}} = \frac{1}{N_C} \sum_{i=1}^{N_C} (p_i - y_i)^2$$
   $$BS_{\text{base}} = \bar{y}_C (1 - \bar{y}_C), \quad \text{where } \bar{y}_C = \frac{1}{N_C} \sum_{i=1}^{N_C} y_i$$
   $$\text{Condition: } BS_{\text{model}} < BS_{\text{base}}$$
3. **Reliability Gate (3-Bin Calibration):**
   For bins $b \in \{0, 1, 2\}$ with $b = \min(2, \lfloor 3 p_i \rfloor)$:
   - Bin sample count: $n_b = \sum_{i \in b} 1$
   - Mean predicted: $\bar{p}_b = \frac{1}{n_b} \sum_{i \in b} p_i$
   - Observed rate: $\bar{y}_b = \frac{1}{n_b} \sum_{i \in b} y_i$
   - Evaluability: $\text{evaluable}(b) \iff n_b \ge 5$
   - Bin Error: $e_b = |\bar{y}_b - \bar{p}_b|$
   $$\text{Condition: } \forall b \text{ where } \text{evaluable}(b): e_b \le 0.10$$
4. **Minimum Support Gate:**
   $$\sum_{b=0}^2 \mathbf{1}_{\{\text{evaluable}(b)\}} \ge 2$$

### 3.3 Reversibility / Un-Graduation Policy
- Calibration graduation is **dynamic and reversible**.
- If a subsequent weekly recomputation indicates that $BS_{\text{model}} \ge BS_{\text{base}}$ or any evaluable bin exhibits $e_b > 0.10$ (for example due to provider drift or model regression):
  - The status reverts immediately from `'graduated'` to `'ungraduated'` (or `'degraded'`).
  - Calibrated percentages are immediately revoked from Dad-facing templates.
  - Dev Mode displays the un-graduation event with the specific failing metric (e.g., `"Un-graduated: Bin 1 error 0.14 exceeds 0.10 threshold"`).
